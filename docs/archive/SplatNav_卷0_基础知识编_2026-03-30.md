## 第 1 章 工位机、SSH、Shell 与最常用命令

### 1.1 为什么算法实验常在 Linux GPU 机上做

深度学习与大规模科学计算依赖 **GPU 并行**。笔记本往往没有同级别 GPU 或散热不足。实验室把 **带显卡的工作站或服务器** 放在机柜或桌边，我通过 **网络** 登录使用。操作系统常见 **Ubuntu** 系。我要习惯 **终端** 是第一界面，而不是只有鼠标。

### 1.2 SSH 是什么

SSH 是加密远程登录协议。我本地终端输入 `ssh user@host`，通过验证后，我在对方机器上拿到一个 shell。此后我执行的 `ls`、`python` 都在 **远端**。我若 **断开 SSH**，前台任务可能被挂断，因此长任务要配合 **tmux** 或 **nohup**，本仓库选用 tmux。

### 1.3 Shell 与 Bash

Shell 是命令解释器。Bash 是最常见的一种。提示符后我输入命令，回车后 shell 解析、找可执行文件、启动进程。`echo $SHELL` 可看默认 shell。

### 1.4 当前工作目录 pwd 与 cd

`pwd` 打印我在哪。`cd 路径` 切换目录。`cd ..` 上一级。`cd ~` 回家目录。新手最大错误是 **在 A 目录执行了相对路径脚本**，以为自己在 B 目录。养成习惯 **每条长命令前 pwd 一次**。

### 1.5 ls、mkdir、cp、mv、rm

`ls` 列表，`ls -la` 看权限与隐藏文件。`mkdir -p` 递归建目录。`cp -r` 复制目录。`mv` 移动或改名。`rm -rf` **极危险**，删错难恢复，我先用 `ls` 确认。

### 1.6 文本查看 cat、less、head、tail

`cat` 一次打印全文，大日志慎用。`less` 分页看。`head -n 50`、`tail -n 100` 看头尾。我读 `stdout.log` 常用 `tail -f` 跟随刷新。

### 1.7 搜索 grep 与 find

`grep -R "feasible" runs/` 递归搜字符串。`find . -name "*.json"` 找文件。注意 **当前目录** 很大时 find 会慢。

### 1.8 磁盘 df 与 du

`df -hT` 看分区挂载与剩余空间。`du -sh 目录` 看目录体积。空间不足时安装与下载会 **半路失败**，我先查 `df`。

### 1.9 系统信息 uname、whoami、hostname

`uname -a` 内核信息。`whoami` 当前用户。`hostname` 机器名。我写实验记录时 **这三项与 GPU 信息** 一起记。

### 1.10 与 GPU 相关的入口命令 nvidia-smi

`nvidia-smi` 列出驱动版本、GPU 型号、显存、占用进程。若命令不存在，说明 **驱动未装或没权限**。若存在但 torch 不可用，问题在 **PyTorch 与驱动匹配**，见第 6 章。

### 1.11 本项目中我第一条要熟练的命令组合

```bash

ls -la
readlink -f splatnav-official
```

### 1.12 常见误区

**误区一**：以为 SSH 里看到的路径是我 U 盘上的路径。  
**误区二**：在 root 或其他用户目录乱 `chmod`。本仓库边界是 **只动 howard 账户约定路径**，见第 17 章。

## 第 2 章 路径、权限、软链接与本项目双跳链

### 2.1 绝对路径与相对路径

绝对路径从根 `/` 开始。相对路径相对当前目录。写文档给 **未来的我** 时，关键命令旁写 **绝对路径**，减少复现失败。

### 2.2 Linux 权限 rwx 粗懂

`ls -la` 输出如 `drwxr-xr-x`。前三位是用户权限，中间三位组，后三位其他。`x` 对目录表示 **可进入**。若脚本不可执行，用 `chmod +x` 或 `bash 脚本.sh` 调用。

### 2.3 软链接 symlink

`ln -s 目标 链接名` 创建软链。软链可指向目录。删除软链 **不要** 随便 `rm -rf 链接/` 带斜杠，可能删到目标内容，我应先学习 `rm 链接名` 的正确姿势。

### 2.4 本项目的双跳链

工作区根上 `splatnav-official` 指向 `third_party/splatnav-official`，再指向 `/data/howard/repos/splatnav-official`。**runs** 指向 `/data/howard/splatnav/runs`。我要会画 **箭头图**。

### 2.5 readlink -f

`readlink -f 路径` 解析最终真实路径。我写论文笔记时 **记录真实 git 根**，避免只说「软链那个」。

### 2.6 为何需要短路径软链

IDE 与文档里写短路径 **人类可读**。数据盘真实仓库 **只有一份**，节省空间。团队统一从 `/home/howard/Splat-Nav/splatnav-official` 进，减少口误。

### 2.7 常见故障

软链断了会出现 **找不到目录** 或 **git 不是仓库**。我检查中间每一跳是否存在。

## 第 3 章 环境变量、进程、管道、重定向与日志

### 3.1 环境变量是什么

子进程继承父进程的环境变量。常见 `PATH` 决定找可执行文件的搜索顺序。`export VAR=值` 设置。`printenv VAR` 查看。

### 3.2 管道 |

左边标准输出接右边标准输入。`grep`、`awk` 常与管道配合。

### 3.3 重定向 与 tee

`cmd > file` 覆盖写。`cmd >> file` 追加。`cmd | tee file` 屏幕与文件都有。本仓库 `run_in_tmux.sh` 用 `tee` 写 `stdout.log`。

### 3.4 进程与退出码

命令成功退出码多为 0。`echo $?` 看上一条。脚本 `set -e` 遇非零退出会停止，这是 **bash 严格模式**。

### 3.5 pgrep 与后台任务

`pgrep -f 模式` 按命令行匹配进程。overnight 监控脚本依赖 **固定命令行子串**，我改启动参数时要同步改监控脚本，卷1第 13 节有写。

### 3.6 与本项目的关系

`job.sh` 里 `unset LD_LIBRARY_PATH` 是 **环境变量级修复**。我读日志时同时打开 `env.txt` 与 `stdout.log`，对照 **当时环境** 与 **当时输出**。

## 第 6 章 GPU、驱动、CUDA 与 PyTorch 排错

### 6.1 GPU 与显存

显存大小限制 **一次能加载的场景规模**。OOM 时日志会有 **out of memory**。我先用 `nvidia-smi` 看谁占满显存。

### 6.2 驱动

驱动由系统管理员安装。太老的驱动无法运行新 CUDA 应用。`nvidia-smi` 右上角显示驱动版本。

### 6.3 PyTorch 的 CUDA 构建

`torch.version.cuda` 表示 **此 wheel 构建时针对的 CUDA 版本**，不等于系统 `/usr/local/cuda`。我用 pip 安装 **带 cu124 等后缀的 wheel** 与驱动匹配。

### 6.4 cuda_available 为 False 的排查顺序

先看 `nvidia-smi` 是否正常。再看 `python -c "import torch; print(torch.__version__, torch.cuda.is_available())"`。再看 **LD_LIBRARY_PATH** 是否搅局，见第 7 章。最后才考虑重装 torch，`fix_torch_cuda.sh` 是本项目提供的钉版本脚本。

### 6.5 我不升系统 CUDA 的边界

`docs/00` 与 `docs/01` 约定 **不动系统 CUDA**。我与管理员冲突时 **以实验室规定为准**，本卷只解释 **为何项目脚本这样写**。

## 第 7 章 LD_LIBRARY_PATH 与本次项目中的真实案例

### 7.1 动态链接器如何找 .so

Linux 用动态链接库。除默认路径外，`LD_LIBRARY_PATH` 可插入 **额外搜索路径**。若路径里有 **旧版 libcudart 或与 torch 不匹配的库**，会导致 **奇怪崩溃或 CUDA 不可用**。

### 7.2 本项目策略

`run_in_tmux.sh` 默认 `unset LD_LIBRARY_PATH`。部分 Python 调用使用 `env -u LD_LIBRARY_PATH python ...`。目标是让 **PyTorch wheel 自带解析** 占主导。

### 7.3 我何时要临时保留

若极少数工具 **必须** 依赖自定义库路径，我可设 `KEEP_LD_LIBRARY_PATH=1`，但要 **记录到 notes.md** 并知悉风险。

### 7.4 与就业的关系

企业里也有 **容器与干净环境** 规范。理解这一条，等于理解 **可复现运行** 的一个侧面。

## 第 10 章 ROS2、Gazebo、Nav2、RViz 名词课

### 10.1 ROS2 是什么

## 深度扩展篇一 · Linux 与 Shell 深讲（实操向）

本篇把第 1～3 章展开到 **可照着练** 的程度。我每读完一小节，就在工控机开终端敲一遍。只看不敲，等于没读。

### E1.1 登录与会话：我首先要确认的十件事

我登录成功后，第一件事不是跑 Python，而是 **确认我在哪台机器、哪个账户、哪个目录**。我依次执行 `whoami`、`hostname`、`pwd`、`date`。若 `hostname` 与我想象不一致，说明我连错了机器，后面所有路径都可能错。第二件事是 `df -hT / /data`，确认 **根分区与数据分区** 是否挂载、剩余空间是否够我下载数据。第三件事是 `nvidia-smi | head`，确认 **GPU 是否可见**。这三件事构成 **环境三角**：我是谁、盘够不够、卡有没有。任何一条异常，我都应先停下手里的安装，去翻 `docs/05` 或找师兄，而不是继续重复执行同一条 pip 命令。

### E1.2 路径心智模型：从「文件夹图标」到「树」

Windows 习惯用图形界面点进文件夹。Linux 终端里 **一切都是树**。根是 `/`。家目录常是 `/home/用户名`。我的项目根是 `/home/howard/Splat-Nav`。数据常在 `/data/howard/...`。我要练习 **口述** 一个文件的绝对路径，从根开始说到文件名，中间不能停顿太久。例如 `config.yml` 的绝对路径可能是 `/home/howard/Splat-Nav/splatnav-official/outputs/某场景/splatfacto/某时间/config.yml`。我若说不全，说明我还没建立树形记忆。

### E1.3 相对路径什么时候可以用

相对路径在 **写脚本内部** 很方便，例如 `cd scripts && bash foo.sh`。但我在 **文档里给未来的自己留命令** 时，尽量写绝对路径，或在命令前写死 `cd /home/howard/Splat-Nav`。新手最常见的事故是：师兄的笔记写的是相对路径，我在错误目录执行，结果创建了 **一堆垃圾目录在错误位置**。我若发现家目录下突然出现 `runs` 或 `data`，要警惕自己是否误操作。

### E1.4 Tab 补全与少打字

Bash 支持 Tab 补全路径与命令。长路径我输入前几个字母按 Tab，可减少拼写错误。若按两次 Tab 会列出候选。我要养成习惯，**不手打完整长路径**。

### E1.5 引号与空格

路径含空格时必须加引号，例如 `cd "My Documents"`。本项目路径一般无空格，但若我从网盘拷贝数据，要注意。

### E1.6 后台与 jobs

`command &` 后台执行。`jobs` 看当前 shell 后台任务。`fg` 拉回前台。我与 tmux 相比，裸 `&` 在 SSH 断开时仍可能出问题，因此 **长任务优先 tmux**。

### E1.7 脚本权限与 shebang

脚本首行 `#!/usr/bin/env bash` 指定解释器。我要 `chmod +x` 后才能 `./script.sh` 执行，否则用 `bash script.sh`。本项目脚本多为 bash，我要 **不要随意改成 sh** 除非我懂差异。

### E1.8 `set -euo pipefail` 是什么意思

本项目 bash 脚本常见这三项。**`-e`** 遇错退出。**`-u`** 未定义变量报错。**`pipefail`** 管道中任一环节失败则整体失败。这会让脚本 **更严格**，我调试时若需要临时宽松，要知悉我在改什么，不要永久删除这三项。

### E1.9 `echo` 与调试

我可在脚本里临时加 `echo "到这里了 VAR=$VAR"` 做跟踪。调试完删除，避免日志污染。正式排错仍以 `stdout.log` 为准。

### E1.10 `which` 与 `command -v`

我想知道 `python` 指向哪，用 `which python` 或 `command -v python`。激活 conda 前后各执行一次，我会看到 **路径变化**。若激活后仍指向 `/usr/bin/python`，说明 **激活失败**。

### E1.11 时间与日志

`date` 打印当前时间。我的 `runs` 目录名含时间戳，我要理解 **这是 create_run_dir 按本机时钟生成的**。若机器时钟错乱，排序会乱，但不影响单次实验内容。

### E1.12 压缩与解压（扩展）

我若从师兄处拿到 `tar.gz`，用 `tar -xzf`。打包自己的小型结果 `tar -czf`。大数据慎用压缩，耗时与 CPU 要考虑。

### E1.13 `ssh` 断线后我为什么会丢进程

SSH 会话里的前台进程会收到 **SIGHUP**。tmux 会话不随 SSH 断而杀内部任务，因此本项目选 tmux。我要在组内统一这个习惯。

## 深度扩展篇二 · Conda、pip、GPU 与 PyTorch 深讲

本篇对应第 5～7 章。目标是 **我能在组会上解释清楚** 为什么这台机子用 cu124 的 torch、为什么脚本要 unset 某环境变量，而不是只会说「师兄让我这么跑」。

### E2.1 Conda 环境里到底有什么

一个 Conda 环境是一个 **前缀目录**，下面有 `bin/python`、`lib` 等。`conda activate splatnav` 本质是 **把 PATH 等变量指到该前缀**。我 `which python` 看到的路径应在 `/data/howard/splatnav/conda_envs/splatnav` 或团队约定位置。若我还在用 `/usr/bin/python`，说明 **没激活**。

### E2.2 为什么同一个机器会有多个 Python

系统自带 Python、Conda base、Conda splatnav、用户编译的 Python 都可能共存。**谁在前谁生效** 由 PATH 决定。我要建立 **「当前 python 是谁」** 的条件反射。

### E2.3 conda install 与 pip install 的分工粗讲

Conda 擅长带 **二进制依赖** 的包。pip 擅长 **纯 Python 与 PyPI**。本项目 `bootstrap_env.sh` 用 conda 建 Python，再用 pip 装 nerfstudio 等。我若反过来乱装，可能 **破坏依赖解析**。

### E2.4 渠道与 ToS 的实质

Conda 默认渠道可能要求交互接受条款，CI 或无头环境会失败。用 **conda-forge** 并 `--override-channels` 是常见规避。我不是在「绕过法律」，我是在 **选可自动化** 的发行渠道，具体合规以实验室为准。

### E2.5 pip 缓存与 TMPDIR

本项目把 `TMPDIR` 与 `PIP_CACHE_DIR` 指到数据盘，避免 **系统盘爆满**。我若看到下载极慢，可能是缓存目录在机械盘或网络盘，我要有心理预期。

### E2.6 显存占满时会发生什么

训练或加载大模型时显存不足会报错。规划侧也可能因场景体素分辨率过大而吃显存。我先用 `nvidia-smi` 看谁占满，再 `kill` 无关进程（**确认可杀**）或换小配置。

### E2.7 驱动与 CUDA 的「两层皮」

**驱动** 在内核侧。**CUDA 运行时** 可在用户态由 PyTorch wheel 携带。系统 `/usr/local/cuda` 可能与我实际跑的 **torch CUDA** 不一致。我汇报版本时要 **分开说** 驱动版本、torch 版本、torch.cuda 版本。

### E2.8 `torch.cuda.is_available()` 为 False 的分支图

分支 A：`nvidia-smi` 就不行 → 驱动或权限。分支 B：`nvidia-smi` 行但 torch 不行 → wheel 与驱动不匹配或 **LD_LIBRARY_PATH** 污染。分支 C：都在容器里 → 可能没 `--gpus all`。本项目主要在分支 B。

### E2.9 `fix_torch_cuda.sh` 的逻辑

脚本强制重装指定版本的 torch 与 torchvision，从 **PyTorch 官方 cu124 索引** 拉 wheel。这 **不改系统 CUDA**，只改 **当前 conda 环境里的 Python 包**。我运行后要再 `env_health_check`。

### E2.10 `LD_LIBRARY_PATH` 污染的典型来源

我自己 `export` 过旧版 CUDA。某软件安装脚本自动写入 `.bashrc`。系统里多个 CUDA 版本并存。我要会 `echo $LD_LIBRARY_PATH` 并 **理解每一项从哪来**。

### E2.11 `env -u LD_LIBRARY_PATH python` 与 `unset` 的差异场景

`unset` 影响当前 shell 子进程继承。`env -u` 只对 **这一条命令** 生效，更安全地做对比实验。我要会 **AB 测试**：同一命令带与不带 `env -u` 各跑一次，看 torch 是否从不 available 变 available。

### E2.12 记录环境是科研习惯

我每次正式实验，在 `env.txt` 或笔记里固定记录：**上游 commit、torch 版本、cuda_available、GPU 型号、关键 pip 包版本**。半年后写论文 **Methods** 会直接感谢今天的我。

### E2.13 小结与练习

**练习一**：激活前后各 `which python` 与 `pip -V`。  
**练习二**：打印 `torch.__version__` 与 `torch.version.cuda`。  
**练习三**：故意 `export LD_LIBRARY_PATH=/随便` 再测 cuda_available，再 `env -u` 测回来，理解差异。

## 深度扩展篇三 · 导航、规划与评价指标深讲

本篇把第 11、13、19 章展开。我与卷1对照阅读时，要能把 **`feasible_rate` 曲线** 说成 **实验设计故事**，而不只是「图挺好看」。

### E3.1 再画一遍闭环

我用纸笔或白板画四个框：**定位、地图、规划、控制**。箭头顺时针或按数据流方向。Splat-Nav 论文主要动 **地图表示与规划**。我当前 wrapper 自动化主要在 **规划统计**。我若被问「控制呢」，我答 **本阶段离线不做控制执行**。

### E3.2 地图表示如何影响规划

栅格地图把空间离散成格，碰撞检测快但分辨率有限。点云密但可能噪声大。3DGS 表示 **连续且外观丰富**，规划器要 **从这种表示里提取几何约束**，计算成本与精度权衡在论文里。我跑实验时改 **体素分辨率**（在预设或上游参数里）会直接影响 **速度与可行性**。

### E3.3 起点终点采样与 batch 的意义

batch 脚本在圆环上采样多组起终点，打乱顺序，统计可行率。这回答的是 **「在这个场景族里规划器平均多稳」** 而不是 **「这一条线能不能过」**。我写论文 Related Work 或 Experiments 时要 **说清楚采样协议**，否则审稿人会质疑。

### E3.4 `feasible` 与「crash」不同

`feasible=False` 可能是 **正常返回值**。Python 异常 traceback 是 **实现错误或未处理边界**。我分析日志时要 **先分类**。把正常不可行当 bug 修，会浪费时间。

### E3.5 `PrimalInfeasible` 我如何口头解释

「求解器在数学上判断这组约束同时满足是不可能的。」下一步不是重装软件，而是 **检查约束是否建模过度、起终点是否非法、场景数据是否残缺导致障碍铺满**。

### E3.6 方法对比 `sfc-1` 到 `splatplan`

我每换 `method`，应 **固定 config 与 trials**，只改方法，才叫公平对比。我若同时改两个变量，结果 **无法归因**。

### E3.7 overnight 在科学上的利弊

利：**堆样本量**，看趋势。弊：**机器状态漂移**（温度、后台进程）。我应在 `env.txt` 里记录 **是否有其他大任务同跑**。

### E3.8 轨迹可视化我读什么

## 深度扩展篇五 · 与本项目绑定的实操与排错案例集

本篇是 **情景题**。我每读一题，闭卷回答「我先看什么文件」，再翻卷1核对。

### E5.1 情景：smoke 秒退且无 JSON

**我先看** `stdout.log` 与 `cmd.txt`。常见原因：**conda 未激活**、**config 路径不存在**、**上游根解析失败**。我运行 `readlink -f splatnav-official` 与 `test -f config路径 && echo ok`。

### E5.2 情景：import nerfstudio 失败

**我先看** 是否激活 splatnav。再看 **pip 是否装进对的环境**。最后看 **磁盘是否满**。

### E5.3 情景：CUDA 不可用但 nvidia-smi 正常

**我先做** `env -u LD_LIBRARY_PATH python -c "import torch;print(torch.cuda.is_available())"`。若变 True，说明 **库路径污染**。若仍 False，走 **torch 版本与驱动** 分支。

### E5.4 情景：batch 很慢

**我先看** trials 是否过大、分辨率是否过高、是否 **多方法串行** 总时长正常。再用 `nvidia-smi dmon` 粗看 GPU 是否在算。

### E5.5 情景：feasible_rate 全零

**我先分** 数据是否链全、起终点是否全在障碍内、方法是否选对。再看 **单次 smoke 的 output** 是否恒 False。

### E5.6 情景：overnight 停了但无汇总

**我先看** `post_overnight_report.sh` 的 `pgrep` 模式是否仍匹配实际命令行。硬编码不一致会导致 **永远等不到结束** 或 **早退**。

### E5.7 情景：watchdog 疯狂重启

**我看** `watchdog_restart.log` 与当前是否真有进程在跑。可能是 **路径或参数改了**。

### E5.8 情景：权限 denied

**我查** 是否动了他人家目录或系统目录。回到 **docs/01** 边界。

### E5.9 情景：磁盘满

**我查** `/` 与 `/data`。清 **pip 缓存、tmp、旧 runs**（确认可删）。

### E5.10 情景：Git 冲突

**我若改上游**，先 `git status`，**分支隔离**。不确定就 **问师兄**，不要 `git push -f` 到共享分支。

**我对齐** commit、config、seed、trials、method、机器 GPU。五元组缺一，**不叫复现失败，叫条件不一致**。

### E5.12 情景：我要向导师汇报本周没进度

**我也能汇报**：排除了哪些分支、记录了哪些负结果、下一步最小实验是什么。这比 **沉默** 好。

### E8.13 我要比较两种方法时要固定什么

固定 **数据与 config、scene、trials、机器、软件版本**。只改 **method**。若我必须改 config，我要 **另开一组** 对比表，不能混在一张图里 **假装单一变量**。

### E8.14 我要展示「我改了算法」时要有什么

**前后 commit 对比**、**同样协议下的指标变化**、**至少一个失败案例分析**。没有第三项，容易被质疑 **过拟合偶然**。

### E8.15 最小可发表实验（硕士语境）

**一个场景**、**两个方法**、**三次重复**、**一张主图**、**一张表**。先把 **故事讲圆**，再扩展场景数量。
