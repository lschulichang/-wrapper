# Splat-Nav 文档主线总说明

这一组文档不是给“已经会写导航算法的人”准备的，而是给一个代码基础很弱、但愿意认真学、愿意照着做、愿意把事情做成的人准备的。你可以把它理解成一套真正面向新人交接的项目课程。它既不是论文精读笔记，也不是命令速查表，更不是那种读完以后仍然不知道下一步该干什么的“大而空”手册。它的目标非常实际：让你在离线和仿真阶段，先把项目看明白、把一次完整运行走通、把结果说清楚，再逐步进入更深的代码阅读、实验设计与创新思考。

如果你是第一次接触 Linux、SSH、Conda、tmux、3DGS、规划、可视化、批处理这些词，请不要紧张。这个项目确实同时涉及系统、工程、三维表示、规划、实验和汇报，刚上手时很容易有一种“每个词都认识一点，但串不起来”的感觉。我们写这套文档，就是要把这种混乱感拆开：哪些东西是环境问题，哪些东西是代码问题，哪些东西是论文问题，哪些东西是结果验收问题，分别在哪一份文档里讲，什么阶段该学到什么程度，都会在这里交代清楚。

## 一、先知道这套材料在解决什么

这一部分不急着让你做动作，而是先把门牌、边界和主线说清楚。对一个第一次进项目的人来说，先知道“这套材料到底在带我解决什么问题”，比一上来就扎进某个脚本细节更重要。

### 1、先用一句话把项目说清楚

Splat-Nav 是一个基于 Gaussian Splatting 场景表示的导航系统。它的核心目标，不是把场景“看漂亮”，而是让机器人在这种三维场景表示里安全地规划路径、在运行中不断重规划，并且在需要的时候用视觉估计自己的位姿。论文把它分成两个模块：一个叫 `Splat-Plan`，负责“如何安全地从当前点到目标点”；另一个叫 `Splat-Loc`，负责“只看 RGB 图像时，怎么估计机器人现在在哪”。

对于当前这台机器上的工作区来说，我们的第一阶段目标更聚焦一些：先把 `Splat-Plan` 相关的离线/仿真实验跑明白，能解释输入和输出，能读懂 `runs` 目录里的结果，能说清 wrapper 脚本层和官方源码层分别承担什么职责。真机、ROS 分支部署、在线闭环飞行、论文创新点实现，都不是你第一周必须啃下来的东西。

### 2、这套文档的边界

这套文档只服务一个很具体的目标：让你在 `/home/howard/Splat-Nav` 这个工作区里，围绕当前已经搭好的 wrapper 工程和上游官方源码，把作者提供的离线/仿真主链路走通。它不会教你如何从零搭建整个机器人系统，也不会把 ROS2、Gazebo、Nav2、视觉 SLAM、无人机控制全部展开讲一遍。那些东西以后可能会接上，但现在如果一股脑全讲，只会让新人更快迷路。

你要牢牢记住一句话：现在的主任务不是“懂所有相关领域”，而是“围绕这个工作区，把能落地的最短路径走通”。这也是为什么文档的组织方式不再按“想到什么写什么”，而是按“先理解什么，后做什么，再看什么结果”来安排。

### 3、这 6 份文档各自解决什么问题

#### 3.1 00 这份文档：总入口与总摘要

你现在读的这份文档，是整个体系的入口。它回答三个问题：第一，我应该先看哪一份；第二，每一份文档解决什么问题；第三，当前做到什么程度算过关。它还会提醒你哪些旧稿不建议再看，避免你在历史草稿里兜圈子。

#### 3.2 01《专业术语全解》：把陌生词先拆开

很多新人不是不努力，而是一开始就被术语堵住了。比如 `SSH`、`Conda`、`config.yml`、`GSplatLoader`、`feasible`、`polytope`、`batch`、`LD_LIBRARY_PATH` 这些词，如果只是听过而没真正对应到项目里的路径、日志和脚本，你会很快进入“每句话都能看懂一点，但整段意思抓不住”的状态。`01` 这份文档就是为了解决这个问题。你不需要一次背完，但你读目录时遇到不熟悉的词，就应该回到那里查。

#### 3.3 02《项目全景与边界》：把论文、源码、工作区三层关系串起来

如果说 `01` 是拆词，那么 `02` 就是搭骨架。它会从论文出发，把 `Splat-Nav = Splat-Plan + Splat-Loc` 说清楚，再把当前工作区里的三层结构讲清楚：本地 wrapper 工程层、上游官方源码层、数据与输出落盘层。你会在这份文档里真正理解 `/home/howard/Splat-Nav/scripts` 为什么存在、`/home/howard/Splat-Nav/splatnav-official` 为什么是软链接、哪些文件是“论文实现本体”，哪些文件是“为了复现稳定、日志规范和批量实验而加的外层工程壳”。

#### 3.4 03《输入输出与一次运行验收》：把“跑一次”真正拆明白

很多人会跑命令，但说不清“输入是什么”“输出是什么”“跑完为什么算成功”“为什么这次虽然没报错却不算真正成功”。`03` 这份文档专门干这件事。它会围绕一次 smoke、一次 batch、一次 overnight，把配置、模型、场景、脚本参数、日志、JSON、图表、CSV、`runs` 目录结构和验收证据逐个讲清楚。你读完它以后，应该能自己回答：为什么先看 `stdout.log`，什么时候去看 `summary.md`，什么时候去看 `batch_results.json`，什么叫“假成功”。

#### 3.5 04《顺序化快速上手》：把动作串成路线

这是一份真正拿来照着走的文档。它不是死板的日程表，而是一条按阶段推进的路线。开头会把 Cursor、SSH、GitHub、ChatGPT、Codex 插件、Gmail 这些工具链为什么要准备讲清楚；后面会告诉你，第一天先做什么最小检查，第二步为什么先 smoke，第三步为什么要在 `runs` 里找证据，而不是一跑完就宣布成功。每段命令前后都会有说明，不会再给你孤零零一坨命令。

#### 3.6 05《阶段性目标》：告诉你这一周、这一月、这三个月该长成什么样

新人最怕的一件事，不是难，而是不知道自己到底有没有在前进。`05` 这份文档不是来安排你每天几点做什么，而是告诉你：一周内做到什么样算入门过关，一个月做到什么样算能接项目，三个月做到什么样才算开始具备独立研究和汇报能力。它还会特别提醒你哪些进展是“看起来很努力，其实没有沉淀证据”的假进展。

### 4、推荐阅读顺序

如果你是从零开始，我推荐你按下面这个顺序读，而不是在 `docs` 目录里看到什么点什么。

先读这份 `00`，因为你要先知道整套材料的用途和边界。然后去读 `01` 的前几章，先把最常见的环境、路径、日志、运行术语拆开。接着读 `02`，建立对整个项目、目录、脚本和源码层次的全景认识。做到这里，你对“这个项目是什么”会有一个比较稳的骨架。然后读 `04`，照着它做真正的最小动作。等你已经能把一次最小 smoke 或一次已有结果的目录看懂了，再配合 `03` 深入理解输入、输出和验收。最后再用 `05` 给自己定位：我现在在一周目标里，还是一月目标里，我缺的是理解、执行、记录，还是汇报。

换句话说，这套文档不是线性教材，而是有主线、有回跳的。你第一次读 `01` 时不可能把所有术语记住，这很正常。你在 `02` 里看到 `GSplatLoader`、`SFC`、`Bezier` 这些词时，回去翻 `01` 就行。你在 `04` 里看到某条命令不明白，也应该回到 `03` 去查它的输入输出含义。真正有效的阅读，不是从第一页直冲到最后一页，而是围绕一个具体问题，在几份文档之间来回穿针引线。

### 5、当前工作区到底是什么

你现在所在的工作区根目录是 `/home/howard/Splat-Nav`。它不是论文作者的原始源码仓库本体，而是在本机上包了一层工程化工作区。这个工作区的价值在于三件事。第一，它把环境、日志、长任务、批跑、结果归档这些复现中最容易乱掉的部分收敛到了统一的脚本和 `runs` 规范里。第二，它通过软链接把上游官方仓库引进来，让你既能保留官方源码原貌，又能在本地用统一入口读代码、跑任务。第三，它把文档、脚本、数据盘落盘规范放在一起，减少“脚本在这里、数据在那里、结果又在另一个地方”的碎片感。

这件事非常重要。很多新人一开始看到 `scripts/`，以为这里就是论文算法本身；再看到 `splatnav-official/`，又会怀疑是不是有两套代码。这种混乱如果不先讲明白，后面几乎所有阅读成本都会被放大。简单说：`scripts/` 主要是 wrapper 层，负责环境、路径、tmux、smoke、batch、overnight、汇总和图表；`splatnav-official/` 才是论文核心实现的主要承载位置。你读代码时需要同时知道这两层，但不能把它们混成一层。

### 6、当前阶段的验收口径

对一个零基础学弟来说，第一阶段不要求你提出创新点，不要求你马上改算法，也不要求你一周内读透所有数学推导。真正的过关标准，是你能拿出可信证据证明三件事：第一，你知道项目的主链路是什么；第二，你知道怎么在这台机器上把已有场景的离线流程走起来；第三，你知道跑完之后该去哪里看结果、怎么用大白话把结果讲给别人听。

所以，现阶段的“成功”不是“背下所有术语”，也不是“把目录逛过一遍”，而是你能把项目讲清楚、把最小流程走一遍、把结果文件解释清楚。哪怕你现在还不会改源码，只要这三件事做到了，你就已经从“看不懂项目”进入“能接手项目”的状态了。

## 二、怎么真正使用这套文档

很多手册的问题不在于信息少，而在于读者不知道该怎么用。这里我们不再把文档当成线性教材，而是把它当成围绕当前工作区服务的使用系统来看。

### 1、这一套文档应该怎么用，而不是怎么“读完”

很多人会问，文档这么多，是不是要先全部读完再开始跑项目。答案是否定的。真正有效的做法，是先用 `00` 和 `02` 建立框架，再边做边查。比如你准备做第一次 smoke，那么你不需要先把 `01` 全词典读完，而是先读 `04` 对 smoke 的引导，再回头到 `03` 理解输入输出，再针对自己不懂的词去查 `01`。同理，如果你正在读 `splatnav-official/run_splatplan.py`，发现里面有 `GSplatLoader`、`SplinePlanner`、`SafeFlightCorridor`，你可以回到 `02` 看它们在全局链路中分别处于哪一层，而不必试图在第一次阅读时把每个函数都抠完。

你也要逐渐养成一个习惯：任何一段命令、任何一个目录、任何一个结果文件，不能只问“它怎么用”，还要问“它在整个链路里解决了什么问题”。如果你只学“命令怎么敲”，你会很快陷入记忆负担；但如果你知道“为什么现在运行它、它生成什么证据、出了问题先去哪排”，命令反而会变得容易记。

### 2、一张非常朴素但非常重要的路线图

把第一阶段拆成最朴素的五步，会比把自己压在“我要完全掌握这个项目”这种大话题下更有效。第一步，把工具链打通，也就是 SSH、Cursor、GitHub、ChatGPT/Codex 这些前置条件先齐活。第二步，知道工作区三层结构是什么，别把 wrapper 和上游算法混了。第三步，围绕 smoke 路线，理解最小输入、最小输出和最小验收。第四步，读懂 `runs` 目录里的证据，知道一轮 batch 或 overnight 的结果该怎么解释。第五步，在这个基础上再进入更深入的源码阅读、可视化解读和阶段性汇报。

如果你未来要写专利、做创新、投会议，那些工作当然重要，但它们都建立在前面这五步真的做扎实的基础上。一个对输入输出和运行证据都说不清楚的人，谈创新通常只会很虚。反过来，一个能把现有链路讲明白、跑明白、记录明白的人，哪怕现在还没有提出新点子，也已经走在很稳的路上了。

### 3、你现在最应该做的事

如果你是第一次打开这些文档，不要继续在目录里左右横跳了。先读完这份 `00`，然后去看 `01` 的前部，把环境、路径、日志、运行这些高频词先清一遍。接着读 `02` 的开头和“工作区三层结构”部分，把整个项目的大地图装进脑子里。然后再进入 `04`，开始做最小动作。这样你会发现，原来这个项目不是“天书”，而是一条可以被拆开、被走通、被复盘的链路。

### 4、本文档读完后，你应该回答得出的三个问题

第一，你应该能用自己的话说出：这套 `00-05` 文档分别是干什么的，我为什么不能继续把旧稿当主线。第二，你应该能说出：当前这个工作区是 wrapper 工程层加上游官方源码层的组合，而不是一坨混在一起的脚本。第三，你应该知道：自己下一步最该去看哪一份，而不是继续在多个历史文件之间来回试错。

如果这三个问题你已经能答上来，说明这份总说明已经起作用了。下一步，请去读 `01_专业术语全解_项目全词典.md` 和 `02_项目全景与边界_从论文到代码到数据流.md`。

## 三、把它当成一个导航系统来使用

到了这里，重点已经不再是“文档里写了什么”，而是“你现在处在哪种状态、下一步应该被送去哪里”。这一部分就是要把 `00 -> 01 -> 02 -> 03 -> 04 -> 05` 之间的跳转关系真正搭起来。

### 1、这一套文档真正的阅读入口，不是“按文件名从上到下翻”，而是“按你现在的状态进入”

虽然我们把文档编号成了 `00` 到 `05`，但它们并不是那种必须从第一页机械读到最后一页的线性课本。更像实际情况的说法是：它们共同组成了一个导航系统。导航系统的价值，不在于逼着所有人按同一条路走，而在于你在不同状态下，都能被送到最该去的地方。一个完全没接触过远程机器和 Linux 的学弟，和一个已经能跑 smoke、正准备看 batch 结果的人，显然不应该被要求用完全一样的阅读起点。

所以你以后带学弟时，不妨先别问“你读到第几页了”，而是先问“你现在最困惑的是哪一层”。如果他现在连 SSH、工作区路径、`scripts/` 和 `splatnav-official/` 的关系都还没站稳，那么他的入口应该更靠近 `00 + 01 + 02`。如果他已经能进工作区，但看不明白 run 目录、JSON 和日志，那入口就应该更靠近 `03`。如果他知道项目是什么，却迟迟不知道自己第一步该干嘛，那最该去的是 `04`。如果他已经做了一些动作，却老在焦虑“我这样算不算在前进”，那就该回到 `05`。

你会发现，这样一分，文档就不再是静止资料，而开始像一个会把人送到正确房间里的前台。前台不是替你工作，但它会大大降低你走错路的概率。这也是我现在特别希望 `00` 承担起来的功能。

### 2、六份文档之间的接力关系，应该怎么理解

如果用一种更像接力棒的方式来理解这六份文档，它们之间的关系其实非常清楚。`00` 负责把人领进门，并告诉你这套材料到底怎么用；`01` 负责把“看着吓人”的词拆开，让你不至于在第一步就被术语压住；`02` 负责把项目骨架搭起来，让你知道论文、源码、wrapper、目录、数据流彼此怎么咬合；`03` 负责把“一次运行”这件事拆成能解释的链条；`04` 负责把动作排成路线，让你真的迈出第一步、第二步、第三步；`05` 负责告诉你，在一周、一月、三个月这些不同时间尺度上，什么叫真的前进，什么又只是表面热闹。

这条接力关系里有一个特别重要的特点，就是前面的文档并不会“过期”。比如你已经进入 `04` 真正开始跑 smoke 了，也依然会经常回到 `01` 查词、回到 `02` 确认结构、回到 `03` 核对输入输出。再比如你已经开始用 `05` 规划阶段目标了，也仍然需要回到 `04` 看最小动作顺序，甚至回到 `00` 重新校准自己现在到底属于哪一类状态。所以这套体系不是楼梯式的一次性通过，而更像一张网。只是它有一条主绳，能避免你在这张网里掉下去。

### 3、如果你今天只剩 30 分钟，该怎么用这套文档

很多人会误以为，文档体系一旦建立起来，就意味着每次都要花很长时间系统阅读。其实恰恰相反，一套好的体系反而应该适应碎片化使用。比如你今天只有半小时，完全可以先读完 `00` 当前这一份，然后去 `01` 查最频繁会碰到的环境和路径术语，再去 `02` 看项目三层结构的部分。这半小时不会让你立刻变成项目专家，但它足够让你第二天不再把工作区看成一整团黑。

如果你今天已经做过一点动作，比如成功进入了工作区，那么这半小时更适合用在 `03` 或 `04`。你可以拿着一份已有 run 目录，对着 `03` 看输入输出和验收逻辑；或者对着 `04` 看自己下一步到底该先 smoke、先读日志、还是先做环境检查。也就是说，时间少不代表学不了，关键在于你能不能把这半小时用在当前最该补的那一层。

### 4、如果你今天有半天时间，最推荐的推进方式是什么

半天是一个很适合真正建立感觉的长度。因为它既不短到只能看几段文字，也不长到必须安排特别复杂的计划。对零基础学弟来说，一个很舒服的半天推进方式通常是这样的：先用四十分钟左右读 `00` 和 `01` 的高频部分，把环境、路径、日志、run 目录这些词清掉；再用一个小时左右去 `02` 看项目骨架和工作区三层关系；然后休息一下，再用一到两个小时跟着 `04` 做一次最小动作，比如环境检查或者已有 run 目录复盘；最后留二三十分钟，用 `03` 把刚才做的事重新解释一遍。

这个节奏有个很大的好处，就是它不会把“读”和“做”撕开。你不是先读几天再碰机器，也不是一上来只敲命令不看材料。你是在同一个半天里，让框架、动作和结果开始互相对上。对新人来说，这种体验特别重要。因为很多真正的信心，就是在第一次“我竟然开始看得懂一点了”里长出来的。

### 5、如果你已经能跑 smoke，但还不会讲项目，最该怎么跳转

这是一个非常常见、也非常值得单独讲清楚的状态。很多人到了这个阶段会有点迷惑：我命令其实能跑，run 目录也能看到，为什么一被问到“这个项目到底在干什么”，我还是会发虚？原因通常不是你做得不够，而是你缺少一条从动作回到结构的跳转路径。

这时候最有效的路线，通常不是继续多跑几次同样的 smoke，而是回到 `02` 和 `03`。你应该先用 `02` 把项目总骨架重新过一遍，尤其是工作区三层结构、论文主线和 wrapper 与上游的关系；然后用 `03` 把自己刚刚跑过的那轮 smoke 拆成输入、处理、输出、验收四段。做完这两步以后，再回到 `04` 看自己的动作链条，你会明显感觉“我不是只会跑了，我开始知道自己跑的是什么了”。

所以以后如果学弟说自己“好像能跑，但讲不明白”，你不要立刻再给他更多命令。更有帮助的做法，往往是让他回到 `02` 和 `03` 做一次结构性复盘。

### 6、如果你已经会讲项目，但还不会稳定排错，最该怎么跳转

还有一种状态也很典型，就是学弟口头上已经能把项目讲得八九不离十，可一旦真的碰到环境异常、路径不对、JSON 字段异常或者 run 目录不完整，还是会明显慌掉。这说明他的结构感已经开始有了，但还没真正把结构感落实到排错动作里。

这时候最好的跳转方式，通常是从 `05` 回到 `03` 和 `04`。为什么要先看 `05`？因为很多排错焦虑，其实不是技术问题先起，而是阶段判断先乱了。你要先知道，当前目标是不是本来就只要求最小 smoke，还是已经进入 batch 稳定化阶段。目标一旦清楚，再回到 `03` 用输入输出三段式去拆问题，再回到 `04` 看自己现在最该做的最小动作。这样排错就会从“我是不是哪都不行”重新落回“我当前是某一层卡住了”。

### 7、一份真正可交接的导航系统，至少要回答五个问题

如果我们真想把 `00` 做成一份能长期交接的导航文档，它至少应该稳定回答五个问题。第一，我现在到底在什么阶段。第二，我这一阶段最该读哪几份文档。第三，我读完以后下一步是去做动作，还是去回查术语、结构、输入输出。第四，如果我卡住，应该优先回哪一份文档而不是到处乱翻。第五，如果我要带别人，应该先把别人送到哪一份文档，而不是把一整个目录丢给他自己摸。

你现在可以对照一下，前面的 `00` 已经把这些问题回答出一个基础框架了，但我希望在这一版里把它们回答得更像一个真的“导航台”。也就是说，不只是告诉你“有哪几份文档”，而是让你能顺着自己的当前状态，找到最合适的起点、下一跳和回查点。

### 8、三种最常见的阅读入口，我替你先分好

为了让导航更实用，我们不妨把最常见的三种阅读入口直接分出来。第一种入口，是“我几乎什么都不会，甚至不知道项目到底长什么样”。这种情况下，最推荐的顺序是 `00 -> 01 -> 02`，先别急着碰太多命令。第二种入口，是“我已经能连进机器，也愿意开始动手，但我不知道第一步该落在哪”。这种情况下，最推荐的顺序是 `00 -> 04 -> 03`，先通过动作建立感觉，再回到输入输出解释。第三种入口，是“我已经跑过一些东西，但讲不明白，也不知道自己接下来是不是在正路上”。这种情况下，最推荐的顺序是 `00 -> 05 -> 02 -> 03`，先做阶段定位，再补结构和结果解释。

这三种入口不是把人固定死，而是帮你少走弯路。新人最怕的一件事，其实不是材料少，而是材料很多却没有入口。只要入口对了，后面的努力基本都能积起来；入口错了，越努力越容易绕远。

### 9、带教时，师兄最值得发给学弟的不是一串路径，而是一条阅读动作链

如果你以后真要把这套材料交给学弟，最不建议的方式就是只发一句“你先看看 docs”。这种说法太宽了，新人拿到以后很容易继续靠本能乱点。更好的交接方式，是发一条很短但很清楚的阅读动作链。比如你完全可以说：先看 `00`，知道整套材料怎么用；再看 `01` 前半，把最常碰到的术语扫一遍；然后看 `02` 开头和工作区三层结构部分；看完以后再回来按 `04` 做第一次最小动作；做完以后拿着结果回 `03` 看输入输出和验收。最后用 `05` 给自己定位，看自己现在属于一周目标还是一月目标。

这条交接链的好处，在于它既没有压得太死，又不会把新人放进完全开放的树林里。它像一根牵引绳，牵着他先沿主线走。等主线走熟了，再慢慢允许他自由穿梭于不同文档之间。

### 10、对师兄来说，`00` 还有一个隐藏用途：它是阶段沟通时的对齐文本

除了给学弟用，这份 `00` 其实对带教的人也很有价值。因为带学弟最累的一个时刻，不是他不会，而是你们对“现在到底该做到什么程度”没有对齐。你觉得他现在应该先把 smoke 路线站稳，他却以为自己应该马上想创新点；你觉得他现在主要缺 run 目录阅读能力，他却拼命在啃论文里的某个高级细节。这个错位一旦出现，双方都会累。

所以 `00` 还可以作为一个对齐文本来用。你们在阶段沟通时，完全可以回到这里重新校准：当前这套文档主线解决的是什么，第一阶段的边界是什么，现在最重要的是哪一层。这种校准会非常省力。因为很多时候，人不是做得不认真，而是起点和目标没对齐。

### 11、为什么我一直强调“主线文档”和“历史草稿”要分开

这件事表面看像文档管理问题，实际上和学习效率直接相关。一个新人在刚开始时，最需要的是稳定、可依赖、顺着走不会太痛苦的主线。如果主线和历史草稿混在一起，他就会不停地在“这个看起来也像手册”“那个也好像有内容”之间来回切，最后很难建立对任何一份材料的信任感。

所以把 `00-05` 明确成主线，把旧的 `v0.1` 和 `v0.2` 明确成历史草稿，并不是在否定旧稿，而是在保护新人的注意力。你以后如果要带学弟，这一点一定要坚持。真正好的交接，不是给更多材料，而是给更清楚的主线。

### 12、如果把这套导航系统再压成一句最朴素的话

如果一定要把整个 `00 -> 01 -> 02 -> 03 -> 04 -> 05` 导航体系再压成一句最朴素的话，我会愿意这么说：先知道自己面对的是什么，再知道自己该从哪里开始；先知道词，再知道结构；先知道结构，再知道一次运行到底发生了什么；先知道运行，再真正去做；做完以后再回头判断自己现在处在哪个阶段。这句话听起来很平常，但它几乎就是当前这套文档想替学弟修出来的那条路。

只要这句话开始在脑子里立住，复杂项目就不会再那么像一团密不透风的墙。它会慢慢变成一条虽然长、但有方向、有路标、有扶手的路。
