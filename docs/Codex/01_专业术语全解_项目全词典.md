# 01 专业术语全解：把项目里那些“看着吓人”的词，慢慢讲成人话

如果你是第一次认真接触一个像 Splat-Nav 这样的项目，很容易在第一天就被术语打懵。不是因为这些词每个都特别难，而是因为它们来自不同世界：有的是 Linux 世界的词，有的是 Python 环境世界的词，有的是三维重建世界的词，有的是导航规划世界的词，还有的是实验记录和工程协作世界的词。它们像几股水一下子冲进来，如果没有人帮你拢一下，你脑子里就会出现一种很典型的感受：每个词都好像听过一点，但一放在项目里就不知道到底在说什么。

这一份文档就是来做这件事的。我们不追求把你训练成“术语答题机器”，也不打算上来就拿定义压人。更实际的目标是：把你在当前工作区里一定会碰到、一定会反复看到、如果不懂就会卡住的词，一个一个放回真实语境里讲明白。你会看到我反复问同一个问题：这个词在当前项目里到底指什么，它为什么重要，它和哪些词最容易混，它一般会出现在什么路径、什么脚本、什么日志、什么结果里。

你完全不需要在第一次阅读时把所有词死记硬背。真正有效的用法，是把它当成一本贴着项目现场的“词典型陪跑文档”。你在读 [02_项目全景与边界_从论文到代码到数据流.md](/home/howard/Splat-Nav/docs/Codex/02_项目全景与边界_从论文到代码到数据流.md) 时，读到不熟的词就回来查；你在跑 `smoke`、看 `stdout.log`、打开 `batch_results.json` 的时候，碰到拿不准的概念，也回来查。这个节奏是对的。没有必要把自己逼成一天内背完几十页名词的人。

## 一、先知道这本词典应该怎么用

这一部分先不急着讲术语本身，而是先把使用方法讲明白。因为真正有效的词典，从来不是背完的，而是在项目推进中反复回查、反复加深的。

### 1、你该怎么用这份词典，而不是怎么“背完”它

先把一个误区拆掉。很多同学拿到这类文档，会很自然地想按顺序一页一页往下刷，像背单词书一样把它背完。这种想法听起来认真，其实不太适合当前项目。因为项目不是单向输入，而是边看、边跑、边回查、边纠正理解的过程。你今天可能先碰到 `SSH`、`tmux`、`Conda`，明天再碰到 `config.yml`、`GSplatLoader`、`feasible`，下周才会认真面对 `polytope`、`Bezier`、`P95` 这些词。理解的顺序，本来就不是绝对线性的。

所以更有效的读法，是把这份文档看成一张“术语地图”。地图不是为了让你把每条街一次背熟，而是为了让你不迷路。你今天在某一块区域活动，就重点看那一块。你明天进入下一块，再回过头把前面的词和后面的词连起来。慢一点完全没关系，只要每次回来看时，你能比上一次多懂一点，就已经在前进了。

你还会发现，这份词典虽然叫“术语全解”，但其实不是纯词条堆砌。我会尽量让相邻词之间有上下文关系。比如讲完 `SSH`，我会接着讲 `Shell`、`Terminal`、绝对路径、相对路径，因为它们本来就经常一起出现；讲完 `Conda`，我会接着讲 `pip`、Python 解释器、环境变量、`LD_LIBRARY_PATH`，因为这些词在排错时几乎是连着来的。这样读起来会轻松不少，也更像有人在旁边带你，而不是让你一个人在词海里扑腾。

## 二、进入工作区前必须站稳的系统词汇

这一部分聚焦你一上机器就会碰到的词：Linux、路径、权限、日志、终端、搜索。这些词听起来基础，但它们决定了你后面是不是会一直脚下发虚。

### 1、你坐到工位上，第一批最先会撞到的词

#### 1.1 Linux 到底是什么，为什么实验老爱在它上面做

不少跨专业同学第一反应会觉得，自己以前也写过点代码，为什么一到实验室项目就突然都是 Linux。这里先别把它想得太高深。你完全可以先把 Linux 理解成当前这台机器的工作语言。它不是为了显得专业才出现，而是因为很多科研环境、GPU 工位机、远程服务器、开源工具链、自动化脚本和工程部署流程都在这个生态里更顺手、更稳定。

你眼前这台机器上，项目工作区在 `/home/howard/Splat-Nav`，数据和结果很多又放在 `/data/howard/...`。这种目录结构、权限方式、软链接机制、环境变量和远程登录方式，本来就是 Linux 世界的日常。你只要真在这个项目上待一周，就会发现自己并不是在“学一门陌生操作系统”，而是在适应一个默认规则不同的工作环境。

真正会让新手焦虑的，不是 Linux 本身，而是刚上来时看到很多陌生命令。这个焦虑很正常。你要做的不是假装自己全懂，而是先接受一个事实：你现在不是来当系统运维的，你只是需要掌握一套足够让自己稳定工作、稳定排错、稳定读结果的基本动作。只要把这件事想清楚，压力会小很多。

#### 1.2 SSH：你和这台机器建立关系的第一根线

`SSH` 可以先很朴素地理解成“远程上机器”的标准方式。你人不在工控机前，但项目和显卡在那台机器上，于是你需要通过网络把自己接进去。很多新同学第一次看到 `ssh howard@<ip>` 会莫名紧张，仿佛自己在做一件很危险的事。其实大可不必。它本质上只是告诉系统：我现在想以这个用户身份，进入这台远程主机。

对当前项目来说，`SSH` 的重要性不是抽象的，而是具体得不能再具体：如果它没通，你连工作区都进不来；如果它通了但你没意识到自己现在已经在远端，你后面看路径、跑脚本、查日志时就会一直混淆“这是我电脑上的东西，还是服务器上的东西”。所以你以后只要一开始工作，脑子里最好先确认一句：我现在的这个终端，到底连到了哪里。

一个非常小、但非常值得反复做的确认动作是：连接上去之后，先打 `pwd` 和 `hostname`。前者告诉你当前目录，后者告诉你当前机器名。听起来土，但极其有效。很多“我明明跑了怎么结果不见了”的事故，追到最后都只是因为人其实跑在了错误的地方。

#### 1.3 Terminal 和 Shell：别把窗口和语言混成一个东西

很多人嘴里会把“终端”“shell”“命令行”混着说，日常聊天没问题，但一到排错就容易乱。一个相对清楚的记法是：`Terminal` 更像窗口或门面，`Shell` 更像你在这个窗口里真正用来和系统对话的语言解释器。你打开一个终端窗口，里面通常跑着一个 shell，在这台机器上通常就是 `bash`。

为什么这个区分值得记一下？因为你后面会遇到好几种上下文。你可能有本地电脑上的终端，有 SSH 进去后的远程终端，还有 tmux 里的远程终端。表面看都是黑框，实则上下文完全可能不同。你如果只记“我刚刚在终端里敲过这个命令”，是远远不够的。你真正应该记的是：我是在本地终端敲的，还是在远程终端敲的；我是在普通 shell 里敲的，还是在 tmux 会话里敲的；当时是不是已经激活了 `splatnav` 环境。

这种区分一开始看起来细碎，后面却会救你很多次。因为工程问题最怕的，从来不是某个命令太复杂，而是你连自己站在哪里都没看清。

#### 1.4 `pwd`、`cd`、`ls`：你在项目里走路时最像“脚感”的三个动作

一说 Linux 命令，很多新手最容易小看这三个：`pwd`、`cd`、`ls`。觉得这不就是看路径、切目录、列文件吗？的确是，但它们的重要性恰恰在于太基础了。项目里的很多错误，本质上都不是算法问题，而是“你人站错地方了”。

`pwd` 是“我现在站在哪”。`cd` 是“我现在往哪走”。`ls` 是“我站在这儿能看到什么”。把这三个动作用熟，不是为了炫命令行，而是为了让自己在目录结构里有脚感。你以后只要一感到混乱，就先别急着点文件、别急着敲长命令，先问自己：我现在在哪？我该在哪？我看到了什么？这三个问题，往往比多搜十篇帖子更快。

比如说，你今天第一天接手项目，连上机器以后，最值得做的不是立刻去找 `splatplan.py`，而是先这样确认：

```bash
pwd
cd /home/howard/Splat-Nav
ls
```

这三行的意义，不是你不会写长命令，而是你先把“主工作区门口”找准。你看到了 `docs`、`scripts`、`splatnav-official`、`runs` 这些目录，你脑子里的地图才真正开始长出来。

#### 1.5 `mkdir`、`cp`、`mv`、`rm`：会用，但不要轻浮地用

这些命令看起来都很常见，但对共享机器来说，态度要稍微稳一点。`mkdir` 是建目录，`cp` 是复制，`mv` 是移动或重命名，`rm` 是删除。前三个本质上是在“增添或搬运东西”，`rm` 则是让东西直接消失。对于当前工作区这种共用机器、共用资源、又明确划了边界的环境，`rm` 尤其要慢一点。

不是说 `rm` 不能用，而是你要先形成一个反射：每次准备删东西前，先确认自己删的是哪一层的东西。你删的是自己新建的 run 目录，还是师兄也在看的共享结果？你删的是 home 目录里的文档草稿，还是某个被软链接出去的重要位置？尤其是当你看到带通配符的删除命令时，更应该停半秒。新手最怕的不是不会删，而是删得太爽。

对学弟来说，一开始你甚至可以把一个习惯记死：凡是涉及 `rm`、涉及密码、涉及 `sudo` 的动作，先想明白“它到底改谁”。你会发现，这个习惯能帮你规避很多本来完全没必要付出的代价。

#### 1.6 `cat`、`less`、`head`、`tail`：看文件不是只能靠编辑器

很多同学一开始觉得，看文件当然就是打开编辑器。可是在远程和日志场景里，这种习惯并不总是最高效。尤其是当你只是想快速确认一个文本文件里有没有某一段内容、最后几十行是不是报错、开头几行是不是头信息时，命令行查看工具反而更轻巧。

`cat` 适合很短的文件，一口气全看完。`less` 更适合长文件，可以翻页、搜索。`head` 看前几行，`tail` 看后几行。到了项目里，这几个动作会非常频繁。你跑完一次任务，不会第一时间把整个 `stdout.log` 拖进编辑器慢慢滚，而是很可能先 `tail -n 40 stdout.log` 看看结尾发生了什么。你怀疑 `cmd.txt` 记录的命令不对，可能就 `cat cmd.txt` 快速确认。

你别小看这些“好像很初级”的动作。真正成熟的工作习惯，往往就是这样一点一点长出来的。你越早接受“远程项目里看文件不只靠编辑器”，后面会越顺。

#### 1.7 `grep`、`find`、`rg`：当你开始不知道某个词在哪儿时，它们会救你

你刚接项目时很容易出现一种情况：我知道这个词出现过，我知道这个脚本大概在哪层，但就是不知道具体在哪个文件、哪一行。这个时候，搜索工具的价值就出来了。传统上很多人用 `grep` 和 `find`，现在更常用、更快的是 `rg`，也就是 ripgrep。

如果你要找文件名，`find` 很有用；如果你要搜内容，`rg` 往往更舒服。比如你想知道工作区里哪里提到过 `old_union`，或者哪个脚本里写了 `LD_LIBRARY_PATH`，与其靠肉眼翻，不如搜索。对新人来说，真正值得练的是一种工作心态：不知道位置不是耻辱，不会利用搜索工具才会让自己一直卡住。

我非常建议学弟尽早接受一个现实：一个中型项目里，没人会靠记忆把所有文件和函数位置背下来。会搜、会定位、会顺藤摸瓜，本身就是能力。

#### 1.8 `df` 与 `du`：磁盘空间是项目现实，不是旁枝末节

你们这台机器有一个非常现实的背景：系统盘剩余空间紧，数据盘更宽裕。所以像 `df -h`、`du -sh` 这样的命令，不是系统管理员才会用的工具，而是你做项目时需要有的现实感。`df -h` 看的是整体分区剩余空间，`du -sh <目录>` 更像是在问某个目录已经长到多大。

为什么这件事在当前项目里尤其重要？因为你后面会生成很多 `runs`，会下载场景数据，会产生 JSON、图、日志，甚至可能做更多可视化。如果你对磁盘空间完全没感觉，最后很容易把本来是实验问题，拖成空间问题。

你不需要天天盯着磁盘，但至少要养成一个常识：系统盘紧张时，别往 `/` 附近乱堆重资产；结果和缓存尽量走数据盘；看到异常大的 run 目录要有感知。工程感有时候就是这么朴素。

### 2、路径、权限、软链接：为什么你总觉得“好像有两份代码”

#### 2.1 绝对路径和相对路径：不是谁高级，而是谁更不容易让你迷路

这两个词是所有新人都会遇到的，但真正理解它们的差别，通常要到第一次踩坑以后。绝对路径，就是从系统根目录 `/` 开始一路写死的位置。比如 `/home/howard/Splat-Nav/scripts/run_in_tmux.sh`。相对路径，则依赖你当前所站的位置。比如你已经在 `/home/howard/Splat-Nav` 根目录下，那 `scripts/run_in_tmux.sh` 就能工作。

听起来只是写法长短不同，实际上它们影响的是“歧义大小”。在你还没对项目目录很熟的时候，绝对路径像路牌，长一点但不容易走丢。相对路径像熟人之间的口头简称，前提是双方都知道你现在站在小区哪栋楼下。对于刚接项目的学弟，我会很明确地建议：前期多用绝对路径，把地图压实；后期熟了，再自然切到相对路径提高效率。

#### 2.2 权限：先不用学得太系统，但要知道“谁能读、谁能写、谁能执行”

Linux 的权限讲深了会很多，但你第一阶段只需要抓住最朴素的一层：文件和目录不是天然想干嘛就能干嘛的，系统会区分谁能读、谁能写、谁能执行。你以后看到一个脚本能不能直接运行，和它有没有执行权限有关；你能不能修改某个目录里的东西，和它的写权限有关。

对于当前项目最有价值的，不是背权限位细节，而是先建立一种边界意识：你用的是自己的账户，在自己的工作区里做事情；不要轻易假定自己对某个系统位置天然有写权限；也不要一遇到权限问题就想 `sudo`。很多时候，正确做法反而是先问：我为什么会碰到这个位置，我本来是不是就不该动它。

#### 2.3 软链接：理解了它，你就不会再问“为什么 home 和 data 都有一份仓库”

`软链接` 是当前项目里必须真正讲透的词。你可以把它先粗略理解成“快捷入口”。它看起来像一个目录或文件，但真正内容不在这里，而是在别的真实位置。对当前工作区，最典型的例子就是 `/home/howard/Splat-Nav/splatnav-official`。你看上去像是在 home 目录里打开了官方源码，其实它通过 `third_party/splatnav-official` 又继续指向 `/data/howard/repos/splatnav-official`。

这就是为什么很多新人第一次会困惑：“怎么 home 下面有一份，data 下面也有一份？”真正答案往往是：不是两份，而是一个入口加一个真实位置。如果你不把软链接理解清楚，后面读代码、解释项目结构、甚至汇报时都会绕进死胡同。你会一直怀疑自己是不是在看错仓库。

一个很适合记住的确认命令是：

```bash
readlink -f /home/howard/Splat-Nav/splatnav-official
```

这条命令的价值不在于炫技巧，而在于“追根问底”。你想知道这个入口最后落到哪里，就让系统替你把链路摊平。

#### 2.4 双跳链：为什么当前工作区要这么设计

当前工作区最值得新人尽早建立的路径直觉之一，就是所谓“双跳链”。也就是 `splatnav-official -> third_party/splatnav-official -> /data/howard/repos/splatnav-official`。为什么不直接只留一个？原因其实很工程化。这样做能同时满足几件事：工作区内部有一个好找、好讲、好点击的源码入口；第三方依赖的概念被显式表达出来；真实仓库存放在数据盘，更符合空间和协作边界。

你可以把它理解成办公室里常见的一种安排：门口贴了个牌子写“会议室在这边”，但真正的会议室在走廊尽头。那个牌子的价值，不是它自己能开会，而是它让所有人都更容易找到真正的房间。软链接很多时候就是这个牌子。

#### 2.5 `readlink -f` 值得你变成熟练动作

有些命令不是天天用，但一旦会了，就特别值。`readlink -f` 就属于这一类。你以后只要看到一个目录“感觉像软链接”、一个路径“看上去不太对劲”、或者一个仓库入口“怎么像是转了一道弯”，都可以直接用它来追真实位置。

对于当前项目，尤其推荐学弟在刚开始就对 `runs`、`splatnav-official` 这些关键入口跑一下 `readlink -f`。不是为了完成某个任务，而是为了把“当前工作区里有些东西只是入口，有些东西才是真实位置”这个观念真正装进脑子。观念一旦稳了，后面很多目录问题就不再吓人。

#### 2.6 为什么短路径入口很有价值，不是为了偷懒

有的同学一看到软链接，会觉得是不是只是为了少打一段长路径。这个理解不全错，但太浅了。短路径入口真正的价值，不只是省字符，而是省认知负担。比如你让学弟以后都去记 `/data/howard/repos/splatnav-official/splatplan/splatplan.py`，当然也能记，但负担会更大。相反，如果工作区里统一从 `/home/howard/Splat-Nav/splatnav-official/...` 进入，路径叙事会清晰很多。

你未来带人的时候会更明显感受到这一点。新人最怕的不是字多，而是路径没有规律。一个路径入口如果既稳定又容易讲，它就不仅是工具，也是教学材料。

#### 2.7 相对路径什么时候会突然坑你

很多新手第一次真踩坑，就是因为相对路径在某个目录下能跑，在另一个目录下突然不行。比如你在工作区根目录下运行 `scripts/run_splatplan_smoke.sh` 没问题，结果进了别的目录以后照着敲，系统就找不到脚本了。这时候千万别急着怀疑脚本坏了。先回到最基础的问题：你现在到底站在哪。

这类坑的核心不是“相对路径不好”，而是“相对路径需要上下文”。当你对上下文不敏感时，最好先稳一点，用绝对路径。等你在工作区里来回走得已经很熟了，再逐步切回相对路径就好。

### 3、日志、环境变量、进程：项目跑起来以后你真正会用到的词

#### 3.1 环境变量：不是神秘黑魔法，而是“当前上下文的一张说明卡”

`环境变量` 这个词听起来特别像考试内容，所以很多人一听就犯怵。其实你先完全可以把它理解成“当前 shell 上下文里附带的一组说明信息”。系统和程序在运行时，会参考这些说明信息决定很多行为，比如去哪找命令、去哪找动态库、临时目录放哪、缓存放哪。

在当前项目里，环境变量最常见的价值不是让你自己发明一堆变量，而是帮你理解“为什么同样一条命令，在不同会话里行为不一样”。因为变量不同，上下文就不同。等你后面看到 `PATH`、`LD_LIBRARY_PATH`、`TMPDIR`、`PIP_CACHE_DIR`，你就知道，它们其实都只是环境变量家族里的成员。

#### 3.2 管道 `|`：把一个命令的输出递给下一个命令

管道的图像化理解很简单：前一个命令吐出来的文本，不落地，直接顺着管子流给后一个命令。比如你列了一堆文件，接着想搜某个关键词，就可以把前者的输出直接喂给后者。它特别适合日志查看、过滤结果和快速检查。

你以后看一些脚本时，会发现很多 shell 技巧其实没有想象中复杂，管道就是其中最值得尽早熟悉的一个。它帮你建立的是一种“把简单动作串起来”的思维，而这和项目工程化的逻辑其实很一致。

#### 3.3 重定向和 `tee`：程序说的话，怎么同时留在屏幕和文件里

`stdout.log` 为什么会有内容？很多时候就是靠重定向或 `tee` 这类机制。你可以先粗略理解成：普通重定向是把输出写到文件里，`tee` 则像一个分流器，一边继续显示在屏幕上，一边同时写进文件。对于当前工作区，这特别重要，因为长任务不可能都靠你盯着屏幕看，输出必须落盘。

当你看到脚本里有 `|& tee "$RUN_DIR/stdout.log"` 这种写法时，不要把它当魔法。它只是很认真地在做一件事：把标准输出和错误输出都留下来。后面你做复盘时，会特别感谢它。

#### 3.4 进程：程序不是“运行中”或“没运行”那么简单

在 Linux 里，程序运行起来以后会变成进程。你现在不用对进程模型理解得很底层，但至少要知道：一个长任务在跑、一个 tmux window 里挂着一个 Python 脚本、一个 watchdog 在后台盯着 overnight，本质上都对应某些进程。你以后看到 `pgrep -f ...`，其实就是在问“某类进程现在还活着吗”。

这个概念的重要性，在于它把“任务状态”从一种模糊感觉，变成一种可观察事实。不是你觉得它应该还在跑，它就真的在跑。你可以查。工程感有时候就是从这种地方长出来的。

#### 3.5 退出码：为什么“没输出”不一定等于“成功”

程序结束以后，系统通常会带一个退出码。最常见的习惯是 `0` 表示成功，非 `0` 表示异常。很多脚本开头会写 `set -euo pipefail`，其中一个核心目的，就是当命令失败时不要继续装作没事，直接停下来。对共享机器和实验复现来说，这种“失败就承认失败”的态度比什么都重要。

新人很容易被一种情况骗到：终端上没看到特别明显的报错，就以为没问题。可实际上，命令可能早就失败了。你如果能逐渐对退出码和 shell 的失败传播机制有感觉，后面读脚本时会更踏实。

#### 3.6 `pgrep`：不是高级命令，是“我到底有没有在跑那个任务”的实话器

当你开始接触 overnight、watchdog、tmux 里的长任务时，`pgrep` 会变得很实用。它的朴素意义就是：按名字或匹配模式找进程。你以后看到 wrapper 脚本里用 `pgrep -f` 去查某个任务是否存在，不要觉得神秘。它只是把“我感觉任务还活着”变成“我真的查到了对应进程”。

这种把感觉变事实的能力，在实验项目里特别值钱。

### 4、在 Cursor 里读代码，和在项目里真的“会读代码”，差别在哪

#### 4.1 工作区文件夹：你打开的，不只是一个目录

当你在 Cursor 或 VS Code 里打开 `/home/howard/Splat-Nav` 时，你打开的不只是一个目录，而是一个上下文。这个上下文里既有文档，又有 wrapper，又有上游源码入口，还有结果目录和配置目录。也正因为如此，读代码不能只靠“看到文件就点”，而要先知道自己现在是在读哪一层。

当前工作区里，你至少要有一个简单分层意识：`docs` 是解释层，`scripts` 是 wrapper 执行层，`splatnav-official` 是上游算法层，`runs` 是结果证据层。你只要先把这个层次感带进编辑器，阅读成本就会下降很多。

#### 4.2 全局搜索：不是偷懒，是中型项目里的基本生存技能

很多新人一开始读代码的方式，是从一个文件顶部开始硬往下刷。这种方式在小作业里可以，在中型工作区里效率很低。因为你真正的问题常常是“这个名字在哪里被定义”“这个方法到底是谁调用的”“这个字段在结果里哪里出现过”。这时候，全局搜索不是捷径，而是正路。

比如你在文档里看到 `feasible`，想知道它在代码里从哪来；或者你在某个 JSON 里看到 `num_polytopes`，想追到上游实现里谁在写它；这时候搜索比死翻靠谱得多。很多人误以为“会读代码”就是能一眼把所有文件串起来，实际上会搜、会跳、会定位，才是真正的读码能力。

#### 4.3 Traceback：一段报错不是羞辱你，而是在给你路线图

Python 报错最容易让新人情绪受挫。看着一长串 traceback，会本能地觉得“完了，我什么都不会”。其实反过来想，traceback 正是在给你一条线索链：最后一行通常告诉你错误类型和直接症状，上面的栈则告诉你是从哪些函数一路走到这里的。它不是故意吓你，而是在交代案发现场。

你一开始不需要把每层栈都读懂，最有效的方法是先看最后一句，再往上找第一段明显属于你当前工作区的路径。比如你看到报错里出现 `/home/howard/Splat-Nav/scripts/...` 或 `splatnav-official/...`，这就已经是很有价值的锚点。慢慢地，你会发现自己对报错不再只剩恐惧，而是开始能从里面抽出结构。

#### 4.4 求助时最有价值的，不是“我报错了”，而是你能带来上下文

新人最怕求助，担心自己显得太基础。其实真正让人难接球的，不是基础问题，而是没有上下文的问题。如果你来一句“师兄我报错了”，但不说你跑了什么命令、在哪个目录、哪个环境、哪份日志、最后一行是什么，别人很难帮你。反过来，如果你能把 `cmd.txt`、`stdout.log` 末尾、当前 run 目录和自己的判断一起说出来，哪怕问题很基础，推进也会快很多。

这其实也是为什么当前工作区这么强调 run 目录和日志落盘。不是为了形式，而是为了让问题能够被复盘、被协作、被继续推进。

## 三、环境、GPU 与运行上下文

很多新人真正的第一道坎不是算法，而是环境。这里把 Conda、Python、CUDA、Torch、tmux 和 Git 这些会反复出现的运行词汇集中整理在一起。

### 1、Conda、pip、解释器：环境到底在管什么

#### 1.1 为什么当前项目必须认真对待环境，而不是“装上就行”

很多同学刚开始写代码时，对环境没什么概念。觉得能跑就行，装在哪儿都差不多。可一旦项目开始涉及 GPU、Torch、Nerfstudio、Open3D、可视化和多个依赖源，环境立刻变成一件非常现实的事。当前项目又是共享机器、共享硬件、明确不能乱动系统 CUDA 的场景，所以环境更不可能靠“随手装一装”解决。

环境在这里的价值，可以先理解成一个受控的工作小屋。你在小屋里装包、修包、调解释器，不去砸整栋楼的总线路。这个比喻虽然朴素，但很适合当前工作区。你们之所以专门在 `/data/howard/miniconda3` 下装 Miniconda、再建 `splatnav` 环境，就是在做这件事。

#### 1.2 Conda：给项目一间相对独立的屋子

`Conda` 不是一句“装 Python 的工具”就能讲完的。对当前项目，最有价值的理解是：它帮你为这个项目准备一个相对独立、相对可控的软件空间。你可以在里面固定 Python 版本、安装一组依赖、做一些局部修复，而不用把系统环境和别人的环境一起拖下水。

你后面看到 `conda activate splatnav` 时，不要把它当礼仪性动作。它真正的含义是：我现在准备在 `splatnav` 这间小屋里做事，而不是在系统大厅里乱摆工具。这件事在共享机器上特别重要，因为边界一旦模糊，排错和协作都会变得很难。

#### 1.3 Miniconda：为什么这里不是 Anaconda 全家桶

`Miniconda` 可以理解成更轻量的安装方式。对于当前机器来说，这种选择很合理。原因很简单：系统盘紧、数据盘相对宽裕、项目强调边界和可控性，不需要一上来就拉一个巨大生态包。把 Miniconda 安装在 `/data/howard/miniconda3`，既避免压迫系统盘，又方便把环境、缓存和工具链集中管理在相对独立的位置。

你以后在脚本里看到 `source /data/howard/miniconda3/etc/profile.d/conda.sh`，应该意识到这是在显式接入当前机器上这套 Miniconda 环境，而不是假设用户的 shell 已经自动配置好了所有事情。

#### 1.4 `conda activate` 真正在改变什么

很多新手会觉得，激活环境就是“形式上切换一下”。实际上，它通常至少在改几件关键事情：当前 `python` 指向哪一个解释器，当前 `pip` 会把包装到哪里，以及一部分依赖和路径的查找顺序。也就是说，激活环境不是给你一种心理安慰，而是在真正改变你接下来命令运行的上下文。

这也是为什么“我明明装了包但 import 不进来”这种问题，很多时候先别怀疑包本身，而是先问：我刚才到底激活了哪个环境？

#### 1.5 pip：在环境内部继续装具体 Python 包

当前项目里，环境管理的常见路线是：用 Conda 建立壳，再用 `pip` 装很多具体 Python 依赖，比如 `nerfstudio`、`clarabel`、`cvxpy`、`open3d`、`viser`、`lightglue` 等。你可以把它理解成：Conda 先帮你准备房间和基本框架，`pip` 再把房间里的家具一件件搬进来。

这里最需要避免的，不是用 `pip`，而是脱离上下文乱用 `pip`。同样一条 `pip install`，在不同解释器和不同环境里装进去的位置可能完全不一样。你以后看到任何与 `pip` 相关的问题，第一反应都应该回到上下文：我在什么环境里装的？我现在又在什么环境里跑的？

#### 1.6 Python 解释器：不是只有“有 Python”这一个维度

很多新手心里对 Python 的图像是：机器里有个 Python，就能跑脚本。真正项目里，事情通常没这么简单。同一台机器上可能有系统 Python、Conda 环境里的 Python、别的工具链附带的 Python。当前项目最值得你养成的不是“我会写 Python”，而是“我会先确认当前到底是哪一个 Python 在跑”。

一个很朴素但很好用的动作，是在关键环境里看一下：

```bash
which python
python --version
```

这不是形式主义，而是在防止你后面调半天包，结果其实调错了解释器。

#### 1.7 渠道、缓存和临时目录：为什么脚本里会主动设置 `TMPDIR` 和 `PIP_CACHE_DIR`

你在 `scripts/bootstrap_env.sh` 和 `scripts/run_in_tmux.sh` 里会看到对 `TMPDIR`、`PIP_CACHE_DIR` 的设置。这件事对新人很容易显得细碎，但它背后其实很现实：当前机器系统盘紧，数据盘更合适放缓存和临时文件。把这些位置显式指向 `/data/howard/splatnav/tmp` 和 `/data/howard/splatnav/cache/pip`，是在避免安装和运行把系统盘悄悄塞满。

你不用把它理解得太工程黑话。先把它看作“给垃圾桶和中转区找对地方”。找对地方，后面很多看似奇怪的空间问题都会少很多。

### 2、GPU、CUDA、Torch、LD_LIBRARY_PATH：最像黑魔法的一组词，其实也能讲明白

#### 2.1 GPU：不是越满越好，也不是不满就说明程序没跑

很多新人第一次接触 GPU 项目，会把 `nvidia-smi` 当心电图看。显存高一点就兴奋，利用率低一点就怀疑程序没跑。这个反应很真实，但还不够成熟。对当前项目更准确的理解是：GPU 只是某些计算阶段的重要资源，不是所有阶段都必须把它打满。官方 README 也明确提到，某些轨迹和优化步骤主要跑在 CPU，这样能把 GPU 资源留给更需要它的地方。

所以你以后看到 GPU 利用率不高，不要立刻惊慌。先看任务到底处在哪个阶段，再结合日志和结果判断。工程判断最怕只盯一个数字。

#### 2.2 驱动：它决定系统能不能和显卡好好说话

`驱动` 是一个特别容易被新人抽象化的词。你可以先把它理解成“操作系统和显卡沟通的底层桥梁”。当前工作区明确的一条边界就是：不去升级系统驱动，不去升级系统 CUDA，不去碰师兄已有环境。这个边界不是保守，而是非常现实。共享机器上，乱动驱动往往是牵一发动全身。

这意味着当前项目的很多修复动作，思路都不是“把楼拆了重盖”，而是“在自己这间屋里把兼容性问题解决掉”。只要把这个原则记住，很多后续决策都会清晰很多。

#### 2.3 CUDA：你先把它理解成“GPU 运行时家族”就够了

`CUDA` 这个词第一次出现时，很多人会自动紧张，仿佛背后藏着一整个专门学科。对当前项目第一阶段，完全没必要把它想那么大。你现在真正需要的，是知道 Torch 和一些依赖会和某个 CUDA 运行时版本绑定，而当前系统驱动又要能支持这套绑定。也就是说，它是兼容链里的一环。

你在脚本里会看到 `cu124` 这类字样，也会看到 `torch.version.cuda`。这些都在回答一个问题：当前这个 Torch 是按哪套 CUDA 运行时构建的。你暂时不需要会配开发环境，只要会读这层信息，就已经很有用了。

#### 2.4 `torch.cuda.is_available()`：它不是人生判断题，但它是很好的岔路口

当前项目里很常见的一个检查，就是 `torch.cuda.is_available()`。这个值如果是 `True`，说明 Torch 至少认为自己能用 CUDA。它如果是 `False`，你后面很多依赖 GPU 的步骤都会受影响。对新人来说，这个布尔值最大的价值不是“神奇”，而是它帮你把排查路线切成了两条。一个 `True`，说明你可以继续往别的地方查；一个 `False`，说明你先别急着碰算法，要先回到环境和兼容链。

很多工程排错之所以显得神秘，就是因为大家没有先找一个像这样的路口值。你只要记住这一个检查，后面排错会稳很多。

#### 2.5 Torch：当前项目不是“深度学习项目”，但 Torch 仍然是主力数值引擎

有些跨专业同学会以为，既然当前重点在规划，不在训练，那 Torch 会不会没那么关键。恰恰相反。即使当前重点不是端到端训练，Torch 依然是很多几何和张量计算的主力。`GSplatLoader` 会读张量，`SplatPlan` 和 `SafeFlightCorridor` 会在张量层面处理场景和路径，设备管理也靠 Torch。

所以你对 Torch 的最初理解，不一定要从“神经网络框架”开始。你完全可以先把它理解成当前项目在 CPU/GPU 上搬运和计算多维数组的主要工具。这样会更贴近你眼前的代码现实。

#### 2.6 `LD_LIBRARY_PATH`：为什么它老和奇怪的导入错误绑在一起

到了这里，我们要认真讲一下 `LD_LIBRARY_PATH`。如果只给定义，很多人读完还是糊。更有效的讲法是：程序启动时，除了要找到主程序，还要找到它依赖的各种动态库文件。`LD_LIBRARY_PATH` 就是在告诉系统，优先去哪几类位置找这些库。问题在于，如果这条路径里混进了和当前环境不匹配的库，程序就可能被“错误地帮助”，最终表现为导入失败、符号不匹配或更隐蔽的问题。

当前工作区采取了很明确的策略：很多关键 Python 命令运行前，先 `unset LD_LIBRARY_PATH`，或者直接用 `env -u LD_LIBRARY_PATH python ...`。你要理解，这不是土办法，而是一种很务实的隔离方式。因为系统里可能存在别的 CUDA 相关库、别的用户环境遗留的库，而你们又明确不想升级系统层。那最直接的办法，就是尽量让当前 Conda 环境自己解决自己的库问题。

#### 2.7 为什么 `fix_torch_cuda.sh` 的思路是“环境内修”，不是“系统级修”

`fix_torch_cuda.sh` 的价值非常能体现当前项目的工程边界。它不是去碰系统驱动，也不是去碰全局 CUDA，而是在 `splatnav` 环境里强制重装一套与当前驱动兼容的 Torch。这个思路对学弟尤其值得学，因为它背后其实是一种成熟判断：当机器是共享的、系统不能乱动时，你应该优先在自己控制范围内修复问题。

这种思路以后会迁移到很多地方。你不只是修 Torch 时这么想，未来改路径、改缓存位置、改日志输出，也应该先从自己这层入手。边界感，不是保守，而是合作环境里的基本素养。

### 3、tmux、Git、版本与协作：项目不是只做给当下这一分钟看的

#### 3.1 tmux：当你不想让任务随着网络一起掉线时，它就是救命绳

对很多新同学来说，`tmux` 是第一个看起来“有点像高手工具”的东西。其实完全不用把它神化。你可以先把它理解成远程机器上的持久终端会话。你本地断线了，窗口关了，Cursor 重载了，tmux 里的任务还可以继续跑。对于当前这种会有 smoke、batch、overnight、watchdog 之类长任务的项目，它非常实用。

当前工作区甚至已经帮你把 tmux 用法包了一层，也就是 `scripts/run_in_tmux.sh`。这更说明一件事：tmux 在这里不是锦上添花，而是主流程的一部分。学弟最值得先形成的，不是手动记所有 tmux 子命令，而是一个判断力：这个任务会跑很久，那我就别赌当前窗口稳定，尽量送进 tmux。

#### 3.2 会话、窗口：tmux 里真正值得你先懂的两个词

`session` 可以先理解成一组长期存在的工作空间，`window` 则像这个空间里的标签页。当前工作区统一使用 `splatnav_jobs` 作为一个会话名，然后不同任务对应不同窗口。这种组织方式的好处很明显：你第二天回来看，不会完全失去线索。

新手经常一听到 tmux 就想把所有快捷键都记住。其实没必要。先把“会话”和“窗口”这两个概念装进去，就已经够你看懂 wrapper 脚本在干什么了。因为你至少知道，它不是在凭空变戏法，而是在替你管理远程任务的生命周期。

#### 3.3 Git：不是为了装专业，而是为了让修改有来有回

`Git` 在项目里经常被两种极端理解。一种是神话它，觉得不会 Git 就不配做工程；另一种是轻视它，觉得不就是保存历史吗。都不太对。对当前工作区更准确的理解是：Git 让修改有来有回，让你知道什么是原来的、什么是你改的、什么时候变的、能不能回头看。

尤其当你们现在已经有 wrapper 层、上游层、文档层时，Git 的意义更大。因为你不是一个人在纸上写草稿，而是在真实项目里积累可交接资产。没有版本意识，很多工作都会越来越难讲。

#### 3.4 commit：不是“任务做完了才配提交”，而是“某个小阶段有了稳定证据”

很多新人会把提交想成一件很隆重的事，觉得必须等到“做了很大事情”才能 commit。其实一个更成熟的理解是：当你完成了一个稳定的小阶段，比如修了一份文档结构、补了一条脚本说明、让一条 smoke 路线变得可复现，就已经可以形成一个提交节点。提交不是庆功，而是把某个状态钉住。

你现在不一定马上就要提交，但这种“把阶段钉住”的意识，越早有越好。它会让你做事情的时候更自觉地组织证据和边界。

#### 3.5 上游仓库和 wrapper 仓库：为什么脑子里必须有“双仓库模型”

当前工作区最值得新人尽早建立的协作心智之一，就是“双仓库模型”。一个是上游官方仓库，也就是论文作者的实现；另一个是你们本地为了复现、文档、日志、长任务管理而加的 wrapper 工作区。它们不是竞争关系，而是分工关系。上游负责“算法本体”，wrapper 负责“工程护栏”。

你以后一旦读代码、改文档、写汇报，就会不断用到这个模型。因为很多话只有分层说才说得清。比如“这个 bug 在 wrapper 层还是上游层”“这个改动属于工程封装还是算法逻辑”“这个路径规范为什么不写进上游代码里”。如果你脑子里没有双仓库模型，很多讨论会一直混成一锅。

## 四、项目本体与核心技术词汇

从这一部分开始，术语不再只是系统和环境层，而开始真正进入项目本体。你会在这里建立对 Splat-Nav、Splat-Plan、GSplat、SFC 和轨迹优化的基本语言感觉。

### 1、进入项目本体：Splat-Nav、Splat-Plan、Splat-Loc 到底各是谁

#### 1.1 Splat-Nav：先别把它想成一个脚本，它是一整套系统的名字

`Splat-Nav` 是论文和项目的总名字。很多新人一开始会下意识地把项目名和某个主脚本等同起来，仿佛只要找到一个叫 `splatnav.py` 的文件就万事大吉。其实不是。`Splat-Nav` 更像总品牌，下面分着不同模块和链路。官方 README 和项目页都明确写了，它由 `Splat-Plan` 和 `Splat-Loc` 两个关键组件组成。

你以后在汇报时特别需要分清这个层次。说“我现在在复现 Splat-Nav”时，最好能继续说清“具体聚焦的是哪一条链路”。对当前工作区第一阶段，最主要的是 `Splat-Plan` 离线/仿真链路，而不是整套硬件闭环都已经完成。

#### 1.2 Splat-Plan：当前第一阶段最该真正理解的主角

如果说当前项目第一阶段有一个必须讲明白的核心词，那一定是 `Splat-Plan`。你可以先用最通俗的话理解它：给定一个用 GSplat 表示的场景，再给定起点和终点，它的任务是先找出一条安全走廊，再在这条走廊里生成一条平滑可执行的轨迹。项目页里说的是“safe-by-construction polytope corridor”，代码层面则最终会落到 `splatplan/splatplan.py` 和相关样条优化器上。

为什么这个词如此重要？因为你当前绝大多数真正能跑、能看、能讲的主线工作，都是围绕它展开的。`smoke_splatplan.py` 是在调用它，`run_official_style_batch.py` 是在批量比较它和基线，`runs` 里的很多结果最终也都是围绕它的可行性和耗时在组织。

#### 1.3 Splat-Loc：现在先知道它是谁，不着急立刻啃透

`Splat-Loc` 是论文的另一个关键模块，作用是用 RGB 图像做位姿估计。它和 `Splat-Plan` 合起来，才构成完整导航闭环。对当前学弟第一阶段来说，它不是最优先的执行主线，但绝对不能完全不知道它的存在。因为如果你只知道 `Splat-Plan`，读论文时会误以为整套系统就只是规划。

一个很稳的态度是：现在先知道它负责“我现在在哪”的问题，并且知道上游有 `run_splatloc.py` 这条入口；等你把当前离线规划主线站稳以后，再回来认真啃它。这种节奏是合理的，不是逃避。

#### 1.4 Gaussian Splatting / GSplat / 3DGS：别让三种叫法把你绕晕

这几个词经常在项目里交替出现，所以很多新人会担心它们是不是三个完全不同的技术。其实你先完全可以把它们理解成同一片语义区域里的不同说法。核心意思都是：场景不是主要用传统稠密网格或纯点云来表示，而是用大量带有位置、方向、尺度、颜色、不透明度等属性的高斯元素来近似表示。

当前项目的关键，不是“会背这个表示的历史”，而是知道：Splat-Nav 不是把场景只是看一眼，而是把这种表示本身拿来服务规划和定位。这个点很重要。因为它解释了为什么当前项目和单纯“训练一个漂亮场景模型”不是一回事。

#### 1.5 Nerfstudio：为什么 `config.yml` 会成为很多脚本的入口

`Nerfstudio` 是当前上游依赖生态里的一个重要名字。你不用一开始就把它研究成独立课题，但至少要知道：Splat-Nav 在读取和使用 GSplat 模型时，是建立在 Nerfstudio 风格的训练产物和目录结构之上的。这就是为什么你会不断看到 `outputs/<scene>/splatfacto/.../config.yml` 这样的路径。

理解了这一点，你对 `config.yml` 的直觉就会更准确。它不是一个神秘黑箱，也不是随便起个文件名，而是连接训练产物和下游规划使用的重要入口。

#### 1.6 `config.yml`：它不是“参数堆”，而是场景模型的门把手

`config.yml` 是项目里最值得早理解的文件类型之一。对学弟来说，你可以先把它粗略看成“进入某个场景模型的门把手”。你告诉脚本这个门把手在哪，它就知道去读对应的模型、数据解析信息和场景上下文。你以后看到 smoke、batch、上游 `run_splatplan.py` 都围绕它打转，就不会奇怪了。

很多新人第一次看实验命令，只盯着 `--scene old_union`，觉得场景就是 `old_union` 这个字符串。其实这只是一半。真正决定“你到底读的是哪套场景模型”的，往往还是 `config.yml` 路径。字符串是标签，配置才是入口。

#### 1.7 Wrapper：别小看这个词，它决定你怎么理解整个工作区

`wrapper` 在很多人耳朵里像是“套壳”，好像不够高级。对当前工作区，我反而很希望学弟尽早摆脱这种偏见。wrapper 层不是多余，而是在共享机器、复杂依赖、长任务和结果沉淀环境里，保证复现稳定性的关键护栏。你们现在能用统一 run 目录、统一 tmux 启动方式、统一结果汇总、统一可视化输出，很大程度上都是 wrapper 层的功劳。

所以当你看 `scripts/` 目录时，不要用“这不是论文创新，所以不重要”的态度看。更准确的看法应该是：它不是论文算法本体，但它是让论文算法在这台机器上变得可管理、可交接、可复盘的那一层。

#### 1.8 Upstream：为什么这个词一懂，项目结构就顺了很多

`upstream` 指的是上游官方实现，也就是论文作者原始仓库那一层。你们当前工作区通过软链接把它接进来，是为了既保留它的原貌，又让本地有一个统一入口读它。学弟最值得形成的一个习惯，是以后谈问题时尽量区分清楚“这是 upstream 的行为，还是 wrapper 的行为”。

这个区分一开始看起来像措辞细节，后面会变成真正的工程判断力。比如某个结果字段是谁定义的，某个路径规范是谁加的，某个脚本为什么和官方 README 不一样，这些问题都要靠“upstream vs wrapper”这个分层来解释。

### 2、规划、几何和结果：那些一开始最像天书的词，其实也能慢慢讲顺

#### 2.1 A*：不要把它想成“另一个项目”，它只是初始化路径的一种办法

很多新人听到 `A*` 会立刻切换到“路径搜索算法课本”模式，觉得又要学一大块新东西。对当前项目，你先不用走那么深。一个足够有用的理解是：在 `Splat-Plan` 和 `SafeFlightCorridor` 这类方法里，往往先需要一条粗路径做初始化。`A*` 很多时候就在扮演这个角色。它不是最终轨迹，也不是整个算法的全部，而是一条“先把方向找出来”的路径骨架。

当你带着这个理解去看 `generate_path` 里的处理流程，就会舒服很多。你会知道：这不是从零直接魔法变轨迹，而是先有粗路径，再有安全几何，再有平滑优化。结构一旦清楚，数学压力会小不少。

#### 2.2 Voxel：体素就是把空间切成很多小格子

`voxel` 的图像其实很好记。你可以把它想成三维版像素。二维图像里一个个小格子叫像素，三维空间里规则划分的小方格就可以叫体素。为什么这个词在项目里频繁出现？因为把连续空间离散成体素后，很多搜索和占据判断会更好组织。上游里有 `GSplatVoxel`、`PointCloudVoxel` 这些类，正说明它在不同方法里承担的是空间离散化和初始化路径相关的职责。

新手最容易混淆的是：体素和点云不是一回事。点云是散点集合，体素是规则格子。它们都能表达空间信息，但侧重点不同。你只要先抓住这个区别，后面阅读就会顺很多。

#### 2.3 Point Cloud：不是所有三维表示都一样，项目恰恰在比较这种差异

点云对很多人来说更熟一些，因为它比较直观：空间里一堆三维点。当前项目里，一些 `sfc-*` baseline 就会围绕点云相关表示组织碰撞集合和初始化路径。论文和代码的一个关键价值恰恰在于，它不是只会用传统点云思路，而是把 GSplat 这种表示真正带进规划逻辑里。

所以你以后如果看到 `PointCloudCollisionSet`、`PointCloudVoxel`，不要觉得这是旁枝末节。它们是在告诉你：项目不是只有一个方法，而是在拿不同表示或不同安全策略做对比。

#### 2.4 Collision Set：为什么不需要把整个场景都拿来碰撞

`collision set` 可以先理解成“当前这段路径附近真正值得关注的障碍子集”。它不是整个场景所有元素的无差别全集。这个直觉非常重要。因为如果每走一小段路径都把整个场景所有高斯或所有点全拿进来算，不仅慢，也不必要。项目里很多几何处理，都是围绕“局部相关元素”展开的。

你一旦把这个词理解成“为当前这小段路径挑出最相关的一批对象”，后面看到 `compute_set_one_step` 或类似逻辑时，脑子里就不会只有一团黑箱。

#### 2.5 Polytope：先把它想成“安全多面体房间”

`polytope` 初看会很唬人，因为它背后连着线性约束、半空间、凸几何这些内容。对当前第一阶段，你完全可以先用一个直观比喻：它像一个由很多平面围出来的安全房间，只不过这个房间不是拍脑袋画的，而是由一组不等式严格定义出来的。路径不直接在整个场景里乱飞，而是先穿过一串这样的安全房间。

一旦你接受了这个房间比喻，`num_polytopes` 这种结果字段就好懂了。它在说的是：这条规划结果一共用了多少个安全房间。你现在不需要马上会写 `Ax <= b`，先把图像感建立起来就够了。

#### 2.6 Safe Flight Corridor / SFC：思想和方法名，这两层不要混

`Safe Flight Corridor` 一方面是一种经典规划思路，也就是先构造连续的安全区域走廊，再在走廊里找轨迹；另一方面，在当前项目里，它又具体化成了 `sfc-1` 到 `sfc-4` 这些 baseline 名称。这两个层次很容易被新人混成一层。

更稳的理解是：SFC 先是一种思想，然后项目里把不同实现细节和安全保守程度做成了几个模式。你看到 `SafeFlightCorridor` 类时，更多是在看实现；你看到 `sfc-1`、`sfc-4` 时，更多是在看实验方法标签。这个区分一旦有了，你后面就不会一直把“思想”和“具体实验方法名”搅在一起。

#### 2.7 Ellipsoid：你可以先把它看成高斯几何的“方便外形”

椭球这个词一出来，很多人脑子里立刻跳到复杂数学。其实你先不必着急。对当前项目更贴近实际的理解是：高斯体和椭球类近似天然关系很近，所以很多碰撞和安全几何处理会借助椭球这一层来建立更可算的约束，再进一步转成多面体或半空间。

你现在不用一开始就掌握全部推导，只要知道它在链路里的职责：它常常不是最后结果，而是中间几何处理的一层桥梁。知道它在桥上，不在终点，阅读时就不容易被它吓住。

#### 2.8 Bézier、B-spline、SplinePlanner：它们都在回答“怎么让轨迹平滑下来”

论文里说的是 Bézier 轨迹，代码里核心类叫 `SplinePlanner`，新手常常因此犯迷糊，仿佛这是两套不同东西。其实你先抓功能就行：前面安全走廊已经出来了，但机器人真正执行时需要的是一条平滑、连续、满足约束的轨迹。样条、Bezier 这些词，都是围绕“怎么把走廊变成平滑轨迹”这个问题展开。

对新人最稳的方式，不是立刻去抠公式，而是先问：它在链路里处于哪一段？答案是：走廊之后、最终轨迹之前。这个定位一旦清楚，名字差异反而不会让你乱。

#### 2.9 feasible：这是项目里最值得你尽早敏感起来的结果词

`feasible` 是当前整个项目里，我最希望学弟尽早真正理解的词之一。因为它直接关系到你有没有能力判断“这次到底算不算成功”。它说的不是“程序是否退出”，而是“在当前约束下，有没有找到可行解”。也就是说，脚本不报错，不等于这次规划就一定成功；同样，某次 `feasible` 为 `false`，也不自动等于程序坏了。两者完全不是一回事。

你以后在 smoke JSON、batch 统计、汇总 CSV、图表标题里会无数次看到这个词。只要你真正把它装进脑子，很多结果误判都会自动减少。因为你会开始问正确的问题：这次是链路没通，还是链路通了但方法不可行？

#### 2.10 `PrimalInfeasible` 这种词听着可怕，其实是在说“约束打架了”

当你开始进入优化求解器相关日志时，可能会遇到一些像 `PrimalInfeasible` 的词。这类词一开始很吓人，但你可以先把它翻成人话：在当前这组约束下，求解器找不到满足所有条件的解。你不用一开始就背严谨定义。只要先知道它是在说“这组要求彼此冲突或太紧了”，不是在说“电脑坏了”，就已经很有用了。

很多新手一看到这种词就彻底不敢看日志，其实完全没必要。把它翻成人话以后，心理负担会小很多。

## 五、实验、结果与汇报常用词

当你开始真正动手时，最常见的困惑会转向运行规模、结果结构和汇报表达。这一部分把实验链路里最常反复出现的词集中放在一起。

### 1、一轮实验里你最该看懂的词：smoke、batch、overnight、run_dir

#### 1.1 smoke：别嫌它小，它是你最值钱的第一步

`smoke` 在工程里通常就是冒烟测试。放到当前项目，就是用最小成本确认主链路能不能通。你不该把它理解成“简化版正式实验”，而应该理解成“先排雷”。当前工作区里，`smoke_splatplan.py` 和 `run_splatplan_smoke.sh` 就是在做这件事。

新手最容易犯的错，是觉得 smoke 太小，不如直接跑大实验。其实恰恰相反。越是刚接项目，越要先珍惜 smoke。因为一旦 smoke 都不稳，你直接冲 batch 或 overnight，排错成本会指数级上升。

#### 1.2 batch：从“单条样例”走向“有统计意义的一批结果”

`batch` 在这里不是深度学习里那种 mini-batch 训练，而是指批量实验执行。它会在一组起终点上运行多种方法，并统计可行率、平均耗时、P95 耗时等指标。也就是说，它关注的是一批样本上的整体表现，而不是某一条轨迹偶然跑得好不好。

你从 smoke 进入 batch，相当于从“看个例”进入“看总体”。这个台阶非常重要。因为真正能支撑汇报和比较的，通常都不是单次样例，而是有统计意义的一组结果。

#### 1.3 overnight：长时段批跑，不是另一个新项目

`overnight` 这个词听着像一个很高级的新阶段，其实你先把它理解成“把 batch 一轮轮串起来，在夜间窗口里持续跑”就够了。当前 wrapper 层用 `run_overnight_12h.sh`、`watch_overnight_job.sh`、`post_overnight_report.sh` 共同支撑这条链。

它的重要性不在于名字，而在于工程组织方式。你开始会体会到：项目推进不是只看一条命令，而是要考虑长时间运行、自动汇总、异常恢复和第二天快速消费结果。这就是为什么 wrapper 层如此重要。

#### 1.4 run_dir：项目不是做给当前屏幕看的，而是做给未来复盘看的

`run_dir` 可以理解成“某一次任务的证据盒子”。一个规范的 run 目录里，不只是结果，还有 `cmd.txt`、`stdout.log`、`env.txt`、`notes.md` 这些上下文材料。它把“做了什么、怎么做的、当时环境怎样、结果长什么样”尽量放在一个地方。

新手如果能尽早尊重 run 目录，成长会非常快。因为你会逐渐从“我记得我昨天好像跑了什么”变成“我知道我昨天哪一轮任务的证据在哪儿”。这两种状态在科研和工程里差别很大。

#### 1.5 `stdout.log`、`cmd.txt`、`env.txt`、`notes.md`：四个文件，四种不同价值

这四个文件是当前工作区特别值得学弟尽早重视的一组。`stdout.log` 是过程记录，告诉你程序运行时说了什么、报了什么。`cmd.txt` 是命令记录，告诉你当时到底是怎么启动的。`env.txt` 是上下文摘要，记录用户、时间、GPU、Python 和上游提交等环境信息。`notes.md` 则是人工补充位，适合写这轮做了什么、结果怎样、还卡什么。

这四个文件一起，才构成真正有复盘价值的一轮任务证据。只看其中一个，往往都不够。

#### 1.6 JSON、CSV、Markdown 报告：不是重复劳动，而是不同层级的结果表达

新手经常会问：既然已经有 JSON，为什么还要 CSV、还要 Markdown 摘要、还要图？其实它们承担的是不同层级的表达。JSON 更适合结构化细节和程序继续读取，CSV 更适合横向表格比较，Markdown 和图则更适合人快速消费和汇报。

你慢慢会体会到，一个真正成熟的实验输出，不会只给一种形式。因为不同角色需要看的东西不同。你自己排错时可能先看 JSON 和日志，师兄看汇报时可能先看 Markdown 和图，做进一步分析时又会回到 CSV。

#### 1.7 Seed：为什么结果里的“随机性”不能被当成空气

`seed` 是随机数种子。很多新人一开始会对它有两种极端态度：一种是完全忽略，觉得不重要；另一种是过度要求，觉得所有结果都应该一模一样。更成熟的理解是：seed 是在帮助你管理一部分随机性。你不需要把它消灭，但你需要记录它、解释它。

当前 batch 脚本里，seed 会影响样本顺序等行为。这就意味着，如果你完全不记录 seed，后续复现会变难；如果你把结果的每一点波动都当灾难，也会让自己很紧张。对新人来说，先接受“随机性是要被管理的，不是要被神化的”，就已经很够用。

### 2、汇报、协作与判断：让你从“会跑”走向“会讲”

#### 2.1 复现：不是把命令抄下来就算结束

`复现` 这个词非常容易被说空。对当前项目，一个更扎实的理解至少有三层。第一，你真的在这台机器上把主链路跑起来了。第二，你保留了足够的上下文和证据，让别人能知道你是怎么跑的。第三，你能解释自己得到的结果，知道它和论文、上游实现、wrapper 封装之间是什么关系。

你只要缺一层，复现就还不够稳。抄命令不是复现，跑出一张图也不是复现。真正的复现，是能落地、能回看、能解释、能交接的。

#### 2.2 验收：你要学会对自己讲“这一步到底算不算过”

`验收` 是一个看起来很像管理词，但对新人非常重要。因为如果没有明确验收口径，人就会很容易自我感觉“差不多了”。而项目最怕的，恰恰就是这种模糊完成。比如一次 smoke 的验收，不该只是“终端退出了”，而应包括 run 目录完整、结果 JSON 可读、关键字段可解释。一次 batch 的验收，也不是“有几张图”，而是日志、JSON、图、摘要彼此对得上。

学会验收，本质上是在培养一种对事实负责的习惯。

#### 2.3 周报：不是行政负担，而是训练你把事情讲清楚的场子

不少同学一提周报就烦，觉得是在额外写材料。可你把它放到当前项目里看，会发现它其实是在逼你练很重要的一项能力：把“这周做了什么、看到了什么、卡在哪里、下周准备干什么”讲清楚。一个好的周报，应该建立在 run 目录、日志、结果图和自己的判断之上，而不是靠印象编。

你越早把周报和证据绑定起来，越不容易在汇报时心虚。这个习惯以后不仅对科研有用，对工作也非常有用。

#### 2.4 假成功：工程里最应该敏感起来的危险词之一

如果说当前整套词典里，有一个非正式但我非常建议你尽早敏感起来的词，那就是“假成功”。它指的是：看上去任务结束了，甚至还有图、有目录，但真正关键的东西没成立。比如 `feasible` 全是 `false`，比如 JSON 缺字段，图和统计对不上，或者你其实看错了 run 目录。

很多新手的问题，不是不会跑，而是太容易被假成功安慰。学会对假成功保持警惕，会让你比很多看起来更会敲命令的人更稳。

#### 2.5 带人时最重要的，不是你讲得多，而是你有没有把上下文交出来

你未来如果要把项目交给学弟，这份词典背后的真正目的就更清楚了。带人不是把所有知识一股脑丢过去，而是把上下文交出去：这台机器怎么进，工作区怎么分层，哪个脚本是做什么的，为什么 run 目录重要，为什么这次不能直接去动系统 CUDA。你只要把上下文交清楚，学弟即使一开始不懂所有细节，也不至于在完全错误的方向上狂奔。

这其实也是文档为什么值钱。文档不是替代交流，而是在帮交流把底盘铺平。

### 3、读到这里，你脑子里应该已经长出来的那几根“主钉子”

如果这一份重型词典起作用了，你现在不一定已经掌握了所有概念，但脑子里至少应该有几根钉子开始稳定了。第一，你应该知道当前项目里哪些词属于系统和环境层，哪些词属于项目与论文层，哪些词属于规划几何层，哪些词属于实验和结果层。第二，你应该已经不再把 `scripts/`、`splatnav-official/`、`runs/` 混成一团。第三，你应该开始能把 `SSH -> 环境 -> config.yml -> planner -> run_dir -> feasible -> 汇报` 这条词汇链串起来。

请你留意一下，这其实已经不是“记住了很多定义”，而是开始形成一个工作语言。真正的项目理解，往往就是这样慢慢长出来的。你会发现，某些词一开始很可怕，读到第三次时已经不再吓人；某些词一开始看起来很抽象，等你真的在代码、日志和结果里碰到它几次，就突然活了起来。

如果你现在已经有这种感觉，说明这份文档在起作用。下一步，最适合做的事情不是继续埋头背新词，而是带着这些词去读 [02_项目全景与边界_从论文到代码到数据流.md](/home/howard/Splat-Nav/docs/Codex/02_项目全景与边界_从论文到代码到数据流.md)。到了那一份文档里，这些词不会再像散点，而会开始进入真正的项目地图。

## 六、扩展系统、三维表示与工程边界词汇

这里收拢的是那些不会在第一天全用上，但很快就会在交流里频繁听到的词。提前把它们归到一处，能明显降低后面被陌生名词打断节奏的次数。

### 1、你现在还没真正用上，但很快会听到的那批系统词

#### 1.1 ROS2：现在先知道它是“系统集成层的语言”，不是第一周的主战场

`ROS2` 这个词对很多机器人背景项目来说都绕不过去，所以新人一看论文或者听组会讨论，很容易立刻觉得“我是不是必须先把 ROS2 学透，才有资格看 Splat-Nav”。这种想法特别正常，但当前阶段不必这么卷。你先把 `ROS2` 理解成机器人系统里常用的通信与模块组织框架就够了。它更像整车里的总线和接口层，而不是你当前离线规划主线必须先啃透的对象。

为什么这个词仍然值得现在就讲？因为它会频繁出现在项目背景和未来方向里。上游官方 README 也提到 ROS 节点在另一个分支中。也就是说，完整系统最终确实会和 ROS2 发生关系，但对当前工作区第一阶段来说，你的主任务仍然是离线/仿真侧的 `Splat-Plan`。知道它存在，知道它大致负责“系统怎么串起来”，就够了。不要一听到 ROS2 就把自己吓得不敢往下走。

#### 1.2 Gazebo：它更像仿真舞台，不是当前第一步的门槛

`Gazebo` 往往和仿真环境联系很紧。你可以把它先理解成“给机器人提供一个虚拟世界去测试”的仿真舞台。很多同学第一次听到机器人项目，会本能地把 Gazebo 和“我现在要做的一切”绑定起来。其实对当前项目第一阶段，并不是这样。你现在主要在看的是作者已有场景和离线/仿真规划实验，不是立刻去自己搭一个完整的 Gazebo 世界。

换句话说，Gazebo 是你未来可能会碰到的舞台，但不是当前最小主线的第一道门。你先把这个边界记住，会轻松很多。因为你不会再一看到它就觉得自己要同时学仿真引擎、学规划、学视觉、学系统集成。

#### 1.3 Nav2：如果未来谈系统导航，它会出现，但现在先别抢戏

`Nav2` 经常被理解成 ROS2 生态里的导航栈。这个理解大方向没问题。它主要关心的是在系统层怎样把地图、定位、规划、控制这些模块串起来。对当前项目而言，Nav2 不是你这一周必须操作的工具，但它是你以后听到“系统怎么接起来”时很可能会出现的词。

所以我们现在给它一个不费劲的定位：先知道它属于机器人系统级导航框架的一部分，和当前工作区主线不是同一层；以后真的走到系统集成那一步，再回过头认真学。这个顺序没问题，不是偷懒。

#### 1.4 RViz：先把它看成“系统可视化窗口”，别把它和项目结果图混掉

`RViz` 也是 ROS 相关讨论里很常见的词。你可以先理解成一个系统可视化窗口，用来显示机器人状态、地图、轨迹、坐标系等信息。很多新人听到“可视化”就会自动把 RViz 和当前项目里生成的 PNG 图、viser 结果、trajectory overlay 图混在一起。其实不是一回事。

当前工作区里你最常看到的可视化，更偏实验图和网页可视化，而不是 RViz 这种系统级调试窗口。先分清这一点很有必要。因为“可视化”这个词一旦被你混成一层，后面听别人说话时会一直串戏。

#### 1.5 为什么要现在提这些词，但又不要求你现在精通

原因其实很简单：新人最容易焦虑的，不是眼前这个词不会，而是感觉“后面还有好多东西等着我”。把这些词提前点出来，反而会让你安心。因为你知道：是的，它们存在；但不是现在这一周必须一起拿下的对象。你只要知道它们大致在机器人系统图谱中的位置，就已经够用了。

这种“先知道边界，再决定何时深入”的能力，本身就是很成熟的学习方式。

### 2、导航闭环里那些你迟早会碰到的词

#### 2.1 定位、地图、规划、控制：很多大词，其实是四块朴素分工

当别人说“导航系统”时，新人最容易把它想成一个巨大黑盒。更好一点的理解，是把它拆成四块：定位回答“我在哪”，地图回答“世界长什么样”，规划回答“我该怎么走”，控制回答“我怎么真的动起来”。你现在之所以已经能对 `Splat-Nav` 有点轮廓，就是因为论文本身就在这四块里挑了两块重点做：`Splat-Loc` 更贴近定位，`Splat-Plan` 更贴近规划，而地图则是 GSplat 场景表示。

控制那一块在当前离线工作区里没有被展开到第一阶段，但这并不影响你先建立闭环视角。相反，一旦你脑子里有了这四格图，以后很多系统讨论都会变得更清楚。你会知道某个问题到底是在“我在哪”这层，还是“怎么走”这层，而不是所有东西都混成导航两个字。

#### 2.2 坐标系：你先把它想成“大家说的位置是不是在同一本词典里”

`坐标系` 是机器人和三维项目里绕不过去的词。它第一次出现时，几乎所有新人都会紧张，因为觉得这玩意一听就数学很多。其实你先可以用很生活化的一句话理解：坐标系是在约定“位置和方向到底用哪套参照来表达”。如果两个人都说自己在“左边一点”，但参照方向不同，那就会产生混乱。坐标系就是在防止这种混乱。

当前项目里，`config.yml`、Nerfstudio、GSplat 模型、起终点、轨迹结果之间，其实都隐含着坐标表达问题。你现在不需要把每套变换矩阵都推到明明白白，但至少要知道：路径点不是孤立数字，它们总是在某个坐标系里成立。只要先建立这层敬畏，后面读代码和结果就不会太草率。

#### 2.3 frame：为什么有时候大家说的是同一个位置，却数字不一样

`frame` 往往就是“某个具体坐标参照框架”的意思。这个词在视觉、重建、导航里都很常见。最容易让新人困惑的，是“明明都在说同一个物体，为什么数字不一样”。原因通常不是谁错了，而是表达所依据的 frame 不同。一个在相机 frame 里，一个在世界 frame 里，数字当然可能完全不一样。

你不用一上来就把 frame 关系全画出来，但至少要对这个现象敏感。只要你以后看到两个结果对不上，就别急着说哪个错了，先问一句：是不是根本不在同一个 frame 里。

#### 2.4 世界坐标、相机坐标、数据坐标：它们不是故意为难你

很多跨专业同学会在这儿心态崩一下，觉得“怎么同一个项目里还要有这么多坐标说法”。其实这很正常。相机拍到的内容天然有一套相机视角表达，数据采集过程可能有自己的数据坐标，训练和重建过程中又可能映射到某种统一场景坐标。你先接受这是不同层的表达，而不是故意玩花活，压力就会小很多。

当前项目里，尤其值得你先记住的是一句：当你看到坐标相关问题，先别把它当成“数字没对上”的普通 bug，它很可能是表达语境的问题。这个判断一旦会了，很多疑惑都能少走弯路。

#### 2.5 goal：在这个项目里，“目标”并不总是一串随便写的数字

`goal` 这个词听起来太普通了，所以新人反而容易忽略它的细节。在当前项目语境里，goal 有时是明确的终点坐标，有时在论文完整系统层还可以是更高层语义目标。也就是说，它不是永远都只意味着“你在代码里手填的三个浮点数”。

对第一阶段来说，你先把 goal 理解成规划终点就够了。但你应该知道，论文完整叙事中它可以延伸得更丰富。这层认识，会帮助你以后读论文和看项目页时不觉得跳跃。

#### 2.6 trajectory：路径和轨迹，别先把它们混成一个词

很多人口语里会把路径和轨迹混着用，问题不大。但你在当前项目里，最好还是有一个基本区分。`path` 更像几何上的通路，强调“从哪里经过”；`trajectory` 更像准备给执行系统用的、更平滑、更具动态约束意味的表达。上游结果里经常会同时出现 `path` 和 `traj`，这不是重复，而是在区分不同层级的输出。

只要你把这个区别先记住，后面看 JSON 结果时就不会疑惑“怎么两份结果都像路线”。

### 3、三维表示世界里那些很容易混在一起的词

#### 3.1 点云、网格、NeRF、3DGS：它们都在回答“场景怎么表示”，但答案不同

这四个词一开始看上去像同类型名词堆在一起，确实容易让新人发懵。更轻松一点的理解方式是：它们都在回答“我拿什么来表示一个三维场景”，只是回答方式不同。点云更像一堆离散点，网格更像面片拼起来的表面，NeRF 更像连续隐式辐射场表示，而 3DGS / GSplat 则是用很多高斯元素来近似场景。

在当前项目里，你不需要把这四者的论文历史都啃一遍，但你至少要知道：Splat-Nav 之所以叫这个名字，就是因为它不是建立在纯点云或纯网格地图上的，而是建立在 Gaussian Splatting 场景之上的。这层差异本身就是项目存在的意义之一。

#### 3.2 为什么不是所有“看起来都能表示场景”的方法都适合做同样的导航

这是一个特别值得新人早一点理解的点。很多时候我们会本能觉得：只要场景能表示出来，后面导航不就一样做吗？其实不是。场景表示方式会深刻影响规划和定位怎么做、速度怎样、安全约束怎么构造、计算成本落在哪。项目之所以强调 GSplat，不是为了跟风，而是在强调这种表示方式对实时导航有现实影响。

你把这个逻辑抓住了，后面读论文时就不会只把 Gaussian Splatting 当作“画面好看”的噱头。

#### 3.3 `splatfacto`：它在路径里出现时，意味着你已经站在训练产物门口了

在当前目录里，你经常会看到 `outputs/<scene>/splatfacto/.../config.yml` 这种路径结构。这里的 `splatfacto` 不是随便起的文件夹名，它通常代表 Nerfstudio 里某类 GSplat 模型训练产物的组织路径。对新人来说，它最有价值的不是精确定义，而是路径直觉：看到它，说明你正在接近场景模型产物，而不是普通脚本目录。

这类路径词一开始看起来像细节，但当你多看几次以后，会慢慢形成一种“路径读图能力”。这很重要。

#### 3.4 `transforms.json`：很多时候它在帮助你把图像和空间关系对上

这个文件在数据和重建语境里很常见。你现在不需要精读其格式细节，但要知道，它通常在帮系统记录图像与空间变换、相机视角等相关信息。当前项目的数据下载和补齐脚本也会关心它是否存在，这说明它在场景数据可用性上不是无关紧要的附件。

对新人来说，最重要的不是会手改它，而是知道它属于“场景数据几何关系的重要文件”，缺了它很多链路就不完整。

#### 3.5 `sparse_pc.ply`：它为什么会出现在下载验收条件里

`ply` 文件是点云或网格类数据常见的格式之一。当前脚本里会把 `sparse_pc.ply` 是否存在当成场景下载完整度的一部分检查条件，这说明它至少在数据准备链上扮演重要角色。新人不一定要马上打开它，但要知道：它不是普通图片，而是和空间几何有关的资产。

理解这一点，能帮你更快看懂为什么下载脚本和补齐脚本会特别在意它。

#### 3.6 `images_2`、`images`、frame 图像：别把“图片文件夹”看得太随意

很多新手看到数据目录里的图像，会觉得不就是图像吗，在哪个文件夹区别大吗？在真实项目里，区别往往很大。不同图像目录可能代表不同下采样、不同筛选策略、不同训练或评估版本。当前下载脚本里甚至会直接用帧数门槛来判断某些目录是不是足够完整。这就说明图像目录不是随便起的名字，而是数据链中的有意义节点。

你未来只要养成一个习惯：看到图像目录，别只把它当“图片堆”，先问它在数据流里是什么角色。

### 4、优化与求解器：先理解“它在解决什么”，再去想“它怎么算”

#### 4.1 优化：为什么规划里常常绕不开它

很多同学一听到优化，就自动回到数学课的紧张情绪里。其实你先可以用非常朴素的话理解：当我们希望轨迹既平滑、又满足安全区域、又满足起终点要求时，这本身就是一类“在若干条件下找一个最合适解”的问题。优化就是在处理这类事。

对当前项目而言，你最重要的不是先会推导所有矩阵，而是知道优化在链路里的职责：前面有走廊，后面要变成平滑轨迹，这个转换不是拍脑袋完成的，而是通过求解一个带约束的问题来完成。

#### 4.2 凸优化：你先把它理解成“相对更规整、相对更好求的一类问题”

`凸优化` 这个词不用上来就往严格定义上走。你先记一个工程直觉就行：它通常意味着问题结构相对规整，因此更有机会被稳定、高效地求解。当前项目里，当你看到 `cvxpy`、`Clarabel` 这些词，通常就是在和这种规整的优化问题打交道。

这层直觉很有价值。因为你会知道项目不是在随便乱试，而是在把轨迹生成问题落到一类可求解、可复现的结构里。

#### 4.3 `cvxpy`：别把它看成“算法本身”，它更像建模语言

`cvxpy` 对新人来说最容易被误解成某种“核心创新算法”。更贴切一点的理解是：它更像是你用来描述优化问题的一套建模工具。你在里面写变量、写约束、写目标，然后调用后端求解器去解。也就是说，它更像问题表达层，不是最后真正动手算的那台机器。

一旦你理解了它更像“说清问题”的工具，而不是“就是它发明了算法”，很多读码和读日志时的紧张感会下降。

#### 4.4 Clarabel：它更像“真正负责求解的那个人”

和 `cvxpy` 对照看，`Clarabel` 更像真正负责把那个优化问题解出来的求解器。你在当前项目里看到它，重点不是背它的论文，而是知道它在链路里的职责：问题已经建好了，现在轮到它来算。这样你以后看到 `Clarabel` 日志时，就不会误以为自己进入了一个完全无关的新世界。

#### 4.5 QP：你不必现在精通缩写，但知道它在说“某类优化问题”就够了

`QP` 是 quadratic programming，也就是二次规划。对新人来说，你第一阶段并不需要背它的标准形式。知道它是在说某类有特定目标函数和约束结构的优化问题，就够了。你以后在看样条优化器时，只要知道这不是在瞎调参数，而是在解某种结构明确的问题，就已经很不错了。

#### 4.6 为什么看不懂求解器细节，不妨碍你先把主链路讲明白

这是一个很重要的心理减压点。很多同学一看到优化器细节，就觉得“完了，这个项目我暂时讲不清了”。其实不是。你完全可以先把主链路讲清楚：场景是怎么读进来的、路径怎么初始化、安全走廊怎么构出来、最后怎么通过样条优化变成轨迹。等这条线稳了，再回头慢慢补求解器的细节。顺序没错，也很正常。

### 5、数据、下载和实验室边界：这些词不花哨，但特别决定你能不能稳着干

#### 5.1 gdown：很多场景数据进入你电脑前，会先经过它

`gdown` 本质上是一个帮助你从 Google Drive 下载数据的工具。放在当前项目里，它的重要性在于：官方数据、图像目录、某些场景资源，很可能要靠它来批量拉取。你不一定非得自己手敲每次下载，但至少要知道，很多 wrapper 下载脚本其实都是在帮你更稳定地使用 `gdown`。

这个词的价值不是高深，而是现实。知道数据是怎么来的，后面你对路径和缺文件问题的敏感度就会高很多。

#### 5.2 partial：为什么有时候“先下够最小可跑资产”是合理策略

`partial` 这个词在项目执行里很有意思。它不是“敷衍做一半”，而常常是在现实资源条件下，先把最小能跑的部分准备齐。比如系统盘紧、网络不稳定、某些场景资产很大，那就可能先拉最必要的一部分，至少把最小链路走通。这种做法不是偷懒，而是一种策略。

当然，这里有边界。你要知道自己现在拿到的是 partial 资产，哪些结论可以先做，哪些结论暂时别说得太满。工程诚实也很重要。

#### 5.3 `transforms.json`、`sparse_pc.ply`、帧数门槛：下载成功不是“命令结束”，而是“结构真的完整”

当前下载和补齐脚本之所以会去检查这些文件和帧数，不是因为写脚本的人太较真，而是因为“下载命令看起来结束了”并不自动等于“场景资产足够可用”。一个目录里少了关键 JSON，或者图像少得离谱，后面照样会出问题。

你如果早一点接受这种“结构验收”思维，会比只盯退出码成熟很多。实验室里的很多事故，本质上都不是程序有多坏，而是数据准备阶段就已经不完整了。

#### 5.4 共用机器、共用资源：边界意识不是客套，是工程礼貌

这一点在当前项目里尤其需要反复说。你们共用这台工控机，师兄也有自己的账户和环境。当前所有 wrapper、环境和文档策略，本质上都在围绕一个原则：尽量把影响收敛在 howard 自己的工作区和 Conda 环境里，不碰系统级 CUDA，不碰别人的账户环境，不把系统盘再压爆。对新人来说，理解这个原则，比会多几条命令更重要。

因为这决定了你将来遇到问题时，是不是会本能地先在自己这一层找办法，而不是动不动就想“我去升个系统 CUDA 试试”。共享环境里，边界感就是职业素养。

## 七、把术语重新串回工作流与场景

前面是拆词，这一部分开始重新连词。目标不再是“我认识多少个词”，而是“这些词在真实工作里会怎样一起出现、怎样一起帮助我理解项目”。

### 1、最后，把这些词连成一个你可以带着走的故事

到这里，如果你还把这些词看成散点，那这份词典就还没真正起作用。我们最后试着把它们连成一个尽量顺的故事。你先通过 `SSH` 进入 Linux 工位机，在 `Terminal` 里通过 `Shell` 开始工作。你用 `pwd`、`cd`、`ls` 确认自己来到 `/home/howard/Splat-Nav` 这个工作区。你知道这里有 wrapper 层、有 upstream 层、有 run 目录层。你理解软链接，所以不会再被 `splatnav-official` 的双跳链吓到。

接着，你通过 `Conda` 进入 `splatnav` 环境，明白当前 `python` 和 `pip` 的上下文是什么，也知道为什么 `LD_LIBRARY_PATH` 需要小心对待。你跑环境检查，确认 `torch.cuda.is_available()` 正常。然后你拿着一个 `config.yml`，让脚本通过 `GSplatLoader` 读取某个 GSplat 场景。你知道当前主角是 `Splat-Plan`，而不是把完整系统所有模块一次性都扛起来。你知道它会先做初始化路径，再构造安全多面体，再做样条优化。你看到结果里的 `feasible`、`path`、`traj`、`num_polytopes`，不会再觉得这些都是凭空冒出来的词。

最后，你把一次任务的证据沉淀到 run 目录里，看 `stdout.log`、看 `cmd.txt`、看 JSON 和图，知道什么叫假成功，也知道什么样的结果才能拿去做汇报。这时候，这套词汇就不再是一堆分离名词，而是开始组成你自己的工作语言了。

如果你能读到这一步，说明你已经不是那个刚打开目录就头皮发麻的状态了。接下来再去看 [02_项目全景与边界_从论文到代码到数据流.md](/home/howard/Splat-Nav/docs/Codex/02_项目全景与边界_从论文到代码到数据流.md)，你会明显觉得顺很多。因为你现在已经不是在看陌生字，而是在看一张能落回现实项目的地图。

### 2、最容易混掉的词，我把它们成对摆给你看

#### 2.1 `PATH` 和 `LD_LIBRARY_PATH`：一个找程序，一个找库，别再混了

这是新人里最经典的一组混淆。因为名字都带 `PATH`，又都跟“找东西”有关，所以很多人脑子里会自动把它们混成一种东西。更轻松一点的记法是：`PATH` 更像在问“当我敲一个命令名时，去哪里找这个程序本体”；`LD_LIBRARY_PATH` 更像在问“当程序运行起来以后，去哪里找它依赖的动态库”。一个是在找主角，一个是在找配角。它们都重要，但作用层不一样。

这个区分对当前项目非常关键。因为环境排错时，你会同时遇到“python 解释器找错了”和“动态库解析错了”两类问题。如果你脑子里只有一个模糊的 `PATH` 概念，就很容易把两类问题混在一起。混在一起以后，排错就会变得特别痛苦。真正成熟的状态，不是会背定义，而是出问题时能先判断：这更像是程序入口问题，还是库入口问题。

#### 2.2 `path` 和 `traj`：都像路线，但不是同一层东西

这一组词在结果文件里经常一起出现，所以特别容易混。前面已经讲过，`path` 更像几何通路，`traj` 更像给执行侧看的平滑轨迹。这里再换个角度说一次，因为它太重要了。你可以把 `path` 想成你在地图上先画出的走法骨架，把 `traj` 想成真正能开车、能飞、能平滑经过这些位置的轨迹曲线。

为什么要这么反复强调？因为学弟以后很容易拿着 `path` 去解释执行可行性，或者拿 `traj` 去讨论初始化搜索。两者如果一直混着说，汇报会显得非常飘。只要你肯把它们分清，表达质量会立刻提升一个台阶。

#### 2.3 `scene` 和 `config.yml`：一个像标签，一个像门把手

`scene` 常常是 `old_union`、`flight`、`stonehenge` 这种名字，看起来很像“场景本体”。但实际项目里，它更像一个标签，用来帮脚本选取场景预设。真正决定读取哪套模型和相关配置的，通常还是 `config.yml`。所以这两个词的区别，不是有没有关联，而是层级不同。`scene` 帮你定位语义和预设，`config.yml` 帮你真正进入具体资产。

很多新手第一次看命令时，会下意识只盯着 `--scene`，觉得这个已经把场景说完了。其实不够。只要你脑子里建立了“scene 像标签，config 像门把手”这个图像，后面理解会轻松很多。

#### 2.4 `smoke` 和 `batch`：一个是排雷，一个是统计，不是大小版关系而已

很多人以为 batch 就是“多跑几次的 smoke”，这话只对了一半。更准确一点说，smoke 的重点在于尽快验证主链路是否能通，batch 的重点则在于形成统计意义上的比较。一个的心态更像工程排雷，一个的心态更像实验分析。你如果只把它们看成大和小的关系，会漏掉它们各自的功能定位。

这也是为什么我一直强调，学弟不能把 smoke 当正式结论，也不能直接跳过 smoke。两者都重要，但重要得不一样。

#### 2.5 `wrapper` 和 `upstream`：一个是护栏，一个是本体

这一对词会贯穿整个工作区。最容易犯的错是把它们都叫“项目代码”，然后讲半天谁也不知道你在说哪层。更顺一点的记法是：upstream 更像论文算法本体，wrapper 更像让这套本体在本机上更稳定、更好管理地跑起来的护栏层。一个解决“算法怎么做”，另一个解决“我们怎么稳当地跑和管”。

这两层都重要，但混起来就会特别乱。比如你看到 `scripts/run_overnight_12h.sh`，就应该知道这明显更偏 wrapper；你看到 `splatplan/splatplan.py`，则明显更偏 upstream。只要肯一直带着这个眼镜看项目，很多结构问题会自动变清楚。

#### 2.6 `success` 和 `feasible`：程序成功结束，不等于规划可行

这也是特别需要反复敲的一个点。程序成功结束，说的是链路有没有正常走到头；`feasible` 说的是当前规划问题有没有找到可行解。它们可能同时成立，也可能只成立其一。比如程序跑完了，但 `feasible = false`；也可能程序自己就炸了，连 `feasible` 都没正常写出来。把这两种状态分清，是新人迈向成熟非常关键的一步。

真正会读结果的人，从来不会只看“脚本有没有退出”。他会同时问：退出状态怎样，结构化结果是否完整，`feasible` 如何，图和统计是否一致。这种多看一眼的习惯，会让你少踩很多坑。

#### 2.7 `run_dir` 和 `workdir`：一个是结果落点，一个是命令执行位置

这两个词也很容易被轻忽。`run_dir` 是结果沉淀目录，用来保存当前任务的日志、命令、环境摘要和结构化产物。`workdir` 更偏执行上下文，也就是命令真正在哪个目录下运行。它们当然可能相关，但绝对不是一回事。很多任务会在某个工作目录下执行，然后把结果写到另一个 run 目录。

为什么要区分？因为你以后排错时会非常需要这层意识。你不能因为结果在 `runs/...`，就以为命令当时一定也是在那个目录里跑的。当前脚本链里，这两者往往是清楚分开的。

#### 2.8 `data`、`outputs`、`runs`：都是目录，但职责完全不同

`data` 更偏原始数据和数据解析资产，`outputs` 更偏模型训练产物，`runs` 更偏你当前工作区的实验执行证据。很多新手一看到都是目录，就会把它们笼统看成“项目文件”。这样看太粗了。真正成熟一点的看法是：这三个目录分别站在数据流的不同阶段。一个偏输入原料，一个偏中间产物，一个偏实验证据。

你把它们分开以后，后面再讲“输入、模型、实验结果”就不会老是绕在一起。

### 3、用五个真实场景，把术语串成你真的会遇到的故事

#### 3.1 场景一：学弟第一天连上机器，看着黑框发愣

这几乎是所有人都会经历的一幕。你第一次用 `SSH` 连上机器，终端一黑，提示符一出来，脑子里第一反应通常不是“我已经进入生产环境”，而是“我现在到底在哪”。这时真正有用的词，不是什么高大上的三维表示，而是 `pwd`、`ls`、绝对路径、相对路径、`hostname`。你先用这些词把自己站稳，先知道自己是不是已经到了 `/home/howard/Splat-Nav`，再谈后面的事情。

你会发现，越是第一天，这些看起来“基础得不好意思问”的词，越是决定你能不能平稳起步。只要第一步没站稳，后面所有高阶词都只能浮在空中。

#### 3.2 场景二：学弟觉得环境应该差不多好了，但程序就是 import 失败

这时跳出来的词往往是 `Conda`、`pip`、Python 解释器、`PATH`、`LD_LIBRARY_PATH`、Torch、CUDA。很多新人此时的情绪会突然变糟，觉得自己是不是天生不适合弄环境。其实你只是在第一次面对“项目环境不是系统默认空气”这件事而已。成熟一点的排法，不是乱装包，而是回到上下文：我激活了哪个环境？当前 `python` 指向哪里？是不是库解析被污染了？

只要你脑子里已经有这几个词的基本定位，排错就不会完全失控。哪怕还不能自己一步到位修好，也至少能把问题说清楚。

#### 3.3 场景三：学弟终于跑了一条命令，但不知道跑出来的是啥

这时真正重要的词会切到 `run_dir`、`stdout.log`、`cmd.txt`、`env.txt`、JSON、`feasible`、`path`、`traj`。也就是说，你的注意力开始从“程序能不能启动”转向“结果到底说了什么”。很多人走到这一步会短暂兴奋，觉得“终于有东西了”；但如果没有术语支撑，这个“东西”就仍然是黑箱。你看见 JSON，却不知道先看哪几个字段；你看见 `feasible`，却不知道它和程序是否成功结束是两回事；你看见图，却不知道它和 JSON 是否一致。

所以术语并不是读书人的乐趣，它在这里是在帮你形成结果判断能力。没有这层能力，结果再多也很难沉淀成真正的经验。

#### 3.4 场景四：学弟开始读代码，结果被 `GSplatLoader`、`SafeFlightCorridor`、`SplinePlanner` 吓住

这时你会明显感觉到，术语已经从系统层切换到了项目与算法层。好消息是，如果前面的词你已经有了基本底子，这里不会再像第一天那样全是黑的。你会知道 `GSplatLoader` 更接近“把场景读进来”，`SafeFlightCorridor` 更像某类基线方法实现，`SplinePlanner` 更像最后把轨迹平滑出来的那个环节。你未必已经会推导它们，但你已经不会完全失去方向。

这就是术语体系带来的真正价值：它不替你阅读代码，但它让你不会一上来就被名字压垮。

#### 3.5 场景五：学弟准备做周报，不知道怎么把这周做的事讲清楚

这个场景往往比前面几个更能检验术语是不是进脑子了。因为到了这一步，你不能只会识别词，还要会用词来组织叙述。比如你要说清：这周主要在 `wrapper` 层完成了环境检查与最小 smoke；输入是某个 `config.yml` 指向的 GSplat 场景；输出写进了 run 目录；当前主要问题不在 `Splat-Plan` 核心逻辑，而在环境和数据完整性；下一步准备进入小规模 batch 比较 `splatplan` 和 `sfc-*`。

你看，到了周报这一步，术语已经不再是单独存在的知识点，而是你组织思路的骨架。如果骨架稳，你讲什么都会稳很多。

### 4、最后送你一套“术语肌肉记忆”

到了这里，我不想再加更多新词了。相反，我更想帮你把已经见过的词压成一套肌肉记忆。不是那种死板背诵，而是你以后碰到项目时，脑子里能自动冒出来的几句问话。

第一句是：我现在在哪里？这句话对应的是 `SSH`、终端、路径、软链接、工作区层次。第二句是：我现在在什么环境里？这句话对应的是 Conda、Python 解释器、Torch、CUDA、`LD_LIBRARY_PATH`。第三句是：我现在跑的是哪条链路？这句话对应的是 `Splat-Plan`、`Splat-Loc`、wrapper、upstream、`config.yml`、scene。第四句是：结果到底落在哪、我该先看什么？这句话对应的是 run 目录、日志、JSON、图、`feasible`。第五句是：我现在的问题属于哪一层？这句话对应的是系统、环境、数据、脚本、算法、结果解释这几层分工。

如果你把这五句问话带走，这份词典就已经非常值了。因为它不只是帮你认识了很多词，更帮你建立了一套遇事先分层、先定位、再判断的习惯。这个习惯一旦长出来，后面你学什么都会更快、更稳，也更不容易慌。

读到这里，请你先别急着继续往下刷资料。更推荐的动作是回到 [02_项目全景与边界_从论文到代码到数据流.md](/home/howard/Splat-Nav/docs/Codex/02_项目全景与边界_从论文到代码到数据流.md)，看看你现在是不是已经能更从容地把那些路径、脚本、目录和论文主线串起来了。如果答案是“是”，那这份词典就已经开始真正发挥作用了。

## 八、协作、工具与研究表达

等你开始真正接手项目，协作、工具和研究表达会同时出现。这一部分把 Git、Cursor、Codex、ChatGPT、文件格式、汇报指标和研究型术语收在一起。

### 1、当你开始真正接手项目时，一批“协作型术语”会集中出现

前面那二十一章，更多是在帮你把系统、环境、路径、规划和结果这些词压稳。到了这里，我们要进入另一批很实际、但很多跨专业同学也会发怵的词：代码协作词汇。它们乍看没有 `GSplat`、`polytope` 那么“学术”，可如果你真的开始接手一个项目、开始跟别人协作、开始整理自己的修改、开始让师兄或导师看到你的进展，这一批词的重量一点也不低。

很多新人一开始会下意识把它们看成“程序员圈子里的黑话”。其实完全没必要。你可以把这一批词想成项目协作的基本礼仪和交通规则。懂了它们，你就知道自己今天做的改动在哪里、如何不把别人的工作弄乱、怎么把自己的进展说清楚。对当前项目这种明确有上游源码、wrapper 工作区、共享机器和后续交接目标的环境来说，这一层尤其重要。

#### 1.1 `repo`、`repository`、仓库：别把它想得太神秘

`repo` 或 `repository`，说到底就是一套被版本控制组织起来的工程目录。你完全可以把它理解成“一个有历史、有规则、有边界的项目文件夹”。它和普通文件夹的区别，不在于长得更花哨，而在于它通常带着 `.git/`，能记录修改历史、分支关系和提交状态。

为什么这个词你必须尽早适应？因为你以后听到“官方仓库”“本地工作区仓库”“上游仓库”“第三方仓库”时，如果脑子里没有一个稳定概念，就会总以为大家在说完全不同的抽象东西。其实他们很多时候只是在区分不同层次、不同来源、不同责任边界的工程目录。

在当前项目里，`/home/howard/Splat-Nav` 是你现在最常接触的 wrapper 工作区仓库，而 `splatnav-official` 最终指向的是上游官方仓库。把这两个都叫 repo 没问题，但你必须知道它们不是同一层。

#### 1.2 `commit`：一次提交不是“我改完了”，而是“我留下一块可回看的历史”

很多新手一听 `commit`，第一反应就是“提交代码”。这当然没错，但还不够。更好的理解是：一次 commit 是你把当前一组相对完整、相对可解释的修改，压成一个可回看、可比较、可恢复的历史节点。它不只是技术动作，也是表达动作。你在说：我在这个时间点，对项目做了这一组事情。

为什么这个词对学弟重要？因为一旦你开始真正整理项目，就会发现“我改了很多东西”和“我留下了一组可理解的历史”完全不是一回事。前者很混乱，后者才有工程价值。哪怕你现在还不急着正式提交代码，先把 `commit` 理解成“项目历史上的清晰刻度”，对以后也非常有帮助。

#### 1.3 `branch`：它像平行工作线，不是另一个宇宙

`branch` 常被翻译成分支。很多人一听分支，就想象成项目被切成完全不同的几个世界。其实更好的理解是：它像一条并行工作线。主线继续往前走的时候，你也可以在另一条线上实验、开发、整理、对照，不必把所有试验都直接砸在主线上。

当前上游 README 就提到了 `ros` 分支和 `semantics` 分支。这其实特别值得学弟理解。因为它说明同一个仓库可以因为任务目标不同，在不同分支上承载不同形态的实现。你以后一看到分支名，就要习惯先问：这个分支是为了什么任务，它和当前主线是什么关系。

#### 1.4 `fetch`、`pull`、`push`：这些词为什么听起来像搬运，但实际上是在同步历史

这三个词是很多新人最容易混的。你可以先用最朴素的方式记：`fetch` 更像把远端的新信息拿到本地，但先不自动并入当前工作线；`pull` 更像获取远端更新并尝试并入本地当前分支；`push` 则是把你本地已有的提交送到远端。它们表面像在搬东西，实际上是在同步项目历史。

对当前项目来说，你暂时未必每天都要执行这些动作，但你非常有必要把概念分清。因为一旦以后你要同步上游、保护自己的修改、和别人对齐版本，这几个词会很频繁地出现。概念一清楚，胆子就不会那么慌。

#### 1.5 `diff`：它像“改动体检报告”，能告诉你到底变了什么

很多同学一开始写代码时，最容易陷入一种模糊感：我改了不少，可到底改了哪些地方、哪一行变了、是不是把别的东西也带坏了，不太说得清。`diff` 的价值就在这里。你可以把它理解成“改动体检报告”。它不是告诉你项目是什么，而是告诉你“和之前比，现在哪里不一样了”。

这个词特别值得学弟早一点习惯。因为真正成熟的协作，不是只会改，还得会检查自己到底改了什么。你以后越早形成“每做一轮修改，就看看 diff”的习惯，越不容易写着写着把自己也绕糊。

#### 1.6 `README`：不是每份 README 都是教材，但每份 README 都在回答“怎么从门口进来”

前面我们在项目全景里已经讲过 README 的角色，这里换个术语视角再说一遍。`README` 的本质，不是“所有知识都写在这里”，而是“后来的人第一次打开仓库时，至少不至于完全没有门”。所以你读 README 时，重点不应该是期待它把所有问题都讲透，而是先抓它回答了哪几个门口问题：这个仓库干什么、怎么开始、依赖是什么、路径大概怎样、典型命令从哪进。

你以后自己写项目，也最好逐渐形成这个意识。README 的职责不是替代整套文档，而是做项目门口的第一块说明牌。

### 2、Cursor、Codex、ChatGPT、SSH 这些“新工具词”，别让它们把你吓住

对于机械转代码的学弟来说，现代工具链往往比算法词更容易造成心理压力。因为这些工具的界面变化快、视频很多、说法又杂，很容易让人觉得“我是不是先要把所有工具研究明白，才能开始项目”。其实完全不用。更好的节奏是：把这些工具词一个个压成很朴素的用途理解。只要用途理解稳了，具体按钮长什么样、界面怎么变，都不会太影响你。

#### 2.1 `Cursor`：先把它当成“带远程开发能力的代码编辑器”

你如果第一次接触 Cursor，最容易被网上各种标题带偏，好像它是一个“必须先学明白一大堆 AI 工作流”的平台。其实对当前项目更朴素、也更够用的理解是：它首先是一款代码编辑器，而且能比较方便地配合 SSH 打开远程机器上的项目目录。你真正需要它做的第一件事，是稳定连上这台工控机，看到 `/home/howard/Splat-Nav` 里的文件，然后能比较舒服地读文档、读代码、改脚本。

所以你完全不用一开始就给自己加压，觉得必须把 Cursor 所有插件和面板全学明白。先把它作为“远程看代码和改文件的窗口”用稳，就已经很不错了。

#### 2.2 `SSH` 在 Cursor 里再次出现时，不是新概念，只是新入口

很多新手会在这里多绕一层：命令行里学过一次 SSH，到了 Cursor 里看到 Remote SSH，又觉得自己得重新学一遍。其实不需要。概念还是同一个概念，只是入口换了。命令行 SSH 是你手打命令连远端，Cursor 里的 SSH 是编辑器帮你把连接过程做得更图形化、更适合直接打开远程目录。

所以你完全可以把它们看成“同一条路的两个门”。底层关系没变，你还是要知道自己连的是哪台机器、用的是哪个账户、路径是不是远端路径。

#### 2.3 `Codex`：把它先理解成“能帮你读、写、改、查的协作型代理”

对于第一次接触 Codex 的学弟来说，最容易发生的事就是把它想得又神又玄。其实一个更稳的理解是：它像一个比较能干的协作型代理，可以帮你读代码、解释脚本、补文档、修改文件、跑命令，但前提是你给它足够清楚的上下文和任务边界。它不是神灯，也不是你可以完全不理解项目就放心交出去的黑盒。

你以后越早形成一个习惯越好：把 Codex 当成搭档，而不是当成替你承担全部理解责任的外包工。这样你会问出更好的问题，也更容易从它的回答里真正学到东西。

#### 2.4 `ChatGPT`：别把它当搜索引擎，也别把它当老师傅的替身

很多新人一开始用 ChatGPT，容易走两个极端。一个极端是把它当搜索引擎，什么都问一句，得到零碎答案，结果脑子更乱。另一个极端是把它当老师傅，自己完全不判断，只盼它一步到位告诉自己“应该怎么做”。这两种用法都不太理想。

更成熟的用法是：当你已经有一部分上下文，知道自己卡在什么层，比如环境、路径、脚本链、术语解释、代码阅读顺序，这时再去问，它的帮助会很大。也就是说，你越能明确上下文和目标，它越能真的帮到你。

#### 2.5 `prompt`：提示词不是咒语，它更像任务描述

很多关于 AI 工具的内容会把 `prompt` 讲得很玄，好像你必须掌握一套秘密咒语才能让模型工作。其实对当前项目来说，更好的理解是：`prompt` 本质上就是任务描述。你把上下文、目标、边界、输入路径、希望产出的形式讲得越清楚，对方越容易帮到你。

所以以后如果你要让工具帮你读某个脚本，不如直接说清：文件在哪、你现在看到哪一层、你不懂的是输入输出还是调用链、你希望它用大白话还是带代码引用来讲。你会发现，这比追求所谓“高级提示词技巧”更有用。

#### 2.6 `context`：上下文不够，工具再强也容易答偏

`context` 这个词你以后会听很多次。可以先把它理解成“为了让对方不乱猜，必须先提供的背景信息”。对当前项目来说，上下文至少可能包含：你现在是在 `/home/howard/Splat-Nav` 这个 wrapper 工作区里，真正上游源码入口在 `splatnav-official/`，当前目标是离线/仿真复现，不碰实车，机器是共享工控机，不能乱动系统 CUDA。

你只要把这种习惯养起来，以后无论问人还是问工具，都会更高效。因为真正让沟通失控的，往往不是对方不够聪明，而是你默认了很多背景对方其实并不知道。

### 3、YAML、JSON、Markdown、CSV、日志：这些文件格式看着普通，却是项目语言的一部分

很多跨专业同学会下意识觉得，文件格式只是琐碎细节，不值得花脑力去理解。可一旦你真在项目里待上几天，就会发现这些格式简直无处不在。你打开的是 Markdown，传进去的是 YAML，跑出来的是 JSON，汇总后变成 CSV，排错时盯的是日志。如果这批词你一直停留在“听过”的层面，阅读和排错成本会一直很高。

#### 3.1 `YAML`：先把它当成“更适合写配置的人类可读文本”

`YAML` 最大的特点，不是它语法多高级，而是它很适合承载层次化配置。当前项目里最典型的就是 `config.yml`。你打开它时，会看到键值、层次和路径关系。这种文件的重点，不在于你要手写出一整份复杂 YAML，而在于你至少要能看懂：这里在描述什么，哪一层像模型配置，哪一层像数据解析入口，哪一层像训练产物引用。

你可以先把 YAML 理解成“适合人读的配置语言”。这个理解对入门已经够用了。

#### 3.2 `JSON`：它更像“结构化结果记录本”

和 YAML 相比，JSON 在当前项目里更常出现在结果侧。比如 smoke 输出的 JSON、batch 结果的 JSON。它通常把信息组织成键值对、列表和嵌套对象，适合程序保存和后续脚本读取。你以后要培养一个特别实用的能力：看到 JSON 时，不要慌着从第一行读到最后一行，而是先找顶层键，再判断哪部分是 `meta`，哪部分是实验结果，哪部分是 trial 记录。

这种“先看结构”的习惯，会让你读 JSON 的速度快很多。

#### 3.3 `Markdown`：它不是装饰性文本，而是工程里最常见的说明格式

`Markdown` 之所以在工程里这么常见，就是因为它比纯文本更有结构感，又比复杂文档格式更轻。README、手册、总结、汇总摘要、notes 都很爱用它。对学弟来说，Markdown 最重要的不是会不会写炫格式，而是你能不能用它把一件事讲清楚。标题、段落、列表、代码块，这几样基本元素已经足够你写出非常有用的项目说明。

你现在看到的这些 `docs/Codex` 文档，本质上就在示范这件事：Markdown 完全可以承载很重的项目知识，只要结构和叙述安排得合理。

#### 3.4 `CSV`：它像“表格化结果的最朴素通用格式”

当你开始跨 run 汇总实验时，CSV 会变得很有价值。它不像 JSON 那样层次丰富，但非常适合存一张规整表，便于脚本处理、便于表格软件打开、也便于快速做后续分析。比如一行是一种方法在某轮 batch 的摘要，列里放可行率、平均耗时、P95、来源文件等信息，这就很适合 CSV。

你以后一看到 CSV，不要觉得它“没什么技术含量”。在结果管理层，它往往非常实用。

#### 3.5 `stdout` 和 `stderr`：终端里出来的字，其实也有分工

很多新人第一次排错时，会把终端里所有输出都看成“一堆字”。其实更稳的理解是：标准输出 `stdout` 往往承载正常运行过程中的信息，标准错误 `stderr` 更常承载报错或警告。现实里这两者当然可能混着看，但一旦你知道它们的概念，像 `|& tee stdout.log` 这样的写法就不再神秘了。

你会明白，这类写法是在认真地把正常输出和错误输出都一起落盘，为以后复盘留证据。

#### 3.6 `log`、日志：日志不是废话，而是程序留下的行为轨迹

`log` 这个词以后你会看得越来越顺眼。因为你会慢慢意识到，日志不是程序多嘴，而是程序留下的行为轨迹。它告诉你什么时候进入哪一步、读了什么、检查了什么、报了什么异常、最后停在了哪里。尤其在远程和长任务场景里，日志几乎就是你事后唯一能完整回看任务过程的材料。

所以以后别嫌日志烦。学会读日志，本身就是做项目的重要能力。

### 4、实验指标和汇报词汇：你以后做周报时最容易用到的一批词

到了项目中期，很多词的价值会从“帮助你读代码”转向“帮助你讲结果”。也就是说，你不只是自己看懂了，还得开始会汇报、会比较、会总结。这一批词看起来不如算法词高深，但在实际工作里使用频率极高。

#### 4.1 `trial`：它更像“一次试验单元”，不是“程序开了一次”

在 batch 实验里，`trial` 往往对应一次起终点对上的单次规划尝试。它和“脚本启动一次”不是同一层。一个 batch 脚本启动一次，里面可能跑几十次、上百次 trial。把这个词分清很重要，因为你以后讲“这次实验跑了多少”时，必须说清你指的是脚本级、run 级，还是 trial 级。

这点看似细，但在汇报里特别影响清晰度。

#### 4.2 `seed`：随机种子不是玄学，它是在帮你减少“每次都不一样”的混乱

很多新人会把 `seed` 看成一个神秘数字。其实你可以先把它理解成：它是让带随机性的过程尽量可重复的钥匙。在当前 batch 脚本里，`seed` 会影响起终点顺序打乱等行为。你以后做对比实验时，如果想让不同运行之间更可比，这个词就会很重要。

它的意义不在于让世界完全 deterministic，而在于减少没必要的漂移。

#### 4.3 `feasible` 和 `feasible_rate`：一个看单次，一个看整体

`feasible` 是单次规划有没有找到可行解，`feasible_rate` 则是多次 trial 里可行比例有多高。你一定要把这两个词区分清。因为很多新人第一次汇报时，特别容易拿一两次成功例子去替代整体统计。这样很不稳。真正成熟的说法通常会是：单次案例看上去不错，但整体 `feasible_rate` 还需要结合更多 trial 判断。

一旦你开始这样讲话，别人就会明显感觉你对实验的理解更像做项目的人，而不是只会展示一个漂亮案例的人。

#### 4.4 `avg_plan_time`、`p95_plan_time`：为什么“平均快”不等于“整体稳”

平均规划时间好懂，可它不够。因为平均值可能掩盖少量特别慢的尾部情况。`p95` 的价值就在这里，它更像在问：绝大多数情况下，规划时间大概卡在什么水平以下。你可以先不追求特别精确的统计学直觉，但至少要知道，`avg` 和 `p95` 讲的是两个不同侧面：一个偏整体中心，一个偏尾部稳不稳。

所以以后如果你看到一个方法平均时间还不错，但 `p95` 很难看，就要有感觉：它也许不够稳定。

#### 4.5 `summary`、`report`、`overview`：都是总结，但力度不同

很多汇报词看起来像近义词，其实语气和用途是不同的。`summary` 更像摘要，压缩关键信息；`report` 更像完整汇报，有背景、有过程、有结果、有结论；`overview` 更像总览，先把大图给人看清。你以后写文档和周报时，越早对这些词有点感觉，表达会越自然。

当前工作区里 `summary.md`、`overnight_summary.md` 这类文件名，也正是在用这些词提醒你：这是一层偏快速消费的内容，不是完整长篇叙事。

#### 4.6 `visualization`：可视化不是美化，它是在压缩理解成本

很多新人一提可视化，脑子里会先想到“让图更好看”。其实更重要的意义是压缩理解成本。比如同样的批跑结果，可行率柱状图能让你一眼看出方法排序，时间箱线图能让你直观看到分布，轨迹叠图能让你感受到几何差异。这些都不是“锦上添花”，而是在帮助你更快理解实验。

所以以后千万别把可视化看成最后有空再做的装饰工作。它本身就是结果理解的一部分。

### 5、共享机器、谨慎操作、边界意识：这是你做项目时最像“职业习惯”的一批词

最后这一章，我想把一些非常“现实”的词再压一遍。它们不浪漫，也不学术，但它们决定你在共享机器上做项目是不是让人放心。对机械转代码的学弟来说，这一章尤其值得带着一点敬畏去读。因为很多事故不是不会算法，而是基本边界感不够。

#### 5.1 `sudo`：它不是“帮你解决问题的万能钥匙”

很多新人一遇到权限问题，第一反应就是要不要 `sudo`。这是非常危险的直觉。更稳的做法永远是先问：我为什么会碰到这个问题，这个位置是不是本来就不该由我来改，当前问题能不能在自己的 Conda 环境或工作区边界内解决。`sudo` 真正代表的，是更高权限，而更高权限从来不是默认应该用的。

对当前项目来说，这一点尤为重要。因为你们明确说了，这台机器是共享的，不能乱动系统层和别人环境。那就意味着，`sudo` 在这里几乎天然属于需要停下来重新判断的词。

#### 5.2 `rm`：删除不是最可怕的，可怕的是你不知道自己删的是哪一层

前面我们已经讲过 `rm`，这里再从协作角度补一句。真正让人害怕的，从来不是删除这个动作本身，而是你对删除对象没有层次感。删的是自己的 run 缓存，还是共享结果目录？删的是 wrapper 草稿，还是上游关键资产入口？删的是软链接本身，还是它背后的真实目录？

只要这三四个问题你没想清，`rm` 就不该轻易敲。共享机器上尤其如此。

#### 5.3 `shared machine`：共享机器不是一句背景，而是一整套行为约束

很多同学会把“这是共享机器”理解成一句背景说明。其实它更像一整套行为约束：不要乱动系统层；不要默认别人没在用某些目录；不要为了自己方便就升级全局组件；重资产尽量往约定的数据盘走；日志和结果尽量规范落盘；排错优先在自己的边界里解决。你以后越早把这些约束内化，越像一个让人放心的合作者。

真正成熟的人，不是技术多炫，而是别人愿意把机器和项目交给他而不担心。

#### 5.4 `environment pollution`：环境污染听起来抽象，其实就是“你改了不该全局改的东西”

这个词在很多工程里都会出现。可以先把它理解成：你为了局部任务，改动了全局环境，导致别的任务或别的人也受到影响。比如乱动系统 CUDA、全局 pip 安装、把奇怪路径塞进全局环境变量、覆盖掉共享依赖。对当前项目，这显然都是要尽量避免的。

你以后每次排错时，心里不妨多问一句：我现在这个修法，是只影响我自己的小环境，还是会把整台机器都拖下水？这个问题非常值钱。

#### 5.5 `ownership`：负责感不是“我全都懂”，而是“我知道自己该守住什么边界”

做项目时，`ownership` 常被翻译成拥有感、责任感。很多人会把它理解成“我是不是得什么都扛”。其实更成熟的理解是：我知道自己当前负责的是哪一层、哪组文件、哪段逻辑、哪类结果，也知道哪些不是我该随便碰的。真正的负责，不是越界，而是在边界内把事情做扎实。

这对学弟特别重要。因为入门阶段最怕两种极端：一种是什么都不敢碰，另一种是什么都想碰。真正能持续推进的人，往往是在这两者之间找到清楚边界的人。

#### 5.6 这一章读完以后，你至少应该多出一种稳感

如果前面的术语更多是在帮你建立知识地图，那么这一章其实是在帮你建立项目气质。一个人是不是适合长期做工程，很多时候不体现在他说了多少大词，而体现在他对边界、风险、共享资源和结果规范有没有稳感。你现在未必要一下子全做到，但至少应该开始有一种判断力：哪些动作该快，哪些动作该慢，哪些地方该自己试，哪些地方该先停一下问清楚。

只要这种稳感开始长出来，你后面无论是读 `02` 这种全景文档，还是实际跑脚本、改代码、做汇报，都会越来越像一个真正进入状态的人。

### 6、当你开始从“复现”走向“汇报、专利、论文”时，会遇到的一批研究型术语

如果说前面的章节更多是在帮你把项目跑起来、看明白、讲顺，那么这一章开始，我们要面对另一批词。它们通常会在组会、导师交流、专利构思、论文阅读和阶段总结里频繁出现。很多新人到了这一步会突然又紧张起来，觉得自己是不是从“不会代码”升级到了“不会科研表达”。其实不用把这件事想得太玄。更好的理解是：这些词就是研究工作中的常用语言，你早点把它们压成大白话，后面会轻松很多。

#### 6.1 `paper`、论文：别先把它当圣经，先把它当“作者交代自己做了什么、为什么值”的正式说明书

很多跨专业同学一提论文，心理压力会瞬间变大，好像那是某种只有专家才能进入的神圣文本。其实对于项目入门阶段，更合适的理解是：论文首先是一份正式说明书，它在系统地回答作者做了什么、为什么这么做、和谁比、结果怎样、贡献在哪里。它当然有学术语言，但你完全没必要一开始就把它当成一道考试。

对当前项目来说，论文最重要的价值，是帮你确认这套系统的总主线和方法定位。你不用第一次就把每个公式都吃透，但至少要知道总系统是 `Splat-Plan + Splat-Loc`，知道作者为什么要强调 GSplat 表示，知道他们和哪些基线比较，知道他们主打的是安全、实时和视觉定位。

#### 6.2 `arXiv`：先把它当成“论文公开草稿或公开版本的入口”

`arXiv` 对新手来说往往听起来很高大上，其实它最朴素的作用，就是给你一个论文公开版本的入口。你完全可以把它理解成“论文页面和 PDF 的稳定入口”。对当前项目来说，`https://arxiv.org/abs/2403.02751` 就是 Splat-Nav 论文的公开页面。

为什么这个词值得学？因为以后你做项目时，别人让你“先看看论文”，很多时候说的就是先去 arXiv 页面和 PDF 看总结构，而不是必须立刻去查期刊版本、会议最终版的所有差异。

#### 6.3 `project page`：项目页通常是“论文的更友好导览版”

和论文相比，`project page` 往往更像导览版。它通常会放摘要、方法图、视频、关键结果图和常用链接。对新人来说，项目页非常适合做第一眼总览，因为它的信息密度高，但阅读压力比论文正文低。当前项目页就很适合作为你理解 Splat-Nav 总系统和演示效果的入口。

所以以后只要看到项目页，不要觉得它只是宣传页面。对入门者来说，它常常是最好懂的总览材料之一。

#### 6.4 `baseline`：基线不是“随便找个差的方法来衬托自己”

很多新人第一次听 `baseline`，会误以为那只是论文拿来陪跑的角色。实际上，一个严肃的 baseline 往往代表一条合理、公开、在相关任务上有一定代表性的对比路线。对当前项目来说，`SafeFlightCorridor` 不同变体、RRT、NeRF 导航方法都在扮演不同类型的 baseline 角色。

你以后做汇报时，如果把 baseline 讲得太轻，会显得对实验设计理解不够。更成熟的讲法应该是：baseline 是为了让别人判断你的方法到底比什么更好、好在什么维度、是否值得采用。

#### 6.5 `ablation`：消融不是“删着玩”，而是为了回答“到底哪部分在起作用”

`ablation` 也就是消融实验。很多新人一听这个词，会觉得是不是把模型某块删掉试试看。这个理解只对了一半。更完整一点的说法是：消融实验是为了隔离不同设计因素，看看系统表现到底由哪些部分支撑。如果少了一块，性能怎样；换一种初始化，结果怎样；安全缓冲变了，轨迹和可行率怎样。

对当前项目来说，`sfc-1` 到 `sfc-4` 这种 mode 差异，其实就很适合被理解成某种结构化变体比较思路。学弟如果以后想做创新，一定会反复碰到这个词。

#### 6.6 `novelty`、创新点：不是“必须从零发明世界上没有的东西”

很多新人一提创新，就会立刻进入一种非常重的心理状态，仿佛创新必须是完全颠覆性的发明。其实对研究训练阶段更务实的理解是：创新点通常是在已有方法链上，提出一个有根据的新观察、新组合、新约束方式、新系统连接或新的实验验证角度。它不一定要从无到有造一个宇宙。

所以你以后带学弟思考创新时，也尽量别一开始就问“你有什么全新大招”。更现实的问法是：当前链路哪里最痛，哪层最薄，哪种对比不够充分，哪个工程边界如果整理好了会自然形成方法贡献。这样会更容易长出真正靠谱的想法。

#### 6.7 `patent`、专利：它更像“把一个有实用价值的技术方案说清并保护起来”

很多学生第一次听到专利，会误以为那就是“把论文换种格式写一遍”。其实不太一样。专利更强调技术方案、适用场景、系统流程和可实施性。它关心的是你这个方案到底解决了什么问题，流程是什么，模块怎么配合，和已有方案相比有什么实际价值。

对当前项目来说，如果后面要写专利，第一阶段最关键的准备工作不是急着造词，而是把系统链路、输入输出、关键环节和可以主张的改进点真正讲清楚。没有这个底子，专利写作会非常空。

#### 6.8 `contribution`：贡献不是“我做了很多事”，而是“我做了哪些值得别人记住的事”

这是一个特别值得学弟反复体会的词。很多人写汇报时喜欢说“我这周做了很多工作”，但这不等于 contribution。更成熟的说法是：我完成了哪几件真正改变项目状态的事，比如把离线链路跑通了、把结果归档规范固定了、把某个难点解释清楚了、做出一组可信对比、把某个模块工程化整理到了可交接状态。

所以以后无论写周报还是想论文贡献点，都最好少说泛泛的“做了很多”，多说“项目状态因此具体发生了什么改变”。

#### 6.9 `reproduction`、`replication`、复现：重点不在字面差别，而在“别人能不能跟着你走到相同结果”

在学术讨论里，这两个词有时会有更细的区分，但对当前项目入门阶段，你完全可以先把它们放在一起理解：核心关注点都是别人能不能根据公开材料和你的整理路径，走到相近的结果。也就是说，复现不只是“我这台机器上偶然跑通”，而是“方法、路径、输入、输出和结果解释足够清楚，后来者也能跟上”。

这也是为什么你现在花这么大力气整理 `docs/Codex` 是值得的。因为文档和工程规范本身，就是复现质量的一部分。

#### 6.10 `benchmark`：基准不是名词摆设，而是你判断结果有没有位置的参照系

很多新人第一次出结果会非常开心，这是好事。但再往前走一步，你就必须学会问：这个结果放在什么基准上看才有意义。`benchmark` 更像一个参照系，告诉你这个任务、这个场景、这个指标通常是怎样比较的。没有 benchmark，你的结果就容易悬空，看着不错，但不知道到底站在什么位置。

对当前项目来说，论文已有的场景、基线和指标体系，本身就构成了一个很重要的 benchmark 语境。

#### 6.11 `robustness`、鲁棒性：不是“偶尔成功”，而是“换些扰动还基本站得住”

很多同学初学时更容易关注“能不能成功一次”。真正做研究往前走时，`robustness` 会越来越重要。它关心的是：场景换一点、参数抖一点、输入条件变一点、任务多跑几次，系统表现是不是还大体稳定。这个词和 `feasible_rate`、`p95` 这些统计词其实很有缘分，因为它们都在帮助你从“单例漂亮”走向“整体可靠”。

以后你只要听到导师说“这个结果还不够 robust”，通常不是在否定你，而是在提醒你别太早把单次成功当结论。

#### 6.12 `regression`：回归不总是统计课里的回归，它也常指“本来好的东西被你改坏了”

这是一个很容易误会的词。在机器学习或统计语境里，regression 可能指回归任务；但在工程语境里，它还常常表示“功能退化”或“行为回退”。比如你改了一段脚本，本来能跑的 smoke 现在不跑了，这就可能叫 regression。对学弟来说，早点知道这个双重含义很重要，不然以后听到别人说“这次改动引入了 regression”，你可能会一头雾水。

## 九、收束与使用方法回归

最后这部分不再继续铺新名词，而是帮助你把整份词典真正变成工作中的陪跑工具。它关注的是使用姿势，而不是继续增加记忆负担。

### 1、这一份词典最好的使用方式，不是从头背到尾，而是跟着项目回查

写到这里，我其实特别想再提醒你一次：这份词典不是拿来背诵通关的。你越把它当成陪跑工具，越会用得顺。比如你今天在 `02` 里读到 `GSplatLoader`、`run_dir`、`config.yml`、`baseline`，就回来看；明天 batch 跑起来，碰到 `trial`、`seed`、`feasible_rate`、`p95`，再回来看；下周开始想专利、想创新点，碰到 `contribution`、`novelty`、`ablation`，再回来看。

这种回查式学习其实很健康。因为项目里的很多词，本来就不是一次看懂、一次记住就结束的。你会发现，同一个词在第一周、第二周、一个月后读起来，味道都不一样。第一次你只是知道它大概什么意思，第二次你开始知道它在项目里出现在哪，第三次你才会真正知道它对推进工作意味着什么。

如果你能接受这种节奏，这份 `01` 就会越来越像一本真的“工作中的词典”，而不是一次性资料。那它的价值就算真正出来了。

### 2、最后送你一个“查词三层法”：以后遇到新词，不要只问“它是什么意思”

这份词典写到最后，我还想再送你一个很实用的小方法。因为项目不可能永远只出现我们已经写进来的这些词。以后一定还会有新词冒出来，尤其是当你开始看更多论文、更多分支、更多脚本时。如果每次遇到新词，你都只问“它是什么意思”，理解常常会停在很浅的层面。更好的做法，是用一个三层法去问它。

第一层，当然还是“它是什么意思”。也就是最基本的大白话解释。这一层解决的是陌生感，让你不至于看到词就发怵。第二层，要追问“它在当前项目里出现在哪儿”。也就是它会不会出现在某个脚本名、某个日志字段、某个结果目录、某个上游文件或某个报错里。第三层，最重要，要问“如果我现在不懂它，接下来会卡在哪一步”。这一步会让你一下子知道，这个词对你来说到底是眼下必须掌握的，还是先知道名字就够。

你会发现，一旦这么问，词就不再是孤零零的字典条目，而会变成真正有位置、有后果、有行动意义的东西。比如你今天遇到 `dataparser_transforms.json`，第一层是知道它和数据解析变换有关；第二层是知道它常和 Nerfstudio 输出、`config.yml` 背后的训练产物联系在一起；第三层则会提醒你，如果这层不懂，你后面很难真正讲清场景入口链。再比如你遇到 `p95_plan_time`，第一层是知道它表示尾部时延表现；第二层是知道它会出现在 batch 汇总和图表里；第三层则是在提醒你，如果忽略它，你很可能会把“平均值看着不错”误讲成“整体都很稳”。

所以以后你完全可以把这套三层法当成自己的默认查词姿势。先问意思，再问位置，再问后果。只要这个习惯长出来，即便未来再冒出很多新术语，你也不会像最开始那样容易被压住。因为你已经知道，词不是用来吓人的，而是用来帮助你在项目里继续往前走的。

### 3、把前面这些术语真正串成一天工作，而不是一堆孤立名词

如果一份词典写到最后，读者脑子里还是只有很多零散词条，那这份词典其实还没有真正完成任务。因为真实的项目推进，从来不是一个个术语排队出现的，它更像是一整天的工作被很多词共同支撑起来。你早上接入机器，上午确认环境，中午开始读脚本，下午跑 smoke，傍晚看结果，晚上写一段简短汇报。在这个过程中，你不会先单独遇到 `SSH`，然后把它放一边；再单独遇到 `Conda`，又放一边；再单独遇到 `feasible_rate`，又放一边。它们是混在一起、互相咬合着出现的。

所以这一章，我们不再按“词条目录”的方式往前推，而是换一种更像真实工作日的讲法。你可以把它当成一条从早到晚的轻量工作流，也可以把它当成一个小型复盘。目的只有一个：让你感觉前面那些看似分散的术语，开始慢慢长成一张网，而不是继续一颗一颗漂在水面上。

#### 3.1 早上第一件事，不是着急跑命令，而是先确认你现在到底连到了哪里

很多新手一坐下，最容易出现的状态就是“赶紧做点什么”，结果一着急，命令是敲了，事情却并没有真正开始。更稳的做法，其实是先用两分钟做定位。你通过 `SSH` 连上机器，打开 `Terminal`，进入当前用户的 `Shell`，然后先看 `hostname`、`pwd`、`whoami`。这几个动作看起来很朴素，但它们会直接帮你回答三个问题：我现在在哪台机器上，我当前站在什么目录里，我现在是谁的账户。

这一步为什么值得反复强调？因为你正在用的是公用工控机，而且你已经非常明确地说过，不要碰你师兄的环境，不要乱动 CUDA，不要把公共机器搞脏。这些要求并不是“附加提醒”，而是项目边界的一部分。也就是说，`SSH`、`hostname`、`pwd`、用户目录、绝对路径这些看起来像系统基础的词，在当前项目里并不只是“基础知识”，它们直接关系到你能不能安全地开始工作。

当你意识到这一点之后，很多动作会自然变稳。你不会再一上来就把任何路径都当成“自己当然知道”；你也不会轻易把 `/home/howard/Splat-Nav` 和 `/data/howard/...` 混起来。术语一旦和风险绑定，它就不再抽象。

#### 3.2 早上的第二件事，是确认你今天说话的“Python 方言”到底是哪一个环境

你可以把 `Conda` 环境想成“今天工作时我们约定使用哪一套 Python 世界”。项目是不是能正常 import 某个包，`torch` 能不能认出 CUDA，脚本里依赖能不能对得上，很多时候都不是代码逻辑先出问题，而是你说话的这套环境根本没切对。

所以在真实工作里，`Conda`、`python`、`pip`、环境变量、`LD_LIBRARY_PATH`、`which python` 这些词，往往是一串出现的。你如果把它们拆开背，会觉得琐碎；可一旦放到“今天我要不要开始跑任务”这个动作前面，它们就会变得非常有秩序。你会知道：现在我不是在抽象地学环境管理，我是在确认自己到底有没有资格往下运行。

这也是为什么很多老练的人，每次开始之前都会先做一个很轻的小检查。不是因为他们记性不好，而是因为他们知道，环境类问题的本质并不在于“你是不是记住了上次怎么配”，而在于“你有没有在今天、在此刻、在这个终端里重新确认”。这其实是一种工程习惯，而不只是知识点。

#### 3.3 当你打开工作区时，目录就不再只是文件夹，而是项目结构本身在说话

接下来你会进入 `/home/howard/Splat-Nav`。这时候，`README.md`、`docs/`、`scripts/`、`runs/`、`splatnav-official/`、`third_party/` 这些名字就会一起冒出来。很多新手在这一刻会觉得乱，原因并不是目录太多，而是心里还没有“目录会说话”的意识。其实目录从来不是中性的。一个项目把什么放在顶层、什么拆进子目录、什么专门留出 `docs` 和 `runs`，本身就在告诉你：这里在重视什么，这里的工作流大概怎么走。

比如你看到 `scripts/`，不要立刻想“这里全是代码”。更好的第一反应是：这里很可能是把常见动作脚本化的地方。你看到 `runs/`，也不要只把它当输出垃圾桶，而要意识到这是项目为了留存证据专门安排的空间。你看到 `docs/`，更不应该只把它当“以后有空再看”的资料区，而要知道，这里其实是在补算法代码天然不擅长表达的那一层解释。

一旦你这样看目录，项目就开始从“很多文件夹”变成“很多有分工的房间”。这时，`path` 这个词也不再是单纯的斜杠字符串，而会慢慢带上结构含义。

#### 3.4 中午开始读脚本时，文件名、入口函数和参数，三者要一起看

等你真正开始往 `scripts/` 或 `splatnav-official/` 里看，术语又会换一批出现。你会看到 `argparse`、入口脚本、参数、`sys.path`、配置文件、输出目录、日志重定向、JSON 汇总、可视化脚本。这个阶段特别容易犯的错，是只盯着代码正文看，却不先看“这份脚本到底是谁触发的、收什么输入、把结果放哪里”。

对新人来说，更稳的姿势其实是三件事一起看。第一，看文件名，因为文件名经常已经在提示这份脚本负责哪个动作。第二，看入口，因为入口能帮你知道它是被人直接运行，还是被其他脚本间接调用。第三，看参数，因为参数会直接告诉你作者认为“可变”的东西是什么。很多时候，一份脚本的核心意图，不在几十行实现细节里，而在入口和参数层面已经说得七七八八了。

所以以后你看到 `smoke_splatplan.py`、`run_official_style_batch.py`、`aggregate_batch_runs.py` 这类名字时，第一反应不要是“我要先把代码每行都看懂”，而应该是“它分别处在工作流哪一段、吃进去什么、吐出来什么”。这是读脚本时非常省力的思路。

#### 3.5 下午真正开始跑 smoke 时，你第一次会感觉很多词突然活了

到了运行阶段，前面看起来有点散的术语会开始集体落地。你会遇到 `tmux`、`stdout.log`、`run_dir`、时间戳、主题后缀、`feasible`、规划耗时、统计 JSON、图表文件。这个时刻特别宝贵，因为很多词第一次从“我大概知道它是啥”变成“我亲眼看见它出现在自己的结果里”。

比如你以前知道 `tmux` 是长任务会话工具，但只要你亲手把任务放进 tmux，它就不再只是一个工具名，而会变成“我离开终端以后任务还能继续跑”的安全感。你以前知道 `stdout.log` 是日志文件，但只要你真的在里面追过一次错误，它就不再是平淡的名词，而会变成“事情到底发生了什么”的证词。你以前知道 `feasible` 大概和可行性有关，但只要你真的在 batch 汇总里看到不同方法、不同迭代的 feasible rate，它就不再只是概念，而会变成你理解结果好坏的抓手。

这也是为什么真实运行特别重要。因为有些词，光靠解释只能懂到六成，必须亲手见过一次，才会真正进入你的工作语言。

#### 3.6 傍晚看结果时，指标不该被当成成绩单，而该被当成问题定位器

新人在第一次看到结果汇总时，常常会本能地去找一个最像分数的数字。比如平均可行率高不高，计划耗时快不快，最后一轮图看着漂不漂亮。这种直觉可以理解，但如果一直停留在“找分数”的阶段，后面很难真正长出研究和工程判断。

更成熟的看法是：指标首先是问题定位器。`feasible_rate` 不是为了让你喊一句“挺高”，而是为了帮你知道方法整体是否稳定。`plan_time` 不只是快慢比较，它还在告诉你实时性边界到底在哪。`p95` 之类的尾部统计，不是为了显得专业，而是为了提醒你平均值掩盖不了那些拖后腿的极端情况。

一旦这么看，指标就会从“成绩单”变成“手电筒”。它会把你照向更具体的问题：到底是哪类 scene 更难，哪种模式更不稳，哪一步耗时最突出，哪一次运行其实只是看上去成功。术语一旦能帮你提问题，它就开始真正服务于推进项目，而不是只服务于阅读材料。

#### 3.7 晚上写汇报时，词汇量已经不再重要，重要的是你能不能把一天说清楚

到了晚上，如果你要给师兄、导师或者未来的学弟留一点记录，这一天其实就进入了另一个阶段：从“做事”切换到“讲事”。这时候你会突然发现，前面学过那么多词，真正值钱的不是你能说出多少个，而是你能不能把今天这条链讲顺。

比如更成熟的表达不会是“我今天看了很多资料、跑了很多命令”，而会更像：我今天先确认了远程环境和路径边界，然后定位了当前 wrapper 层和上游层的关系，接着用 smoke 跑通了一次最小链路，最后检查了 `runs` 目录下的日志与汇总输出。你看，这里面虽然自然会出现 `SSH`、wrapper、smoke、run_dir、log、summary 这些词，但它们已经不是炫耀术语的装饰品，而是在帮助你把一天说清楚。

这其实也解释了为什么你会觉得以前那种“满篇分点、满篇术语”读起来成本高。因为人的脑子不是靠词堆起来的，而是靠“事情是怎么发生的”来理解的。现在我们把术语重新放回一天的动作链里，它们就开始顺了。

#### 3.8 真正的学习感，不是“今天新认识了多少词”，而是“今天少迷糊了哪一段”

很多人评价自己学得好不好，喜欢用一种很硬的方式，比如今天背了多少概念、看了多少页材料、记了多少命令。可在复杂项目里，更真实也更健康的衡量方式其实是：今天有没有哪一段比昨天少迷糊一点。也许你还是没有完全理解 `Bezier` 为什么放在这里，也还不能把 `polytope` 的几何推导完整讲出来，但你已经不再把 wrapper 和上游混成一团，也知道 `runs` 里的文件应该先看谁后看谁。那这就是很实在的进步。

所以如果你以后带学弟，也尽量别老问那种会把人问虚的问题，比如“你都学会了吗”。更好的问题是：你今天最不迷糊的是哪一段，最迷糊的又是哪一段。前者能帮助他确认进展，后者能帮助你判断下一步怎么带。很多时候，学习动力不是来自“我已经全会”，而是来自“我终于有一块地方开始看明白了”。

### 4、十组最容易混的词，最好现在就把边界拉开

前面我们把很多术语各自讲开了，但真到了实际使用里，新手最容易卡住的，往往不是完全陌生的词，而是“看起来差不多”的词。也就是说，不是所有难点都来自不认识，而有不少混乱来自“仿佛都认识，但边界总是糊”。这一章我们就专门处理这种情况。你不需要把每一组都背成标准答案，只要把它们之间最重要的那条分界线抓住，后面很多理解成本就会降下来。

#### 4.1 `工作区` 和 `上游源码`

这两个词最容易因为都长得像“项目目录”而被混成一个东西。更清楚的说法是，`/home/howard/Splat-Nav` 是当前机器上的工作区，它承载的不只是算法代码，还有脚本、文档、结果规范和交接结构；而 `splatnav-official` 则更偏向论文本体实现，是算法事实主要落地的地方。前者更像工程组织层，后者更像方法实现层。

只要这层关系稳住，你后面无论是解释目录、读脚本还是讲成果，都会自然很多。否则一切都会绕在一起，最后谁都说不清自己在整理什么。

#### 4.2 `脚本` 和 `模块`

`脚本` 更像一个被拿来直接执行的动作入口，而 `模块` 更像被其他地方引用、复用的功能单元。举个更直白的说法，你通常会“跑一个脚本”，但你更常“调用一个模块”或“import 一个模块”。对当前项目来说，`scripts/` 里的很多东西偏脚本，而 `splatplan/`、`splat/`、`SFC/` 下的很多实现则更偏模块。

新手如果不分这两者，就容易读脚本像读模块，或者反过来，结果总觉得信息组织得很散。其实不是项目乱，而是阅读姿势还没切对。

#### 4.3 `配置` 和 `参数`

这两个词看起来都像“控制程序行为的东西”，但在工作流里的感觉不一样。`参数` 往往是你在运行命令时临时带上的，它更即时、更贴近这一次执行；而 `配置` 更像预先写在文件里的约定，通常更稳定，也更成体系。对学弟来说，早点形成这个感觉很重要，因为你后面做复盘时就会自然知道：这次结果的变化，到底是某个命令行参数改了，还是底层配置变了。

#### 4.4 `日志` 和 `结果`

很多人会把运行后留下来的东西一股脑都叫“结果”，这在聊天时可以，但在分析时会很粗。更细一点说，`日志` 主要回答“运行过程中发生了什么”，而 `结果` 更偏“运行完成后沉淀出了什么”。比如 `stdout.log` 更像日志；某张可视化图、某个 `summary.json`、某个汇总 CSV，则更像结果。两者都重要，但它们回答的问题不同。

#### 4.5 `成功运行` 和 `可信运行`

这组词非常关键。很多任务“跑完了”，并不代表“跑对了”。前者只说明程序没有明显中断；后者还要求输入合理、输出齐全、指标能解释、目录可追溯。你以后越早把这两者分开，后面越不容易被假成功骗到。真正成熟的项目习惯，永远更接近“可信运行”，而不是“反正出东西了”。

#### 4.6 `复现` 和 `创新`

这两个词不是对立关系，但确实是不同阶段的问题。`复现` 更像把已有链路真正走通、讲清、沉淀下来；`创新` 则是在这个基础上提出有意义的新东西。很多新人痛苦就在于还没把复现站稳，就已经在逼自己想创新。更好的顺序永远是先复现出稳定底图，再从底图上长出创新方向。

#### 4.7 `看懂` 和 `会讲`

有时候你自己心里觉得“好像懂了”，但一张嘴就讲散了。这个差异非常正常。`看懂` 更偏你和材料之间的关系，而 `会讲` 则要求你把脑子里的结构重新整理出来，让别人也能跟上。对当前项目来说，真正标志你开始掌握一段内容的，往往不是你默读时觉得顺，而是你能不能把它讲给学弟或者导师听。

#### 4.8 `平均值` 和 `尾部情况`

这一组看似偏统计，其实非常贴近日常判断。平均值会给你一个整体印象，但尾部情况决定你是不是会在关键时刻掉链子。比如 `p95` 这类词，就是在提醒你别只看平均表现。你后面如果要真正讲“稳不稳”，就不能只拿均值说话。

#### 4.9 `知道名字` 和 `建立工作感`

有些词你一查就知道大概意思，但这和真正建立工作感还不是一回事。所谓工作感，是你看到它时能立刻想到它大概出现在哪、有什么风险、影响哪一步、自己接下来该做什么。比如知道 `tmux` 是终端复用工具，只是知道名字；可如果你已经自然明白“今晚长任务一定要放 tmux 里，不然断线就白跑”，这才叫建立工作感。

#### 4.10 `会用工具` 和 `依赖工具`

最后这组词，我特别想送给刚开始用 Cursor、ChatGPT、Codex 这些工具的同学。会用工具，是知道它们适合拿来做什么、什么时候帮得上忙；依赖工具，则是离开它们就完全失去判断。我们当然希望学弟尽快用上这些工具，但更希望他在使用过程中长出自己的结构感和判断力。工具应该帮你走得更快，而不是替你把方向感拿走。

### 5、读完 `01` 后，你脑子里最好留下来的，不是更多名词，而是一套更稳的读项目姿势

如果这一份 `01` 真起作用了，那么读到这里时，你最该带走的其实不是“我今天又记住了几十个词”，而是三种更稳的姿势。第一种姿势，是遇到新词别慌，先问它在人话里是什么意思，再问它在当前项目里出现在哪。第二种姿势，是别把术语当摆设，要始终追问它会不会影响你接下来的一步动作。第三种姿势，是允许自己反复回查，不把“一次看懂全部”当作合理目标。

你会慢慢发现，真正让人能走下去的，不是突然变得特别聪明，而是开始学会和复杂材料相处。你知道自己可以先看个大概，知道有问题就回来翻，知道今天懂六成也没关系，只要明天能到七成就已经很好。这种松弛但不散的状态，反而最适合带一个零基础学弟进项目。

所以这份词典最后想送给你的，并不是一场“术语考试”的准备，而是一种处理复杂项目的基本功。你以后换方向、换代码库、换团队，这个基本功也照样值钱。因为任何复杂系统，最终都绕不过同一件事：你得先学会不被那些看起来很多、很杂、很硬的词压住，然后才有余力去真正理解它、改造它、讲清它。只要这一点开始发生，这份 `01` 就没有白写。
