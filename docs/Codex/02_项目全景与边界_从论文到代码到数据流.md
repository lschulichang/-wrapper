# 项目全景与边界：从论文到代码到数据流

这一份文档是整个体系里最关键的一份。前面的术语词典解决的是“词不认识怎么办”，而这里要解决的是另一种更深的困惑：词我好像都见过了，可是项目整体到底是怎么串起来的？为什么同一个工作区里会同时有 `scripts/`、`runs/`、`docs/`、`splatnav-official/`、`third_party/`？为什么有些脚本看起来像算法，有些看起来像环境工具？论文里讲的是 `Splat-Plan` 和 `Splat-Loc`，可我眼前看到的又是一堆 wrapper 脚本和 run 目录，这些东西到底谁是主角，谁是配角？

如果这类问题不先讲明白，新人会非常痛苦。因为你会一会儿钻进环境脚本，以为那就是算法本体；一会儿又钻进上游仓库，看到一堆模块后完全失去方向；最后看似文件很多、努力很多，但脑子里没有一张稳定地图。我们写这一份文档，就是为了先把地图画出来。地图一旦有了，后面读代码、跑脚本、看结果，都会省很多力。

## 一、先把论文主张和当前边界说清楚

这部分先解决“项目到底是什么”和“当前阶段到底做到哪里”这两个总问题。只有这两个问题稳住了，后面看目录、看脚本、看上游源码才不会一上来就混层。

### 1、先把论文讲的到底是什么说清楚

#### 1.1 一句话版本

Splat-Nav 是一套建立在 Gaussian Splatting 场景表示上的机器人导航系统。它不满足于“把场景重建出来”，而是进一步利用这种场景表示，让机器人在场景里做安全规划和视觉定位。

#### 1.2 30 秒版本

论文把系统拆成两个模块。`Splat-Plan` 负责从当前位置到目标位置，构造安全走廊并生成平滑轨迹；`Splat-Loc` 负责只根据机载 RGB 图像估计机器人当前位姿。两个模块合起来，才能支持机器人在复杂场景里一边估计自己在哪，一边持续规划一条安全路径。

#### 1.3 3 分钟版本

如果用更通俗的话来讲，这篇论文是在回答两个连续问题。第一个问题是：如果我们已经有了一个用 Gaussian Splatting 表示出来的三维场景，那么能不能不把它简单退化成传统地图，而是直接在这种表示上做安全规划？第二个问题是：如果机器人在执行过程中只有摄像头图像，能不能也利用这个 GSplat 场景来做位姿估计，从而形成可重规划的导航闭环？

论文的回答是肯定的。它把 `Splat-Plan` 设计成“先建立安全多面体走廊，再在走廊中生成平滑轨迹”的规划模块；把 `Splat-Loc` 设计成“利用 GSplat 场景和 RGB 观测做实时位姿递推”的定位模块。项目页和官方 README 都明确强调，这样的组合能在仿真和硬件实验中实现实时重规划与视觉定位，并且速度明显快于一类基于 NeRF 的导航方法。

对我们当前工作区来说，最重要的不是把论文里的每个实验数字背下来，而是抓住结构：论文总系统有两大块，而我们当前第一阶段主要在复现和工程化整理 `Splat-Plan` 的离线/仿真链路。这个边界一定要非常清楚。否则你会以为自己一上来就必须把整套机器人系统全部打穿，压力会非常大，也不现实。

### 2、把当前工作区看成三层结构

很多混乱，其实都来自把不同层次的东西放在一个平面里看。当前 `/home/howard/Splat-Nav` 这个工作区，最稳妥的看法是“三层结构”。

第一层是论文与算法层，也就是上游官方仓库真正实现 `Splat-Plan`、`Splat-Loc`、GSplat 读取、几何处理、样条优化的地方。你看到的入口是 `/home/howard/Splat-Nav/splatnav-official`，但它其实通过软链接最终指向 `/data/howard/repos/splatnav-official`。

第二层是本地 wrapper 工程层，也就是 `/home/howard/Splat-Nav/scripts` 这一层。它不去重写论文算法，而是负责把环境、tmux、run 目录、smoke、batch、overnight、结果汇总和可视化这些工程动作标准化。这一层非常像大厂项目里常见的“实验操作系统”。它不替代算法，但决定你能不能稳定、可追踪地复现算法。

第三层是文档与结果层，也就是 `/home/howard/Splat-Nav/docs` 和 `/home/howard/Splat-Nav/runs`。前者负责把知识、规范和交接路线沉淀下来，后者负责把每一次任务的证据、日志、配置和图表沉淀下来。你可以把这一层看成“项目的记忆系统”。

只要把这三层分开，很多问题就立刻清晰了。比如你要问“论文的核心算法在哪”，答案应该落在第一层。你要问“如何让长任务稳定跑在 tmux 里并自动归档结果”，答案在第二层。你要问“我应该读什么、怎么知道这次实验算成功”，答案在第三层。很多新人之所以累，就是因为把这三类问题全部丢给同一份代码去回答。

## 二、工作区地图与目录结构

这一部分把 `/home/howard/Splat-Nav` 这棵树真正讲开。目标不是让你背目录，而是让你看见每个目录各自承担什么职责、彼此为什么这样放。

### 1、当前工作区根目录里到底有什么

#### 1.1 `/home/howard/Splat-Nav`

这是主工作区根目录，也是你未来绝大多数操作的逻辑起点。你可以把它想成“整个项目在本机上的主门面”。它本身不是论文原仓库，也不是纯粹的数据目录，而是把上游源码、wrapper、文档、结果入口组织在一起的工作区。

#### 1.2 `configs/`

这个目录目前主要放工作区级的路径和环境约定，比如 `configs/project_paths.env`。它的意义在于：某些和本机部署相关、但又不适合散落在脚本里的路径信息，可以在这里集中管理。对新人来说，它不是第一优先级的阅读对象，但你要知道它代表的是“工作区的工程配置”，不是论文数学参数。

#### 1.3 `docs/`

这是文档总目录，用来沉淀项目说明、交接资料、排错、规范和阶段进展。里面又分成三类。`archive/` 是历史材料和合并版草稿，信息覆盖广，但不再作为新人主线。`guidang/` 更像工程执行过程中的规范和归档文档。`Codex/` 则是现在重新搭建的主文档体系，专门面向零基础学弟和当前工作区的最短路径阅读。

#### 1.4 `runs/`

`runs/` 是结果落盘入口。当前根目录下这个路径本身是一个软链接，实际指向数据盘上的结果目录。这样设计的目的很现实：系统盘空间紧张，但实验日志、JSON、图表和批跑结果会越来越多，所以要尽量把重资产沉淀到 `/data`。你以后看到的 `YYYY-MM-DD_HHMM_topic` 目录，几乎都会从这里进入。

#### 1.5 `scripts/`

这里是 wrapper 工程层最密集的地方。它不是论文主算法本体，但非常重要，因为你真正日常执行的大多数命令，都要通过这里进入。这里面既有环境相关脚本，也有数据下载、smoke、batch、overnight、watchdog、可视化和汇总脚本。后面我们会逐个讲。

#### 1.6 `splatnav-official/`

这是上游官方源码的推荐阅读入口。它是一个软链接，指向 `third_party/splatnav-official`，后者再指向真正的上游仓库 `/data/howard/repos/splatnav-official`。对新人来说，这个设计有两个好处：第一，工作区内部可以直接看到官方源码；第二，官方源码保留在数据盘位置，避免 home 目录和数据盘之间出现两套真正独立的副本。

#### 1.7 `third_party/`

这个目录体现的是工程化协作里常见的第三方依赖管理思路。当前它最重要的内容是 `third_party/splatnav-official` 这个软链接入口。它在概念上提醒你：上游官方仓库是被当作第三方依赖接入当前工作区的，而不是和 wrapper 混为一谈。

#### 1.8 `README.md`

根 README 是这套工作区的总入口说明之一。它强调三件事：这是一个 wrapper workspace；复现范围聚焦离线/仿真，不碰别人的环境和系统 CUDA；`scripts/` 负责工程化，核心论文算法仍在上游源码树。对于学弟来说，这份 README 很适合当第一眼总览，但它不能替代你现在读的这一份文档，因为它更像总览摘要，而不是完整地图。

#### 1.9 `Makefile`

`Makefile` 提供的是若干快捷入口，比如环境安装、环境检查、数据下载、数据链接、smoke 这类常见动作。它的功能更偏“常用命令别每次手打太长”，而不是实现复杂业务逻辑。对新人来说，你要知道它是便捷入口，不是算法核心。

## 三、wrapper 工程层是怎么把事情组织起来的

对当前工作区来说，wrapper 层是理解成本最高、但也是最值得先看懂的一层。这里会把环境、tmux、run 目录、批跑、可视化和汇总脚本系统地归到一起。

### 1、wrapper 脚本层到底承担什么职责

这里我们不按文件名机械罗列，而是先按职责分组，再在组内解释每个脚本。这样你更容易建立“我现在该找哪类脚本”的直觉。

#### 1.1 环境与健康检查脚本

##### 1.1.1 `scripts/bootstrap_env.sh`

这是当前工作区环境搭建的主入口之一。它会连接 `/data/howard/miniconda3` 这套 Miniconda 安装，在其中创建或复用 `splatnav` 环境，然后安装项目需要的关键 Python 依赖，包括 `nerfstudio`、`clarabel`、`cvxpy`、`open3d`、`viser`、`LightGlue` 等。这个脚本的重要性不在于“装很多包”，而在于它把环境搭建策略固定下来了：优先把环境、缓存和临时目录放在数据盘，不去动系统 CUDA，不去污染其他人的环境。

如果你将来带学弟，这个脚本就是最值得你先讲清楚的环境脚本之一。因为它直接体现当前项目的边界意识：只在自己的 Conda 环境里解决问题。

##### 1.1.2 `scripts/env_health_check.sh`

环境搭好以后，不能凭感觉宣布成功，这就是 `env_health_check.sh` 的价值。它会检查系统信息、GPU、Python 版本、Torch CUDA 状态以及一系列关键依赖的 import 能否通过。对新人来说，这个脚本的意义非常大，因为它把“环境能不能用”变成了可见证据，而不是主观判断。

你以后看到某次 smoke 失败，不要直接怀疑算法，先回到这个脚本确认环境是否健康，这是非常稳的排查起点。

##### 1.1.3 `scripts/fix_torch_cuda.sh`

这个脚本是针对 Torch 与 CUDA 运行时兼容问题的定向修复脚本。它的核心思想不是升级系统 CUDA，也不是升级显卡驱动，而是在当前 `splatnav` 环境里重装一个与现有驱动兼容的 Torch 版本。对于共用机器、共用显卡、又明确不能乱动系统环境的场景，这个脚本非常符合边界要求。

你可以把它理解成“只在自己的小屋里修灯泡，不去动整栋楼总闸”。这个比喻很土，但很好记。

#### 1.2 run 目录、tmux 与长任务调度脚本

##### 1.2.1 `scripts/create_run_dir.sh`

这是 run 目录规范的核心脚本。它负责创建 `runs/YYYY-MM-DD_HHMM_topic/` 这样的目录，并自动生成 `env.txt`、`notes.md`、空的 `cmd.txt` 和 `stdout.log`。对工程化复现来说，这个脚本的价值非常大，因为它把“每次任务都应留下什么证据”写成了默认动作。

你后面无论是 smoke、tmux 任务还是 overnight，都能看到它的身影。对新人来说，理解这个脚本，就相当于理解“项目为什么强调每次任务都要留下上下文”。

##### 1.2.2 `scripts/run_in_tmux.sh`

这是当前工作区里最重要的长任务入口之一。它会自动准备 run 目录、生成 job 脚本、创建或复用 `splatnav_jobs` 这个 tmux 会话，并把你的命令放到新的 tmux window 里执行，同时把输出写入 `stdout.log`。它不是算法脚本，但在工程实践里价值极高，因为它解决的是“任务如何在断开终端后继续跑、如何把命令和日志绑定保存”的问题。

如果学弟以后只记住一个 wrapper 级核心脚本，我认为就是这个。因为它体现了当前工作区的一个重要原则：长任务尽量进入 tmux，并与 run 目录规范绑定。

##### 1.2.3 `scripts/watch_overnight_job.sh`

这个脚本扮演的是 watchdog 角色。它会监测目标 overnight 进程是否还活着，如果发现任务消失，就尝试重新拉起。对新人来说，watchdog 这个概念本身就很值得学：它说明工程上的问题不仅是“怎么启动一次”，还包括“任务中途挂了怎么办，能不能自动恢复”。

当然，这个脚本也提醒你一件事：自动恢复是补救，不是替代排错。真正长期稳定，还是要回到环境、输入、脚本链路本身。

#### 1.3 数据与资源准备脚本

##### 1.3.1 `scripts/download_official_data.sh`

这是一个官方数据下载入口，用 `gdown --folder` 从论文 README 给出的 Google Drive 地址拉取官方资产。它的意义不是“下载就是结束”，而是把数据来源和下载动作固定在一个可追踪的脚本里。对于新人来说，这能减少随手点网页、下载到奇怪目录、最后自己也不知道文件从哪来的问题。

##### 1.3.2 `scripts/link_official_assets.sh`

这个脚本负责把下载好的 `training/data`、`training/outputs`、`traj` 等内容，通过软链接接到上游仓库期望的位置。它之所以重要，是因为上游论文代码往往默认某种目录结构，而我们本机又希望把重数据统一放在数据盘。软链接正好解决这个矛盾：既不改上游逻辑，也能把真实资产放在更合适的位置。

##### 1.3.3 `scripts/retry_gdown_folder.sh`

网络下载尤其是 Google Drive 批量下载，很容易出现中途中断、缺文件、文件数不足的问题。这个脚本的作用，就是围绕一个文件夹 URL 做重试下载，并用帧数、`transforms.json`、`sparse_pc.ply` 这些条件判断是否真正下载完整。它代表了一种很重要的工程思想：下载成功不是“命令退出码看起来没事”，而是“目标文件结构达到最低验收条件”。

##### 1.3.4 `scripts/fill_missing_scene_files.sh`

这个脚本进一步处理“日志里显示下载过，但本地还缺文件”的场景。它会从 gdown 日志中解析文件 ID，再对缺失的图片、`transforms.json` 和 `sparse_pc.ply` 做定向补齐。对新人来说，这个脚本很有启发：很多真实工程问题不是完全重来，而是“如何补最后那几块缺失拼图”。

##### 1.3.5 `scripts/pull_images2_full.sh`

这个脚本专门围绕 `images2` 这样的场景资源做多次尝试拉取，并按帧数是否达到最低标准来判断完成度。它本质上和前两个下载补齐脚本属于同一类：处理网络资源不稳定、需要重试和最低数量验收的下载问题。

#### 1.4 smoke、batch、overnight 主执行链脚本

##### 1.4.1 `scripts/smoke_splatplan.py`

这是最小规划冒烟测试的 Python 入口。它负责做几件非常具体的事：解析 `--config`、`--scene`、`--method`、`--output` 参数；根据场景预设构建机器人与体素配置；通过 `GSplatLoader` 加载模型；根据方法名构建 `SplatPlan` 或 `SafeFlightCorridor`；然后只对一组固定的起终点做一次规划，并把结果写成 JSON。这个脚本的重要性不在于它短，而在于它是“最小可跑链路”的缩影。

对新人来说，读这个脚本非常合适，因为它不会像大批量脚本那样一下子引入太多循环和统计逻辑。你可以在这里先看懂：输入是什么，核心 planner 是怎么被构建出来的，输出 JSON 大概长什么样。

##### 1.4.2 `scripts/run_splatplan_smoke.sh`

这个 shell 脚本是 smoke Python 入口的直接包装。它会创建 run 目录、记录命令、激活 Conda 环境、清理 `LD_LIBRARY_PATH`，然后调用 `smoke_splatplan.py`，并把日志写进当前 run 目录。它的角色很像一个“规范化启动器”：不是替代 Python 主逻辑，而是保证每次 smoke 都按统一工程规矩执行。

##### 1.4.3 `scripts/run_splatplan_smoke_tmux.sh`

这是 smoke 的 tmux 版本入口。它不会直接自己跑规划，而是组装好命令后交给 `run_in_tmux.sh`。这个设计很好理解：如果 smoke 任务也想脱离当前终端独立运行，就复用统一 tmux 调度入口，而不是每个脚本自己再造一套后台运行逻辑。

##### 1.4.4 `scripts/run_official_style_batch.py`

这是当前 wrapper 层最重要的批量实验脚本。它会在多个起终点对上运行 `splatplan` 或 `sfc-1..4` 等方法，记录每次 trial 的结果，统计可行率、平均耗时、P95 耗时，并把部分轨迹和详细记录打包成一个 `batch_results.json`。你可以把它理解成“从单次 smoke 走向正式实验统计”的主桥梁。

它和上游 `run_splatplan.py` 的关系值得你认真体会。上游脚本更像论文作者自己组织实验的原始入口，而 wrapper 这份 batch 脚本则在保留算法调用逻辑的同时，把输入参数、输出结构、保存格式、轨迹抽样、统计摘要都包装得更适合本机复现和结果沉淀。这就是工程化封装的典型样子。

##### 1.4.5 `scripts/run_overnight_12h.sh`

这个脚本会在给定的时长内，循环调用 batch 脚本，每一轮都建立新的 run 目录、保存 JSON，并在成功后生成可视化图。它的本质不是另一种算法，而是把一轮又一轮正式 batch 组织成可长期运行、可分轮归档的实验流水线。对于当前机器夜间空闲、GPU 可持续使用的场景，这个脚本非常实用。

##### 1.4.6 `scripts/post_overnight_report.sh`

overnight 跑完之后，如果只留下很多 run 目录而没有总览，第二天会很难看。这个脚本的作用就是在目标 overnight 任务结束后，自动运行汇总脚本，产出 CSV、Markdown 报告和最新报告的稳定软链接。它体现的是“结果不仅要产生，还要能被第二天的人快速消费”。

#### 1.5 汇总与可视化脚本

##### 1.5.1 `scripts/visualize_batch_results.py`

这个脚本负责把 batch JSON 结果进一步做成更容易阅读的图，包括可行率柱状图、规划耗时箱线图、示例轨迹 XY 投影叠图，并生成一个简要的 Markdown 摘要。它属于“从原始统计到汇报素材”的一层。你以后做组会、周报，很可能第一眼看的就是它生成的图，而不是原始 JSON。

##### 1.5.2 `scripts/aggregate_batch_runs.py`

这个脚本的目标是把多轮 batch 的结果横向汇总起来，形成 `overnight_summary.csv`、`overnight_summary.md` 和迭代曲线图。它是“跨 run 目录”的汇总层。与 `visualize_batch_results.py` 不同，后者更关注某一次 batch 的内部对比，这个脚本则更关注多轮正式实验之间的整体趋势。

#### 1.6 同步与维护脚本

##### 1.6.1 `scripts/sync_upstream.sh`

这个脚本用于查看和同步上游官方仓库的分支与提交状态。它不会替你解决所有合并问题，但会明确告诉你当前上游提交和分支情况。对新人来说，它的意义是建立一个概念：上游不是死的，wrapper 也不是闭门造车，二者之间要有版本感知。

## 四、上游官方源码层到底在做什么

当你已经知道 wrapper 在做什么之后，才更适合进入上游源码。这里重点处理的是：哪些文件是主轴，哪些目录是支撑层，哪些内容现在先知道位置就够。

### 1、上游官方源码层到底怎么看

很多人一看到上游源码目录多，就立刻想逐文件读。这个想法听起来勤奋，但对新人来说通常效率很低。更稳的方式，是抓住主链路入口，再顺着调用关系往里走。对当前项目，最值得你优先读懂的入口就是以下几类。

#### 1.1 `run_splatplan.py`

这是上游最直接的 `Splat-Plan` 仿真运行入口。你从这份脚本里能一眼看到论文实现者自己是怎么组织实验的：先设定场景名、方法名、机器人参数、体素边界、分辨率和 GSplat 配置路径；再加载 `GSplatLoader`；再根据方法构建 `SplatPlan` 或 `SafeFlightCorridor`；然后在一圈起终点样本上循环调用 `generate_path`，最终把结果写进 `trajs/` 目录。

这份脚本非常像“原始实验台面”。它没有 wrapper 那么讲究 run 目录和日志结构，但恰恰因为直接，它很适合你理解：上游论文作者心中的实验主流程到底是什么。

#### 1.2 `run_splatloc.py`

这是上游的 `Splat-Loc` 入口。它主要围绕 GSplat 场景、相机内参、图像数据集和位姿估计流程展开。对当前阶段来说，它不是最先要啃透的文件，但你至少应该知道它在总系统里代表“定位链路”，从而和 `run_splatplan.py` 形成清晰对照。

如果学弟读到这里觉得压力大，很正常。第一阶段只要先知道它存在、知道它负责什么，就够了。

#### 1.3 `splat/splat_utils.py`

这份文件里最关键的类是 `GSplatLoader`。它的作用是把 GSplat 模型从指定位置加载出来，并整理成后续规划所需的张量属性，比如均值、旋转、尺度、颜色、不透明度以及相关协方差表示。对新人来说，这份文件很重要，因为它回答了一个非常基础但关键的问题：规划模块到底是怎么接触到“场景”的。

你如果把 `Splat-Plan` 想象成一个只吃起点终点的黑盒，会很难理解为什么 `config.yml` 这么重要。看过 `GSplatLoader` 以后，你会知道规划器不是凭空工作，而是建立在一个具体的 GSplat 场景表示之上。

#### 1.4 `SFC/corridor_utils.py`

这份文件承载的是 `SafeFlightCorridor` 及相关走廊生成逻辑。你会在这里看到多种 mode 对应 `sfc-1` 到 `sfc-4` 这些 baseline 的差异：有的在点云网格上初始化，有的在 GSplat 网格上初始化，有的走廊收缩更保守。对新人来说，这个文件很值钱，因为它不仅实现一个方法，还通过 mode 让你看到“对比方法的家族差异”。

你读它的时候，不要试图一次记住所有几何细节。先抓住结构：初始化路径、获取碰撞集合、构造多面体、最终生成轨迹。只要这个骨架稳住，细节可以后面再补。

#### 1.5 `splatplan/splatplan.py`

这份文件是 `SplatPlan` 核心实现。它大致做四件事：利用体素网格生成初始路径；逐段计算碰撞集合；根据高斯相关几何关系构造安全多面体；再调用样条优化器得到平滑轨迹。这个文件很适合作为你理解论文核心主张的代码落点，因为它把项目页和论文中那句“safe-by-construction polytope corridor + Bézier trajectory”真正在代码里展开了。

你以后如果要向别人解释 `Splat-Plan`，这份文件是最值得你反复读的核心落点。

#### 1.6 `splatplan/spline_utils.py`

这份文件更多承载“给定走廊以后，如何把轨迹优化出来”的逻辑。里面会出现样条基、导数、约束矩阵、`cvxpy`、`clarabel` 这些内容。很多新人读到这里会被吓住，但你只要记住：这不是另一套无关算法，而是 `Splat-Plan` 最后一段“从安全走廊到平滑轨迹”的求解器实现。

## 五、从数据流和调用链把整套系统串起来

目录、脚本和源码真正有意义，是因为它们共同组成了一条流。这里开始把输入资产、调用顺序、结果落盘和阅读顺序整体串成链。

### 1、文件夹之间的数据流到底怎么走

讲清项目全景，最终一定要落到数据流上。因为只有数据流清楚了，你才知道“输入从哪里进，输出往哪里出，中间谁做了什么”。

最上游的输入，是一个已经训练好的场景模型及其配置，通常表现为某个 `config.yml`。这个配置文件背后关联着 Nerfstudio 风格的训练输出目录、数据解析信息和场景模型参数。wrapper 或上游入口脚本接收到这个配置路径后，会调用 `GSplatLoader` 把模型读进来。

读进来之后，规划链路会根据场景名选择一组机器人和体素预设，包括机器人半径、最大速度、最大加速度、体素边界和分辨率。这一步不是数据下载意义上的输入，而是实验设定意义上的输入。接着，脚本根据方法名决定构建 `SplatPlan` 还是 `SafeFlightCorridor`。此时，场景表示已经和规划器绑定起来了。

随后，单次 smoke 会选择一组固定起终点并调用 `generate_path`；batch 会生成一批起终点对并循环调用；overnight 则会在更长时间窗口里多次调用 batch。每一次调用都会得到规划结果，里面包含是否可行、耗时、多面体数量、路径和轨迹等信息。wrapper 脚本会把这些原始结果整理成 JSON，并额外生成图表、Markdown 摘要、CSV 汇总等更方便阅读的产物。

最终，这些结果都会沉淀到 `runs/` 下某个具体 run 目录里。也就是说，当前工作区真正的核心数据流，可以简单概括成：`config.yml 与场景预设 -> 规划器构建 -> 单次或批量 generate_path -> JSON 与日志 -> 图表与汇总 -> runs 目录沉淀`。把这条线背住，你再去看单个文件，就不会那么容易迷路。

### 2、这个项目现在能做什么，不能做什么

当前这套工作区和文档体系，已经很适合做以下几类事情。第一，围绕作者场景做离线和仿真级别的 `Splat-Plan` 复现。第二，使用统一 wrapper 脚本做 smoke、batch、overnight 实验，并把结果按 run 目录规范保存。第三，基于 `runs` 里的 JSON、图和汇总文件，完成周报、组会和阶段性汇报。第四，在不破坏上游原样的前提下，逐步做外层工程整理、注释补充和有限的重构思考。

但它暂时不等于一套完整真机部署系统。当前阶段不碰实车，不展开 ROS 分支的节点部署，不把 `Splat-Loc` 和硬件飞行闭环作为新人第一周的刚性任务，也不要求一开始就进入论文创新点实现。你可以把这些方向放在后续一月、三月阶段里逐步展开，但不能混入第一阶段目标。

这个边界说清楚，其实是在保护项目推进节奏。很多人不是能力不够，而是一开始给自己塞了过多目标，最后所有目标都推进得很浅。

### 3、把论文语言翻译成你每天会遇到的工作语言

前面那几节，其实只是先帮你把大地图钉在墙上。接下来我们要做的，是把地图上的抽象文字翻译成你真会遇到的工作语言。因为很多新人真正崩溃的地方，不是“论文看不懂”，而是“论文里那些看起来很高级的话，跟我眼前的文件、脚本、日志，到底有什么关系”。只要这层翻译没做，项目就会一直悬在空中。你知道它厉害，也知道它大概做导航，但你不知道自己今天下午打开哪个脚本，和论文里哪句主张其实是同一件事。

所以我建议你换一个很接地气的读法。以后每次看到论文里的一个关键词，不要急着去背定义，先问三个问题。第一，它在本机工作区里落到哪个目录、哪个脚本、哪个类上。第二，它输入了什么、输出了什么。第三，它如果坏了，我会在哪一层看到异常。只要这三个问题能回答出来，这个概念就真正开始归你用了。

#### 3.1 论文说“Gaussian Splatting map”，你在工作区里该想到什么

论文里的 `Gaussian Splatting map`，如果只停留在“一个很新潮的三维表示”，那它对新人来说帮助不大。你真正应该想到的，是它在当前项目里不是一张普通图片，也不是一个传统的二维栅格图，而是一套通过 Nerfstudio 训练出来、最终由 `config.yml` 作为入口的场景模型。也就是说，当你在 wrapper 脚本里写 `--config /.../config.yml` 时，你不是在给脚本随便塞个配置文件，而是在告诉它“你现在要读哪一个 GSplat 场景”。

一旦这么想，很多事情会突然顺起来。你会明白为什么本地文档老是反复提 `config.yml`，明白为什么 `GSplatLoader` 是核心入口之一，也明白为什么数据下载、资产软链接、`outputs/` 目录结构这些事情会和规划算法扯上关系。因为规划器本身并不是无中生有，它是站在一个已经训练好的 GSplat 场景表示之上工作的。

#### 3.2 论文说“safe-by-construction polytope corridor”，你在代码里该想到什么

这句话看起来很学术，但如果你把它翻译成代码语言，其实可以变得很具体。所谓 `safe-by-construction polytope corridor`，不是一句口号，而是会落到 `SplatPlan.generate_path()` 里那条很明确的链路：先用体素网格做 A* 找一条初始化路径，再按段构造碰撞集合，再逐段生成多面体约束，最后把这些多面体送进样条优化器。也就是说，安全不是最后画图时顺手检查一下，而是在规划过程中被逐段写进约束里的。

你后面读 `splatnav-official/splatplan/splatplan.py` 时，别一上来盯着每个张量的维度。先抓住这个骨架：`A* 初始化 -> collision set -> polytope -> spline optimization`。只要骨架稳住，后面的矩阵、半空间、约束拼接，就都只是往骨架上长肌肉，而不是完全陌生的天书。

#### 3.3 论文说“recursive re-planning”，你在当前阶段该怎么理解

很多新人一看到 `re-planning`，脑海里就会直接跳到真机飞行、闭环控制、相机在动、机器人在房间里躲障碍。这种联想不完全错，但对当前阶段来说，太早了。你在本机工作区第一阶段更合适的理解，是“同一套规划器被多次调用，在不同起终点、不同 trial、不同 batch 里重复运行，并把结果做成结构化统计”。

也就是说，当前阶段你暂时不用把 `re-planning` 想得那么像机器人操作系统里的闭环回路。你可以先把它理解成“对规划器的重复、可追踪、可比较调用”。`smoke` 是一次很小的调用，`batch` 是一批系统化调用，`overnight` 是很多轮调用的组织方式。等这三层都真正摸熟以后，你再回头看论文里的在线重规划，会发现自己已经有了很强的地基。

#### 3.4 论文说“Splat-Loc”，你在当前工作区里应该保持什么态度

`Splat-Loc` 既不能被你忽略，也不能被你第一周就当成必须打透的主线。更稳妥的态度是：知道它在总系统里很关键，知道它负责的是视觉定位链路，知道 `run_splatloc.py`、`pose_estimator/utils.py`、`ns_utils/nerfstudio_utils.py` 这些地方和它强相关，但当前离线复现主任务主要先把 `Splat-Plan` 跑顺、讲清、固化下来。

这样安排不是在回避难点，而是在做任务排序。因为如果学弟连工作区三层结构都没稳住，就直接扎进 `Splat-Loc` 的特征匹配、PnP-RANSAC、ICP、UKF 式状态估计细节里，阅读压力会非常大。相反，如果先把 `Splat-Plan` 的输入、输出、结果目录、规划链路看稳，再回来看定位链路，就像先学会走一条路，再学怎么在路上定位自己。顺序会合理很多。

#### 3.5 论文说“real-time”，你在共用工控机上该怎么落地这个词

`real-time` 在论文里当然有算法和系统层面的含义，但落到你现在这台机器上，它还多了一层很实际的工程含义：任务要稳、结果要能看、日志要能留、环境不能乱、资源不能伤及别人。也就是说，实时性不只关乎算法快不快，也关乎你能不能用一套可靠的 wrapper 和 run 规范，把实验长期稳定地组织起来。

这也是为什么当前工作区里 `scripts/run_in_tmux.sh`、`create_run_dir.sh`、`aggregate_batch_runs.py` 这些文件虽然不是论文创新，却同样重要。它们保证的不是“数学上更优”，而是“工程上更稳”。如果你以后去大厂做算法工程，会越来越感受到这一点。真正能把工作推进下去的人，往往不是最会讲概念的人，而是既懂概念，又能把概念压进工程流程的人。

新手经常有一种错觉，以为项目结构图只是给汇报用的。其实不是。最好的结构图，是你每天工作时真的能用上的图。为了让这件事更具体，我们不妨把当前项目想象成一个完整工作日。你早上连上机器，白天读文档、读代码、跑小实验，晚上可能发起长任务，第二天再回来看结果。只要你能把一天的动作和目录结构一一对应起来，整个项目就会变得非常立体。

#### 4.2 上午：先读文档，再带着问题去看代码

很多新人最容易犯的错，是一上来就直扑代码，认为这样最踏实。事实上，对当前项目这种“论文算法 + 上游源码 + wrapper 工程 + 本机运行边界”四股信息缠在一起的工作区来说，先读主文档反而更省时间。不是因为文档比代码高级，而是因为文档能先帮你划边界、划层次、划优先级。

所以对学弟来说，上午最理想的动作不是到处点文件，而是先在 `docs/Codex` 里把主线走一遍。先看 `00_统一说明_阅读导航与项目总摘要.md`，知道自己应该从哪进；再回看 `01_专业术语全解_项目全词典.md`，把眼下会撞到的词压一压；最后来到这一份 `02_项目全景与边界_从论文到代码到数据流.md`，把项目地图定下来。这样做之后，你再打开 `scripts/smoke_splatplan.py` 或 `splatnav-official/splatplan/splatplan.py`，会轻松很多。

#### 4.3 下午：开始做小规模验证，把“看懂一点”变成“我真跑过”

到了下午，你通常已经不满足于只看文字了。这个时候最自然的动作，就是先做一条最小验证链。也就是说，不追求大规模 batch，不追求炫图，而是先找一个可信的 `config.yml`，用 smoke 跑一条最短路径，让自己第一次亲眼看到 `run_dir`、`stdout.log`、输出 JSON 和里面的 `feasible`、`path`、`traj` 等字段。

为什么这一步重要？因为很多理解只有在你真的跑过一次以后才会变得牢。比如你以前知道 `GSplatLoader` 是读场景的，可直到你发现 smoke 入口确实在先构建 planner、再传入 `config.yml`，这个概念才真正落地。再比如你知道 `create_run_dir.sh` 会创建 run 目录，可直到你亲手看到 `cmd.txt`、`env.txt`、`stdout.log` 被生成出来，这个规范才不再只是文档里的要求。

#### 4.4 傍晚：开始看结构化结果，而不是只盯着终端输出

很多人跑出第一条结果以后，会下意识只盯着终端里最后几行输出，仿佛那里藏着所有答案。其实不是。真正成熟一点的工作方式，是尽快把注意力从终端滚动文本转移到结构化结果上。你会开始打开 JSON，开始对照 `meta`、`device`、`plan_time_sec`、`output.feasible`，开始看图、看 Markdown 摘要、看 CSV 汇总。

这个转变非常重要。因为只看终端输出，很容易让你一直停留在“程序有没有炸”。而看结构化结果，会把你带向另一种更高级的问题：这次规划到底表现怎样，和上次有什么差异，失败是链路故障还是问题本身不可行。科研和工程真正的成长，很多时候就是从这里开始的。

#### 4.5 晚上：长任务交给 tmux 和 run 规范，自己不要做系统的人肉守夜员

当前工作区里，晚上最典型的动作不是继续手盯终端，而是把需要长时间运行的任务规范地交给 tmux、交给 run 目录、交给 watchdog 和后处理脚本。这背后其实是一种很重要的工程态度：人应该负责设计和判断，不应该长期充当“人肉终端保持器”。

所以如果你晚上要跑正式 batch 或 overnight，最值钱的不是再多盯两小时，而是提前把命令、结果目录、监控和汇总链路安排好。这样第二天早上回来，你看到的就不是一团混乱输出，而是一套已经归档到 `runs/` 的实验记录。学弟越早理解这种“把任务交给系统规范”的思路，越能减少被重复劳动吞掉的精力。

### 5、把根目录真正讲细：每个文件夹在这套工程里都扮演什么角色

前面我们已经大概走过一遍根目录，但那更像总览。这里我们把它讲得更细一点。不是为了追求百科全书式覆盖，而是因为学弟第一次看一个工程，最容易被目录名骗。很多目录看起来都很普通，真正的区别藏在它们对项目节奏的影响上。你如果只看名字，不看角色，就会一直把工具层、算法层、结果层混在一起。

#### 5.1 `.git/`：它平时很安静，但它是这套工作区的时间轴

很多初学者一看到 `.git/` 会下意识略过，觉得那是版本控制内部实现，不重要。对做项目的人来说，这个判断并不完全对。你当然不需要天天钻进 `.git/objects` 去看对象存储，但你必须知道 `.git` 的存在意味着什么。它意味着当前这个 `/home/howard/Splat-Nav` 工作区是一个被版本控制管理的工程，而不是一堆随手扔在磁盘上的文件。

这件事的重要性，在你未来开始整理 wrapper、补注释、做结构优化时会越来越明显。因为一旦文档、脚本和外层工程开始稳定演化，版本历史就会成为你的第二套记忆系统。你会知道哪些修改是你做的，哪些是历史遗留，哪些适合继续推进，哪些只是一次性草稿。也就是说，`.git` 不只是开发者的工具，它其实是项目成长的时间轴。

#### 5.2 `configs/`：它不吵闹，但它在帮工作区收拢机器相关约定

`configs/` 在很多工程里都会被新人低估，因为它不像 `scripts/` 那样“会跑”，也不像 `docs/` 那样“能读”。但它的作用其实很稳：把一些和当前机器部署、路径约定、环境变量相关的信息放在一个单独位置，不让这些内容散落到几十个脚本里。当前工作区里它最典型的例子是 `configs/project_paths.env` 这类文件。

你可以把这个目录理解成“工程习惯的中控台”。它不直接产生论文结果，但它决定很多脚本会不会越来越乱。对于带新人来说，这个目录还有一个隐含价值：它提醒大家，本机部署相关的东西和论文算法参数不是一回事。别把这两类配置混着讲。

#### 5.3 `docs/`：它不是陪衬，而是这个项目真正的交接面

对学生项目来说，`docs/` 经常被当成“最后想起来再补一补”的东西。可在当前这套工程里，`docs/` 实际上是很关键的主层之一。因为你们现在做的事情，不只是自己把实验跑通，还包括把这个项目整理成可以交接、可以带人、可以汇报、可以让后来者接着干的形态。只要有这个目标，文档就不再是附属品，而是项目本体的一部分。

而且你会注意到，`docs/` 在当前工作区里不是单薄的一层。它内部又自然分成三个性格不同的区域：历史档案、归档规范和当前主线。理解这三者的差别，对学弟很重要。

#### 5.4 `docs/archive/`：像旧讲义，覆盖广，但不适合直接拿来带零基础同学

`archive/` 最大的优点是信息覆盖广。你在里面能看到很多历史版本的合并稿、全景稿、基础知识稿。这些材料对你后面做深挖很有价值，因为它们常常保留了很多最初搜集到的知识点、路径和上下文。但它的缺点也很明显：内容容易混杂、叙事层级不稳定、对零基础读者来说负担偏大。

这就是为什么当前 `docs/Codex` 要重建主线，而不是直接把 `archive` 扔给学弟。不是因为 archive 没价值，而是因为它更像资料库，不像真正的陪跑教材。等学弟第一轮稳定入门以后，你当然可以再带他回去挖里面那些更全、更散、更原始的材料。

#### 5.5 `docs/guidang/`：更偏执行与规范，是项目管理感比较强的一层

如果说 `archive` 像资料库，那么 `guidang` 更像工程过程中的制度层。这里面的东西往往更偏执行约束、归档口径、阶段说明。它不一定是学弟第一天最适合啃的内容，但当你开始把实验做成周期任务、需要做验收口径和结果归档时，这一层会非常有价值。

你以后如果开始真正带人，就会发现 `guidang` 这种目录非常必要。因为很多问题不是“不知道怎么做”，而是“不知道做到什么程度算完成”。而规范目录存在的意义，就是减少这种模糊地带。

#### 5.6 `docs/Codex/`：现在这套主线文档真正希望你从这里开始

`docs/Codex/` 是当前重新搭建后的主阅读入口。它的设计目标非常明确：不是信息最全，而是对现在这台机器、现在这套 wrapper、现在这个复现边界最友好。你在这里看到的 `00` 到 `05` 六份文档，本质上是在做一件事：把原本散在 archive、README、脚本注释和口头交接里的知识，重新排成一条零基础可以往前走的路。

所以学弟第一次进工作区，真正应该优先看的就是这一层。它不会替代上游源码，也不会替代论文，但它会把“先看什么、后看什么、现在做到哪一步算过关”讲清楚。对于入门阶段，这种作用非常大。

#### 5.7 `runs/`：这是项目最有证据感的目录，不是普通输出箱

你以后会越来越发现，一个项目做得稳不稳，不是看它能不能偶尔跑通，而是看它能不能把每一次运行都留下可靠证据。从这个角度看，`runs/` 是当前工作区里极其关键的一层。它不是简单的“输出目录”，更像实验事实的沉淀区。每一个带时间戳的子目录，都对应一次具体任务、一个明确命令、一个环境快照和一组结果文件。

更重要的是，当前 `runs/` 本身还是一个软链接，最终落到 `/data/howard/splatnav/runs`。这个细节看似只是磁盘管理，实际上含义很强：重资产和长历史要尽量往数据盘沉，系统盘要克制；结果入口依然放在工作区根目录，保证查找和讲解方便。这就是一种很成熟的工程取舍。

#### 5.8 `scripts/`：它像中控台，不是论文算法本体，但你每天都离不开它

很多人第一次看到 `scripts/` 会很容易出现两个极端。一个极端是完全忽略它，觉得真正的东西都在上游源码。另一个极端是把它当成全部项目，以为论文算法都写在这里。两种看法都不对。更准确的理解是：`scripts/` 是当前工作区的中控台。它负责把环境、路径、tmux、smoke、batch、overnight、汇总和可视化这些工程动作规范化。

为什么说它不是论文算法本体？因为真正的规划器类和定位逻辑还在 `splatnav-official/`。为什么又说你每天都离不开它？因为你绝大多数日常动作，不会直接从上游源码敲起，而是要通过这里的脚本进入。你可以把它理解成“让上游论文实现更适合本机复现”的外层操作系统。

#### 5.9 `scripts/__pycache__/`：它不值得读，但它提醒你 Python 在这里被实际执行过

像 `__pycache__` 这种目录，新手往往会疑惑它是不是很重要。结论很简单：它不值得你花时间读，也通常不该被当成项目主结构的一部分。但它至少提醒你，这里对应的 Python 文件已经在本机被解释器加载和执行过，系统因此留下了缓存。

对学弟来说，最有价值的不是研究它内部，而是形成一种“什么是源码、什么是缓存、什么是结果、什么是依赖入口”的基本分层意识。很多混乱，本质上就是把这些不同性质的东西都看成“目录而已”。

#### 5.10 `splatnav-official/`：它是你阅读官方源码最顺手的门

这一层我们前面已经提过很多次，但这里仍然值得再压实一下。`splatnav-official/` 在当前工作区里的价值，不只是“能打开官方代码”，而是“给所有文档和讨论提供统一入口”。如果没有这个入口，你每次跟学弟讲代码都要绕去数据盘真实路径，叙事会变得很重。现在有了这个入口，大家都能从同一个门进去，再通过 `readlink -f` 追到真实仓库位置。

这在教学和协作里非常有帮助。因为好的入口本身就会降低理解成本。你以后让学弟打开 `[splatplan/splatplan.py](/home/howard/Splat-Nav/splatnav-official/splatplan/splatplan.py)`，就比让他背数据盘长路径要轻松得多。

#### 5.11 `third_party/`：它像一个“关系声明”，提醒你这份官方仓库是被接入进来的

很多工程里都会有 `third_party/`，但新人第一次看到时常常不明白它为什么非要存在。当前工作区里，它最主要的意义其实是一种结构声明：官方 Splat-Nav 源码在概念上是作为第三方依赖被接入当前 wrapper 工作区的。你没有把它和自己的工程层糊成一团，而是明确说“这是上游，这是外层包装”。

这种分层非常值得珍惜。因为一旦这层边界清楚，后面你做同步、做注释、做封装、做局部优化时，心里就会一直知道“哪些是上游原样保留，哪些是我们自己加的”。对于共享机器和多人协作环境，这种边界意识会保护项目很多次。

#### 5.12 `README.md`：它是门口告示牌，不是整本教材

根 README 很重要，但你要用对它。它最适合承担的是“门口告示牌”的角色，也就是告诉后来者：这里是什么工作区，边界是什么，重资产放哪，核心路径怎么找，典型命令从哪进。它不适合直接承载所有教学任务，因为 README 必须相对短，必须适合第一次进门的人快速扫一眼。

所以如果学弟问“是不是把 README 看懂就够了”，更准确的回答应该是：README 是起点，不是终点。它负责把你带进门，而现在这些 `docs/Codex` 文档负责带你真正走路。

#### 5.13 `Makefile`：它更像快捷拨号盘，不是秘密控制中心

有些新人看到 `Makefile` 会莫名紧张，觉得里面一定藏着整个项目的核心逻辑。其实对当前工作区来说，`Makefile` 更像快捷拨号盘。它把一些常用动作，比如环境初始化、环境检查、数据下载、数据链接、smoke 入口，整理成更短的命令，方便你少打字、少记长命令。

这种设计当然很实用，但也要防止另一个误区：不要把 `make xxx` 当成魔法。你最好始终知道它最终调的还是哪些脚本。这样以后出问题时，你就不会被隐藏的调用关系蒙住。

#### 5.14 根目录这张图，最终要在你脑子里变成什么样

如果把上面这些目录都压成一句很朴素的话，那么当前根目录其实在做三件事：给你一个稳定门面，给你一个干净边界，给你一个容易带人的讲法。门面体现在你总能从 `/home/howard/Splat-Nav` 进入项目；边界体现在 wrapper、上游、文档、结果、第三方之间没有硬糊在一起；带人的讲法体现在你可以很自然地从根目录出发，往 `docs`、`scripts`、`runs`、`splatnav-official` 四个方向展开。

到了这里，你应该已经能感觉到，项目结构不是为了好看，而是为了降低未来每一次解释、每一次排错、每一次交接的成本。真正好的结构，第一天可能不觉得华丽，但一个月以后你会开始非常感谢它。

### 6、把 wrapper 层真正讲透：这些脚本不是散兵游勇，而是一条工程主线

如果你已经接受了“`scripts/` 不是论文算法本体，但又是你每天最常接触的一层”，那么下一步就不能只停留在“我知道有这个目录”了。你要继续往前走，真正把 wrapper 层看成一条有主次、有入口、有顺序的工程主线。很多同学之所以会觉得 `scripts/` 零碎，是因为他是按文件名一个个偶遇这些脚本，而不是按项目任务流去理解它们。

更顺的视角是：这些脚本并不是各自为政，它们是在回答六类固定问题。第一，环境怎么搭和怎么查。第二，数据和资产怎么准备。第三，最小 smoke 怎么起。第四，正式 batch 和 overnight 怎么组织。第五，结果怎么汇总和可视化。第六，上游源码和当前 wrapper 的关系怎么保持清楚。你只要按这个视角看，脚本层就不再像工具箱，而更像一条有序的生产线。

#### 6.1 先讲一个总原则：wrapper 脚本最重要的价值，是把“重复但容易出错”的事情固定下来

为什么工程里总喜欢写 wrapper？因为真正消耗人的，往往不是那些你只做一次的大难题，而是那些你每周都要重复做、但每次稍不注意就会出问题的动作。比如环境激活到底是不是同一个、`LD_LIBRARY_PATH` 要不要清、run 目录有没有按规范创建、命令有没有被落到 `cmd.txt`、日志有没有被保存在 `stdout.log`、批跑结果有没有顺手生成图和摘要。这些事单独看都不难，但一旦要重复做十次、二十次，就非常容易出错。

wrapper 脚本的价值，就是把这些动作写成默认行为。这样你以后不是靠记忆去完成这些步骤，而是靠脚本去托底。这一点对新人尤其关键。因为新人最怕的不是复杂，而是每一步都不确定自己有没有漏掉什么。wrapper 的存在，恰恰是在把这种不确定性降下来。

#### 6.2 环境组脚本：它们负责回答“这台机器上到底怎么开始”

当前工作区里，最先应该被学弟认识的一组脚本，是环境相关脚本。不是因为环境比算法高级，而是因为它们决定你后面所有动作有没有地基。对机械转代码背景的同学来说，这一组脚本越早讲清，心里越稳。

##### 6.2.1 `scripts/bootstrap_env.sh`：为什么它不只是“装包脚本”

如果你只从名字看，`bootstrap_env.sh` 很容易被理解成“一个把依赖装上去的脚本”。这样理解只说对了一半。它真正的重要性在于，它把当前项目在这台共享工控机上的环境边界写成了默认策略。脚本里明确把 Conda 根放在 `/data/howard/miniconda3`，把临时目录和 pip 缓存也放到 `/data/howard/splatnav/...`，然后在这个边界内创建或复用 `splatnav` 环境。它安装的依赖里既有 Nerfstudio，也有 `clarabel`、`cvxpy`、`dijkstra3d`、`open3d`、`viser`、LightGlue 这些当前上游代码会直接或间接用到的包。

换句话说，这个脚本不是在粗暴地“把一堆包塞进系统里”，而是在明确地说：我们只在自己的 Conda 小环境里解决问题，不碰系统 CUDA，不碰别人账户的环境，不把缓存乱堆到系统盘。这种克制本身就是工程能力的一部分。学弟如果能从第一天就建立这种边界感，后面会少走很多弯路。

##### 6.2.2 `scripts/env_health_check.sh`：为什么“环境搭好”不能靠感觉宣布

很多人一旦看到 `pip install` 结束，就会忍不住说“环境应该差不多了”。这是最常见的幻觉之一。真正稳妥的做法，是让环境自己出示证据。`env_health_check.sh` 做的正是这件事。它会打印系统信息、GPU 信息、Python 版本、Torch CUDA 状态，并进一步尝试 import 关键依赖模块。这样你就能分清楚：是安装阶段出了问题，还是运行时链接有问题，还是某个包虽然装了但不能正常 import。

这对新人极其重要。因为一旦没有这一步，你后面所有 smoke 失败都可能被误判成算法问题。可实际上，很多“算法没跑起来”的事故，根本还停留在环境层。这个脚本的价值，就是帮你把这一层先排干净。

##### 6.2.3 `scripts/fix_torch_cuda.sh`：为什么它体现的是“只在自己边界内修复”

这个脚本从名字看也很直接，但它背后的工程态度值得学弟记一记。它不是去升级整机 CUDA，更不是碰显卡驱动，而是在当前 Conda 环境内重装一个和现有驱动兼容的 PyTorch CUDA 运行时版本。也就是说，它修的是“我的小环境里 Torch 跟当前机器的关系”，不是“整个机器的全局软件栈”。

对于共享机器来说，这种做法非常成熟。它承认自己要解决的问题是局部问题，就只在局部边界里动手。很多新手一遇到 CUDA 相关报错就很容易慌，脑子里只剩“是不是要升级 CUDA”。你越早知道并不是所有 CUDA 问题都要动系统层，就越不容易做出过度破坏性的决定。

#### 6.3 数据准备组脚本：它们在处理“论文给了数据，但真实下载没你想得那么顺”

对于第一次复现论文项目的同学来说，最容易低估的一件事，就是数据准备。很多人会想：作者不是给了 Google Drive 吗，那我下下来不就行了。现实往往没这么丝滑。网络波动、文件夹下载不完整、某些帧缺失、`transforms.json` 或 `sparse_pc.ply` 漏掉、训练输出和数据目录之间还要重新挂接，这些都是真实问题。当前 wrapper 里的这一组脚本，就是在替你处理这些“下载不是一句话”的现实。

##### 6.3.1 `scripts/download_official_data.sh`：它像统一下载入口，帮你把来源和落点说清

这份脚本的价值不在于它用了 `gdown`，而在于它把“从哪里下载、下载到哪里、在什么环境里执行”这三件事固定了下来。你以后做复盘时，也更容易说清：数据是按官方给出的 Google Drive 来源下载的，落在数据盘指定目录，而不是散落在 home 目录、浏览器默认下载目录或某个临时文件夹里。

这种可追踪性对新人非常重要。因为很多人第一次复现时最大的混乱，不是代码，而是“我到底从哪下的、下到了哪、这个目录是不是完整的”。统一入口恰恰就是在减少这种混乱。

##### 6.3.2 `scripts/link_official_assets.sh`：为什么软链接比复制更像成熟工程

这个脚本做的事情特别值得讲，因为它把“上游默认目录结构”和“本机真实资产存放策略”优雅地接起来了。它会把数据盘里的 `training/data`、`training/outputs`、`traj` 通过软链接接到上游仓库期望的位置。这样你既不需要真的复制出两大份重资产，也不用为了一次复现去魔改上游源码里写死的相对路径逻辑。

这其实就是工程里非常经典的一类操作：尽量不改上游假设，而是在外围把环境整理成它能接受的样子。学弟如果能理解这一点，后面读更大的工程也会更顺。因为很多时候，高质量工程不是“把别人代码改得面目全非”，而是“在不破坏上游的前提下，把自己的接入层做漂亮”。

##### 6.3.3 `scripts/retry_gdown_folder.sh`、`fill_missing_scene_files.sh`、`pull_images2_full.sh`：为什么这些脚本听起来琐碎，却非常像真实项目

这三个脚本放在一起看，能很好地帮助学弟建立一种现实感。真实世界里的数据准备，往往不是一次命令就收工，而是要面对“不稳定但可补救”的状态。也就是说，下载过程不是全成全败，而是可能出现少数帧缺、关键文件缺、文件夹结构看着像到了但其实不完整的情况。

`retry_gdown_folder.sh` 更像“多次重试并按最低验收条件判断完整度”；`fill_missing_scene_files.sh` 更像“根据已有日志精确补洞”；`pull_images2_full.sh` 更像“针对已知的图片文件夹做多轮尝试直到达到最低数量门槛”。你不必把这几个脚本全背下来，但你应该通过它们学会一个成熟观念：很多工程问题不是重新来一遍，而是识别缺口、局部修补、用条件判断是否真正完整。

#### 6.4 run 管理与 tmux 组脚本：它们在回答“长任务怎么跑得像个工程，而不是像赌运气”

很多人初学时，脑海里只有一种运行方式：打开终端，敲命令，盯着输出。这样当然也能工作，但一旦任务需要几小时，或者你需要把日志和环境都留住，或者中途网络断了，或者你第二天还要复盘，就会很痛苦。当前工作区在这方面做得比较成熟，因为它把 run 目录规范和 tmux 绑定在了一起。

##### 6.4.1 `scripts/create_run_dir.sh`：为什么它是当前工程层的“证据生成器”

学弟一定要把这份脚本看得重一点。不是因为它长，而是因为它定义了“每次任务应该留下什么痕迹”。它会按 `runs/YYYY-MM-DD_HHMM_topic` 的命名规范建目录，同时自动生成 `env.txt`、`notes.md`、`cmd.txt` 和 `stdout.log`。你可以把它理解成一个实验记录起点。任何一次任务，只要先经过它，就不会是“跑过就算了”。

这背后其实是一种非常值得培养的职业习惯。科研也好，工程也好，真正能复盘的人，一定会让每次运行有最小证据集。以后你回看某次失败实验，不是只能靠模糊记忆想“当时好像跑的是那个命令”，而是能直接打开 `cmd.txt` 和 `env.txt` 看清楚。这个差距非常大。

##### 6.4.2 `scripts/run_in_tmux.sh`：它为什么值得你反复讲给学弟听

如果只能挑一个最能体现当前 wrapper 层价值的脚本，我会很愿意选 `run_in_tmux.sh`。原因不复杂：它把长任务管理、run 目录规范和日志沉淀三件事一次性绑在一起了。你给它一个窗口名、一个 topic 和一条命令，它会先帮你创建 run 目录，把命令记下来，生成 job 脚本，再把任务放到 `splatnav_jobs` 这个 tmux 会话的新窗口里执行，并通过 `tee` 把终端输出同步写进 `stdout.log`。

你稍微体会一下，就会发现这不是普通的“后台运行脚本”。它是在告诉你一套完整的工程态度：长任务应该进入 tmux，tmux 任务应该有统一 session，session 里的窗口应该和 run 目录绑定，run 目录里应该能反查命令和环境，日志应该自动落盘而不是指望手工复制。你以后如果进入大厂，会发现这种“把工程习惯封进工具”的思路无处不在。

##### 6.4.3 `scripts/watch_overnight_job.sh`：它在教你“工程要考虑失效恢复”

这个脚本很像守夜员，但它真正教会人的不是“晚上也有人盯着”，而是“成熟工程会显式考虑任务突然消失怎么办”。它会根据特定模式去找 overnight 进程，如果发现进程没了，就尝试重启。这里的关键，不是它一定能修好所有问题，而是它把“失效恢复”当成系统设计的一部分，而不是全靠人运气守着。

学弟第一次接触这种脚本时，最好顺势理解一个概念：自动恢复不是替代分析，而是降低脆弱性。它不能替你查清为什么挂，但它能避免一次中断直接让一整夜作废。这种思想，本身就是工程经验的一部分。

#### 6.5 执行链脚本：从最小 smoke 到正式批跑，工作区是怎样一步步放大规模的

这组脚本是学弟最应该建立顺序感的一组。因为它们几乎直接对应你的学习和实验路径：先 smoke，再 batch，再 overnight，再报告。你一旦把这个顺序走顺，项目推进会非常自然。你如果跳着来，反而更容易焦虑。

##### 6.5.1 `scripts/smoke_splatplan.py`：为什么说它是理解规划主链最好的第一入口

在所有执行链脚本里，`smoke_splatplan.py` 是最适合新人先啃的一份。因为它足够真实，又足够短。它已经具备一条完整规划链该有的关键结构：从命令行拿到 `--config`、`--scene`、`--method`、`--output`，根据场景预设组装机器人配置和体素配置，通过 `GSplatLoader` 读取模型，再根据方法名实例化 `SplatPlan` 或 `SafeFlightCorridor`，最后用一组固定起终点调用 `generate_path()`，把结果写进 JSON。

你只要真的把这份脚本看懂一次，项目里很多抽象概念都会落地。你会知道场景名不是空词，知道 `config.yml` 真的是模型入口，知道规划器构造时需要机器人参数和体素边界，知道输出并不只是一个轨迹数组，而是包含 `meta`、`device`、时间和规划结果的结构化对象。对新人来说，这种“缩微版的完整链路”价值极高。

##### 6.5.2 `scripts/run_splatplan_smoke.sh`：它在做什么规范化动作

如果说 `smoke_splatplan.py` 是主逻辑，那么 `run_splatplan_smoke.sh` 更像一个规范化启动器。它负责调用 `create_run_dir.sh`，生成输出 JSON 路径，把命令落进 `cmd.txt`，激活 `splatnav` 环境，清理 `LD_LIBRARY_PATH`，最后再真正调用 Python smoke 入口。它没有改变规划算法，但它把“如何正确地跑一次 smoke”固定成了统一步骤。

这类 shell 包装脚本非常值得新人认真看。因为它恰好处在“工程规范”和“算法入口”之间，是理解整个工作区为什么不乱的重要桥梁。

##### 6.5.3 `scripts/run_splatplan_smoke_tmux.sh`：为什么 smoke 也值得有 tmux 版本

有些同学会觉得 smoke 任务不是很短吗，为什么还要出个 tmux 版。这个问题问得很好。答案是：不是每次 smoke 都短到你愿意盯着，也不是每次网络都稳定到你敢把实验绑定在当前会话上。tmux 版的 smoke，其实是在延续同一种工程原则：只要任务值得保留日志和上下文，就尽量交给统一的 run + tmux 机制。

从教学角度看，这个脚本还很有帮助，因为它让你看见 wrapper 层是如何“层层复用”的。它并没有自己重写一套 tmux 管理，而是把命令进一步交给 `run_in_tmux.sh`。这种复用关系，就是工程结构感的体现。

##### 6.5.4 `scripts/run_official_style_batch.py`：为什么它是当前工作区最关键的正式实验入口

如果说 smoke 是最小验证，那么 `run_official_style_batch.py` 就是正式分析的起点。它会围绕场景预设生成一批起终点对，支持多个方法名，比如 `splatplan` 和 `sfc-1` 到 `sfc-4`，并在多次 trial 上重复调用同一规划器接口。更重要的是，它会把结果整理成适合后续汇总和可视化消费的 `batch_results.json`：里面不仅有方法级统计，还有部分保留的轨迹样本、每个 trial 的压缩输出、可行率、平均耗时和 P95 等信息。

这一份脚本特别值得你带着学弟慢慢读。因为它恰好体现了“工程化地尊重上游算法本体”。它没有重写 `SplatPlan` 的数学，而是在调用层面把输入、输出、统计和保存方式做了标准化。对未来想练大厂工程感的人来说，这种写法非常有代表性。

##### 6.5.5 `scripts/run_overnight_12h.sh`：为什么夜间任务本质上是在组织很多轮 batch，而不是在造另一套算法

新人很容易把 overnight 想得很神秘，仿佛一到了晚上，项目就切到了另一种模式。其实不是。`run_overnight_12h.sh` 的本质，是在给定时间窗口内重复发起正式 batch，每一轮都建自己的 run 目录、保存自己的 `batch_results.json`，并尝试顺手生成图表。它做的事情更像实验生产线调度，而不是算法创新。

理解这一点很重要。因为你以后会逐渐知道，很多“复杂实验系统”的本质，其实只是把基础单元组织得更稳了。overnight 之所以有价值，不是因为它玄乎，而是因为它让“多轮实验 + 自动落盘 + 次日可读”这件事变得低摩擦。

##### 6.5.6 `scripts/post_overnight_report.sh`：为什么第二天早上应该看到的是报告，不是一堆零散 run 目录

夜间任务最怕的是什么？不是某一轮失败，而是第二天早上你打开 `runs/`，只看到几十个目录，不知道该先看哪个、该看什么。`post_overnight_report.sh` 的价值就是避免这种局面。它会等 overnight 任务结束，再调用聚合脚本，产出 CSV、Markdown 和稳定软链接。这样第二天的人不会面对“目录山”，而是先面对一份总报告。

这背后是一种很贴近实际工作节奏的思路：结果不只是为了存在，还要为了被人消费。你以后做周报、做组会、带学弟，都会很需要这种思维。

#### 6.6 结果消费组脚本：为什么“会看结果”本身就是能力

很多新人以为项目能力主要体现在会不会把程序跑起来。其实再往前走一步你就会发现，真正稀缺的能力之一是“会看结果”。当前 wrapper 里负责这个部分的脚本，虽然不直接参与规划，但对项目推进同样重要。

##### 6.6.1 `scripts/visualize_batch_results.py`：它在把 JSON 翻译成更容易汇报的语言

这份脚本会把 `batch_results.json` 里的内容进一步做成可视化图和简要 Markdown 摘要。比如不同方法的可行率柱状图、规划时间箱线图、示例轨迹的 XY 叠图。它存在的意义，不只是好看，而是把原本需要你盯着 JSON 逐项解释的内容，翻译成了更适合人眼和汇报的形式。

学弟越早理解这点越好。因为实验的终点从来不是一个 JSON 文件，而是“你能不能把 JSON 里的信息讲给别人听”。可视化脚本其实就是在帮助你完成这种翻译。

##### 6.6.2 `scripts/aggregate_batch_runs.py`：它在告诉你，跨 run 的比较才是正式实验真正的视角

单次 batch 很重要，但如果你的实验要持续很多轮，真正能支撑决策的往往是跨轮比较。`aggregate_batch_runs.py` 就是在做这件事。它会去收集匹配场景名的多个 `batch_results.json`，按方法和 iteration 汇总成 CSV、Markdown 和趋势图。这让你不再只盯着某一轮结果，而开始看整体稳定性、方法排序和夜间任务的收敛走势。

这对培养工程和研究判断都非常关键。因为真正靠谱的结论，通常不是建立在一次“看起来挺好”的 run 上，而是建立在多次记录一致指向某种趋势之上。

#### 6.7 同步维护脚本：它提醒你上游不是空气，wrapper 也不是孤岛

`sync_upstream.sh` 这类脚本，日常使用频率可能没有 smoke 和 batch 高，但它在概念上非常关键。它会帮你抓上游仓库的当前提交和分支状态，提醒你 wrapper 是建立在一个具体版本的上游之上的，而不是漂浮在空中。你如果以后开始做更多工程整理，就会越来越感受到这种版本感知的重要性。

因为一旦你不知道自己封装的是哪一版上游，后面别人问你“这个行为到底是原作者这样写的，还是你们外层后来改的”，你就很难说清楚。同步脚本存在的意义，就是帮你减少这种版本失忆。

### 7、从一条 smoke 命令出发，把调用链完整走一遍

讲到这里，如果还只是停留在“每个脚本大概干什么”，你对项目的掌握还不够稳。真正能让你脑子开始成型的，是把一条最小调用链完整走一遍。也就是说，不只是知道会调用哪些名字，而是知道命令从哪里进入、在哪里切层、什么时候从 wrapper 进入上游、什么时候再回到 run 目录落盘。

#### 7.1 先从 shell 层开始：命令不是凭空跑的

假设你用的是最常见的 smoke 入口之一，也就是 `scripts/run_splatplan_smoke.sh`。当你从 shell 层调用它时，第一件发生的事情不是规划，而是工程规范动作。脚本会检查参数够不够，会用 `create_run_dir.sh` 先建立当前 run 目录，再在里面准备输出 JSON 的路径，同时把你即将运行的命令记录到 `cmd.txt`。这意味着在真正执行规划之前，当前任务已经有了一个归档容器。

这一点非常值得你反复体会。因为很多项目出问题，不是因为算法错，而是因为命令和结果没有被绑定。你日后再找这次运行时，连它用的参数是什么都说不清。当前 wrapper 把这件事提前做了，所以它一开始就在为未来的复盘负责。

#### 7.2 环境切换发生在什么时候，为什么这一步必须显式写出来

继续往下走，shell 脚本会 `source /data/howard/miniconda3/etc/profile.d/conda.sh`，再 `conda activate splatnav`，同时显式清掉 `LD_LIBRARY_PATH`。这一步对新人非常关键，因为它意味着“我要用哪一个 Python、哪一套依赖、哪一套动态库解析规则”并不是空气，而是任务的一部分。工程上真正稳的做法，就是把这些前提写出来，而不是默默认定它们已经是对的。

你以后如果在日志里看到有些运行会故意 `env -u LD_LIBRARY_PATH python ...`，也不要觉得奇怪。这恰恰是在防止系统层的库解析污染当前 Conda 环境。对于共享机器，这是一种很常见也很成熟的克制做法。

#### 7.3 进入 Python 入口后，第一件事不是规划，而是找上游源码

进入 `scripts/smoke_splatplan.py` 后，很值得学弟注意的第一件事，是它先做了 `resolve_upstream_root()`。也就是说，它先去确认上游官方仓库实际在哪里，再通过 `sys.path.insert(0, ...)` 把上游路径插进来。这个细节特别值得理解，因为它充分说明：wrapper 工作区并不是把上游代码复制进自己脚本里，而是显式把上游当依赖导入。

这就是当前工作区“官方仓库保留原样 + 外层工程化封装”的设计哲学在代码层的直接体现。你未来做更复杂的工程时，也会很常遇到这种结构：自己的脚本层负责组织，核心实现仍然从依赖仓库导入。

#### 7.4 参数解析之后，scene preset 开始真正发挥作用

`smoke_splatplan.py` 里的 `SCENE_PRESETS` 是一个极其值得学弟重视的结构。因为它把论文实验里那些散落的场景特定参数，收拢成了一种可以复用的、本机可解释的配置表。里面不仅有 `radius`、`vmax`、`amax` 这些机器人相关参数，还有 `lower_bound`、`upper_bound`、`resolution` 这些体素空间边界，以及 `radius_config`、`mean_config` 这种用来构造起终点位置的参数。

你可以把 `scene preset` 理解成“论文场景在本机上的实验入口说明书”。它不是场景模型本身，却决定了你如何围绕这个场景发起实验。如果这一层你理解得很浅，后面就会经常困惑：为什么同样是 `old_union`，还要再有一堆边界、半径和分辨率参数。其实它们不是多余，而是把抽象场景落成可运行实验的必需条件。

#### 7.5 `GSplatLoader` 介入的那一刻，项目才真正接上“场景”

在 planner 构造前，脚本会先实例化 `GSplatLoader(config_path, device)`。这一步非常关键，因为它是整个规划链第一次真正接触具体场景表示的地方。你在文档里、论文里、README 里听过很多遍 Gaussian Splatting，可直到这里，它才从概念变成当前 Python 进程里的一组真实张量：均值、旋转、尺度、协方差、颜色、不透明度。

所以以后你只要问“这个项目到底是怎么把场景读进来的”，答案就该自然落到这里。它不是从某张地图图片读进来的，也不是从一个抽象接口突然蹦出来的，而是通过 `GSplatLoader` 把 Nerfstudio 训练产物接进了规划系统。

#### 7.6 planner 构造阶段：为什么同一个入口既能跑 `splatplan`，也能跑 `sfc-*`

接下来脚本会构造 `SplinePlanner`，再根据方法名决定实例化 `SplatPlan` 还是 `SafeFlightCorridor`。这一段对新人非常有启发，因为它让你看到一个好用的实验入口应该是什么样：同样的场景输入、同样的机器人参数和体素配置，通过不同 planner 类去跑，就能形成方法对比。

也正因为这一层结构清楚，wrapper 的 batch 脚本才能很自然地扩展到多方法比较。你未来做实验时，也应该逐渐培养这种思维：尽量让不同方法在统一的输入和落盘规范下被调用，这样比较才公平、结果才好看、后处理才不乱。

#### 7.7 真正进入 `generate_path()` 后，规划链开始像论文那样展开

当 `planner.generate_path(x, g)` 被调用时，当前任务才正式进入论文主链。以 `SplatPlan` 为例，`generate_path()` 的第一步是让 `GSplatVoxel` 生成可导航体素网格，并在其上做 A* 初始化。然后，它把初始化路径切成一段一段的 line segment，对每一段计算碰撞集合，再逐段构造多面体约束，最后把多面体序列交给 `SplinePlanner.optimize_b_spline()` 做平滑轨迹优化。

如果你把这条链真走明白一次，后面论文里很多抽象说法就不会再让你发虚。你会知道所谓“safety corridor”不是修辞，所谓“Bezier trajectory”也不是停留在图里，而是真的在 `spline_utils.py` 里通过 QP 去解的。代码一旦跟论文主张对应上，理解就会稳定很多。

#### 7.8 JSON 落盘阶段：算法输出为什么要被重新整理

`generate_path()` 返回的结果虽然已经有很多信息，但 wrapper 并不会就地停下。`smoke_splatplan.py` 还会把 `meta`、`device`、`plan_time_sec`、`start`、`goal` 和 `output` 一起写成结构化 JSON。这个动作很值得重视，因为它体现了工程层一个非常成熟的判断：原始算法输出是一回事，适合长期保存和后续消费的实验记录是另一回事。

也就是说，wrapper 在做的是“结果包装”。它没有篡改算法意义，但它让结果更适合被以后的人理解、检索和比较。对学弟来说，这一点非常值得学习。因为真正好的工程，从来不是“只要能 print 出来就行”，而是会认真设计结果对象该长什么样。

#### 7.9 如果你把这条链能口头讲出来，说明你已经真正开始会了

很多人喜欢用“我看懂了”来描述自己的进度，但更可靠的标准其实是：你能不能把一条最小调用链不用看代码、用自己的话讲出来。如果你现在已经能说清楚“shell 包装先建 run 目录，再激活环境，再调 Python 入口；Python 入口先找上游仓库，再根据 scene preset 和 `config.yml` 构造 planner；planner 再调 `generate_path()` 走 A*、碰撞集合、多面体和样条优化；最后结果被写成 JSON 并落进 run 目录”，那你就已经不是停留在文件浏览层了。

而一旦你过了这一关，后面的 batch、overnight、汇总和可视化，基本都是在这条最小链路上做规模放大和结果管理。项目会突然变得没那么神秘，这是一种非常明显的成长体验。

### 8、把上游源码树真正读出层次：不是所有目录都同等重要，但每个目录都在回答一个问题

到了这里，我们要正式进入 `splatnav-official/` 这一层。很多新人一到上游源码树就容易出现两种反应。一种是被目录多吓住，直接放弃，退回去只看 wrapper。另一种是过度兴奋，想一口气逐文件读完，结果越读越散。更合理的办法，是先把上游源码树按职责分层，再决定先读哪一层、后读哪一层。

你可以先接受一个现实：上游源码不是一本线性教材，它更像一个实验室里逐渐长出来的实现集合。里面有非常核心的主链文件，也有辅助可视化、基线比较、结果处理和定位实验工具。你的任务不是把它们平均用力，而是学会判断谁是主轴、谁是侧翼、谁是现在先知道存在就够了。

#### 8.1 先把最核心的一句话记住：上游源码树至少同时承载了五种东西

第一种，是规划核心实现，也就是 `Splat-Plan` 真正在哪里算路径、造多面体、解样条。第二种，是场景表示与几何工具，也就是 GSplat 怎么被加载、协方差怎么被处理、碰撞集合怎么被抽出来。第三种，是定位相关实现，也就是 `Splat-Loc` 所依赖的视觉与位姿估计链。第四种，是对比方法和实验入口，比如 `run_rrt.py`、`run_nerfnav.py`。第五种，是可视化、绘图和结果处理工具。

你如果先把这五类分开，再看目录名，就不容易被吓住。因为目录多并不代表结构乱，很多时候只是因为它把不同问题拆开了。

#### 8.2 `run_splatplan.py`：为什么说它像作者自己的实验工作台

我们前面已经简要提过这份文件，这里要把它讲得更细一点。`run_splatplan.py` 非常像作者自己的实验工作台。它里面有一整套围绕场景名切换的实验设定，包括 `old_union`、`stonehenge`、`statues`、`flight` 这些论文场景；也有稠密和稀疏 GSplat 模型的切换；还有机器人半径、速度、体素边界和分辨率等参数。接着，它会加载 GSplat、构造 `SplinePlanner`，再根据方法名实例化 `SplatPlan` 或 `SafeFlightCorridor`，最后围绕圆形轨迹上的多个起终点对循环做规划，并把结果保存到 `trajs/` 目录。

为什么我说它像实验工作台？因为它暴露得很直接，很少做“用户友好封装”。你能从里面明显感受到作者自己在调实验、对比方法、改场景参数时的使用方式。对新人来说，这种文件一开始看起来不如 wrapper 漂亮，但它反而非常有帮助，因为它让你看见论文作者原始的实验心智模型是什么。

#### 8.3 `run_splatloc.py`：它为什么不像规划入口那样短平快

`run_splatloc.py` 一眼看上去就比 `run_splatplan.py` 更厚重。原因很简单，定位问题在实现上本来就涉及更多模块：图像数据集、相机内参、RGB 观测、点云、特征匹配、全局配准、局部精配准、PnP、可能的递推估计等。它不是一条“给起点终点就生成轨迹”的单一链路，而是一条以感知和估计为核心的流水线。

这也是为什么我不建议零基础学弟第一周就扎进去硬啃。不是说它不重要，而是说它的认知压力会更大。更适合的节奏，是先知道它在总系统里负责什么，再随着项目推进逐步把 `pose_estimator/utils.py` 和 `ns_utils/nerfstudio_utils.py` 这些支撑文件拆开读。

#### 8.4 `SFC/` 目录：它不只是一个 baseline 文件夹，而是一整个“安全走廊家族”

很多人第一次看到 `SFC/`，会很自然地以为它只是放一个 baseline 实现。实际上，它比“单个 baseline”更像一组围绕安全飞行走廊思想组织起来的工具模块。`corridor_utils.py` 是核心，它定义了 `Corridor` 抽象基类和 `SafeFlightCorridor` 具体实现，负责不同 `mode` 下的初始化、碰撞集合和多面体生成逻辑。`astar_utils.py`、`helper_utils.py`、`viz_utils.py` 则分别承担初始化搜索、几何辅助和可视化支持。

这一组代码非常适合学弟去理解“baseline 为什么不是一句名字”。论文里写 `sfc-1` 到 `sfc-4`，你如果只是把它们当成四个标签，理解会很浅。读过 `SFC/corridor_utils.py` 以后，你会知道这些 mode 在初始化网格、碰撞集合类型和安全缓冲策略上都真的有区别。这样你以后看实验结果时，就不会只会说“某个 baseline 好像更强”，而能说清它强弱背后的结构原因。

#### 8.5 `splat/` 目录：为什么说这里是“场景入口层”

`Splat-Plan` 再核心，也不能脱离场景表示自己工作。`splat/` 目录的意义就在这里。它主要回答一个基础但关键的问题：当前项目如何把一个 Gaussian Splatting 场景读成后续模块能用的数据结构。`splat_utils.py` 里的 `GSplatLoader` 就是这层的主角。

当你真正去看它的实现时，会发现它做的事情其实很朴素但很关键：根据输入是 `json` 还是 Nerfstudio `config.yml`，走不同加载流程；把场景中的均值、旋转、尺度、协方差、颜色和不透明度整理成统一属性；必要时还能把 GSplat 转成 mesh 供可视化使用。你以后只要问“规划器到底在处理什么几何对象”，都绕不过这一层。

#### 8.6 `splatplan/` 目录：这是真正该反复读、反复讲、反复对照论文的一层

如果让我给学弟在上游源码里只挑一个最值得深耕的目录，那一定是 `splatplan/`。因为这里就是论文核心主张的主要落点。`splatplan.py` 负责从初始化路径到碰撞集合、多面体约束再到最终轨迹的整体流程组织；`spline_utils.py` 负责把多段多面体约束转换为样条优化问题，并调用 `clarabel` 或 `cvxpy` 相关求解流程求出轨迹系数。

一个很实用的建议是：你第一次读 `splatplan.py` 时，不要试图逐行证明，而要先把函数里的阶段划分看清。第二次再回来看 `get_polytope_from_outputs()`，理解它是怎么从碰撞集合和交点信息生成半空间约束的。第三次再去读 `spline_utils.py`，理解为什么这些多面体最终会变成一个带等式、带不等式、带二次目标项的 QP。这样读法会比一开始就死抠矩阵舒服很多。

#### 8.7 `initialization/` 目录：它在处理“先给我一条能走的种子路径”

规划里很容易被忽视的一层，是初始化。很多人张口就是优化、约束、多面体，好像一切都从目标函数开始。其实不是。`initialization/` 目录提醒你，真正的规划往往先要有一条粗路径，再围绕它做后续几何与优化处理。`grid_utils.py` 里定义了 `Voxel`、`PointCloudVoxel` 和 `GSplatVoxel`，它们负责把场景离散成可导航网格，处理占据情况，并在需要时把起点或终点投影到最近可导航位置。`astar_utils.py` 则负责底层的 A* 搜索。

这一层对新人特别有启发，因为它让你看到：规划不是从连续优化凭空起步的，而是先通过离散网格建立可行的骨架路线。你以后再听到“hybrid planning”之类的词，也会更容易理解，因为你已经在当前项目里亲眼见过离散初始化和连续优化是怎么接上的。

#### 8.8 `polytopes/` 目录：它为什么是理解安全性的真正几何后院

如果说 `splatplan/` 是主舞台，那么 `polytopes/` 更像后台真正控制几何约束生成的地方。这里有 `collision_set.py`、`decomposition.py`、`polytopes_utils.py`、`connectivity_utils.py` 等文件，负责从路径段出发，抽取可能碰撞的几何基元，形成边界约束，并做半空间表示和相关辅助计算。

对新人来说，最值得先读的是 `collision_set.py`。因为它比较直接地把“碰撞集合”这件事展开了：根据路径段先构造一个包围盒，然后判断哪些点云点或哪些高斯椭球与这个包围盒相关，把这些相关对象打包返回。你只要把这一步理解清楚，后面再去看多面体生成，就不会觉得它像在凭空造约束。

#### 8.9 `ellipsoids/` 目录：为什么高斯不是抽象云团，而是会变成可算几何对象

GSplat 听起来像图形表示，但在规划里它要能变成可计算几何对象。`ellipsoids/` 目录做的正是这种翻译工作。这里有协方差相关工具、相交测试、mesh 构造、椭球采样等函数。比如 `covariance_utils.py` 会处理旋转和尺度到协方差的关系，`intersection_utils.py` 会参与线性运动与椭球相交的计算，`mesh_utils.py` 能把 GSplat 场景生成可视化 mesh。

你如果以后要向别人解释“为什么论文说高斯约束是数学严格的”，这层会非常重要。因为它在代码里把高斯从视觉对象变成了碰撞检测和半空间构造的几何基础。

#### 8.10 `ns_utils/` 目录：它是项目和 Nerfstudio 世界连接的接口层

上游 README 已经明确说这个仓库建立在 Nerfstudio 之上，所以你在源码里看到 `ns_utils/` 一点也不奇怪。这里的关键文件是 `nerfstudio_utils.py`，其中的 `GaussianSplat` 类和数据集加载函数承担了“把 Nerfstudio 训练输出和数据解析结果转成当前项目可用对象”的角色。你可以把它想成一座桥：一头连着 Nerfstudio 的训练与数据解析世界，一头连着当前项目的规划与定位世界。

这一层对学弟非常关键，因为它解释了为什么 `config.yml` 会如此重要。`config.yml` 不是某个普通参数文件，而是把你带回 Nerfstudio 训练结果上下文的入口。没有这层桥梁，规划器和定位器都不知道该去哪里拿模型和数据。

#### 8.11 `pose_estimator/` 目录：它让你看见 `Splat-Loc` 不是一句名字，而是一整套视觉与几何流水线

如果说 `Splat-Loc` 在宏观上代表定位模块，那么 `pose_estimator/` 就是在微观上把定位真正做出来的地方。`utils.py` 里面你会看到一大串看起来跨度很大的工具：SIFT、ORB、LightGlue、RANSAC、ICP、颜色 ICP、PnP、SE(3) 和李代数相关操作、甚至一些递推估计和 sigma points 相关函数。这种密度很容易把新人吓住，但你换个角度就会好很多。

更顺的理解是：定位本来就要同时面对视觉特征、几何配准和位姿表示这几类问题，所以工具会多是正常的。你不需要第一周就把这里的每一个函数都吃透，但至少应该知道它们是定位链路的工具箱，而不是和主项目无关的杂项。

#### 8.12 `nerfnav/` 目录与 `run_nerfnav.py`：它们在提醒你论文作者认真对比了另一条技术路线

很多新人一读当前项目，很容易把视线完全集中在 GSplat 世界。这样虽然自然，但也会漏掉论文很重要的一部分背景：作者不是只证明自己的方法能跑，还拿它和一类 NeRF 导航方法做了比较。`nerfnav/` 目录和 `run_nerfnav.py` 就是在源码层保留了这种对比路线。

你以后做汇报时，这一层很有帮助。因为它提醒你 Splat-Nav 的价值不只是“能规划”，而是“在 GSplat 表示上做规划与定位，有机会比 NeRF-based 导航更实时”。至于第一阶段要不要深入这里，答案是不急。但你要知道它存在，而且它不是装饰。

#### 8.13 `run_rrt.py`：它在让经典采样法也进入实验比较视野

和 `run_nerfnav.py` 一样，`run_rrt.py` 也在提醒你：好的论文不会只和自己说话，而是会把经典方法拉进来对比。RRT 这类方法对机器人规划读者来说并不陌生，上游把它单独保留为实验入口，本质上是在支持横向比较。

对学弟来说，这有两个好处。第一，它帮助你建立一点研究感，知道方法评价从来不是自说自话。第二，它也帮你理解当前 wrapper 为什么优先聚焦 `splatplan` 和 `sfc-*`。因为这两类方法与当前离线仿真链的结构更近，更适合作为第一阶段的对比主线。

#### 8.14 `visualize.py`、`blender/`、`plotting/`、`results/`：它们在负责“怎么把实验讲出去”

上游源码里并不只有“怎么算”，还有一整层是“怎么算完以后怎么展示”。`visualize.py` 会用 viser 加载 GSplat、mesh、体素和轨迹，支持交互式查看。`blender/` 更偏离线渲染和视频相关的辅助可视化。`plotting/` 与 `results/` 则更偏统计结果的处理和图表生成。

这类目录在新人眼里很容易被当成可有可无，但它们其实很重要。因为一个项目如果只会产出数字，不会把结果讲给别人听，它的传播能力和协作效率都会很受限。你以后做周报、组会、专利图、论文图，都会逐渐感受到这些“展示层工具”的价值。

### 9、把几个核心类讲成人话：你以后读代码时要知道自己在看谁扮演什么角色

目录知道了，还不够。很多人真正卡住的，是一打开代码，满眼都是类和函数名，根本不知道自己该把谁当主角。这里我们把最关键的几个类和函数，用一种更接近“老师在白板前讲角色分工”的方式讲明白。

#### 9.1 `GSplatLoader`：它像把场景搬进房间的人

如果把整个规划问题想成在一个房间里工作，那么 `GSplatLoader` 就像把房间本身搬进来的人。没有它，后面的 `SplatPlan`、`SafeFlightCorridor`、`GSplatVoxel` 都无从谈起。它把 `config.yml` 背后的模型状态读出来，整理成统一属性，让其他模块能够直接使用高斯的均值、旋转、尺度和协方差。

你以后读到哪里一旦看见 `GSplatLoader(config_path, device)`，脑子里就应该很自然地浮现一句话：好，场景现在要进内存了，后面的规划和几何模块终于有对象可以处理了。这个角色感一旦建立，代码会好懂很多。

#### 9.2 `GSplatVoxel`：它像把连续场景压成“先走得起来”的离散骨架

`GSplatVoxel` 的价值，在于它让连续、复杂、密度很高的 GSplat 场景，变成了一个可以做网格搜索的离散工作空间。它会根据边界和分辨率建立网格中心，利用高斯包围盒等信息去判断哪些体素不可通行，并在需要时把起点和终点投影到最近可导航位置。最后，A* 就能在这个离散空间里跑起来。

所以你以后如果觉得论文里“先初始化一条路径再做精细规划”很抽象，就回到这里想。`GSplatVoxel` 就是在提供那条粗骨架。它不负责最终优美轨迹，但它保证你不是从一片完全连续的未知空间直接跳进优化器里。

#### 9.3 `GSplatCollisionSet` 和 `PointCloudCollisionSet`：它们像两种不同口味的“相关障碍提取器”

这两个类很适合放在一起理解。它们都继承自 `CollisionSet`，都在回答一个共同问题：对于当前路径的一段，哪些障碍物最相关，值得拿来构造约束。不同之处在于，`PointCloudCollisionSet` 更像在点云或点采样层面工作，而 `GSplatCollisionSet` 更像直接在高斯椭球层面工作。

这就是为什么你在 `sfc-*` 不同 mode 里会看到它们以不同方式出现。某些 baseline 更依赖点云式近似，某些则更直接围绕 GSplat 椭球做处理。你把这层理解清楚，以后看不同方法的安全性和可行率差异，就会更有感觉。

#### 9.4 `SafeFlightCorridor`：它像“先搭走廊，再从走廊中取轨迹”的家族总管

`SafeFlightCorridor` 不只是单个 baseline 类，它更像一整个家族总管。通过 mode 切换，它把几种安全走廊策略收在同一接口下。它会先做初始化路径，再针对每一段提碰撞集合，再生成对应多面体，最后同样调用样条规划器生成轨迹。你可以把它看成“多种 SFC 变体的统一外壳”。

这层统一外壳很重要，因为它让方法比较变得整齐。你以后不必每次都在脑子里重新记一套 completely different 的接口，而只需记住：`sfc-1` 到 `sfc-4` 是同一家族里不同的几何与安全缓冲策略。

#### 9.5 `SplatPlan`：它是当前阶段你最该反复结交的主角

如果你未来一个月只能和一个类建立真正熟悉的关系，我会建议你选 `SplatPlan`。原因很简单：它是当前离线/仿真复现主线里的算法核心主角。它串起了 `GSplatVoxel`、`GSplatCollisionSet`、多面体生成和 `SplinePlanner`。你只要把它的主流程掌握扎实，项目最重要的“输入怎么变成输出”就已经抓住了大半。

更重要的是，这个类的结构很适合教学。`__init__` 里主要是把场景、机器人参数、环境参数和样条规划器绑在一起；`generate_path()` 里则显式地走完初始化、碰撞集合、多面体和优化四步。对新人来说，这种“骨架清楚”的类特别适合作为主学习对象。

#### 9.6 `SplinePlanner`：它像一个把“安全区域”翻译成“平滑轨迹”的数学翻译官

很多新人一看到 `SplinePlanner` 会本能地害怕，因为这里会出现 `cvxpy`、`clarabel`、矩阵块拼接、等式约束和不等式约束。其实你先别急着怕。更好的理解是：前面多面体阶段给你的，是“每一段轨迹大概必须待在什么安全区域里”；`SplinePlanner` 做的，是把这些区域约束和首尾点约束组织起来，求出一条真正连续、平滑、满足连接条件的样条轨迹。

也就是说，它不是另起炉灶，而是在给前面几何阶段“翻译成人能用的轨迹”。你一旦把这个角色感抓住，读 `spline_utils.py` 时心态会好很多。你不是在看一份无缘无故的优化作业，而是在看项目最后一公里如何被数学化。

### 10、把论文主张和代码落点一一配对：以后你做汇报时就不会空讲

很多同学读论文时容易出现一种状态：内容大概懂了，可一旦要回到代码或做汇报，就会变空。嘴里都是论文里的漂亮词，但一说到“你本机上哪里体现了这件事”，就停住了。这一节的目标，就是帮你把几组最关键的论文主张和代码落点配对起来。以后你讲项目时，能做到“说一句论文主张，就能顺手指出代码在哪”。这会让你的表达质量立刻提升。

#### 10.1 “GSplat 作为环境表示”对应哪里

这条主张最直接的代码落点，就是 `ns_utils/nerfstudio_utils.py` 和 `splat/splat_utils.py`。前者把 Nerfstudio 世界的模型和数据接口接进来，后者通过 `GSplatLoader` 把它们整理成当前规划和定位能直接使用的张量属性。你以后如果要用大白话解释，就可以说：论文里说用 Gaussian Splatting 表示环境，落到代码上就是先把 Nerfstudio 训练出来的 GSplat 模型通过 `config.yml` 读进来，再把高斯属性变成可供后续规划和定位使用的数据结构。

这个说法很重要，因为它把“环境表示”从抽象概念翻译成了实际输入链路。你不会再只会说“这是 3DGS”，而会知道当前项目到底是怎么用它的。

#### 10.2 “安全走廊”对应哪里

这条主张最核心的落点，是 `SFC/corridor_utils.py` 和 `splatplan/splatplan.py` 里对多面体约束的生成流程。尤其是 `generate_path()` 和 `get_polytope_from_outputs()` 这一类函数。你如果要讲得更白一点，可以说：所谓安全走廊，不是把障碍物画出来那么简单，而是把沿路径段相关的障碍抽出来，逐段构造成一组半空间约束，从而得到机器人中心可以安全通过的多面体走廊。

一旦你能这样讲，听的人就会明显感觉你不是只背了个术语，而是真知道它在代码里怎么活着。

#### 10.3 “Bezier 或样条轨迹”对应哪里

这个落点主要在 `splatplan/spline_utils.py`。那里有时间基函数、导数矩阵、等式约束、不等式约束和二次目标项的构建，然后再用求解器算出轨迹系数。这里你不必执着于“论文里写 Bezier，我代码里看到的是 B-spline 命名，到底怎么说才完全精确”这种细枝末节。对入门阶段更重要的是抓住本质：前面几何阶段给出安全区域，后面样条优化阶段把安全区域转成一条真正平滑、可执行的轨迹。

你以后做汇报时完全可以这样讲，而且这比只说“这里用了优化器”要强得多。

#### 10.4 “实时性”对应哪里

这条主张最容易被讲空。因为一提实时性，很多人就只会复述论文或 README 里的数字。更好的做法，是把它拆成两层。算法层面，实时性对应规划与定位链路的求解组织方式，以及 CPU/GPU 负载分工；工程层面，当前工作区对实时性的落地则体现在 wrapper 把多轮实验、结果保存和可视化整理得足够顺，使你能快速重复调用和快速回看结果。

所以在当前阶段，你完全可以把“实时性”解释成：上游算法设计追求实时级导航，而本地 wrapper 负责把这套算法以低摩擦、可复盘的方式组织成可重复实验。这样讲，比空背一个“快”字要成熟得多。

#### 10.5 “定位模块只靠 RGB 图像”对应哪里

这条主张的主要落点，是 `run_splatloc.py` 配合 `pose_estimator/utils.py` 和 `ns_utils/nerfstudio_utils.py`。其中前者组织定位实验流程，后者提供视觉特征、PnP、配准和位姿表示相关工具，再结合 GSplat 场景和数据集图像完成定位任务。当前阶段你不一定要把这条链读透，但你至少应该知道，论文不是只说了一个定位名字，而是已经在上游代码里给出了完整入口和工具支撑。

这会让你以后讲项目全景时不至于只剩规划半边。

#### 10.6 “对比 NeRF 导航和经典规划方法”对应哪里

这条主张落在 `run_nerfnav.py` 和 `run_rrt.py`。它们提醒你：论文不是把自己的方法孤零零摆出来，而是和至少两条不同技术路线进行比较，一条偏 NeRF-based 导航，一条偏经典采样式规划。你在做全景介绍时，只要轻轻点出这两个入口，就已经足够让听众意识到这篇工作在研究比较上的完整度。

对学弟来说，这还会自然地培养一个很有价值的习惯：以后读论文时，不要只看自己方法的主图，也要留意它到底和谁比、为什么这么比、代码里有没有留下这些对比入口。

### 11、把输入资产和场景配置讲透：为什么一个 `config.yml` 背后站着一整棵目录树

学弟第一次接触这个项目时，常常会被一个现象困住：为什么命令里常常只传一个 `config.yml`，可大家又总在谈 `data/`、`outputs/`、`transforms.json`、`images/`、`sparse_pc.ply`、`dataparser_transforms.json` 这些东西。看起来好像有很多入口，实际又似乎都绕到同一个地方。这里最需要建立的，是“单个文件入口”和“背后整棵资产树”之间的关系意识。

#### 11.1 `config.yml` 像门把手，不像整间屋子

如果你以后只能记住一句关于 `config.yml` 的比喻，我希望你记住这个：它像门把手，不像整间屋子。你在命令里传它，是因为脚本要通过它进入某个训练输出目录，并进一步找到模型、数据解析信息和相关场景上下文。也就是说，`config.yml` 自己不是全部资产，但它是打开资产世界最方便的手柄。

这也是为什么很多文档和脚本都把它当成最核心输入。因为从执行入口设计来看，传一个稳定的配置入口，远比让用户同时传十个文件路径要清晰得多。但你千万不要因此误以为“有了 config 就万事大吉”。它背后真正站着的，是一整套数据、模型和变换关系。

#### 11.2 `data/` 和 `outputs/` 为什么要同时存在

上游 README 其实已经给过一个非常重要的暗示：训练数据在 `data/`，训练输出在 `outputs/`。这两个目录经常被新人混成一个“大场景目录”，但它们站在完全不同的阶段。`data/` 更像原料区，里面放图像、`transforms.json` 以及数据解析所需的原始内容；`outputs/` 更像生产结果区，里面放的是训练出来的模型及其配置，比如 `splatfacto/.../config.yml` 和 `nerfstudio_models`。

对当前项目来说，这个区分特别重要。因为规划和定位真正直接接触的往往是训练输出入口，而不是原始图像文件本身。可训练输出之所以有意义，又离不开 `data/` 提供的数据来源和解析上下文。你一旦把这两者分清，后面看资产软链接和目录组织就不会糊。

#### 11.3 `transforms.json`、`dataparser_transforms.json`、`config.yml`：三者为什么都重要，但职责不同

这三个名字很容易把人绕晕，尤其是对第一次接触 Nerfstudio 生态的同学。更顺的记法是：`transforms.json` 更接近数据解析输入，告诉系统图像与相机位姿等基础信息；`dataparser_transforms.json` 更接近训练过程中对数据坐标关系的进一步整理；`config.yml` 则是训练输出入口，能把你带回整套训练产物和模型状态。

换句话说，它们不是互相替代的三个版本，而是处在链路不同位置的三个文件。你以后只要带着“一个偏原始数据解析，一个偏解析后的变换结果，一个偏训练产物入口”这个思路去看，就会顺很多。

#### 11.4 `images/`、`images2`、`images_2` 这些名字为什么总让人紧张

这类名字的混乱感，几乎是所有新手都会有的。因为它们看起来只差一个数字或下划线，可背后可能对应完全不同的数据子集或场景版本。面对这种情况，最好的习惯不是靠猜，而是回到两个锚点：一是目录实际包含多少帧、哪些关键文件；二是当前 `config.yml` 到底指向哪一套资产。

所以当你看到 `images2` 相关脚本时，不要只把它当成“另一组图片”。更成熟的理解是：这往往代表作者或当前工作区在处理特定场景变体时的一套数据入口。你必须把它和具体配置路径绑定起来看，才能避免混乱。

#### 11.5 `sparse_pc.ply` 为什么会反复出现在补数据脚本里

对新人来说，`sparse_pc.ply` 很容易被当成一个不太重要的辅助文件。但从当前工作区的数据补齐脚本设计来看，它恰恰是完整性判断的重要条件之一。这说明什么？说明这份文件在上游链路里并不是装饰，而是很多场景资产完整度的一部分。你如果把它漏掉，很可能会导致某些流程虽然表面还能跑，实际上上下文已经不完整。

所以你以后看数据准备脚本时，不妨换个角度：不是在看“作者怎么这么麻烦”，而是在看“项目真正依赖哪些最小资产集合”。这是非常有价值的工程敏感度。

### 12、再往前一步：一次规划从输入到输出，文件夹之间到底怎么传递信息

前面我们已经讲过数据流的大骨架，但这里要再落细一点。因为很多新人虽然能复述“`config.yml` 进来，结果落到 `runs/`”，可一旦被追问“中间哪一层起什么作用”，就又发虚了。现在我们把这件事说得更细一点，而且尽量贴近你日后真实会看到的文件。

#### 12.1 输入层：命令行参数把哪几类信息带进系统

在当前工作区最典型的执行入口里，命令行参数至少会携带四类信息。第一类是场景入口信息，比如 `--config` 和 `--scene`。第二类是方法选择信息，比如 `--method splatplan` 或 `--method sfc-3`。第三类是实验规模信息，比如 `--trials`、`--seed`、`--keep_traj_limit`。第四类是输出落盘信息，比如 `--output` 或 `--output_dir`。

这四类信息加在一起，才构成一次真正完整的实验调用。你如果只盯着其中一类，比如只记场景路径，不记方法名和输出路径，理解就会偏。学弟越早形成这种“输入是分层的”意识，后面排错越稳。

#### 12.2 配置层：scene preset 和 `config.yml` 是怎样互补的

上面说的四类输入里，最容易被误会的一对就是 scene preset 和 `config.yml`。它们不是重复输入，而是互补输入。`config.yml` 决定你进的是哪一个训练场景模型，scene preset 决定你围绕这个场景怎么摆实验：机器人半径多少、边界多大、体素分辨率多少、起终点怎样生成。

你可以把它们想成“模型入口”和“实验摆法”。少任何一边都不完整。只有把这两者拼在一起，当前规划链才真正具备可执行含义。

#### 12.3 构造层：为什么 planner 初始化阶段已经做了很多重活

很多新人会把真正的“计算”只理解成 `generate_path()` 那一步。其实在 planner 初始化阶段，就已经做了相当多的重活。比如 `GSplatLoader` 会把场景模型读成张量属性；`SplatPlan` 初始化时会构建 `GSplatCollisionSet` 和 `GSplatVoxel`；`SafeFlightCorridor` 在不同 mode 下也会构建不同形式的 voxel 和碰撞集合；`SplinePlanner` 还会准备时间基函数和后续优化会用到的结构。

这意味着什么？意味着你以后看运行耗时时，不能只盯着单次 `generate_path()`。有些准备工作在 planner 构造阶段就已经发生了。当前 batch 脚本之所以会单独记录 `load_time_sec`，就是因为它在明确区分“场景和 planner 构造成本”与“多次 trial 的纯规划成本”。这其实是很成熟的统计意识。

#### 12.4 执行层：一次 `generate_path()` 到底交换了哪些对象

当 `generate_path(x, g)` 被调用时，系统手里至少已经有了这些东西：当前场景的高斯表示、机器人动力学近似参数、体素边界、离散网格工具、碰撞集合工具和样条优化器。然后它会以 `x` 和 `g` 为新的任务输入，产生一组路径段、多面体集合、轨迹点列、可行性标志和时间统计。换句话说，它不是单纯输入两个点、输出一条线，而是在调用一整套已经配置好的规划器系统。

这个理解很关键，因为它能让你以后在解释代码时避免一种常见错误：把 planner 当成一个轻飘飘的函数，而忽略它其实是带着大量初始化上下文运行的对象。

#### 12.5 结果层：为什么当前工作区总在强调结构化输出

一次规划结果落盘后，当前工作区特别强调结构化输出。比如 smoke 会保存 `meta`、`device`、`plan_time_sec` 和 `output`；batch 会保存方法级统计和 trial 记录；可视化脚本再把这些结构化信息翻成图表；聚合脚本则继续把多轮 batch 翻成 CSV 和总报告。看起来好像多绕了几层，但这恰恰是在把“程序输出”升级成“项目记忆”。

你以后做周报时会很感谢这种结构化。因为它让你不是在原始终端截图里找信息，而是在已经有层次的结果文件中查信息。

### 13、学弟第一次读源码，最容易在哪里迷路

一个文档如果只讲正确路线，不讲容易迷路的地方，往往是不够实用的。这里我想故意讲一讲，学弟第一次进源码最容易在哪些地方失去方向。不是为了吓人，而是为了让你提前有点免疫力。

#### 13.1 迷路点一：把 wrapper 当上游，把上游当 wrapper

这是最常见的混淆。你明明在看 `scripts/run_official_style_batch.py` 这种 wrapper 文件，却以为自己已经进入论文算法核心；或者你明明在看 `splatplan/splatplan.py` 这种上游主逻辑，却又总是用“这个脚本会自动建 run 目录吗”之类的外层问题去要求它。出现这种错位，阅读就会非常别扭。

最好的补救方法很简单：每次打开文件前，先问自己一句，这个文件站在哪一层。只要层次先分出来，很多困惑会自然消失。

#### 13.2 迷路点二：看到很多参数，就以为自己必须一次全懂

像 `SCENE_PRESETS` 这样的结构，第一次看确实会让人有点压力，因为里面同时出现半径、速度、边界、分辨率、均值偏移等参数。很多新人一看到就想：完了，我是不是得先把每个参数的物理意义和数值来源全搞懂，才能继续看。其实不用。

更合理的做法，是先把参数按角色分组：哪些是机器人参数，哪些是空间边界，哪些是起终点生成参数。只要角色先分清，数值细节可以后面再慢慢压。读工程代码最怕的不是暂时有些数值没背下来，而是因为怕自己没全懂，就不敢继续往前走。

#### 13.3 迷路点三：一看见矩阵和优化就立刻失去耐心

这点尤其容易发生在 `spline_utils.py`。很多人前面都还看得挺顺，一到矩阵块、约束矩阵和求解器部分，立刻觉得太数学，整个人就抽离了。其实更稳的办法是，把这一层先看成“把前面的几何要求翻译成求解器语言”。只要这个角色先成立，后面每多看懂一块矩阵，都是在给这个翻译官加细节，而不是在硬吞陌生数学。

对数学稍微好一点、代码稍弱一点的同学来说，这里反而可能是你的优势区。你不一定一开始就写得出这些代码，但你是有机会把它背后的逻辑理解得很扎实的。

#### 13.4 迷路点四：误把一次成功运行当成“我已经完全会了”

这其实是另一个方向的风险。很多同学第一次 smoke 成功以后，会短暂产生一种幻觉：好像自己已经把项目拿下了。实际上，一次成功运行只证明一条最小链路在当前条件下能通。它距离“真正理解项目结构、会排常见问题、会读 batch 结果、会讲清调用链”还有很长距离。

所以学弟如果第一次跑通了，不要过度膨胀，也不要反过来觉得“我还是不够会，干脆继续瞎翻资料”。更好的心态是：很好，至少链路通了。现在我终于有资格开始认真读它、问它、比较它了。

### 14、如果我是带学弟的老师，我会怎样安排他用一周把 `01 + 02` 啃下来

你说希望把 `01` 和 `02` 扩成能让学弟连续读一周的重型版本，这个目标非常好。但“能读一周”并不意味着“第一天就从头刷到尾”。更好的节奏，是让他每天有一个清晰问题去读，而不是像背书一样硬压。这里我给出一种很适合零基础同学的阅读组织方式。

#### 14.1 第一天：只做地图建立，不碰深层数学

第一天最重要的不是理解所有细节，而是建立“这到底是个什么项目”的轮廓。所以最适合的读法是：先看 `00`，再看 `02` 前半部分，也就是论文总系统、三层结构、根目录和 wrapper 总览。读到这里，你的目标不是“我会复述所有脚本”，而是“我终于知道工作区、上游和结果层分别是谁”。

只要第一天能把这张图立住，后面所有深入都不会太虚。

#### 14.2 第二天：把术语词典和目录结构互相对照

第二天很适合在 `01` 和 `02` 之间来回跳。比如你在 `02` 里看到 `SSH`、`tmux`、`Conda`、`config.yml`、`GSplatLoader`、`SafeFlightCorridor`，就回 `01` 查；查完再回 `02` 看这些词在项目里的位置。这样做比单独背词典舒服很多，因为术语会自动带着语境进入脑子。

对零基础学弟来说，这一步特别重要。因为它能让“词”和“路径”第一次绑在一起。

#### 14.3 第三天：把 wrapper 主线啃下来，形成工程工作流感觉

第三天最合适的任务，是把 `02` 里关于 `scripts/` 的部分认真读一遍。重点不是每个脚本都背出参数，而是知道它们在工程主线上的顺序：环境、数据、smoke、batch、overnight、汇总。到这一步为止，学弟应该开始形成一种感觉：原来当前工作区不是文件堆，而是一条可以顺着走的工程流水线。

这一步做成了，后面再碰任何脚本，都不太容易慌。

#### 14.4 第四天：开始跟一条 smoke 调用链走到底

第四天最适合做的事，是把 `run_splatplan_smoke.sh -> smoke_splatplan.py -> GSplatLoader -> planner -> generate_path` 这条链路跟着读一遍。如果有精力，甚至可以边读边在终端里打开对应文件。此时的目标不是读懂所有张量运算，而是把调用关系压平。

只要学弟到第四天能口头讲清这条最小链路，他对项目的掌握就已经超过很多“只会翻文件”的状态了。

#### 14.5 第五天到第七天：开始把上游主轴和论文主张配对起来

最后几天最合适的工作，是把 `02` 后半部分的上游目录讲解、核心类角色和论文主张映射认真过一遍。这个阶段不要贪图速度，而要有一种“终于开始把概念和代码焊在一起”的耐心。你会发现，到了这个阶段，`01` 里的术语也会重新变得更有味道，因为它们不再是孤立名词，而成了你读代码时随时会用到的语言。

如果一周读下来，学弟还不能自己写算法，完全没关系。只要他已经能稳定回答“项目做什么、三层结构是什么、smoke 调用链怎么走、`config.yml` 和 scene preset 各干什么、`SplatPlan` 大概在哪几步完成规划”，这周就已经非常值了。

### 15、你以后给别人讲这个项目时，最值得保留的三种讲法

一个项目讲得清不清，不只体现在你自己有没有看懂，还体现在你能不能根据对象切换讲法。对这个项目来说，我特别建议你保留三种版本：一句话版、两分钟版和十分钟版。因为你以后一定会遇到不同场景：有人只是随口问，有人要听你做组会，有人可能要听你做完整汇报。

#### 15.1 一句话版：给第一次听说这个项目的人

一句话版其实很简单：Splat-Nav 是把 Gaussian Splatting 场景表示进一步拿来做安全规划和视觉定位的导航系统；当前我们在本机主要复现的是它的离线/仿真规划链路，并用 wrapper 工程层把环境、运行和结果归档整理清楚。

这句话的好处在于，既讲了论文系统，又交代了当前工作区的现实边界。不会让人误以为你现在已经在做实车闭环，也不会把项目缩小成“只是几个脚本”。

#### 15.2 两分钟版：给准备真正接手项目的学弟

两分钟版可以稍微展开一点：Splat-Nav 总体由 `Splat-Plan` 和 `Splat-Loc` 两部分组成。前者负责在 GSplat 场景里构造安全走廊并生成平滑轨迹，后者负责只根据 RGB 图像做位姿估计。当前工作区 `/home/howard/Splat-Nav` 不直接等于官方论文仓库，而是一个 wrapper 工作区。这里的 `scripts/` 负责环境、tmux、smoke、batch、overnight 和汇总；`splatnav-official/` 是官方源码入口；`runs/` 用来沉淀每次实验结果。第一阶段我们主要做离线/仿真，不碰实车，重点把 `Splat-Plan` 跑顺、读顺、讲顺。

如果一个学弟听完这段话还不觉得迷糊，说明项目交接已经成功了一半。

#### 15.3 十分钟版：给组会、周报或阶段汇报

十分钟版就可以把论文结构、工作区三层结构、最小调用链和当前阶段进展一起讲出来。先说论文总系统，再说本机为什么要有 wrapper，接着说从 `config.yml` 和 scene preset 到 `GSplatLoader`、`SplatPlan.generate_path()`、run 目录落盘的完整链路，最后再说目前已经完成哪些 run、可行率大概怎样、接下来准备往哪里深化。这个版本是你未来最常用的主力版本。

而且你会发现，只要 `02` 这份文档真的读透了，这个十分钟版其实并不需要你背稿，它会很自然地长出来。

## 七、当前边界、典型场景与后续整理方向

最后这部分负责收边界、压重点，也顺带把几个关键场景和后续工程整理思路放进来。这样读到尾声时，读者不会只留下很多信息，而会留下一个比较稳的判断框架。

### 1、当前边界一定要再强调一遍：什么是现在该做的，什么不是

一份全景文档如果不反复强调边界，很容易把新人带到“什么都想碰”的状态。这里我想把当前阶段的边界再明确说一次，而且说得更像做项目而不是写概念文章。

第一，当前主任务是离线/仿真复现与工程整理，不是实车部署。第二，当前主重点是 `Splat-Plan` 链路，不是要求学弟第一周吃透 `Splat-Loc`。第三，wrapper 层可以适度重构、补注释、做大厂风格整理，但上游官方源码要保持边界意识。第四，任何涉及共享机器系统层的操作都要克制，尤其不能为了局部问题去动全局 CUDA、驱动或别人的账户环境。第五，结果要优先做成可汇报、可复盘、可交接，而不是只追求“我本地看起来跑了”。

这些边界不是在限制你，而是在保护推进节奏。尤其是带新人时，边界越清楚，项目越容易形成稳定预期。

### 2、这份文档读到最后，你脑子里最好留下哪几张图

一份好文档最后不应该只留下一堆文字，而应该留下几张很稳的图。第一张图，是论文系统图：`Splat-Nav = Splat-Plan + Splat-Loc`。第二张图，是当前工作区三层图：上游算法层、wrapper 工程层、文档与结果层。第三张图，是一次 smoke 的最小调用链：shell 包装、环境激活、上游导入、GSplat 加载、planner 构造、`generate_path()`、结果 JSON、run 目录落盘。第四张图，是上游源码树的角色图：`splatplan/` 是主轴，`splat/` 和 `ns_utils/` 处理场景入口，`polytopes/` 和 `ellipsoids/` 处理几何，`pose_estimator/` 处理定位，`run_rrt.py` 和 `run_nerfnav.py` 提供对比方法。

如果这四张图你已经开始能在脑中调出来，那这份 `02` 的任务就基本完成了。你再去读 `03_输入输出与一次运行验收_从脚本到结果.md` 时，会明显感觉轻松很多。因为现在你不再是在盲读一个项目，而是在沿着一张已经成形的地图走。

### 3、第一次真正读源码时，别平均用力：给学弟的一条顺序化读码路线

很多同学一听“要读源码”，脑子里会默认一个非常累的策略：从仓库第一层开始，一个文件不落地看下去。这种策略在课本上也许显得认真，在真实项目里却常常效率很低。因为真实工程从来不是平均展开的。它总有主轴、有侧翼、有暂时先知道名字就够的部分。所以真正高效的读码，不是平均用力，而是有意地先抓骨架，再补肌肉，最后才去看更细的血管和神经。

#### 3.1 第一遍：只读“主轴文件”，目标是把链路拉直

第一遍读码，最适合看的其实只有少数几个文件。对当前项目来说，我最建议的顺序是：先看 `scripts/run_splatplan_smoke.sh`，再看 `scripts/smoke_splatplan.py`，然后看 `splatnav-official/splat/splat_utils.py`、`splatnav-official/splatplan/splatplan.py`、`splatnav-official/splatplan/spline_utils.py`。为什么是这几份？因为它们刚好构成最小规划主轴。

你要带着的目标也非常单纯：不是证明每一行都对，而是回答“命令从哪进、场景从哪读、planner 怎么构、`generate_path()` 里大概怎么走、最后结果从哪出”。这一遍只要能把主轴拉直，后面再读什么都不会太飘。

#### 3.2 第二遍：补“支撑文件”，目标是知道主角背后站着谁

主轴拉直以后，第二遍就适合读支撑文件。也就是 `SFC/corridor_utils.py`、`initialization/grid_utils.py`、`polytopes/collision_set.py`、`ns_utils/nerfstudio_utils.py` 这类文件。它们不是你第一次最该盯住的主角，但它们在给主角输血。比如 `grid_utils.py` 解释了离散初始化从哪来，`collision_set.py` 解释了约束不是凭空造的，`nerfstudio_utils.py` 则说明 `config.yml` 背后到底连接着什么世界。

这一遍的目标也不是全懂，而是让你以后再回头看主轴时，知道主轴每一步到底借了哪些支撑模块。也就是说，第一遍像在看故事线，第二遍像在认识配角和幕后团队。

#### 3.3 第三遍：再去看“侧翼入口”，目标是把项目全景彻底焊牢

到了第三遍，你就可以去读 `run_splatloc.py`、`pose_estimator/utils.py`、`run_rrt.py`、`run_nerfnav.py`、`visualize.py` 这些文件了。此时你已经不再是一个第一次进门的人，而是一个主轴比较稳的人。你再看这些侧翼入口，会自然地把它们放回整个项目全景里。你会知道哪些是定位链、哪些是对比基线、哪些是结果展示。

这时候阅读体验会轻松很多。因为你已经不需要靠它们来建立主线，而是在用它们丰富主线。

#### 3.4 第一次看代码时，最不值得做的事情是什么

最不值得做的，是一上来就跟自己较劲，非要把每个类、每个矩阵、每个文件全吃透。这样做只会让阅读变成惩罚。更好的方法永远是：先问这份文件在大图里站哪一层，再问它回答了哪个问题，再决定这轮要不要细抠。工程源码和教科书不一样，它不是按你的认知顺序写出来的，所以你也没必要假装必须按文件自然顺序全懂。

学弟只要把这个观念立住，以后读任何项目都会顺很多。

#### 3.5 一个很实用的读码笔记法：每个文件只先回答四个问题

很多新人读代码容易越看越散，是因为没有笔记抓手。我特别建议你前两遍读码时，每个文件只先回答四个问题。第一，这个文件在项目哪一层。第二，它主要回答什么问题。第三，它最关键的输入和输出是什么。第四，它和上一个或下一个文件怎么接。只要这四个问题写下来，你会发现很多之前“看着看着就丢了”的文件，突然变得有位置了。

这套方法看起来朴素，但非常适合零基础同学。因为它逼你先建立结构感，而不是一头扎进细节里出不来。

### 4、四个典型场景不只是名字：它们在当前工作区里各自意味着什么

很多人第一次看 `old_union`、`stonehenge`、`statues`、`flight` 时，会把它们简单理解成“论文用了几个场景”。这个理解当然不算错，但太浅了。对当前项目来说，这几个场景不是抽象标签，而是会直接影响配置路径、机器人半径、体素边界、起终点摆法、结果分布乃至后续你做汇报时的叙事重点。换句话说，它们不是背景板，而是实验个性的一部分。

#### 4.1 `old_union`：为什么它在当前工作区里几乎成了默认主场景

从当前 wrapper 脚本、已有 run 目录和实际推进节奏看，`old_union` 在工作区里几乎扮演了“默认主场景”的角色。它的好处很现实：路径和资产相对清楚，已有结果较多，相关脚本默认值也常围绕它展开。所以对新人来说，这个场景非常适合做第一阶段主入口。你不是因为它“理论上最重要”才从它开始，而是因为在当前机器和当前工程整理节奏下，它最适合作为稳定起点。

你以后带学弟时，也完全可以很坦然地这么说：先别追求平均地把四个场景都摸一遍，先把 `old_union` 跑顺、讲顺，它会给你最多的正反馈。

#### 4.2 `old_union` 的参数为什么值得被认真看一次

在 scene preset 里，`old_union` 的 `radius_config`、`mean_config`、`lower_bound`、`upper_bound` 和 `resolution` 并不是随手写的杂项，它们共同定义了这个场景里实验是怎样被“摆出来”的。起终点大致在什么区域对穿、机器人半径按什么尺度估、体素网格覆盖哪块空间，都是这些参数在共同决定。

新人最容易忽视的一点是：这些值虽然看起来只是数字，但它们实际上代表着作者对场景结构和实验尺度的理解。你不需要第一天就推敲它们为何恰好取这个数，但你至少要知道，它们是实验设置的一部分，不是无关紧要的填空。

#### 4.3 `stonehenge`：为什么它特别适合训练“别把场景名当空标签”的能力

`stonehenge` 这个场景很适合拿来帮助新人建立一个意识：不同场景并不是只换了个名字，很多实验设定会跟着变。你在 preset 里能看到它的 `radius_config`、边界和分辨率都和 `old_union` 不一样。这意味着什么？意味着规划器面对的搜索空间、路径形态和几何尺度都可能不同。

对学弟来说，读这种差异不是为了背参数，而是为了真正学会“场景个性化”。以后只要换了场景，你就不会再下意识地以为所有设置都应该照抄。

#### 4.4 `statues`：为什么它很适合提醒你“机器人尺度和场景尺度是耦合的”

在 `statues` 的 preset 里，你会明显看到机器人半径、边界和均值配置有自己的特点。这特别适合帮助新人理解一个重要观念：机器人尺度不是脱离场景独立存在的。你不能抽象地说“机器人半径是 0.01 或 0.03”，而不去问这是在哪个场景、以什么坐标尺度、围绕什么空间范围说的。

这种尺度感非常关键。因为很多代码读起来只是数字，一旦你忘了它们和场景的耦合关系，就会觉得所有参数都像魔法常数。

#### 4.5 `flight`：为什么它会自然地让你想到“未来更接近真实飞行的味道”

虽然当前阶段不碰实车，但 `flight` 这个场景会天然更容易让人联想到飞行器导航、空间更开阔的运动和更接近动态应用的语境。它在边界设置和 `radius_z` 这些配置上，也能明显让你感受到和其他场景不完全相同的空间特征。

这并不意味着学弟必须一上来就优先跑它。更稳的理解是：当你在 `old_union` 上把流程压稳以后，切到 `flight`，你会明显感觉自己开始接触更丰富的场景风味。它很适合作为后续扩展时的第二梯队目标。

#### 4.6 四个场景一起看时，你应该得到什么能力

如果你把这四个场景一起看，最该得到的能力不是背住四套参数，而是建立一种自然直觉：场景名背后站着一整组实验设定，场景切换意味着路径、边界、尺度和可能的结果分布都会一起变化。只要这个直觉长出来，你以后就不会再把 scene 当纯标签，也更容易理解为什么 wrapper 脚本和上游入口都如此重视 `scene_name`。

这一节我想写得非常实用一点。因为真实世界里，学弟不一定总有整块时间。他有时就只有一个下午，或者一晚上，想先把项目摸出点感觉。这种情况下，最怕的不是时间少，而是打开顺序错了。顺序一错，两个小时就会全花在迷路上。

原因很简单，它能先给你定调。你至少会知道当前主线文档怎么分工，自己现在更适合看术语、看全景、看输入输出还是看快速上手。很多人一上来就跳进最厚的文件，结果看着看着不知道自己为什么要看。先看 `00`，就是在避免这个问题。

如果你只有一个下午，我会非常建议把大头时间留给 `02`。因为它最能帮你解决“项目到底是什么”这个根问题。项目一旦有了地图，后面的术语和脚本才有位置。没有地图，任何局部解释都容易飘。

看完地图以后，不要急着看最数学的文件。先看这份最外层 smoke 入口，会让你非常踏实。因为你会第一次把“当前工作区怎么启动一次最小规划任务”看成一条现实链路，而不是抽象概念。

### 6、从 wrapper 到 upstream 的文件映射关系，最好在脑子里形成一张对照表

很多人项目做到后面会有一种奇怪的割裂感：wrapper 我也看了，上游我也看了，可两边始终像两套语言。更好的状态应该是，你脑子里逐渐形成一个自然对照表。也就是说，一看到某个 wrapper 入口，你就知道大概率会落到哪类上游文件；一看到某个上游主角，你也知道平时是通过哪些 wrapper 脚本接触到它。

#### 6.1 `run_splatplan_smoke.sh` 对应 `smoke_splatplan.py`，而后者继续对应 `GSplatLoader + planner`

这是最基础、也最值得背熟的一条映射。你以后只要听到有人说“先 smoke 一下”，脑子里就应该自动想到：外层 shell 启动器先负责 run 目录和环境，再进入 Python smoke 入口，而 Python 入口又会把上游的 `GSplatLoader`、`SplatPlan` 或 `SafeFlightCorridor` 拉进来。

这种自动联想特别值钱，因为它说明你已经不是在看单个文件，而是在看文件之间的分工关系。

#### 6.2 `run_official_style_batch.py` 对应的是“同一套 planner 被系统化重复调用”

很多新人会把 batch 文件误当成另一种算法实现。其实更成熟的理解是：它主要是在调用层面把相同 planner 放到多 trial、多方法、多统计环境里运行。所以你一看到它，就应该想到下面还是那些核心 planner 类，只不过外面多包了一层实验组织壳。

一旦这个映射关系稳了，你读 batch 文件时就不会误以为自己掉进了另一套世界。

#### 6.3 `visualize_batch_results.py` 和 `aggregate_batch_runs.py` 对应的是“结果消费层”，不是“算法层”

这也是很值得压稳的一组映射。很多新人一看到 Python 文件就自然以为“这也是核心计算代码”。其实不是。它们主要服务的是结果消费：前者把单次 batch 的 JSON 翻成图和摘要，后者把多轮 batch 汇成总报告。你以后只要想到它们，就应该知道自己已经走到了实验后处理层。

这种层次感对做汇报尤其重要。因为你会更自然地知道某个图到底来自哪里，是算法直接产出的，还是后处理脚本进一步整理出来的。

#### 6.4 `sync_upstream.sh` 对应的不是某个算法文件，而是版本感知本身

并不是每个 wrapper 都会落到一个具体上游算法文件。有些 wrapper 在回答的是“我们和上游现在是什么关系”。`sync_upstream.sh` 就属于这一类。它对应的是版本和提交状态，而不是某个数学模块。这种映射也值得学弟有感觉。因为它提醒你，工程里不是只有算法映射，还有版本映射、结果映射、环境映射。

#### 6.5 真正成熟以后，这张对照表会变成你的本能

当你在项目里待上一段时间以后，这种对照关系最好会慢慢变成本能。你不再需要刻意背“这个 shell 对应哪个 Python，这个 Python 又对哪个 planner”，而是自然能顺着走。那时候你就会发现，自己已经从“文件浏览者”变成了“结构理解者”。这是一个很明显、也很值得开心的成长节点。

### 7、如果导师或师兄现在当面追问你几个问题，你应该怎样答才像真的理解了项目

很多同学自己看资料时，总觉得好像懂了一些；可一旦有人当面一问，就发现脑子还是散的。这很正常。项目理解真正成形，往往就是从“我自己觉得看过了”变成“别人一问，我也能稳稳讲出来”。所以这一节我故意按导师追问的口吻来写。不是为了制造压力，而是为了帮你提前练一种能力：把项目的地图、链路和边界讲成别人能听懂的话。

#### 7.1 问：这个项目到底是在做三维重建，还是在做导航

一个很成熟、又不容易把自己说绕的话法是：这个项目的核心不是重新发明三维重建，而是站在 Gaussian Splatting 这种已经建立好的三维场景表示之上，进一步做安全规划和视觉定位，也就是导航系统里的两大核心问题。换句话说，三维重建在这里更像基础设施，而导航才是它真正要完成的系统目标。

你一旦这样回答，听的人就会感觉你已经知道“场景表示”和“导航任务”在项目里的上下位关系。你不会再把它讲成“这是一个 3DGS 项目顺便能导航”，也不会讲成“这是个传统导航项目碰巧用了点 3DGS”。而是会更准确地说：它是在新型场景表示上重做导航这件事。

#### 7.2 问：为什么当前工作区里还有这么多 wrapper 脚本，不能直接跑官方仓库吗

这个问题问得非常好，而且很常见。更成熟的回答不是说“可以直接跑啊”，也不是说“wrapper 比官方好”，而是应该分层回答。官方仓库更像论文作者自己的实现与实验入口，保留它原样非常重要，因为它是事实来源。wrapper 工作区存在的意义，是在不破坏上游实现的前提下，把当前这台共享机器上的环境边界、数据落盘、tmux 长任务、run 目录、汇总图表和交接文档整理出来，让复现和后续带人更稳。

也就是说，wrapper 不是为了取代上游，而是为了让上游更容易在当前现实环境中被重复、被管理、被解释。你如果能这样回答，别人会很容易相信你知道为什么工程化外壳是必要的。

#### 7.3 问：那你们现在到底复现到了什么程度

这时候最怕的是只回答“能跑了”。更好的回答应该是：当前离线/仿真主链已经围绕 `Splat-Plan` 建立起了稳定执行路径，能在作者场景上做 smoke、batch 和 overnight 形式的运行，并把结果按 `runs` 规范沉淀成 JSON、图表和汇总报告。与此同时，工作区结构、文档体系和 wrapper 层已经能支持后来者按更短路径入门。至于实车、ROS 节点部署和 `Splat-Loc` 深入链路，目前被明确放在第一阶段之外。

这样的回答之所以好，是因为它既不虚夸，也不把自己说得太弱。它能准确传达“我们已经把离线/仿真链路和工程组织做出了成果，但边界依然清楚”。

#### 7.4 问：为什么你们现在不直接碰 ROS 和实车

很多新人一听这个问题，容易心虚，好像不碰实车就不算真的做项目。其实更成熟的答法是：当前阶段的目标不是追求表面上覆盖所有模块，而是优先把离线/仿真复现链和项目认知链打牢。因为只要上游场景加载、规划主链、结果验收、文档交接和工程边界都还没稳住，就直接去碰 ROS 和实车，只会把问题层次叠得更高，推进反而会变慢。

你完全可以非常坦然地说：现在先把离线链路做成一个后来者也能跑、也能讲、也能继续改的系统，这是对项目最负责的推进顺序。等这一层稳定后，再切到 ROS/实车会更合理，也更节省时间。

#### 7.5 问：那学弟到底应该先看什么，为什么不是先看论文公式

这个问题其实正好能检验你是不是真的理解“项目入门”和“学术阅读”之间的关系。更成熟的回答是：对零代码基础、机械转来的学弟，先要建立的是工程地图和术语地图，而不是一上来硬啃公式。因为如果他连工作区三层结构都没分清、`config.yml` 和 scene preset 都还在混、wrapper 和上游还没分层，那么先去看公式只会把压力放大，并不会更快进项目。

所以更合理的顺序是：先看主线文档，形成路径感；再跟 smoke 主链读代码；随后再回到论文，把论文主张和代码落点焊在一起。这样公式才不会飘在空中。

### 8、如果要把这个项目进一步整理成更像大厂工程的样子，哪些地方先动，哪些地方不要乱动

你前面已经明确说过，希望这个项目在复现的同时，也能逐步整理成更符合大厂规范的样子。这件事完全可以做，但它特别需要顺序感。因为“工程化重构”这四个字非常容易让人兴奋，一兴奋就什么都想动。真正成熟的做法不是全仓开刀，而是先判断哪些地方动了能立刻降低认知成本、提高稳定性，哪些地方现在不应该碰，至少不应该重手碰。

#### 8.1 第一优先级：文档入口、运行规范和结果结构

最值得先动的，其实不是最底层数学代码，而是认知与运行成本最高、但改动风险相对可控的外层。比如我们现在正在做的 `docs/Codex` 主线文档重建，比如 `runs` 目录命名规范，比如 `create_run_dir.sh`、`run_in_tmux.sh` 这种直接影响长期可追踪性的工程入口。这些地方一旦清楚，后来者不需要先懂所有算法，也能先有稳定工作流。

从大厂工程视角看，这一层非常像“把入口体验和可维护性先拉正”。它未必最炫，但收益通常非常大。

#### 8.2 第二优先级：wrapper 脚本之间的职责边界和日志质量

再往下一层，非常值得整理的是 wrapper 脚本本身的职责边界。哪些脚本只负责环境，哪些只负责 run 目录，哪些只负责单次执行，哪些只负责汇总，哪些只负责可视化，这种边界最好尽量清晰。同时，日志内容也值得系统性整理。因为长期看，工程脚本最容易变乱的不是功能本身，而是边界混起来以后，谁都做一点，最后谁都说不清。

这种整理特别适合练工程感。因为它逼你思考“一个模块到底该负责什么”，而这正是大厂代码能力里很核心的一部分。

#### 8.3 第三优先级：对上游核心类做“解释性增强”，不是先做算法性改写

很多新人一说工程化，就想先去改 `splatplan.py` 或 `spline_utils.py` 的内部逻辑。对当前阶段我并不建议优先这么做。更稳的方式，是先围绕上游核心类做解释性增强，比如在外层文档和注释里把输入输出、调用位置、结果结构讲清楚；再比如在 wrapper 层把参数命名和结果保存方式整理清楚。也就是说，先提升“别人读得懂、用得对”的程度，再决定是否真的要动算法实现。

这不是保守，而是成熟。因为算法核心一旦动，验证和责任链都会变重。先把解释层做厚，是更稳的推进顺序。

#### 8.4 当前不建议重手动的地方：上游数学主链和论文对比基线内部实现

为什么不建议现在重手动？原因很简单。第一，上游核心实现是论文事实来源，动得太早会让“这是作者实现还是你们改过的实现”越来越难分清。第二，学弟当前最缺的不是“新的算法版本”，而是“能稳稳读懂并复现现有链路”的能力。第三，一旦重写或大改核心实现，验证负担会立刻变大，可能反而拖慢整个项目节奏。

所以当前最成熟的姿态，其实是：上游保持尊重和边界，外层做工程组织和认知降噪，局部小修小补以解释性和稳定性为主。

#### 8.5 如果未来真的要重构上游，最成熟的前提是什么

不是“我觉得这里写得乱”，也不是“我想练练代码”，而是你已经对这条链有足够强的理解，能说清原实现做了什么、为什么这样写、你的改动不改变哪些行为、又希望改进哪些可维护性问题，并且你有足够明确的回归验证方式。换句话说，真正成熟的重构不是情绪驱动，而是理解驱动和验证驱动。

这也是为什么我一直建议现在先把 `01` 和 `02` 压厚。没有理解，就没有好重构。重构不是为了看起来忙，而是为了让系统更稳、更清楚。

### 9、如果你第二天早上只看 `runs/`，也应该能大致反推出项目正在以什么方式工作

一个工程好不好，不只是看代码和脚本层，还可以从结果目录反推出来。当前项目尤其如此。因为 `runs/` 不是简单输出箱，而是整个工作区行为方式在文件系统上的投影。你如果真的理解这套工作区，哪怕第二天早上不先看代码，只看 `runs/` 里的目录命名、文件结构和产物类型，也应该能猜出昨晚大概干了什么。

#### 9.1 时间戳目录为什么这么重要

当你看到 `YYYY-MM-DD_HHMM_topic` 这种目录时，不要把它只当成“方便排序”。它其实在告诉你：实验任务被显式当成一个个时间事件在管理。也就是说，每一次运行都不仅有主题，还有发生时刻。这个设计对后来者非常友好，因为它天然支持时间回放。你以后想回看哪一夜跑了什么、哪一次改动前后结果有什么差异，就会很依赖这个时间感。

工程上很多“说不清”问题，其实最终都是因为时间感缺失。run 目录把这件事补上了。

#### 9.2 `env.txt`、`cmd.txt`、`stdout.log` 三件套，为什么像一次运行的身份证

如果你在一个 run 目录里看到这三样东西齐全，基本就能判断这次运行是按当前工程规范组织的。`env.txt` 像身份证背景面，告诉你这次任务运行时的用户、主机、GPU、Python 和上游提交信息。`cmd.txt` 像动作记录，告诉你它到底跑的是什么命令。`stdout.log` 则像过程录像，告诉你运行时说了什么、卡在哪、停在哪。

这三样东西之所以值钱，是因为它们共同让一次运行从“曾经发生过”升级成了“可以被追踪和解释”。

#### 9.3 为什么图、JSON、Markdown 会一起出现

很多新人第一次看到一个 run 目录里同时有 JSON、PNG、Markdown，会下意识觉得是不是有点冗余。其实这是很成熟的结果分层。JSON 更适合程序继续处理和精细追踪；图更适合快速肉眼判断；Markdown 摘要更适合你第二天快速扫一眼就知道大概情况。这三者各自服务不同消费方式，不是重复，而是互补。

只要你有了这层理解，就不会再把结果目录看成“文件好多”。你会开始把它看成“结果被做成了多种阅读层次”。

#### 9.4 从 run 目录反推执行类型：你能看出这是一条 smoke 还是一轮 batch 吗

这件事其实非常适合学弟训练自己。比如目录 topic 里如果带 `smoke`，结果文件里更可能只有单次 JSON 和最基础日志；如果 topic 带 `formal_batch`，则很可能出现 `batch_results.json` 和一个图目录；如果是 `overnight_report`，那你多半能看到 CSV、Markdown 汇总和跨轮趋势图。也就是说，文件结构本身就在泄露任务类型。

你以后越能从结果目录反推出执行类型，越说明你对整个工程链是有结构感的。

#### 9.5 一个真正成熟的项目，结果目录本身就应该会“说话”

这句话非常值得记住。真正成熟的项目，不应该只有代码作者自己知道每个目录是什么意思。结果目录本身也应该能“说话”。当前工作区之所以强调 topic、时间戳、日志、摘要和图表，其实就是在让结果自己具备最小可读性。这样第二天来的人，不必把昨晚的人叫醒，也能迅速接手现场。

这就是工程组织能力最迷人的地方之一：它能让协作变轻，而不是变重。

### 10、为什么当前阶段明确不碰 ROS、语义分支和实车，不是因为它们不重要，而是因为排序更重要

在很多实验室环境里，新人最容易被一种氛围影响：仿佛越快碰到真机、越快碰到 ROS、越快碰到更复杂分支，就越显得自己在做“真的项目”。这种心理很能理解，但从推进效率看，常常不划算。当前阶段明确不碰这些东西，不是低估它们，而是在做更稳的排序。

#### 10.1 `ros` 分支存在，说明它重要；当前不先碰，说明我们在做节奏管理

上游 README 明确提到 ROS 节点在 `ros` 分支。这件事本身就说明作者认真考虑过系统部署和机器人运行。但当前工作区主线没有让学弟先去碰它，理由非常实际：只要离线链路和工程入口还没稳住，就直接切 ROS，只会叠加更多系统层、依赖层和运行时复杂度。

所以更成熟的表达方式应该是：我们知道 ROS 分支的重要性，也尊重它在总系统里的位置；但对当前阶段目标来说，先不碰它，是在保护主线推进。

#### 10.2 语义分支和语义目标查询为什么也不应抢第一阶段风头

同样地，上游 README 还提到了 `semantics` 分支和语义目标查询能力。这听起来很酷，也很容易激发兴趣。但如果学弟现在连 `config.yml` 背后资产树、`SplatPlan` 主链和 run 目录规范都还没完全压稳，就直接去看语义分支，只会把认知层次再往上摞一层。那不是积极，而是过载。

先把基础链路做成可解释、可复现、可汇报的状态，再去碰语义增强，会自然很多。

#### 10.3 实车为什么尤其不能靠热情先冲

实车和离线/仿真最大的差别，不只是“真东西更难”，而是它会把安全、实时、部署、感知误差、系统耦合和硬件资源这些问题一次性压过来。你在离线阶段没稳住的那些小问题，到了实车阶段往往都会被放大。所以真正对项目负责的顺序，绝不是“赶紧上实车看看”，而是“先让离线链路足够稳，再决定要不要让更多复杂性进来”。

这点尤其适合讲给学弟听。因为它能帮他建立一种很重要的职业素质：真正稳的人，不是最敢冲的人，而是知道什么时候该先把地基打厚的人。

### 11、如果未来想从这个项目里长出创新点，第一反应最好不是“发明一个全新名词”，而是观察哪里最痛

很多学生一听到“最终目标是投会议论文”，马上就会被创新焦虑压住，好像必须立刻想出一个听起来全新的方法名字。其实对当前阶段来说，更成熟的创新起点常常不是命名，而是观察。也就是说，你先把现有链路跑顺、读顺、讲顺，再认真看哪里最痛、哪里最不稳定、哪里最费人、哪里最容易被误解、哪里对后来者最不友好。这些地方里，往往就藏着未来的改进点。

#### 11.1 工程层痛点，也可能长成研究问题

很多新人会把工程和研究完全切开，觉得工程问题只能靠整理，研究问题才叫创新。其实不是。某些工程痛点如果背后反复对应同一种系统瓶颈，就很可能是研究问题的入口。比如某类场景切换时参数耦合太强、某类 baseline 可行率总是掉、某种初始化方式对某些场景特别脆、结果解释层成本太高，这些都可能往方法改进或系统论文写法上长。

所以你别轻易低估工程观察。很多很好的创新，就是从“为什么这里总这么痛”开始的。

#### 11.2 方法层痛点，通常藏在“你已经能稳定复现”之后

如果链路还没稳定，方法层痛点很容易和环境问题、数据问题混在一起，根本看不清。只有当你已经比较稳定地知道什么是正常运行、什么是结构化结果、什么是典型场景表现，你才能开始认真分辨：这到底是系统边界导致的，还是方法本身的弱点。也就是说，真正高质量的方法观察，通常都发生在复现稳定之后。

这也是为什么现在先把 `01`、`02`、`03`、`04` 这类材料做厚，是非常值的。它们不是和创新无关，而是在给未来创新铺路。

#### 11.3 创新点的最早形态，往往不是结论，而是一串好问题

很多人误以为创新点应该直接以答案出现。其实在训练阶段，更真实的情况常常是：你先长出一串质量很高的问题。比如“为什么某类场景对某种安全缓冲特别敏感”“为什么 wrapper 层统计出的趋势和某些单次可视化不完全一致”“为什么 GSplat 场景在某种离散边界设置下更容易出现初始化问题”。这些问题如果被追得够深，就很可能长出方法、实验设计或系统改进。

所以学弟如果暂时还提不出完整创新方案，完全不用焦虑。先长出好问题，已经非常有价值。

### 12、最后再送你一个更像老师带学生的建议：别急着把“全懂”当目标，先把“能稳定往前走”当目标

写到这里，其实我最想说的一句心里话是：很多项目不是被难度击败的，而是被不必要的完美主义拖住的。尤其是零基础学弟，很容易一上来就给自己设一个很重的目标，仿佛必须先把所有术语、所有脚本、所有数学和所有上游文件都搞懂，才配开始动手。这个标准实在太高，也不符合真实项目学习规律。

更成熟的目标应该是：我今天比昨天更不迷路一点，我已经能说清一个新概念，我已经把一条新链路看顺，我已经知道一个以前混淆的词其实该怎么区分，我已经知道明天该接着看哪里。只要这种“稳定往前走”的节奏形成，你后面会发现自己进步得非常快，而且不那么痛苦。

这也是为什么我希望 `01` 和 `02` 不是写成冰冷资料，而是写成一种能陪你走路的东西。因为真正能把人带进项目的，从来不是知识点数量本身，而是知识点之间有没有路感、有没有层次、有没有一口气能继续往下看的动力。

如果你把 `01` 和 `02` 真读到这里，最自然的下一步不该是继续盲翻别的资料，而是顺着当前主线往下走。首先应该去读 [03_输入输出与一次运行验收_从脚本到结果.md](/home/howard/Splat-Nav/docs/Codex/03_输入输出与一次运行验收_从脚本到结果.md)，因为现在你已经有了项目地图，正适合把“一次运行”拆开看清。接着应该去读 [04_顺序化快速上手_从第一天到批跑.md](/home/howard/Splat-Nav/docs/Codex/04_顺序化快速上手_从第一天到批跑.md)，因为你已经不再是完全陌生的人了，开始可以按任务顺序真正动手。最后，再去看 [05_阶段性目标_一周一月三个月.md](/home/howard/Splat-Nav/docs/Codex/05_阶段性目标_一周一月三个月.md)，它会帮你把现在的理解往未来节奏里接。

### 14、如果把整个项目讲成一个完整故事：从“我要从 A 点去 B 点”到“第二天我拿到报告”

到这里，我们已经从很多角度拆过项目：从论文、从目录、从脚本、从类、从数据流、从工程边界、从阅读顺序、从场景差异。现在我想把这些碎片重新收回来，讲成一个完整故事。因为对新人来说，真正让理解稳定下来的，往往不是知道了更多知识点，而是突然能把这些知识点串成一条活的叙事线。一旦叙事线出来，项目就会从“很多局部”变成“一个系统”。

#### 14.1 故事的起点，不是脚本，而是一个很朴素的导航需求

想象一下，我们并不先从代码开始，而是先从任务开始。一个机器人现在处在某个三维场景里，它需要从当前位置去目标位置，还希望整个过程尽量安全、轨迹平滑、在复杂环境表示下也能实时运行。你如果从这个角度出发，会发现 Splat-Nav 论文其实是在回答一个很朴素但很难的问题：当环境不再只是二维栅格或传统点云，而是 Gaussian Splatting 这种更丰富的三维表示时，导航系统该怎样重新设计。

一旦你从任务出发，项目很多层次就会自然对位。场景表示层负责把“环境是什么样”这件事讲清楚，规划层负责把“从哪走到哪”这件事做出来，定位层负责把“我现在到底在哪”这件事实时估出来，工程层则负责让整套链路在现实机器上能稳定运行、能留下结果、能被后来者接手。

#### 14.2 故事的第二步，是先得有一个可供导航系统使用的场景

这个场景在当前项目里不是凭空生成的，它通常来自 Nerfstudio 训练出来的 GSplat 模型。也就是说，在导航之前，世界已经先被某种方式表示出来了。这个表示不是一张照片，也不是一个简单 occupancy grid，而是一套能够保留高斯均值、尺度、旋转、颜色和不透明度等信息的三维场景模型。上游 README 已经很明确地告诉你，当前仓库建立在 Nerfstudio 之上，而 `config.yml` 正是把你带回这个训练场景入口的关键门把手。

所以从故事角度看，`config.yml` 并不是某个不起眼的小配置，而像是“我要导航的这个世界”的准入证。没有它，后面的规划和定位就没有具体对象可言。

#### 14.3 场景进入系统之后，当前项目会先把它翻译成不同模块都听得懂的话

一旦场景入口确定，`GSplatLoader` 这类模块就开始发挥作用。它会把训练产物整理成后续规划和几何模块都能直接使用的属性。这一步特别像一个翻译过程。因为原始训练产物属于 Nerfstudio 语境，而规划和定位模块需要的是一种更接近“我能拿来算”的内部表示。于是高斯的均值、协方差、颜色、不透明度等就被抽出来，放进统一对象里。

你以后只要把这一步想成“场景语言转换”，很多细节都会顺。比如你就不会再问为什么 `config.yml` 既像模型入口，又好像跟场景几何有关。因为它确实是在把训练世界和导航世界接到一起。

#### 14.4 对规划来说，真正的难点不是一句“从起点到终点”，而是安全和可执行性要一起成立

如果我们只要求“给我一条连起来的路径”，那问题会简单很多。可导航项目真正难的地方在于，你不能只找一条视觉上连通的线，而要同时考虑碰撞、机器人尺度、轨迹平滑、连续性以及后续执行的合理性。这正是为什么论文里会强调安全走廊、多面体、样条和实时性这些词。因为系统不是在玩几何拼图，而是在为真实导航过程准备一条可靠路径。

对当前项目来说，这层难点主要落在 `Splat-Plan` 链上。它先通过网格初始化找到一条粗路径，再围绕这条粗路径逐段建立安全约束，最后才让样条规划器给出一条更平滑、更可执行的轨迹。你越把这件事想成“逐层收紧问题”，代码就越容易读懂。

#### 14.5 初始化路径为什么像故事里的“草稿线”

很多新人一开始读 `A*` 这部分，会误以为那就是最后答案。其实更好的理解是：初始化路径更像草稿线。它先在离散体素空间里给你一条大致可行的路线，让系统知道应该从哪块区域穿过、哪块区域先避开。它的价值在于提供结构，不在于直接当最终轨迹。

这就像你画图时先打草稿一样。草稿不是最终画面，但没有草稿，你后面的细化就很容易失控。把这一层想明白，`GSplatVoxel` 和 `astar3D` 这些名字就不再只是一串工具，而开始像故事中的“起笔阶段”。

#### 14.6 碰撞集合和多面体阶段，像是在给草稿线外面加一层又一层安全缓冲

有了草稿线以后，系统还不能宣布完成。因为草稿线只说明“有可能这么走”，并没有把安全性真正写进轨迹本身。于是接下来的碰撞集合和多面体阶段就登场了。它会沿着路径段去看，附近有哪些高斯椭球或点云近似对象是相关障碍，哪些半空间约束可以把安全区域刻画出来，哪些段已经被之前的多面体包住、哪些还需要新建约束。

这一步很像给一条细线逐段套上安全走廊。你走得不再是抽象线条，而是一个在几何上被明确界定出来的可通过区域。只有到这里，论文里那种“safe-by-construction”的味道才真正进入代码。

#### 14.7 样条优化阶段不是另开新坑，而是在给故事收尾

很多新人一进入 `spline_utils.py` 就觉得故事突然变了，从几何切成了数学。其实更好的理解是：这不是新故事，而是老故事的收尾阶段。前面你已经知道大概要走哪、哪些区域安全、首尾点在哪，剩下的问题其实是：怎样把这些要求整成一条平滑、连续、看起来像真能执行的轨迹。`SplinePlanner` 做的正是这个工作。

一旦你把它当成“给前面所有几何约束收尾”的角色，心理负担会小很多。你不再是突然被扔进优化作业，而是在看故事最后一公里怎样被严谨地落成轨迹。

#### 14.8 一次规划结束以后，工程故事才真正开始有“可交接性”

很多学生项目的问题就在这里：算法跑完就结束了，结果留在终端里，第二天谁也不知道昨天到底做了什么。当前工作区刻意避免了这种情况。通过 wrapper 和 run 目录规范，一次规划不仅结束在内存里，还会被写成 JSON、摘要、图表和日志，进入一个带时间戳的 run 目录。这个动作的价值不是“形式主义记录”，而是让工作具备可交接性。

你以后带人时会非常深刻地感受到这一点。真正让团队能往前走的，不只是“有人做出了结果”，而是“结果被整理成别人第二天也能接手的状态”。

#### 14.9 如果任务不是一条 smoke，而是一整夜 batch，故事会怎样扩展

一旦任务变成 batch 或 overnight，这个故事并没有换主题，只是把同一套主角重复调用了很多次。场景还是那个场景，planner 还是那套 planner，区别在于起终点对更多、方法对比更系统、结果汇总更正式。换句话说，overnight 不是另一种算法，而是同一故事被讲了很多遍，然后被整理成更有统计意义的总报告。

这件事非常适合讲给学弟听。因为它能帮他理解：复杂实验系统往往不是“多一套神秘模块”，而是“把基础单元做成了可重复、可追踪、可统计的流水线”。

#### 14.10 第二天早上拿到报告时，故事应该进入“解释”而不是“猜测”阶段

理想状态下，第二天你不该再猜昨晚发生了什么。你应该能打开汇总 CSV、Markdown 和趋势图，快速知道哪种方法更稳、哪种更慢、这一夜总共跑了多少轮、是否存在明显异常。也就是说，工程组织的目标是把第二天早上的工作，从“猜测式排查”变成“解释式阅读”。

这就是为什么当前工作区会有 `post_overnight_report.sh`、`aggregate_batch_runs.py` 和 `visualize_batch_results.py`。它们不是锦上添花，而是在确保故事的最后一幕不是混乱，而是清晰。

### 15、如果你拿着论文一页一页对照本地工作区，最值得怎样对照

很多人说“要配合论文理解代码”，这句话当然对，但还不够具体。真正的问题是：怎么配，配哪里，先配什么。很多新人拿着论文和代码坐下以后，最大的困惑不是态度不认真，而是不知道应该拿论文里的哪部分去对本地哪些文件。如果这一层不讲清，配合阅读就会变成漫无目的的来回翻。

#### 15.1 先用论文的题目和摘要，对准当前项目的大边界

论文标题和摘要其实特别值得认真看，因为它们通常已经把系统边界讲得很清楚了。你在当前项目里最值得先对准的几个词是：`Safe`、`Real-Time`、`Robot Navigation`、`Gaussian Splatting Maps`。然后立刻回到本地工作区问：这些词分别落在哪。

`Gaussian Splatting Maps` 对应的是 `config.yml`、Nerfstudio 和 `GSplatLoader` 这条场景入口链；`Robot Navigation` 对应的是 `Splat-Plan` 和 `Splat-Loc` 两条系统主链；`Safe` 更偏多面体与碰撞约束；`Real-Time` 则既是算法主张，也是工程上强调低摩擦实验组织的原因。只要摘要这一层先对准，后面你读论文正文时就不会飘在天上。

#### 15.2 论文总系统图出现时，立刻回到工作区三层结构图

论文里一旦出现系统总览图，你最该做的不是盯着每个箭头看半天，而是马上回想当前工作区的三层结构：上游算法层、wrapper 工程层、文档与结果层。这样会让你意识到，论文图主要在讲算法和系统设计，而当前工作区则额外承担了机器环境、运行规范和交接材料这些落地层。

这个对照特别重要。因为它能帮助你同时尊重论文原意和当前工作区现实，而不会把二者混成一个层面。

#### 15.3 读到 `Splat-Plan` 段落时，该直接去看哪些本地文件

这一部分最适合对照 `run_splatplan.py`、`splatplan/splatplan.py`、`splatplan/spline_utils.py`、`initialization/grid_utils.py`、`polytopes/collision_set.py`。你不需要按这个顺序每份都读透，但至少要知道：论文里一旦开始讲规划链，你在本地最有价值的落点就是这几个文件。

一个很好用的读法是：先从 `splatplan.py` 看整体骨架，再回头用 `grid_utils.py` 看初始化，用 `collision_set.py` 看约束从哪来，用 `spline_utils.py` 看轨迹如何求出来。这样论文里的逻辑会和代码结构自然贴合。

#### 15.4 读到 `Splat-Loc` 段落时，别急着陷进全部细节，先找入口和角色

对当前阶段来说，`Splat-Loc` 更适合作为“认位置”的阅读对象，而不是“马上打透”的主线对象。论文这部分你最应该先抓住的是：它解决的是基于 RGB 图像的位姿估计问题，并且与 GSplat 场景表示紧密相关。对应到本地，就是 `run_splatloc.py` 作为入口，`pose_estimator/utils.py` 作为工具箱，`ns_utils/nerfstudio_utils.py` 作为场景和数据接口桥梁。

只要先把这三件事对准，你就已经赢过很多一头扎进细节然后迷路的人了。

#### 15.5 论文实验部分怎么和本地场景、方法、结果目录对应

一旦论文进入实验部分，你就应该自然地把它和本地场景名、方法名、run 目录结构联系起来。比如论文里提到的 `old union` 就对应当前工作区常见的 `old_union` 场景；`flightgate` 在上游 README 里对应 `flight`；`SFC` 相关对比在本地则会落成 `sfc-1..4` 这些方法名。你以后越能把论文实验和本地方法/场景一一对上，越说明你不是在“看两份材料”，而是在看同一个系统的两个表述面。

#### 15.6 当论文里给出速度或性能数字时，你在本地该怎么保持清醒

这是一个特别值得讲给学弟听的点。很多新人一看到论文或 README 里的性能数字，就会下意识把它当成本机必然能复现的一模一样数字。更成熟的态度应该是：这些数字首先告诉你方法定位和量级，说明作者宣称它具备什么级别的实时性和效率；但你在本地复现时，仍然要区分论文环境、作者硬件、当前机器、当前 wrapper、当前数据版本和当前阶段目标。

也就是说，论文数字要被当成参照，而不是当成机械验收线。你真正要先确保的是链路打通、结果解释稳定、趋势合理，而不是一上来就被数字牵着跑。

### 16、十种特别常见、但非常值得提前拆掉的误解

到了最后，我想故意把一些很常见的误解再集中拆一次。因为很多同学并不是不努力，而是脑子里有几处小误解一直没被点破，导致整个理解都偏着走。你把这些误解拆掉，项目会轻很多。

#### 16.1 误解一：我只要把官方论文看明白，就自然会做当前工作区

不完全对。论文解决的是系统设计和方法主张，当前工作区还额外承载了本机环境、数据落盘、tmux 长任务、共享机器边界和交接路径这些问题。你当然要看论文，但不能期待论文替你回答所有工作区问题。

#### 16.2 误解二：我只要把 wrapper 脚本跑通，就等于会项目了

也不对。wrapper 脚本让你更稳地运行项目，但真正的算法理解仍然在上游源码和论文主链里。只会跑 wrapper 而不知道它调到哪一层，项目理解会很空。

#### 16.3 误解三：scene 名只是为了方便命令短一点

绝对不是。scene 名背后牵着一整套实验设定、场景资产和结果解读方式。你越早把 scene 看成“实验语义入口”，越不容易把场景切换当成换个字符串。

#### 16.4 误解四：`config.yml` 就是一个普通小配置文件

它远比“普通小配置”重要。它更像进入训练产物世界的门把手。你对它越尊重，越容易把场景入口、Nerfstudio 背景和规划器加载链讲清楚。

#### 16.5 误解五：结果目录只是存东西的地方

不对。当前工作区的 `runs/` 既是结果存放层，也是工程规范和项目记忆层。它承载的是“这次运行发生过”的证据，而不是“东西先放这里”。

#### 16.6 误解六：不碰 ROS/实车，是因为我们做得还不够真

这也是错位理解。当前阶段不碰它们，是因为我们在做排序管理和风险管理。把离线/仿真主链和工程组织做稳，本身就是很真也很值的工作。

#### 16.7 误解七：创新一定要等我先把所有东西都学完

现实里很少这样。更常见的是，你先把链路做顺，途中慢慢长出问题意识，再从问题里长出创新点。要是非等“全懂”才敢想创新，往往会一直等不来那个时刻。

#### 16.8 误解八：学弟如果一周后还不会改算法，就说明文档没用

这也太苛刻了。对零基础同学来说，一周真正有价值的目标是：能讲清项目做什么、知道从哪里跑起、知道结果去哪里看、能分清 wrapper 和上游、能跟着一条主链读到核心文件。做到这些，就已经非常值了。

#### 16.9 误解九：工程整理不算真正的项目推进

如果没有工程整理，你后面很多算法结果都无法稳定沉淀、无法被别人接手、无法形成可比较记录。从长期看，工程整理不仅算推进，而且常常是让推进真正成立的条件。

#### 16.10 误解十：看不懂的地方越多，说明我越不适合这个项目

这大概是最需要被拆掉的一条。一个中型项目本来就不可能第一次全懂。真正重要的是，你有没有一张地图，能不能知道自己现在不懂的是哪一层，能不能把不懂的问题逐步压小。只要这三件事在发生，你就是在很正常地进入项目，而不是被项目拒之门外。

### 17、这两份文档最终想帮学弟建立的，不是“知道很多名词”，而是三种底层能力

写到最后，我想把这轮重写的真正目标再说透一点。`01` 和 `02` 如果只是让学弟知道很多词、看过很多文件名，其实还远远不够。它们真正想建立的，是三种底层能力。

第一种能力，是定位能力。也就是碰到一个词、一个脚本、一个目录、一个报错时，你能迅速判断它站在哪一层、跟谁有关、接下来该往哪走。第二种能力，是讲述能力。也就是别人问你项目是什么、主链怎么走、当前边界是什么时，你能把它讲成一条别人听得懂的线。第三种能力，是推进能力。也就是你不需要再靠运气乱翻文件，而是知道下一步该读哪份文档、看哪个脚本、跑哪条最小链路。

如果这三种能力开始长出来，那么哪怕你现在还不是很会写算法，也已经真正进入项目状态了。对一个零基础转进来的学弟来说，这恰恰是最宝贵的起点。

### 18、把这份 `02` 放下之前，你最值得记住的最后一句话

如果一定要把整份 `02` 压成一句最值得带走的话，我希望是这一句：当前 `/home/howard/Splat-Nav` 工作区，不是论文本体的替身，也不是一堆零散脚本的堆积，而是一套把上游算法、共享机器现实、运行规范、结果沉淀和后来者入门路径接在一起的工程化工作区。你只要把这句话真正装进脑子里，很多之前让人焦虑的分岔路都会慢慢变清楚。

因为从这句话往下，你自然会知道：该去哪里看算法，该去哪里看运行入口，该去哪里找结果，该去哪里看解释材料，该在哪里保持边界。项目一旦开始以这种方式在你脑中成形，它就不再是吓人的陌生对象，而会变成一张确实可以走、可以讲、可以继续扩展的地图。

### 19、如果你真的把论文 PDF 摊开来读，我建议你按怎样的节奏读，才能和当前工作区真正对上

前面我们已经讲过“论文应该和本地工作区对照着读”，但如果再往实操推进一步，你可能还会问：那我真的把 PDF 打开以后，应该按什么节奏读？我不想一上来就淹死在论文里，也不想读完了却和本机一点没对上。这个问题问得非常好，因为很多新人卡的恰恰不是态度，而是节奏。节奏一错，就会出现要么看得很痛苦、要么看完也落不回项目的情况。

#### 19.1 第一轮阅读：只抓“题目、摘要、方法图、实验结论”，不急着碰推导

第一轮看论文时，我非常建议你先把姿态放轻。只读题目、摘要、方法总图、实验总览和结论性段落。为什么这么安排？因为这几块最能帮助你建立“作者到底想解决什么问题、系统有哪些部分、论文想主打什么价值”的宏观轮廓。对当前项目来说，这一轮最关键的输出不是笔记很多，而是你开始会说：这篇工作是在 GSplat 场景表示上做安全规划和视觉定位，规划和定位分别对应 `Splat-Plan` 与 `Splat-Loc`，作者强调的是安全、实时和系统级导航能力。

这种第一轮读法一点都不偷懒。相反，它特别成熟。因为它在帮你先建立问题框架，而不是一上来被细节拖住。

#### 19.2 第二轮阅读：把论文里所有“名词大图”对到本地文件和目录

第二轮看论文时，最值得做的事情是对名词和本地落点。也就是说，当你看到 `Gaussian Splatting map`，你要想到 `config.yml`、Nerfstudio、`GSplatLoader`；看到 `Splat-Plan`，要想到 `run_splatplan.py`、`splatplan/splatplan.py`、`spline_utils.py`；看到 `Splat-Loc`，要想到 `run_splatloc.py`、`pose_estimator/utils.py` 和 `ns_utils/nerfstudio_utils.py`；看到 baselines，要想到 `SFC/`、`run_rrt.py`、`run_nerfnav.py`。

你只要真的做过一轮这样的配对，论文就会从“学术叙事”变成“本地可落地系统”。这是一个很大的认知跨越。

#### 19.3 第三轮阅读：只对 `Splat-Plan` 深挖，因为它是当前阶段最值的主线

对当前机器、当前阶段和当前学弟能力背景来说，第三轮最值得深挖的其实不是整篇论文平均用力，而是把 `Splat-Plan` 这一块重点看深。因为这部分和当前工作区的主执行链最直接相关，也是目前最可能在离线/仿真阶段产出稳定结果、稳定汇报和稳定教学价值的部分。你去看论文里关于安全走廊、碰撞约束、平滑轨迹的描述时，就应该自然地回想本地 `splatplan/splatplan.py` 里 `generate_path()` 的几个阶段。

换句话说，第三轮最值得追的不是论文最难的部分，而是论文里当前项目最活的部分。

#### 19.4 第四轮阅读：带着本地结果回看论文，而不是永远停留在“先懂论文再跑代码”

很多人读论文会形成一种单向想象：好像只有“先全懂论文，再跑代码”这一条路。真实项目里更常见、也更有效的节奏其实是来回走。也就是说，你先有了一点本地结果，比如一条 smoke 输出、一个 batch JSON、一张可行率图，再回头看论文。这个时候论文里的很多词会一下子不一样。你不再只是读到 `feasible`、速度、基线、场景，而是能把这些词和你昨晚真正跑出来的东西连在一起。

这种“结果反哺论文理解”的节奏非常值得鼓励。因为项目理解从来就不是只靠输入长出来的，它很大一部分来自于你真正做过事情以后，阅读重新变得有抓手。

#### 19.5 第五轮阅读：当你开始想创新时，再去看论文没展开的边缘地带

真正到了开始想创新、想专利或想后续会议论文方向时，再去看论文里那些你第一轮完全不会关注的边缘地带才最有价值。比如作者没展开讲透的局限、某些对比没做全的部分、某些假设默认成立但在你当前工作区不一定稳的部分。这个阶段的论文阅读已经不是“帮我入门”，而是“帮我发现边界和缺口”。

所以别着急一上来就追这一层。它更像后劲，不像起跑线。

### 21、如果把当前项目当成你练代码能力和项目架构能力的训练场，它到底在训练你什么

你前面很明确地说过，希望这个项目不仅仅是复现论文，还能帮你练代码能力和项目架构能力，往大厂风格靠。这个想法非常对，而且当前项目其实非常适合作为这样的训练场。因为它既有真实论文算法，又有上游与外层包装的边界，还有共享机器的现实限制、长任务管理、结果归档和带新人文档需求。换句话说，它天然不是一个只写几百行 demo 就结束的小玩具。

#### 21.1 它在训练你的分层思维

当前项目最先训练你的，其实不是某个单点算法技巧，而是分层思维。你得分清论文层和工程层，分清上游和 wrapper，分清单次运行和多轮实验，分清环境问题和算法问题，分清结果生成层和结果消费层。很多人做项目越做越乱，本质上就是分层能力不够。一旦这项能力长出来，你以后进任何稍复杂的工程都会轻松很多。

共享机器、上游保留原样、只在自己 Conda 环境里修问题、用软链接整理重资产、结果统一落盘，这些东西都在训练同一件事：边界感。真正成熟的工程师不只是会写，还知道什么该动、什么不该动、什么要留证据、什么要保持可回滚。这个能力在学校里很容易被忽视，但在真实协作里极其重要。

#### 21.3 它在训练你的结果意识

当前工作区特别强调 `runs/`、JSON、图表、Markdown 摘要和跨 run 汇总，这其实是在训练结果意识。也就是说，你做任何事情都不应只停留在“程序跑了”，而要问：结果怎么保存、别人怎么看、下次怎么比较、周报怎么讲、出了问题怎么追溯。很多大厂工程能力，说到底就是这种结果意识特别强。

#### 21.4 它在训练你的讲述能力

别小看文档和汇报。一个能把项目讲清楚的人，通常比一个只会闷头写的人更适合长期推进复杂项目。当前 `docs/Codex` 的重建，本质上就在训练你这件事：把复杂系统讲成后来者听得懂、跟得上、愿意继续往前走的材料。这种能力以后无论写设计文档、周报、答辩还是技术面试，都会很值钱。

#### 21.5 它还在训练你一种更隐性的能力：面对复杂系统时不慌

这可能是最宝贵的一项能力。复杂项目不会因为你希望它简单，就变得简单。真正优秀的人，往往不是一开始什么都懂，而是面对复杂系统时不慌，能一点一点分层、定位、拆开、记录、推进。当前项目如果你真的陪着它整理下来，它非常有机会帮你把这种气质练出来。

### 22、把这轮文档重建的意图说得更直一点：我们不是在写“资料堆”，而是在写一条可交接的路径

最后这一节，我想把整个 `01 + 02` 重写背后的意图说得更直白一点。我们不是在比谁能收集更多资料，也不是在把 archive 里的内容简单扩写成更厚的文件。真正想做的事，是把当前项目整理成一条对零基础学弟也可交接的路径。所谓路径，意思就是：他能从门口进来，先认词，再认图，再认一次运行，再认上游主轴，再认长期节奏。一路上每一步都不是孤立的，而是有承接的。

这件事之所以重要，是因为很多项目并不是死在技术上，而是死在交接上。前人知道很多，但后人接不住；资料很多，但顺序感没有；脚本不少，但入口全是暗门。当前这轮整理如果能把这些问题至少压下一大半，它本身就已经是项目推进的一部分，而不是项目之外的额外工作。

所以你完全可以很坦然地把这轮文档重建看成真正的工程产出。它不是陪衬，不是装饰，而是在给项目未来的持续推进清路。

### 23、二十个最值得反复问自己的关键问题：把项目真正问熟，而不是只看熟

到最后，我特别想留下这一节。因为很多项目理解其实不是“看”出来的，而是“问”出来的。你问得好，项目就会一层一层开；你如果从来不问，很多内容即使看过，也仍然停留在表面。所以这里我故意整理出二十个最值得反复问自己的问题。它们不是考试题，而是帮你把项目真正问熟的一组抓手。以后你带学弟、做周报、做汇报，甚至自己卡住时，都可以回到这里重新问一遍。

#### 23.1 问题一：当前 `/home/howard/Splat-Nav` 到底是不是官方论文仓库本体

最稳的回答是：不是完全等同，但它把官方论文仓库稳定地接进来了。当前工作区是一个 wrapper 工程工作区，主要负责环境边界、运行规范、结果落盘和文档交接；真正的上游核心实现通过 `splatnav-official/` 入口被接入，并最终指向数据盘上的官方源码仓库。把这件事说清，是你理解整个项目的第一关。

#### 23.2 问题二：既然官方仓库已经在，为什么还要保留 wrapper 这一层

因为现实机器和论文作者自己的实验环境从来不会完全一样。共享工控机、数据盘与系统盘分工、tmux 长任务、结果规范、后来者接手路径，这些都不是官方论文仓库天然负责的事情。wrapper 的价值就在于把这些现实问题吸收进一个稳定外壳里，让上游源码既保持事实来源，又能在当前环境中更可靠地被运行和解释。

#### 23.3 问题三：为什么 heavy assets 要尽量放在 `/data` 而不是系统盘

这不仅是空间问题，也是边界问题。系统盘紧张时，把大体量数据、缓存、结果和环境资产集中到数据盘，能显著降低系统层压力，也更适合共享机器的长期维护。对当前项目来说，这一点特别重要，因为 run 目录、数据集、训练输出和可视化结果都会持续增长。如果没有这层纪律，项目很容易被磁盘问题拖垮。

#### 23.4 问题四：为什么当前工作区里要大量使用软链接

因为软链接允许你同时满足两件事：一是用户面对的是清楚、短、好讲的工作区入口；二是真实大体量资产仍然可以放在更合适的位置，比如数据盘。你既不用复制两大份资产，也不用为了适配路径去大改上游逻辑。对当前项目来说，`splatnav-official` 和 `runs` 这两个入口的软链接设计，都是非常典型的成熟工程取舍。

#### 23.5 问题五：为什么 `config.yml` 这么重要，它到底是不是普通配置文件

它当然是配置文件，但绝不是“普通得可以忽略”的那种。它更像进入某个训练产物世界的门把手。它把你带回 Nerfstudio 训练输出、数据解析结果和场景模型上下文，让 `GSplatLoader` 有地方去加载真正的场景表示。如果你把 `config.yml` 看轻，项目的整个输入链就会变得模糊。

#### 23.6 问题六：为什么当前阶段先围绕 `old_union` 组织，而不是把所有场景平均推进

因为工程推进最怕平均用力。`old_union` 在当前工作区已经具备比较清楚的路径、结果和默认脚本支持，更适合作为稳定主场景。先把一个场景跑顺、讲顺、文档顺，再切到其他场景，会比四个场景一起浅推进更有效。这种选择不是偷懒，而是节奏管理。

#### 23.7 问题七：为什么每次运行都要建 `run_dir`，感觉会不会太啰嗦

如果你只看一次运行，当然会觉得多建目录有点繁琐。可一旦你开始做 batch、overnight、周报和多人交接，就会立刻明白 run 目录有多值钱。它让每次运行都有自己的时间戳、命令记录、环境摘要、日志和产物，避免“昨天那个结果到底怎么来的”变成只能靠回忆猜的事情。对长期项目来说，这一点非常重要。

#### 23.8 问题八：为什么日志不能只看终端，非要落到 `stdout.log`

因为人会走，终端会断，记忆会糊。日志落盘的价值就在于它把运行过程从瞬时现象变成可追踪证据。尤其在 tmux 长任务和第二天复盘场景里，没有日志文件几乎等于没有历史。你以后只要真的查过一两次问题，就会非常感谢这个习惯。

#### 23.9 问题九：为什么 smoke 一定要先于 batch 和 overnight

因为 smoke 的价值不是“规模小”，而是“排雷快”。它让你用最小代价检查主链是否通、输入是否合理、输出是否结构化可读。如果一上来就跳 batch，甚至 overnight，任何小问题都会被更长执行时间和更复杂结果掩盖。成熟的工程从来不是一上来就大跑，而是先做最小有效验证。

#### 23.10 问题十：为什么 `run_in_tmux.sh` 会被看得这么重

因为它不是简单后台运行工具，而是把长任务管理、日志落盘和 run 规范绑定在一起的工程入口。很多项目之所以夜里任务常常“跑没了也说不清”，根源就在于缺这种统一入口。当前工作区能比较稳定地组织长任务，很大程度上靠的就是这种工程细节被封装好了。

#### 23.11 问题十一：为什么 batch 结果不止一个 JSON，还要做图和 Markdown 摘要

因为结果有不同消费层。JSON 适合程序继续处理和精细追踪；图适合快速肉眼判断；Markdown 摘要适合第二天快速扫读和做汇报。这不是重复劳动，而是在降低不同阅读场景下的理解成本。真正成熟的结果管理，都会做这种分层。

#### 23.12 问题十二：为什么 `SplatPlan` 是当前阶段最值得优先吃透的类

因为它正处在论文主张、上游实现和当前工作区复现主线的交汇点上。你吃透它，等于同时吃透了“场景怎么进系统”“规划主链怎么组织”“结果为什么长这样”这三件最关键的事。相比之下，很多其他文件虽然也重要，但不具备这么强的主轴性。

#### 23.13 问题十三：为什么现在不优先让学弟钻 `Splat-Loc`

不是因为 `Splat-Loc` 不重要，而是因为它在当前阶段对认知负担更重。定位链同时牵涉图像、特征、配准、位姿表示和递推估计。对零基础学弟来说，先把 `Splat-Plan` 和工作区三层结构稳住，再回来看 `Splat-Loc`，推进顺序会更合理。排序清楚，比一上来贪多更重要。

#### 23.14 问题十四：为什么当前阶段明确不碰 ROS、语义分支和实车

因为它们每一样都会显著提高系统复杂度，而当前第一阶段的核心目标是离线/仿真复现与工程化整理。只要主链、结果验收、文档交接和工程边界还没稳住，就直接把 ROS、语义增强和实车全压进来，项目几乎肯定会失焦。真正稳的推进，不是能碰的都碰，而是知道什么时候先不碰。

#### 23.15 问题十五：为什么工程整理本身也算项目成果，而不只是陪衬

因为没有工程整理，很多结果只是一次性现象；没有文档和规范，很多理解无法被后来者接住；没有 run 目录和汇总，很多实验无法被稳定比较。也就是说，工程整理不是和项目分开的附属工作，而是在把项目从“个人尝试”升级成“团队可接手系统”。对长期推进来说，这非常值钱。

#### 23.16 问题十六：如果未来要重构代码，为什么不能凭感觉乱动上游

因为上游仓库是论文事实来源，动它就等于在动“作者原实现”这层事实。重构当然可以做，但前提应该是你已经非常清楚原逻辑做了什么、你的改动边界在哪、验证方式是什么，以及哪些行为绝不能被改坏。否则所谓重构很容易变成把项目重新搅乱一次。

#### 23.17 问题十七：学弟读完 `01 + 02` 以后，最起码应该具备什么状态

并不是“会发明新算法”，也不是“能把所有代码默写出来”。更现实、也更有价值的状态是：他能用大白话说清项目做什么、能区分上游和 wrapper、知道该从哪条 smoke 链路起步、知道结果先去哪看、知道 `config.yml` 和 scene preset 各干什么、知道 `SplatPlan` 是当前主轴、知道第一阶段为什么不碰实车。这些状态一旦成立，后面真正动手就会顺很多。

#### 23.18 问题十八：如果学弟一周后还觉得有些地方没完全懂，是不是文档失败了

完全不是。只要他已经不再迷路，知道问题站在哪一层、知道接下来该读哪、敢开始问具体问题、能把项目讲出骨架，那这套文档就已经非常成功了。复杂项目本来就不是一周背完，而是靠一周建立稳定地图，再逐步压细节。

#### 23.19 问题十九：如果未来要从这里长创新点，最健康的起点是什么

不是强行发明新名词，而是基于已经稳定的复现和理解，去观察哪里最痛、最脆、最费人、最容易出错、最值得对比再做深一点。很多创新最早都只是好问题，而不是完整答案。学弟越早接受这一点，越不容易被“我现在还提不出大创新”这种焦虑困住。

#### 23.20 问题二十：什么叫“这套工作区已经真正可交接了”

最稳的标准不是“你自己觉得差不多”，而是后来者能按主线文档找到入口，能区分三层结构，能在不破坏机器边界的前提下跑起一条最小 smoke，能读懂结果目录，能继续往 batch 和更长周期推进，同时你还讲得清每一层在干什么。如果这些条件基本都成立，那这套工作区就已经不只是“能用”，而是“能传下去”。

这其实也是我们这轮重建 `01 + 02` 最根本的目标。不是把资料变厚而已，而是让项目真的长出可交接性、可讲述性和可持续推进性。

### 24、把当前工作区和上游仓库的一、二级目录再做一轮“索引式人话说明”

前面的内容已经从故事、脚本、主轴和论文对照等角度把项目讲开了。这里我想再补一层更像“索引册”的说明，但仍然尽量保持人话和路感。这样做的价值在于，当学弟以后真的开始点目录时，不会只看到文件名，而能很快在脑子里冒出一句“这个地方大概是干什么的”。这层说明不追求对每个文件都深讲，但追求目录覆盖更完整、入口感更清楚。

#### 24.1 工作区一级目录再索引：当你站在 `/home/howard/Splat-Nav` 门口时，到底能往哪几条路走

先从最上层说起。当前工作区里最值得你脑子里形成稳定感的一级入口，一共就这么几类。`configs/` 是机器约定和工程配置入口。`docs/` 是知识和交接入口。`runs/` 是结果证据入口。`scripts/` 是工程执行入口。`splatnav-official/` 是上游源码阅读入口。`third_party/` 是第三方依赖关系声明入口。`README.md` 是门口说明牌。`Makefile` 则是常用动作的快捷入口。

你以后只要一进项目就先意识到“我现在站在一级入口层”，很多不必要的乱翻就会减少。因为你会先问自己：我现在是来读材料、跑任务、看结果，还是读上游代码。问题一旦先分层，动作就不乱。

#### 24.2 `docs/` 的二级目录：三种文档人格，三种使用方式

`docs/archive/` 更像旧讲义和历史资料库，信息广，但不适合零基础直接主线阅读。`docs/guidang/` 更像执行规范和阶段归档区，适合你开始有节奏地做项目以后回来看“做到什么算完成”。`docs/Codex/` 则是当前真正的主线阅读区，专门围绕当前机器、当前工作区和零基础学弟的最短路径重写。

很多人读文档会吃亏，就是因为把这三种人格完全混着用。你以后只要记住：`archive` 偏资料、`guidang` 偏规范、`Codex` 偏主线，就已经很稳了。

#### 24.3 `scripts/` 的二级视角：虽然都在一个目录里，但其实分成六种工作性格

你以后不要把 `scripts/` 仅仅看成一个装满可执行文件的目录。更有帮助的做法，是在脑子里把它再切成六种性格。环境脚本负责“让机器准备好”；数据脚本负责“让资产完整并对上路径”；run 和 tmux 脚本负责“让任务稳定发生”；smoke/batch/overnight 脚本负责“让实验真正执行”；可视化和聚合脚本负责“让结果会说话”；同步脚本负责“让上游关系不失忆”。

一旦你有了这种二级视角，哪怕以后再往 `scripts/` 里加脚本，你也会更自然地知道它应该属于哪一类，而不是随手堆进去。

#### 24.4 `runs/` 的二级结构：目录名、日志文件、结构化结果、图和摘要分别承担什么角色

`runs/` 里的二级世界也很值得形成直觉。最外层的时间戳目录是在讲“这是哪次任务”；目录里的 `env.txt`、`cmd.txt`、`stdout.log` 是在讲“任务如何发生”；JSON 是在讲“程序级结构化结果”；图和 Markdown 摘要是在讲“人如何快速消费这些结果”；如果是聚合或报告目录，CSV 和跨轮趋势图又是在讲“多次实验之间如何比较”。

所以 `runs/` 不是简单“文件越来越多”的地方，而是一个结果层次不断往外展开的地方。你越有这种层次感，越会觉得当前工程是清楚的。

#### 24.5 `third_party/` 的二级存在感：它虽然目录不大，但概念很重要

当前 `third_party/` 最显眼的就是 `splatnav-official` 这个入口。它的物理内容不复杂，但概念价值很大。因为它在反复提醒你：上游官方仓库不是和 wrapper 混写的一堆文件，而是一份被接入进来的第三方依赖。对于长期维护和后续带人，这个提醒特别有用。它会让你一直记得“哪些是事实来源，哪些是我们自己的工程组织”。

### 25、上游仓库的一、二级目录索引：以后你点开时，脑子里最好先冒出什么话

现在把目光转到 `splatnav-official/`。这里目录看上去会更“研究仓库”一点，也就是既有核心实现，也有实验入口、可视化工具、历史结果和辅助脚本。对新人来说，最有用的不是把这些目录当成平铺世界，而是先给它们分配一句“角色句”。下面这一轮索引，目的就是帮你建立这种角色句。

#### 25.1 `SFC/`：这里在讲 baseline 家族，而不只是某一个方法文件

点开它时，你脑子里最好先冒出一句：这里是安全飞行走廊家族的实现区。`corridor_utils.py` 是主轴，`astar_utils.py` 和 `helper_utils.py` 是支撑，`viz_utils.py` 是展示辅助。只要这句角色句在，你后面看 `sfc-1..4` 时就不会再像看四个凭空来的标签。

#### 25.2 `splat/`：这里在讲“场景怎样被带进系统”

点开 `splat/` 时，你最好立刻想到：这是场景入口层。核心关键词就是 `GSplatLoader`。也就是说，这里不是在做路径规划，而是在做“让后续系统真正能拿到 GSplat 场景对象”。只要这句话在脑中稳住，`splat_utils.py` 的位置就非常清楚。

#### 25.3 `splatplan/`：这里就是规划主轴，不用客气，优先级最高

这一层你几乎可以直接把它当成“当前阶段最重要目录”。点开它时脑子里就应该是：这里是当前离线/仿真复现主轴。`splatplan.py` 负责主流程，`spline_utils.py` 负责轨迹求解。以后你只要对项目主链有任何疑问，都很适合优先回到这里。

#### 25.4 `initialization/`：这里在讲“先给我一条能走的骨架线”

你点开它时，最值得先想起的就是这句话。这里负责的是离散初始化，不是最后答案。`grid_utils.py` 会让你看到 Voxel、PointCloudVoxel 和 GSplatVoxel 这些角色，帮助你理解连续场景为何要先压成网格骨架。它的角色感一旦成立，后面很多 A* 和投影到最近可导航点的行为就很好理解。

#### 25.5 `polytopes/`：这里在讲“安全约束从哪里长出来”

点开它时，你应该先想到：这里是安全走廊和约束真正被构造出来的几何后台。`collision_set.py` 很适合作为第一入口，因为它直接把“相关障碍提取”和“包围盒 + 半空间”这种概念展开了。以后你只要问“这些约束到底怎么来的”，很自然就该回到这里。

#### 25.6 `ellipsoids/`：这里在讲“高斯怎样变成可算几何对象”

这个目录一开始可能不那么亲切，但它特别关键。因为高斯如果只停留在视觉效果层，就很难真正进入导航约束。这个目录承担的，就是把高斯变成协方差、椭球、相交测试、mesh 等可计算几何对象的工具层。它不总是第一个读，但你越往后越会感谢它的存在。

#### 25.7 `ns_utils/`：这里是和 Nerfstudio 世界握手的地方

点开它时，最好先想到“桥梁”两个字。这里不是在做规划本身，也不是在做结果展示，而是在让 Nerfstudio 的训练世界和当前项目的规划/定位世界能够接上。只要这层角色稳住，`config.yml` 和 `GaussianSplat` 这些东西的关系就不容易乱。

#### 25.8 `pose_estimator/`：这里是定位工具箱，而不是项目的杂物间

新手很容易被这里函数多、概念杂的样子吓住。其实更好的角色句是：这是定位工具箱。SIFT、LightGlue、PnP、ICP、位姿表示和一些递推估计相关工具都在这里，是为了支持 `Splat-Loc` 这条链。只要知道它是“为定位服务的工具箱”，它就不会显得那么杂乱无章。

#### 25.9 `nerfnav/`：这里在提醒你作者不是只和自己比

这个目录的角色句可以很简单：这里对应一条 NeRF-based 导航对比路线。它提醒你论文研究不是只展示自己方法，还保留了与另一类技术路线比较的实现痕迹。对做全景理解和后续可能的研究感培养都很有帮助。

#### 25.10 `results/`、`plotting/`、`blender/`、`visualize.py`：这里统称“结果会说话的一层”

如果把这几部分放在一起记，会很轻松。`results/` 偏已有结果和处理脚本，`plotting/` 偏图表辅助，`blender/` 偏离线可视化或渲染辅助，`visualize.py` 偏交互式查看。你不用第一次就把它们全分得很细，但至少要知道：这里属于展示与结果处理层，而不是规划主轴层。

#### 25.11 `run_splatplan.py`、`run_splatloc.py`、`run_rrt.py`、`run_nerfnav.py`：这些文件名本身就在泄露项目组织方式

看到这些入口文件时，你最好形成一个自然习惯：文件名前半通常就在告诉你它对应哪条方法链，`run_` 则说明它更像实验入口而不是底层工具。只要有这个习惯，你以后点开任何 `run_*.py` 都会先问：这是在跑哪条链，入口之外它会调到哪些目录去。这种提问方式非常值钱。

### 26、如果以后你一段时间没碰这个项目，又回来继续看，最推荐的复位方式是什么

项目不是总能连续推进。有时你会忙几天、忙一周，或者切到别的事上去。等你再回来时，最怕的就是又陷入“我上次看到哪了来着”的失重感。所以这里我想再留一个非常实用的小建议：如果以后你有一阵没碰这个项目，再回来时不要试图从记忆硬接，而是主动做一次复位。

最推荐的复位顺序其实很简单。先回到 `/home/howard/Splat-Nav` 根目录，看一眼一级结构；再打开 `docs/Codex/00_统一说明_阅读导航与项目总摘要.md` 用几分钟复位主线；然后扫一眼这两份厚文档的目录，把自己拉回地图；再根据当前任务是“读代码”还是“看结果”，去 `scripts/`、`splatnav-official/` 或 `runs/` 继续走。只要你接受“项目复位也是工作的一部分”，就不会再因为短暂停顿而把自己搞得特别焦虑。

这其实也是这轮文档重建很想做到的一件事：不仅让第一次进门的人有路，也让中途暂停后再回来的人能迅速找回路。真正好的项目材料，不该只服务第一次阅读，而应该能支持很多次重新进入。

### 27、当论文、项目页、README 和当前工作区说法不完全一致时，你该相信谁、怎么判断

真正做项目的人很快就会发现，一个系统在不同材料里出现时，口径并不总是完全一致。论文会更关注方法主张和实验结论，项目页会更关注总览和展示，README 会更关注依赖、数据和入口，当前工作区文档则更关注本机边界、工程组织和交接路径。对新人来说，这种不完全一致非常容易造成心理波动，好像自己是不是看错了。其实大可不必。真正成熟的做法，不是期待所有材料句句一模一样，而是学会判断“这份材料在回答什么问题”。

#### 27.1 第一原则：先分语境，再谈对错

只要你发现两份材料的说法不完全一样，最先应该做的不是判断谁错，而是先问：它们各自在回答什么问题。论文回答的是系统设计和方法主张；项目页回答的是如何快速理解这项工作；README 回答的是仓库怎么开始；当前工作区文档回答的是在这台机器上怎么稳当地复现、整理和带人。很多所谓不一致，真正原因只是语境不同。

你一旦有了这个第一原则，心态会稳很多。因为你不会再一看到差异就觉得自己看不懂，而是会先去找它们的关注点差异。

#### 27.2 第二原则：涉及“方法做什么”，优先看论文和上游核心代码

如果冲突发生在系统目标、模块作用、方法步骤这种层面，那么最值得优先参考的，通常还是论文和上游核心代码。因为它们更接近作者原始主张和实现事实。比如 `Splat-Nav = Splat-Plan + Splat-Loc`，比如安全走廊和样条轨迹的大骨架，这类东西的事实锚点就更应该落在论文和上游实现上。

当前工作区文档在这一层做的，是翻译和解释，而不是另起一套方法定义。

#### 27.3 第三原则：涉及“在这台机器上怎么跑”，优先看当前工作区 README 和 `docs/Codex`

如果问题变成“这台机器上路径怎么组织”“为什么结果放在 `/data`”“为什么长任务进 tmux”“为什么这里有 wrapper 脚本”，那这时最优先的参考就不再是论文，而是当前工作区自己的 README 和文档。因为这些问题本来就不属于论文要回答的范围。它们是当前机器、当前协作方式和当前工程化组织的产物。

你以后越早接受“不同问题对应不同事实锚点”，越不会在材料差异前焦虑。

#### 27.4 第四原则：涉及“具体命令和目录”，优先看本机实际文件系统

这条尤其重要。无论论文、README 还是文档怎么写，真要落到这台机器上，最终的最高优先级事实仍然是当前文件系统里真实存在的目录、软链接和脚本。也就是说，`readlink -f`、`find`、`ls`、`sed`、打开真实文件本身，很多时候比争论文字口径更可靠。因为路径有没有连对、文件是不是在、脚本实际怎么写，这些都属于机器上最直接的事实。

成熟的项目习惯里，最终永远有一层“回到现场看真实文件”。

#### 27.5 第五原则：一旦发现差异，最好的动作是“补解释”，不是“先焦虑”

当前这轮文档重建本质上就在做这件事。不是假装所有口径天然一致，而是把差异的原因、层次和桥接关系讲出来。比如为什么论文讲系统层，工作区文档讲工程层；为什么 README 提数据结构，而 wrapper 文档提 run 目录和 tmux；为什么上游入口像作者实验台，而本机脚本像可交接外壳。

所以以后只要你发现新差异，不要先焦虑，先想：我能不能把这层差异解释清楚。很多看似冲突的问题，一旦被解释开，反而会让你的理解更深。

### 28、以后无论新场景、新脚本、新结果还是新需求进来，你都应该怎么把它重新挂回这张地图

真正有生命力的项目，不会永远停在今天这批文件和这套结果上。未来很可能还会有新场景、新脚本、新实验方法、新结果格式，甚至新的带人需求。如果你真的把这份全景文档吃进去了，那么面对新增内容时，你最不该做的是慌着把它当成“新宇宙”。更好的做法，是先问：它应该挂回当前地图的哪一层。

#### 28.1 新场景进来时，先把它挂到“场景入口 + 实验设定”这两层

不要一看到新场景就立刻陷进路径细节。先问两个最根的问题。第一，它的 `config.yml` 和相关资产入口在哪里。第二，它对应的 scene preset 或实验摆法怎么定。这两个问题一旦明确，新场景就不再是陌生物，而是被挂回了“场景入口层”和“实验设定层”。

只要这个动作先做，后面无论是 smoke 还是 batch，都比较容易接上当前工作区的主流程。

#### 28.2 新脚本进来时，先问它属于环境、数据、执行、汇总还是同步哪一类

这条特别适合你未来自己继续工程化整理时用。不要让新脚本直接以“又多了个脚本”的形式进入项目。你应该先问它在六种 wrapper 性格里属于哪一种：环境、数据、run/tmux、执行链、结果消费还是同步维护。只有把这个类先分出来，脚本才不会越来越像杂物堆。

这其实就是很实用的架构思维训练。

#### 28.3 新结果进来时，先问它服务的是程序消费、人工快读还是跨轮比较

同样地，新结果文件也不该只是“多了个产物”。你先问它是服务程序继续读取的结构化结果，还是服务人工快读的图和摘要，还是服务跨 run 比较的聚合结果。只要这个功能定位先稳住，结果目录就不容易越长越乱。

很多项目后期难维护，不是结果太多，而是没人再说得清每类结果到底给谁用。

#### 28.4 新需求进来时，先问它是在扩展主线，还是在引入另一条复杂性

未来导师、师兄或者项目阶段推进时，很可能会带来新需求。比如换场景、加一类 baseline、补更多图、切 ROS、碰语义、做专利、做论文初稿。面对这些需求时，最值钱的问题永远是：它是在扩展当前主线，还是在引入另一条复杂性。如果是扩展主线，可以挂到现有地图上继续推进；如果是引入新复杂性，就应该先明确边界和时机，而不是被热情裹着走。

这条判断能力，几乎就是项目推进质量的分水岭。

#### 28.5 真正成熟以后，你会发现地图不是束缚，而是让复杂性变得可接住的工具

很多人一开始会担心，把项目讲得这么分层、这么有地图感，会不会反而限制灵活性。其实恰恰相反。地图越稳，你接复杂性的能力越强。因为新增内容再多，也只是挂回已有层次，而不是每来一个东西都把你打回迷路状态。

这也是这份 `02` 最后真正想送给你的东西：不是一份静态说明书，而是一张能够继续接住未来变化的地图。只要这张地图在，你就不太容易被项目新的复杂性吓住。你会知道，先分层，先定位，再推进。很多看起来很大的事情，其实就是这样一点一点被接住的。

### 29、十个“一分钟复述模板”：以后无论口头汇报、和师兄沟通还是给学弟讲解，都能直接拿来用

有些知识你明明已经懂了七八分，但一张嘴还是容易乱。这不是理解没到，而是表达模板还没长出来。所以最后我再补一个很实用的小附录：十个一分钟复述模板。它们不是标准答案，而是帮助你快速把项目讲清楚的“起手架”。以后你不管是在组会里被点到、和师兄临时沟通、还是带学弟过项目，都可以从这里借一个骨架开始说。

#### 29.1 模板一：一分钟讲清“这个项目到底是干什么的”

你可以这样说：这个项目的核心不是重新做三维重建，而是站在 Gaussian Splatting 场景表示上，进一步完成导航系统里的两件核心事。第一件是 `Splat-Plan`，也就是在场景里规划一条安全、平滑的轨迹；第二件是 `Splat-Loc`，也就是根据 RGB 图像估计机器人当前位姿。当前我们在这台机器上主要先把离线/仿真的 `Splat-Plan` 链路复现和整理清楚，同时用 wrapper 工程层把环境、运行和结果归档规范化。

这段话的好处在于，既讲了论文系统，也交代了当前阶段边界。

#### 29.2 模板二：一分钟讲清“为什么工作区里会有 wrapper 和官方源码两层”

你可以这样说：官方源码是论文算法和作者实验入口的事实来源，必须尽量原样保留；wrapper 工作区则负责解决当前机器上的现实问题，比如 Conda 环境、数据盘落盘、tmux 长任务、run 目录和交接文档。也就是说，wrapper 不是替代上游，而是让上游在本机环境里更稳、更可追踪、更适合后来者接手。

这段话特别适合用来回答“为什么不直接只看官方仓库”。

#### 29.3 模板三：一分钟讲清“从命令到结果，主链路是怎么走的”

你可以这样说：当前最小主链一般是从 shell 包装脚本进入，比如 `run_splatplan_smoke.sh`。它先建 run 目录、记录命令、激活环境，再调用 `smoke_splatplan.py`。Python 入口会根据 `config.yml` 和 scene preset 构造 planner，通过 `GSplatLoader` 读入场景，再调用 `generate_path()` 完成初始化路径、碰撞集合、多面体约束和样条优化，最后把结果写成 JSON，并把日志和相关产物沉淀到 `runs/` 目录。

只要你能把这条链顺着说下来，对项目的骨架理解就已经很稳了。

#### 29.4 模板四：一分钟讲清“为什么 `config.yml` 这么关键”

你可以这样说：`config.yml` 虽然看起来只是一个配置文件，但它在当前项目里更像进入训练场景模型的门把手。它背后连接的是 Nerfstudio 训练输出、数据解析结果和 GSplat 场景上下文。没有它，`GSplatLoader` 就不知道去哪里拿场景，后面的规划和定位链也就失去了具体对象。

这段话很适合讲给第一次接触 Nerfstudio 生态的人听。

#### 29.5 模板五：一分钟讲清“为什么要先 smoke，再 batch，再 overnight”

你可以这样说：smoke 的目的不是跑得少，而是先用最小代价验证主链是否通、输入是否合理、输出是否结构化。batch 的重点则是形成统计意义上的方法比较，比如可行率、平均耗时和 P95。overnight 不是另一套算法，而是在更长时间窗口里反复组织 batch，把多轮实验沉淀成第二天可直接查看的总报告。也就是说，这三层的区别不只是规模大小，更是任务目标不同。

这种讲法会让你的实验理解显得很清楚。

#### 29.6 模板六：一分钟讲清“为什么当前阶段不碰 ROS 和实车”

你可以这样说：当前阶段先不碰 ROS 和实车，不是因为它们不重要，而是因为我们在做更稳的排序。只要离线/仿真链路、结果验收、工程边界和交接路径还没稳住，直接去碰更高复杂度系统只会让问题层次叠加。现在先把 `Splat-Plan` 的离线主链做成可跑、可讲、可交接的状态，后面再切 ROS 和实车会更合理，也更节省时间。

这段话既能保护节奏，也能显得你对系统复杂性有判断。

#### 29.7 模板七：一分钟讲清“学弟第一周最应该学会什么”

你可以这样说：第一周最重要的不是会改算法，而是建立项目地图和运行地图。也就是说，学弟至少要能分清上游和 wrapper，知道 `config.yml` 和 scene preset 各干什么，能顺着 smoke 主链讲出一次运行怎么走，知道结果先去哪看，知道 `runs/` 里的日志、JSON、图和摘要各是什么角色。只要这些骨架立住，后面真正动手就不会那么慌。

这段话特别适合你以后和学弟对齐预期时用。

#### 29.8 模板八：一分钟讲清“这套项目为什么也很适合练工程能力”

你可以这样说：这个项目不只是论文复现，它还天然是一个很好的工程训练场。因为它同时要求你处理上游与外层包装边界、共享机器环境约束、长任务调度、结果沉淀、文档交接和后来者入门路径。也就是说，你在这里练到的不只是算法阅读，还包括分层思维、边界感、结果意识和讲述能力，这些都很符合大厂工程能力的训练方向。

这样讲，会让项目的价值不再只剩“跑论文”。

#### 29.9 模板九：一分钟讲清“如果未来要想创新点，该从哪观察”

你可以这样说：创新点不一定从发明新名词开始，更常见的起点是先把现有链路跑顺、读顺、讲顺，然后认真看哪里最痛、最脆、最费人、最容易解释不清。工程层痛点如果反复对应同一类瓶颈，很可能就是未来研究问题的入口。也就是说，现在先把系统做成可稳定观察的状态，本身就在给未来创新铺路。

这段话能很好地帮新人从“创新焦虑”里缓一口气。

#### 29.10 模板十：一分钟讲清“什么叫这套工作区已经可交接”

你可以这样说：所谓可交接，不是我自己觉得差不多，而是后来者能按主线文档找到入口，能区分工作区三层结构，能在不破坏机器边界的前提下跑起一条最小 smoke，能读懂 `runs/` 目录和结果文件，并知道下一步该往哪条主线推进。如果这些条件基本成立，那这套工作区就已经不是“只有原作者会用”，而是真正长出了后续生命力。

这其实就是我们现在重建 `01` 和 `02` 最想做到的事。不是让资料更厚而已，而是让项目真的可以被接住、被讲清、被继续往前推。

### 30、每次接手、复位或开工前，都值得做的五个 sanity check

写到这里，我再补一个很实用的小附录。因为再厚的文档，如果不能转成一些具体动作，很多时候也容易停留在“看过”。所谓 sanity check，你可以先把它理解成“开工前的理智检查”。它不是复杂流程，而是帮你在项目开始前快速确认自己没站歪、没想歪、没把层次弄混。对共享机器、上游依赖、长任务和多文档并存的当前工作区来说，这种小检查特别值钱。

#### 30.1 第一个 sanity check：我现在到底站在哪台机器、哪个目录、哪个入口层

很多混乱都是从这里开始的。你以为自己已经进入项目，其实还在本地终端；你以为自己站在主工作区，实际上停在某个数据目录或旧 run 目录里；你以为自己在看官方源码，实际上点开的是 wrapper 文档。这种错位一旦发生，后面的判断都容易跟着歪。所以每次开工前，先确认 SSH 上的是哪台机器，当前路径是不是 `/home/howard/Splat-Nav`，自己现在准备进入的是 `docs/`、`scripts/`、`runs/` 还是 `splatnav-official/`。

这个动作听起来很基础，但它特别像开车前先看自己是不是坐对了车。基础，却不能省。

#### 30.2 第二个 sanity check：我现在解决的是哪一层问题

这是整个项目里最值钱的小问句之一。你现在卡的是环境、路径、数据完整性、wrapper 调度、上游算法还是结果解释？只要这层分不清，排错和阅读就会非常乱。比如你明明碰到的是 `config.yml` 找不到、软链接没对好，却把自己拖去研究 `spline_utils.py`；或者你明明只是 batch 汇总图没出来，却开始怀疑 `SplatPlan` 核心逻辑。这种误配层次的消耗非常大。

所以每次卡住时，先别急着乱翻资料。先问自己：这到底是哪一层的问题。这个问题一旦答出来，路就会短很多。

#### 30.3 第三个 sanity check：我现在看的材料，回答的是我眼前这个问题吗

有时候你会发现自己看了很多东西，但问题并没有更清楚。多数情况下，不是你不努力，而是你拿错了材料。你现在想知道的是“这台机器上该怎么跑”，却去翻论文；你现在想知道“为什么这个 scene preset 这样设”，却一直停在 README；你现在想知道“这个实验目录到底算成功没”，却又回头去看术语词典。材料并没有错，只是它们不一定在回答你此刻的问题。

所以 sanity check 的第三步，是提醒自己别让材料和问题错位。材料选对，项目理解会快很多。

#### 30.4 第四个 sanity check：我现在需要的是“继续深入”，还是“先做最小验证”

很多新人一陷入复杂感，就会本能地继续读、继续看、继续搜，仿佛多收集一些信息就会自然解决问题。其实有时候更好的动作恰恰是停下来，做一个最小验证。比如先跑一个 smoke；先打开一个真实 `batch_results.json`；先 `tail` 一下 `stdout.log`；先 `readlink -f` 看看软链接真实落点。你会发现，很多抽象困惑一旦遇到具体证据，就会立刻缩小。

所以每次被复杂感压住时，也许你不是真的需要更多理论，而是需要一个小而真的验证动作。

#### 30.5 第五个 sanity check：我这一步有没有留下后来能接住的痕迹

这是最像工程师的小检查。你这一步做完以后，是不是别人能接住？有没有 run 目录、命令记录、日志、结果文件、简短说明？还是说这件事只存在于你脑子和终端滚动文本里？如果是后者，那它对长期推进的价值会大打折扣。当前工作区之所以不断强调 run 规范、文档、结果摘要，说到底都是在训练这个习惯。

真正能持续推进的项目，不是每一步都巨大，而是每一步都尽量留下一点后来者接得住的痕迹。

### 31、第一次给导师或师兄做阶段汇报时，最值得避开的五个表达错误

最后我再补一个特别像带学生时会忍不住讲的东西。很多同学不是没做事，而是一汇报就把自己做过的努力讲散了。对当前项目来说，尤其容易犯几类表达错误。你早点知道，后面会轻松很多。

#### 31.1 错误一：只说“我跑了很多”，不说“我现在把哪条链路讲清了”

“跑了很多”听起来很勤奋，但信息密度很低。更成熟的讲法应该是：我现在已经把哪条链路跑通、讲顺、结构化沉淀下来了。比如“我已经把 `Splat-Plan` 的 smoke 到 batch 主链和 run 目录结果结构讲清楚了”。这会比“我跑了不少实验”显得更扎实。

#### 31.2 错误二：把 wrapper 成果讲成算法创新，或者把算法理解讲成工程整理

这两种错位都很常见。你如果在讲 wrapper 层成果，就坦率讲工程组织、可复现性、日志规范和交接价值；如果在讲算法层理解，就讲上游主轴、场景入口和规划主链。不要把两层混着邀功，也不要把其中一层的价值说轻。层次清楚，表达就会非常稳。

#### 31.3 错误三：只展示一个好看的结果，不交代边界和下一步

一个好看的图当然很重要，但如果你不说明它是在什么边界下做出的、当前还没做到哪、下一步准备怎么推进，汇报就容易显得虚。对当前项目更好的说法通常是：我们现在已把离线/仿真链路做到什么程度，边界仍然在哪，比如还没碰 ROS/实车，下一步准备补哪层材料或哪条执行链。这样汇报会显得非常成熟。

#### 31.4 错误四：一紧张就开始堆术语，不再说人话

这几乎是所有新人都会犯的错。其实导师和师兄大多数时候并不需要你一口气堆十几个术语，他们更想知道你是不是真的知道这些术语在当前项目里各指什么。所以你越紧张，越要提醒自己把话说成人话。比如不是只说“GSplat 和 polytope corridor”，而是补一句“也就是场景怎么进来、安全区域怎么被逐段构造出来”。这会立刻让你的表达变得可信很多。

#### 31.5 错误五：把“还没完全懂”误表达成“我现在什么都不太行”

这也是特别可惜的一种表达。复杂项目里，“还没全懂”是常态，不等于“我什么都不行”。更成熟的说法是：当前我已经把哪些层讲清了，哪些层还在补，卡点目前在哪一层。这样的表达既诚实，又不会把自己说得很虚。它会让对方更容易看见你的真实进展，也更容易给你有针对性的帮助。

如果你把这五个表达错误提前避开，后面无论是和师兄沟通，还是正式做阶段汇报，都会稳很多。这也是为什么我一直希望 `01` 和 `02` 不只是资料，而是能真正帮学弟长出“会看、会讲、会接”的底子。

### 32、这两份文档不是一次性材料，而是会随着项目推进反复回来的“底图”

最后我想再强调一件事。`01` 和 `02` 并不是那种“入门时看一遍，以后就再也不碰”的一次性材料。更好的理解是：它们是当前项目的两张底图。`01` 更像词的底图，帮你在术语海里不迷路；`02` 更像结构的底图，帮你在论文、代码、目录、结果和未来需求之间始终看见主线。只要项目还在推进，这两张底图就会不断被回看、被重新理解、被补上新经验。

#### 32.1 当你第一次带学弟时，它们是引路材料

第一次带学弟时，它们最主要的作用是引路。也就是说，让后来者别一上来就被术语和目录打散，而是先有一张能站稳脚跟的地图。这个阶段，文档价值主要体现在“降低陌生感”和“减少乱试错”。

#### 32.2 当你开始稳定做实验时，它们会变成复位材料

一旦你开始连续做实验、隔几天回来继续推进，这两份文档的价值会变成复位。你会重新看 scene、看 wrapper、看 run 目录、看上游主轴，把自己从短暂停顿里拉回主线。这个时候你会发现，好的文档并不是只在第一次打开时有用，而是在项目一遍遍重启时都能把人接住。

#### 32.3 当你开始思考创新、专利和论文时，它们又会变成边界材料

到了更后面，这两份文档会帮助你守住边界。你会知道哪些是现有系统已稳的部分，哪些是仍然薄弱的部分，哪些观察更像工程整理，哪些问题有机会长成研究问题。换句话说，它们会开始帮你判断“从哪往外长”才更自然，而不是让创新冲动把项目主线冲散。

#### 32.4 当你以后真的进入更复杂的工程环境时，这套思路也不会白费

就算未来你离开这个具体项目，这两份文档里真正值钱的也不只是 Splat-Nav 的局部知识，而是那种面对复杂系统时的处理方式：先分层、先定边界、先认入口、先抓主轴、先建立最小可跑链、再让结果会说话、最后让后来者能接手。你如果把这套思路练熟，它会远远超出当前项目本身。

#### 32.5 所以这轮重写真正想做的，不是“再写厚一点”，而是“把路修出来”

如果一定要给这轮工作下一个最准确的定义，我会愿意把它叫作“修路”。不是简单扩字数，不是机械堆知识点，而是把原本零散、跳跃、容易让新手读不进去的内容，重新铺成一条能让人一步一步走下去的路。只要这条路开始存在，这轮文档重写就已经非常值了。因为复杂项目里，真正稀缺的从来不只是知识本身，而是通向知识的路。

### 33、读完整份 `02` 以后，最值得带走的五句话

最后的最后，我不想再继续铺新信息了。我更想帮你把前面这么长的一份文档，压成五句真正值得带走的话。因为很多时候，一个人不是缺更多材料，而是缺几句在关键时刻能把自己重新拉回主线的话。下面这五句话，如果你真的记住，以后无论是读代码、跑任务、带学弟，还是和导师沟通，都会很有用。

#### 33.1 第一句：这个项目首先是“在 GSplat 场景表示上做导航”，不是单纯的三维重建项目

只要这句话还在，你就不会一上来把项目理解歪。你会始终知道，三维场景表示在这里是基础设施，真正要完成的系统目标是规划和定位两条导航主线。这个认知会帮你在读论文、看 README、看上游源码和看当前工作区时都保持方向感。

#### 33.2 第二句：当前 `/home/howard/Splat-Nav` 是工程化工作区，不是上游论文本体的替身

只要这句话还在，你就不会再把 wrapper 和上游混成一层。你会自然知道：想看算法事实，去上游；想看当前机器怎么稳稳跑、怎么留结果、怎么带人，回到 wrapper 工作区。层次一清，很多焦虑都会自己掉下来。

#### 33.3 第三句：任何复杂感上来时，先分层，先定位，先做最小验证

这句几乎可以当成整个项目推进的心法。复杂不是问题本身，混层才是。你只要先问“这是哪一层的问题”，再做一个小而真的验证动作，比如看真实路径、看真实日志、看真实 JSON，事情往往就会开始变清楚。你以后越早把这句话变成习惯，越不容易被复杂项目吓住。

#### 33.4 第四句：结果不是跑出来就完了，而是要做成后来者接得住的形状

这句话会直接决定你是不是在做长期可推进的项目。run 目录、日志、图、摘要、汇总，不是形式主义，而是在把一次运行变成可回看、可比较、可交接的证据。只要你还记得这句话，项目就不太容易重新滑回“只有跑的人自己知道发生了什么”的状态。

#### 33.5 第五句：真正的目标不是一下子全懂，而是让自己能稳定地继续往前走

这大概是最该送给学弟、也最该送给你自己的最后一句话。复杂系统本来就不可能第一次全懂。真正成熟的状态，是今天比昨天更不迷路一点，知道自己还没懂的是哪一层，知道下一步该接着读哪、看哪、跑哪。只要这种稳定往前走的节奏长出来，项目就已经真正开始被你接住了。

如果你把这五句话带走，那这份 `02` 就不仅仅是一份长文档了。它会开始像一张在你脑子里活起来的地图，在你每次重新进入项目时，重新把你带回主线。
