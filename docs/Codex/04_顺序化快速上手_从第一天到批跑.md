# 顺序化快速上手：从第一天到批跑

这一份文档不追求“把所有知识一次讲完”，而追求“让你知道现在先做什么、为什么先做它、做完以后去哪看结果”。对零基础新人来说，这种顺序感比知识总量更重要。因为项目真正让人崩溃的，常常不是哪一部分绝对难，而是每件事看起来都要学，于是完全不知道第一步应该落在哪。

所以这里不会按“领域知识章节”展开，而是按动作顺序展开。你可以把它当作一条带你从站在门外，到真正推开门、走进屋子、看见桌子上放着什么、最后能自己做一个最小实验的路线。它不是死板的日程表，也不是那种背完就会的秘籍，而是一条适合当前工作区和当前机器条件的最短上手路径。

## 一、正式开始之前，先把入口和工具链站稳

快速上手的第一步不是跑算法，而是把入口打通。SSH、Cursor、GitHub、账号和远程工作区这些看起来琐碎的东西，实际上决定了后面一切动作有没有真实上下文。

### 1、第一天开始之前，先把工具链打通

很多同学一上来就想看论文、跑代码，这种冲劲是好的，但如果工具链没打通，你很快就会在最基础的问题上反复消耗。对于当前项目，第一批必须具备的工具不是 fancy，而是非常朴素：SSH、Cursor 远程连接、GitHub 账户、ChatGPT 账户、Codex 插件、一个能稳定接收注册邮件的邮箱。你不需要把这些工具研究得很深，但至少要进入“能用”的状态。

#### 1.1 Cursor + SSH

你首先要能从自己的电脑稳定进入这台工控机。这里的关键不是炫技，而是建立“我现在所有阅读、运行和结果查看，都是在真正的项目机器上发生”的意识。连接之前，你需要向师兄索要账户、IP、密码或密钥信息。这个动作看起来很琐碎，但它是后面一切工作的前提。没有 SSH，你就没有真正的工作区上下文。

真正开始连接时，建议你先在本地终端验证 SSH 本身是否能工作，再让 Cursor 接入远程工作区。原因很简单：终端里的 SSH 成功，说明网络和账户层没问题；再在 Cursor 里接入，会更容易判断问题是 SSH 本身还是编辑器插件层。

下面这条命令的目的不是开始跑项目，而只是确认“这扇门能不能打开”。你应该把它当成网络与账户的最小验证。

```bash
ssh howard@<服务器IP>
```

如果这一步成功，你应该会看到远程 shell 提示符，而不是继续停留在本地终端。如果失败，先不要急着怀疑项目，先检查 IP、账户名、密码/密钥、网络连接和防火墙。你只有在“能稳定进远端”这个事实上站稳了，后面的路径和环境问题才值得谈。

#### 1.2 GitHub 账户与基本配置

GitHub 在当前阶段不是让你立刻发 PR 或参与开源协作，而是为了建立最基本的工程协作能力。你需要知道仓库是什么、提交是什么、远程仓库是什么，以及将来如何保存自己的变更历史。对于学弟来说，只要先完成注册、登录和最基础的身份配置就够了。

下面这组命令的目的，是在远程机器上留下最基本的 Git 身份信息。它不是项目算法命令，但以后你做任何文档整理、脚本修改和代码提交时，都会用到。

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

跑完以后，不会有很热闹的输出。它更像是在给未来的自己铺路。如果你后面真正需要提交代码，再由师兄决定是否配置 SSH key、是否接入具体仓库远程。

#### 1.3 ChatGPT、Codex 插件与 Gmail

这一层工具链的作用，不是替你思考，而是降低你求助、查阅、生成总结和理解代码的门槛。你现在面对的是一个跨系统、跨工程、跨论文的项目，完全靠自己一点点摸会非常慢。一个稳定的 ChatGPT 账号、Cursor 里的 Codex 插件、一个能接收验证邮件的 Gmail 邮箱，会显著改善你的学习效率。

这里要有一个态度边界：这些工具是辅助，不是外包。你不能只会把一段报错贴出去等别人救你，也不能让工具替你做所有判断。但你完全可以借助它们来理解术语、解释日志、整理运行步骤和归纳代码结构。对零基础新人来说，这是一种很现实的放大器。

## 二、第一天先建立位置感和主线感

这一部分的目标很朴素，就是先让你知道自己站在哪、该先读什么、为什么不建议一开始就在目录里乱逛。位置站稳了，后面动作才会顺。

### 1、真正进入项目后，不要急着乱逛目录

SSH 和工具链打通以后，很多人会立刻在整个工作区里到处点。这个动作很自然，但效率不高。当前项目最好的开局方式，不是先逛所有目录，而是先确认自己确实来到了正确的工作区，然后再按主线看文档。

下面这两条命令的目的，是确认你当前所处的位置，以及这个目录下都有哪些顶层入口。它们是最基础也最值得保留的起点命令。

```bash
pwd
ls
```

如果一切正常，你应该看到当前目录是 `/home/howard/Splat-Nav`，并看到 `docs`、`scripts`、`splatnav-official`、`runs`、`README.md` 这些顶层内容。如果不是这个路径，不要急着继续。先把路径站稳，再做后续动作。很多后续错误，其实都来自第一步就站错了地方。

### 2、先读什么，不要自己猜

工具链就绪以后，第一件真正有价值的事不是马上跑命令，而是建立阅读顺序。因为项目已经不是一个只有单个 `main.py` 的小作业，而是一套带上游、带 wrapper、带运行规范的工作区。如果没有阅读顺序，你很容易一会儿看 archive，一会儿看旧稿，一会儿看脚本，一会儿看上游代码，最后什么都像看过，脑子里却没有主线。

当前最推荐的顺序非常明确。先读 `docs/Codex/00_统一说明_阅读导航与项目总摘要.md`，知道整套材料怎么用。然后读 `01_专业术语全解_项目全词典.md` 的前半部分，把 Linux、路径、环境、日志、run 目录这些高频词清一清。接着读 `02_项目全景与边界_从论文到代码到数据流.md`，建立整体地图。做到这里以后，你再来读这份 `04`，就会轻松很多。

下面这组命令的目的，是快速进入新主线文档目录，而不是继续在历史文档里漂。

```bash
cd /home/howard/Splat-Nav/docs/Codex
ls
```

你应该能看到 `00` 到 `05` 这些新文档。如果你还看到了 `v0.1`、`v0.2` 旧稿，不要再把它们当主线。它们保留只是为了历史记录，不再是正式交接路径。

### 3、第一波最小检查：不要先跑算法，先看环境是否健康

很多新人最想做的是“跑个什么看看”。但如果环境本身不健康，这一步往往会浪费很多时间。更稳的动作是先做环境健康检查。这样做的价值，不是拖延，而是用最小成本先排除最基础的系统问题。

下面这条命令的目的，是通过统一脚本确认 Conda、Python、GPU、Torch CUDA 和关键依赖是否在可用状态。它不是算法命令，但它会决定后面的算法命令有没有意义。

```bash
bash /home/howard/Splat-Nav/scripts/env_health_check.sh splatnav
```

跑完以后，你应该重点看几件事：是否成功激活了 `splatnav` 环境；`torch.cuda.is_available()` 是否为 `True`；`nerfstudio`、`open3d`、`cv2`、`clarabel` 等关键依赖的 import 是否通过。如果这里已经报错，就不要跳过它直接跑 smoke。先把环境这层站稳，后面会省很多时间。

### 4、第一天真正开始读代码之前，先确认工作区三层结构

到了这里，你已经可以开始看一些目录了，但仍然不建议一股脑乱读。你最先要确认的，是工作区的三层结构：`scripts/` 是 wrapper 工程层，`splatnav-official/` 是上游论文源码层，`runs/` 是结果沉淀层。只要这张图没有进脑子，后面读什么都会绕。

下面这组三条命令的目的，是把这三层最关键的位置肉眼确认一遍，尤其是上游源码软链接到底指向哪。

```bash
ls /home/howard/Splat-Nav
ls /home/howard/Splat-Nav/scripts
readlink -f /home/howard/Splat-Nav/splatnav-official
```

跑完以后，你应该能说出三件事：第一，wrapper 脚本都在 `scripts/`；第二，官方源码入口在 `splatnav-official/`；第三，这个入口最终指向数据盘上的真实仓库，而不是 home 目录里另一份独立拷贝。如果这三件事你能讲明白，说明你对项目地图已经开始成形了。

## 三、第一次真正动手，要先把最小链路走通

从这里开始，手册才真正进入动作层。重点不是跑很多，而是先把一条最小而可靠的执行链做成闭环。

### 1、第一次真正动手：为什么先 smoke，而不是直接 batch

到了这一步，才轮到真正跑规划。这里最容易犯的错，就是一上来想跑正式大实验，甚至 overnight。这样做的问题不是“勇气可嘉”，而是变量太多。一旦失败，你很难判断是环境、路径、模型、方法、图表还是汇总出了问题。smoke 的价值就在于它把变量压到最低。

当前最适合第一次动手的动作，是先找一个已有的 `config.yml`，然后用 `run_splatplan_smoke.sh` 对某个场景、某种方法做一次最小规划测试。这个动作的目标不是跑出论文级结果，而是让你第一次真实看到：输入怎么进，run 目录怎么建，JSON 怎么产出，日志在哪看。

下面这条命令的目的，是用一个已有场景的配置做一次最小 smoke。这里的 `CONFIG` 路径需要替换成当前机器上已经存在、你和师兄确认过的那个配置文件。

```bash
bash /home/howard/Splat-Nav/scripts/run_splatplan_smoke.sh old_union /path/to/config.yml sfc-1
```

跑完以后，你不应该第一反应去看终端最后一行，而应该先记住脚本打印出的 `run_dir`。真正的证据都在那里。然后你去看那个目录里的 `stdout.log`、`cmd.txt` 和 `splatplan_smoke_output.json`。如果 JSON 结构完整、关键信息可读、`feasible` 与耗时能解释，那就说明你第一次最小链路已经碰到实体了。

### 2、为什么建议第二步看 run 目录，而不是继续敲下一条命令

很多新人第一次跑完一个命令，马上就想接着跑第二个。这种推进感很自然，但容易把最宝贵的学习机会浪费掉。因为你真正开始理解项目，往往不是敲命令那一刻，而是回头看刚刚那个 run 目录那一刻。命令只是启动，run 目录才是你真正获得证据和理解的地方。

你第一次 smoke 之后，建议优先做这几件事。先打开 `stdout.log` 看结尾有没有异常退出或关键提示。再打开 `cmd.txt`，确认这次 run 和你记忆里的命令一致。然后打开 JSON，看 `meta.scene_name`、`meta.method`、`plan_time_sec`、`output.feasible`、`output.num_polytopes` 这些字段。你只有在这里真的看明白了，下一步进入 batch 才有意义。

下面这组命令的目的，是围绕刚刚那次 smoke 的 run 目录做最小复盘。这里的 `RUN_DIR` 请替换成刚才脚本打印出来的目录。

```bash
cd <RUN_DIR>
ls
tail -n 40 stdout.log
```

如果最后几十行显示规划正常完成，而且目录里能看到 JSON，那么你已经迈过了从“只会敲命令”到“会看结果证据”的第一步。

### 3、第二次升级：什么时候进入 batch

只有当你已经能说清一次 smoke 的输入和输出以后，才建议进入 batch。batch 的意义不是“把命令变复杂”，而是让你第一次看到方法间对比和样本统计。也就是说，它会逼着你开始关心可行率、平均耗时和轨迹分布，而不再只盯着某一条单独路径。

下面这条命令的目的，是围绕一个场景，跑一个小规模 batch。这里故意不建议你一上来就把 `trials` 设得很大，因为学弟第一次做 batch，重点是理解结构，而不是堆数量。

```bash
python /home/howard/Splat-Nav/scripts/run_official_style_batch.py \
  --config /path/to/config.yml \
  --scene old_union \
  --methods splatplan,sfc-1,sfc-2 \
  --trials 12 \
  --seed 1 \
  --keep_traj_limit 3 \
  --output /home/howard/Splat-Nav/runs/manual_batch_demo/batch_results.json
```

跑完以后，你应该去看 `batch_results.json`，重点关注每个方法条目的 `feasible_rate`、`avg_plan_time_sec` 和保存下来的 `trial_records`。如果这一步你能看懂，就说明你已经从“单样例思维”进入“实验统计思维”了。

### 4、什么时候用 tmux，为什么要用 tmux

tmux 不是高深技巧，而是长任务场景下的基本生存工具。你和远程机器之间的连接可能会断，Cursor 可能会重载，网络可能会波动。如果所有长任务都直接绑在当前终端上，一旦连接断了，任务就可能一起死掉。tmux 的作用，就是把任务留在远程机器自己的会话里继续跑。

当前工作区已经把 tmux 使用方式包装进了 `run_in_tmux.sh`。所以你不需要一开始就手动管理很多 tmux 命令，只要先学会“什么时候该把任务送进 tmux”。原则非常简单：只要预计任务运行时间长于你愿意盯着终端等待的时间，就优先考虑 tmux。

下面这条命令的目的，是把一个环境检查或简单任务送进统一 tmux 会话，让你感受一下 run 目录、tmux window 和日志是如何绑定的。

```bash
bash /home/howard/Splat-Nav/scripts/run_in_tmux.sh env_check env_health "bash /home/howard/Splat-Nav/scripts/env_health_check.sh splatnav"
```

跑完以后，脚本会打印 session、window 和 `run_dir`。这时候你应该意识到：tmux 不是一个额外麻烦，而是让长任务“有家可回”的工具。

### 5、第一次批跑之后，优先打开哪些文件

一轮 batch 跑完，最容易被先打开的是图。但如果你正在学习阶段，更推荐你先看结构化结果，再看图。因为图是压缩后的解释层，JSON 才是事实层。一个更稳的顺序是：先看 `stdout.log` 有没有异常；再看 `batch_results.json` 的总体统计；然后看图；最后自己试着用一句话总结每种方法的大概差异。

如果有可视化目录，比如 `figs/`，你可以先看 `summary.md`，因为它比图更适合作为“快读总览”。当你已经习惯这种顺序后，未来做汇报会自然很多，因为你不再是“先找一张最好看的图”，而是“先抓事实，再选图来解释事实”。

## 四、第一周里最该培养的工作习惯

学弟真正能不能接住项目，很多时候取决于习惯，而不是一时的冲劲。这一部分集中讲边界意识、留痕习惯、慢复盘和表达能力。

### 1、`sudo`、`rm` 和输入密码的命令为什么要格外谨慎

你们共用这台机器，而且当前账户和环境边界已经明确划好了。对新人来说，最重要的习惯之一就是：不要轻易运行需要 `sudo` 的命令，不要随手执行不确定目标的 `rm`，任何需要输入密码的动作都要先想清楚它究竟在改哪里、影响谁。因为这些命令的风险不在于它们“长得吓人”，而在于一旦作用范围判断错了，后果往往超出你当前的控制能力。

在当前工作区，绝大多数日常复现和阅读动作根本不需要 `sudo`。如果你发现自己频繁需要管理员权限，那往往意味着方向可能已经偏了，或者你正在试图修复一个不该由你这个层级修复的问题。这个时候最好的动作不是硬着头皮继续，而是停下来确认。

### 2、什么时候算第一周真正入门

第一周真正的入门，不是你看完了多少页文档，也不是你能把多少命令背下来，而是你已经形成一个基本闭环：能通过 SSH 和 Cursor 进入工作区；知道新文档主线在哪；知道 wrapper 和上游源码的区别；能完成最小环境检查；能跑一次 smoke；能找到 run 目录并读出关键信息；能用自己的话解释当前跑的是什么、看到了什么、还不懂什么。

如果这些事情你做到了，就已经非常好了。因为你已经从“项目看起来像天书”进入“项目可以被拆开理解”的状态了。后面的 batch、overnight、源码深读、周报和创新思考，都会建立在这个基础上。

### 3、接下来你该怎么继续

如果你刚刚按这份文档走完了一轮最小路线，下一步建议你回到 `03_输入输出与一次运行验收_从脚本到结果.md`，把刚才亲手跑过的那次 smoke 或 batch 再对照着解释一遍。然后再去读 `05_阶段性目标_一周一月三个月.md`，把自己定位到当前阶段。

真正能把事情做成的人，往往不是最开始懂得最多的人，而是最早形成“动作有顺序、结果有证据、卡点会复盘”这种工作方式的人。希望你从第一天起，就把这个习惯建立起来。

### 4、不要把“快速上手”理解成“急着多跑”，而要理解成“尽快建立稳定节奏”

很多新人一看到“快速上手”这四个字，就会下意识地以为这里讲的是速度，仿佛越快敲出更多命令、越快点开更多文件，就越接近上手。其实在复杂项目里，真正值钱的从来不是表面动作的速度，而是你能不能尽快形成一种稳定节奏。也就是说，你知道什么时候该先确认环境，什么时候该先看文档，什么时候该先做最小验证，什么时候该停下来解释自己刚刚到底做了什么。

我特别想把这一层讲透，是因为零基础学弟最容易被一种假勤奋拖住。一天看了很多文件，跑了很多命令，窗口开了一堆，感觉自己很努力；但晚上回头一想，却说不清今天真正推进了什么。真正的快速上手，不是这种到处出汗的忙，而是开始知道每一步为什么排在这里、做完之后应该看到什么。只要节奏一稳，后面自然会快；如果节奏不稳，再多时间也会被空转吞掉。

### 5、第一天最重要的成果，不是跑通算法，而是把“我站在哪里”这件事讲清楚

很多同学会对第一天有一种很高的期待，仿佛只要自己够努力，第一天最好就要把算法跑起来。这个心情我完全理解，但对当前项目来说，第一天最有价值的成果其实不是一张图或者一个 JSON，而是你开始能把自己的位置讲清楚。换句话说，你要能回答：我现在用的是哪台机器、哪个账户、哪个工作区、哪一套环境、哪一套文档主线。

你别小看这个目标。它听上去不“酷”，但实际上是复杂项目里特别硬的一层底座。因为所有后续动作，都要建立在“我知道自己站在哪”这件事上。你第一天如果只是着急去碰算法，而没有把位置站稳，后面几乎一定会反复出现那种很挫败的情况：明明自己做了不少事，却总有一种脚下是虚的感觉。

所以我会更愿意把第一天的过关标准说成这样：你能稳定 SSH 进去，能在 Cursor 里连到远程工作区，能确认 `/home/howard/Splat-Nav` 是当前主工作区，能说清 `scripts/` 是 wrapper 层、`splatnav-official/` 是上游算法层、`runs/` 是结果层，能打开 `docs/Codex` 并知道新主线从 `00` 开始。只要这些站稳了，第一天就是成功的。

### 6、第一天真正该怎么读文档：不是从头背，而是读到“能开始动手”为止

很多零基础同学一碰到文档就容易走两个极端。一个极端是完全不看，想着先跑起来再说；另一个极端是想把所有文档先完整看完，再开始动手。前者会导致动作没有地图，后者会导致迟迟不敢开始。当前项目更适合的节奏，其实是读到“能开始动手”为止。

这意味着你第一天读文档时，不需要强迫自己把每一章都吃透。更现实的目标是：先从 `00` 里知道整个体系怎么组织；再从 `01` 里把眼下会高频出现的词，比如 SSH、Conda、tmux、run 目录、日志、JSON、wrapper、上游源码这些词先读顺；然后到 `02` 里把项目总地图看一遍。到这一步，如果你已经知道项目分几层、脚本和源码谁管什么、运行结果会落在哪里，其实就已经可以开始做最小动手了。

也就是说，文档在第一天不应该成为一道门槛，而应该成为你进入项目的扶手。你是扶着它往前走，不是抱着它原地不动。

### 7、第一次打开 `scripts/` 时，不要想着“这些我都得会”，而要先学会分组

`/home/howard/Splat-Nav/scripts` 这个目录，对新人来说很容易带来一种压迫感。因为一眼看过去，既有 `.sh`，也有 `.py`，既有环境类脚本，也有批跑类脚本，还有汇总和可视化脚本。如果你此时的心态是“这些我是不是都得先搞懂”，那压力会很大。更好的做法，是先把它们分组，而不是试图一次掌握全部。

一种很实用的分组方式是这样的。第一组是环境和边界类脚本，比如 `bootstrap_env.sh`、`env_health_check.sh`、`fix_torch_cuda.sh`，它们解决的是“机器和 Python 世界今天能不能正常说话”。第二组是运行启动类脚本，比如 `run_splatplan_smoke.sh`、`run_splatplan_smoke_tmux.sh`、`run_official_style_batch.py`、`run_overnight_12h.sh`，它们解决的是“我要如何把一次实验真正跑起来”。第三组是结果整理类脚本，比如 `visualize_batch_results.py`、`aggregate_batch_runs.py`、`post_overnight_report.sh`，它们解决的是“跑完之后结果怎么整理成可读资产”。第四组才是少量数据准备或补洞脚本，比如下载、链接和缺文件补齐相关的那几份脚本。

只要这四组先分开，脚本目录就不再像一锅粥，而会变成几类有职责的工具箱。新手不需要第一天把工具箱里的每把扳手都研究明白，但必须知道哪类问题该翻哪一层工具。

### 8、第二天开始，真正该练的不是“多跑几轮”，而是“每做一步都留痕”

一旦第一天的位置感站稳，第二天开始最值得刻意练的，其实是留痕。所谓留痕，不是把每次敲命令都截图发群里，而是学会让自己的工作天然留下可回查的痕迹。当前项目已经很贴心地把这个习惯嵌进 wrapper 层了，比如 run 目录、日志、`cmd.txt`、`env.txt` 和 `notes.md`。学弟真正需要练的，是不要跳过这些东西，而是把它们当成工作的一部分。

这件事对零基础同学尤其重要。因为初学者最常见的挫败之一，就是前天好像做出过一点东西，今天却完全接不上。不是因为你变笨了，而是因为昨天的痕迹没留下来。只要留痕习惯开始长出来，你就会发现自己的进度开始变得可回溯，信心也会明显稳很多。

所以第二天你再做环境检查、再进工作区、再跑一次 smoke 时，不妨强迫自己多做一个动作：每次做完以后，都到对应的 run 目录里看一眼，顺手在 `notes.md` 里补上一两句。哪怕只是写“这轮链路通了，但 config 细节还没完全搞懂”，它都比什么不留要强得多。

### 9、第一次 smoke 前，最该准备好的不是命令本身，而是“跑完以后我去哪看”的意识

很多新人第一次 smoke 的焦虑，表面上来自不会写命令，实际上更深一层来自不知道跑完以后该怎么办。所以他们会反复盯着命令本身，生怕少一个参数、拼错一个路径。其实更有效的准备方式是反过来：在敲命令之前，先把“跑完以后我去哪看”这件事想好。

比如你应该先知道，这轮 smoke 跑起来以后，脚本会创建一个新的 run 目录；这个目录里至少会有 `cmd.txt`、`stdout.log` 和结果 JSON；你最先应该看的是日志结尾、命令记录和 JSON 关键信息，而不是着急找一张漂亮的图。如果这套预期提前有了，真正敲命令时你心里会稳很多。因为你知道命令不是终点，它只是把你送进一个自己已经大致知道该怎么阅读的结果空间。

这类预期意识其实非常像做实验前先知道观测指标。它不会让你一步不出错，但会显著降低那种“跑完以后整个人发懵”的感觉。

### 10、第一次 smoke 跑完以后，别急着升级到 batch，先做一次“慢复盘”

我很想替很多新人把这个坑提前填上。因为第一次 smoke 跑完时，人通常会很兴奋，特别容易顺势就想继续跑 batch，甚至再看看 overnight。这个冲动可以理解，但如果你不先做一次慢复盘，后面的提升常常会变成表面的。所谓慢复盘，就是你故意不追求立刻进入下一轮，而是回头用十到二十分钟把刚刚这一轮的输入、脚本、run 目录、日志和 JSON 串起来。

这个过程会有点慢，但非常值。因为它能让你第一次把“动手”和“解释”接到一起。你会开始意识到，自己不仅是在运行脚本，也是在和一个复杂系统建立关系。很多真正的理解，都是在这种慢复盘里长出来的，而不是在连续多跑几轮的热闹里突然降临的。

所以如果学弟第一次 smoke 已经跑通，我会非常建议他做一件事：拿着 run 目录，照着 `03` 里讲的输入输出视角，试着用自己的话把这一轮说一遍。哪怕说得磕磕绊绊，也比立刻继续狂跑更值。

## 五、从 smoke 升级到 batch，再慢慢走向更稳的节奏

当最小闭环开始形成，下一步才是顺着规模自然升级。这一部分讲的不是猛冲，而是怎样在不失控的前提下把动作做大、把判断做稳。

### 1、第一次 batch 的目标，不是“接近论文数字”，而是“第一次学会看总体统计”

一进入 batch，很多人心里就会突然冒出一种很重的比较心理，仿佛自己应该马上开始对照论文里的结果、担心数字是不是不够漂亮。对入门阶段来说，这样想太早了。第一次 batch 的真正目标，其实是让你第一次学会看总体统计，而不是单条路径。也就是说，你要开始知道什么叫 feasible rate，什么叫平均耗时，什么叫 P95，以及为什么这些东西值得被同时摆出来。

这一层一旦开始理解，你的视角就会自然升级。你不再只是盯着“某条轨迹成功没成功”，而开始关心“某种方法在一批样本上的整体稳定性怎样”。这件事和论文结果当然是连着的，但它比“数字像不像论文”更基础，也更适合当前阶段。因为只有你先学会看统计，后面才谈得上真正做比较、讲结果、想创新。

### 2、tmux 最容易学会的方式，不是背命令，而是把它看成“远程任务的保险箱”

很多零基础同学一听到 tmux 就会紧张，觉得这是不是某种高手工具。其实对当前项目来说，tmux 最值得记住的不是一串命令，而是一个很简单的比喻：它像远程任务的保险箱。你把一个长任务放进去，即便本地终端断了、Cursor 重连了、网络抖了一下，任务也不会跟着轻易消失。

一旦把 tmux 看成保险箱，很多事情就立刻简单了。你不再纠结“tmux 到底有多少命令我还不会”，而是会先问一个更实用的问题：这件事值不值得放进保险箱。对于当前项目，环境检查这种很短的动作不一定必须进 tmux，但长一点的 batch、overnight，或者你不想一直盯着的任务，就非常适合放进去。

而且当前工作区并没有要求学弟一开始就手打所有 tmux 操作，而是通过 `run_in_tmux.sh` 做了一层包装。这个设计很友好。因为它允许新手先建立“该不该用 tmux”的判断，再慢慢熟悉“tmux 具体怎么管”。这就是一种很典型的工程友好设计：先降低门槛，再逐步深化。

### 3、如果某一步卡住了，先判断自己卡的是“哪一层”，再决定查哪一类东西

快速上手里最怕的，不是卡住，而是卡住以后方向乱掉。很多新人一出问题就开始同时怀疑环境、脚本、论文、数据、路径和自己，结果越查越散。更稳的习惯是，先判断自己卡的是哪一层，再去对应层找线索。

如果你连 SSH 都进不去，显然是机器接入层的问题；如果能进机器但环境检查不过，显然更像环境层；如果环境没问题但 smoke 命令一跑就说找不到文件，那更像路径或资产层；如果文件都能读但 JSON 字段异常，那就更像运行结果解释层；如果结果有了但你说不清它说明什么，那就是理解与表达层。只要先把层次分对，排错效率会高很多。

这件事你现在就值得练。因为以后无论项目变复杂多少，先分层再处理的能力都会一直值钱。复杂项目真正压人的，往往不是复杂本身，而是人一着急就把所有复杂性搅在一起。

### 4、第一周里最值得刻意培养的一种能力，是“把卡点说清楚”

很多同学会以为第一周最重要的能力是“学会很多内容”。这当然没错，但还有一个更隐蔽、也更值得早练的能力，就是把卡点说清楚。因为你不可能第一周就什么都懂，可你完全可以第一周就开始练会清楚地表达“我现在卡在哪”。这件事对合作尤其重要。

比如更有用的表达不会是“我这里不太行”“这个项目太难了”，而会是“我现在 SSH 和工作区已经通了，环境检查也能过，但我在 smoke 这一步还不能稳定解释 `config.yml` 背后的模型入口，所以结果虽然出来了，我心里还不够稳”。你看，这种表达一出来，别人几乎立刻就知道怎么帮你。因为你的卡点不是情绪化的一团雾，而是已经开始有边界了。

学弟越早学会这样表达，和你、和师兄、和我协作都会越轻松。因为别人不是怕你不会，而是怕你卡得很深却说不清自己到底卡在哪里。

### 5、到了第三到第五天，真正值得做的是“把最小闭环从自己手里走顺”

如果前两天已经把工具链、工作区、文档主线和第一次 smoke 摸到了，那么第三到第五天最值得追求的，就不是继续横向扩很多内容，而是把最小闭环在自己手里再走顺一遍。所谓最小闭环，就是从登录远程机器、进入工作区、做环境确认、找到合适文档、跑一次最小 smoke、阅读 run 目录，到最后能留下一小段自己的结论。只要这一圈能基本顺下来，你就已经真正迈进入门状态了。

这个阶段非常不建议心态太浮。很多人一看自己已经能做一点事，就急着把目标抬得特别高，仿佛立刻就该深入所有上游源码、论文细节和创新点。其实更成熟的推进方式，是先让最小闭环在自己手里变得越来越顺。因为任何更大的事情，最终也还是建立在许多这种闭环之上。

### 6、到了第六到第七天，才适合开始把“我会做”往“我会讲”推一步

第一周后段最自然的升级，不是突然去碰所有高级内容，而是从“我会做一点”往“我会讲一点”过渡。也就是说，你可以开始尝试做两件简单但很值钱的事。第一件事，是把自己已经跑过的一轮 smoke 或 batch，按输入、过程、输出、边界的顺序讲一遍。第二件事，是试着向师兄说明当前工作区三层结构和 wrapper 脚本的大致分工。

为什么这一步很重要？因为真正的理解一旦开始能讲出来，就不容易再滑回“只是跟着做”。而且“会讲”这件事，恰恰是后来带学弟、做周报、做专利材料和做论文表达时最重要的底子之一。你第一周未必要讲得很成熟，但非常值得开始试。

### 7、如果一周结束时你还没碰 batch，也不代表你慢；关键要看你手里有没有形成真实闭环

我特别想把这个焦虑提前拆掉。因为很多新人会给自己一种无形压力，觉得别人一周都在跑 batch、看图、聊结果，自己如果一周结束还在 smoke 附近打转，是不是就太慢了。其实对当前项目来说，这个判断标准并不公平。因为真正重要的不是你表面碰到了多少关键词，而是你手里有没有形成真实闭环。

如果你一周结束时，已经能独立 SSH 进入、知道去哪里看主线文档、知道 wrapper 和上游的关系、能跑一次稳定 smoke、能找到并解释 run 目录里的核心文件、能把自己的卡点说清楚，那这就是非常扎实的一周。相反，如果有人表面上已经碰了很多 batch 或图表，但问到输入输出就说不清，那种快反而是虚的。

所以第一周结束时，最好的自我评估不是“我碰到哪一步了”，而是“我手里的闭环是不是开始成形了”。这个判断会更真实，也更能保护你的节奏。

### 8、跑完第一轮 batch 以后，最值得做的不是继续堆更多 trial，而是学会写一段像样的结论

当学弟终于跑完第一轮 batch，往往会有一种非常强的冲动，想把 trial 再加大一点、方法再加多一点、图再多出几张。这种冲动当然能理解，但从成长效率看，更值钱的一步往往是先学会写一段像样的结论。也就是说，你要开始训练自己把这一轮 batch 的总体印象说清楚：哪种方法总体更稳，哪个指标最值得注意，哪一点还不能贸然下结论。

这个动作之所以重要，是因为它会逼着你从“信息接收”走向“判断组织”。图表和 JSON 是外部材料，而结论是你自己的结构。只要你开始能写出哪怕三五句话的像样结论，你和项目之间的关系就会明显变深。你不再只是看见结果，而是开始处理结果。

如果不知道怎么写，完全可以先用一个非常朴素的模板：这一轮在哪个场景、跑了哪些方法、总体可行率大致怎样、耗时层面有什么直观差别、当前还缺什么信息。这个模板不华丽，但很实用。

## 六、从第一周走向长期可持续的工作方式

最后这部分把短期动作重新接回长期工作方式。目标是让这份手册不只服务“第一次上手”，也服务后面持续几周、几个月的推进。

### 1、什么时候可以开始读更多上游源码？答案不是“越早越好”，而是“当你开始知道自己想从源码里找什么”

很多同学看到 `splatnav-official/` 里那么多目录，会自然地产生一种冲动：我是不是应该尽快冲进去，把所有源码都看了。阅读源码当然非常重要，但更舒服、更有效的节点，并不是越早越好，而是你开始知道自己想从源码里找什么的时候。否则你很容易出现“看了很多文件，但不知道自己到底在看什么”的疲劳感。

一个比较好的时机通常是这样的：你已经有过一两次真实运行，知道 wrapper 启动器和上游实现的大致边界，也已经知道自己最关心的是哪条链路。比如你现在最想搞清楚 planner 到底从哪里实例化，或者 `GSplatLoader` 到底把 `config.yml` 背后的东西加载成了什么形态，这时再进上游源码，就会特别有抓手。因为你不是在盲看，而是在带着问题看。

所以不要把“暂时还没系统精读上游源码”误解成自己懒。更重要的是先把问题意识长出来。一旦问题变清楚，源码阅读会顺很多，而且更不容易陷入只见树木不见森林。

### 2、这一份 `04` 真正想给学弟的，不是时间表，而是一种能持续推进的工作方式

写到这里，我其实特别想再把这份文档的目标说透一次。它真正想给学弟的，不是一张严丝合缝的时间表，也不是一种“按我说的每天几点做什么就一定成功”的幻觉。更真实的目标，是帮助他形成一种能持续推进的工作方式：先站稳位置，再建立主线；先做最小验证，再读结果证据；先分层判断卡点，再决定求助方向；先形成闭环，再自然升级规模。

这种工作方式听起来不华丽，却是复杂项目里最不容易过时的东西。因为你以后换项目、换代码库、换导师要求，表面内容会变，但这套推进方式依然能帮你稳住自己。对一个零基础但愿意投入的人来说，这反而是最值得早早长出来的能力。

### 3、读完整份 `04` 以后，你下一步最应该做的三件事

如果你已经把这份 `04` 读到这里，下一步其实非常清楚。第一，回到你自己的机器和账户上下文，重新确认 SSH、工作区路径和 `docs/Codex` 主线没有偏。第二，结合 `03` 再走一次最小 smoke，把 run 目录真正当档案袋来读，而不是只盯着终端。第三，给自己留一小段总结，哪怕只有几句话，也把这几天最稳的一步、最卡的一步和下一步想做的事写下来。

这三件事都不花哨，但非常有效。因为它们会把文档里的阅读感，重新接回真实动作里。只有读和做重新咬合起来，这套文档体系才算真正开始发挥作用。

### 4、最后送给学弟的一句话：不要怕自己现在懂得慢，怕的是一直不把事情讲清楚

最后我想留一句特别简单的话，送给后来真的会照着这份文档走的人。复杂项目里，懂得慢一点并不可怕。零基础、跨专业、第一次接触 Linux、第一次用远程机器，这些都很正常。真正可惜的，往往不是慢，而是一直不把事情讲清楚。今天不清楚自己站在哪，明天不清楚自己卡在哪，后天不清楚自己刚刚到底跑出了什么，这样时间很容易被稀释掉。

所以你完全可以允许自己慢一点，但一定要尽量让自己越来越清楚。清楚路径，清楚边界，清楚输入输出，清楚结果证据，清楚自己不懂什么。只要这种“越来越清楚”的趋势开始出现，这个项目就已经真正开始被你接住了。那时，所谓快速上手，就不再是一句口号，而会变成你脚下正在发生的现实。
