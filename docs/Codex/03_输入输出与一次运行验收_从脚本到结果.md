# 输入、输出与一次运行验收：从脚本到结果

这一份文档专门解决一个很实际的问题：我在这个项目里到底往程序里送了什么，它又吐出了什么，怎样才算真正跑成功。这个问题看起来朴素，其实特别重要。因为很多新人会把“能启动脚本”和“理解一次运行”混在一起。前者只需要照抄命令，后者则要求你知道输入是什么、输出是什么、为什么现在看这个文件、如果结果不对要先查哪一层。

如果这一关不过，后面很容易出现一种假象：命令我会敲，目录我也见过，图我也能打开，但一旦别人追问“这次输入用了什么场景、哪个脚本起了作用、图里这个数字是怎么算出来的、为什么这次虽然没报错却不能算成功”，你就会立刻卡住。所以这份文档不是教你背命令，而是教你把一次运行拆成一个个可解释的部件。

## 一、先建立“一次运行”的整体观念

这一部分先不急着钻进脚本，而是先把“一次运行”这件事从概念上讲顺。只有整体观站稳了，后面 smoke、batch、overnight 才不会被看成三堆互相无关的命令。

### 1、先把“输入”这个词讲清楚

很多人一说输入，就只想到命令行参数。其实在 Splat-Nav 当前工作区里，一次运行的输入至少有四层。第一层是场景与模型输入，也就是某个 `config.yml` 所指向的 GSplat 场景模型。第二层是实验设定输入，包括场景名、机器人半径、速度、加速度、体素边界、分辨率、方法名这些信息。第三层是运行环境输入，包括你是否进入了正确的 Conda 环境、当前 Python 是否可用、GPU 和依赖状态是否健康。第四层才是命令行输入，也就是你在 shell 或 tmux 里真正敲下去的那一串命令参数。

只要把这四层分开，你对“输入”的理解就会立刻提升一个层次。因为你会发现，很多失败并不是参数本身输错了，而是前面三层有一层不成立。比如 `--scene old_union` 没问题，但 `--config` 指错了；或者 `--config` 对了，但当前环境里的 `torch.cuda.is_available()` 是 `False`；又或者环境没问题，但 run 的工作目录不对，导致相对路径失效。真正成熟的输入意识，不是死记参数，而是知道输入是一整条链。

### 2、一次运行最常见的三种规模

在当前工作区里，你最常接触的运行规模有三种：`smoke`、`batch` 和 `overnight`。它们不是三个完全不同的项目，而是同一条主线上的三个层次。

`smoke` 是最小冒烟测试。它只做一件事：用最小代价确认主链路能不能通。对于学弟来说，这是最适合第一次动手的层次，因为它引入的变量最少，一旦出错，也最容易定位。

`batch` 是批量实验层。它不再满足于一条路径跑通，而是要在多个起终点样本上连续运行，并统计可行率、平均耗时、P95 耗时等指标。它比 smoke 更接近论文实验和真正的结果对比。

`overnight` 则是把 batch 在更长时间窗口里持续跑，自动一轮轮归档、可视化和汇总。它的意义在于充分利用夜间机器空闲时间，积累更稳的统计结果，而不是为了把命令写得更长。

理解这三个层次非常重要。因为你如果一上来就混着看，会觉得当前工作区脚本很多、关系很乱。实际上，它们只是围绕同一条主链路，对应不同规模和管理需求的不同包装。

## 二、先把最小 smoke 链路讲透

smoke 是整个项目最适合新人建立感觉的入口。这部分把 smoke 的输入、处理中间链和最低成功标准完整串起来。

### 1、smoke 的输入到底是什么

先从最小的 smoke 说起，因为这是整个项目里最容易看懂、也最适合作为“输入输出样板”的一条链路。当前最小规划测试的核心 Python 入口是 `scripts/smoke_splatplan.py`。它要求你提供四个显式参数：`--config`、`--scene`、`--method`、`--output`。

这里面最关键的是 `--config`。它指向某个具体的 `config.yml`，而这个文件背后关联着场景模型和数据解析信息。简单说，你不是直接把一堆 Gaussian 参数手工塞给规划器，而是告诉脚本：去这个位置读取某个已经训练好的 GSplat 场景。当前项目里，很多“为什么同一个脚本在不同场景上行为不同”的根源，最终都要回到 `config.yml`。

`--scene` 是实验场景名，比如 `old_union`、`flight`、`stonehenge`、`statues`。它看起来只是一个短字符串，但实际作用非常大。因为脚本内部会根据这个名字去选取一组预设，包括机器人半径、速度上限、加速度上限、体素下边界、上边界和分辨率。这意味着场景名不是纯标签，而是决定实验几何范围和机器人配置的一把钥匙。

`--method` 决定你要跑的是 `splatplan` 主方法，还是 `sfc-1` 到 `sfc-4` 这些 baseline。它的作用不是切换一个显示名称，而是决定到底构建哪个 planner 类。`splatplan` 走 `SplatPlan`，而 `sfc-*` 走 `SafeFlightCorridor` 的不同模式。

`--output` 则决定这次 smoke 的结构化结果写到哪里。注意，它不是说“程序自己随便找个地方存一下”，而是你明确指定一个 JSON 输出位置。通常这个位置会被安排在某个 run 目录里，这样日志、命令、环境摘要和结果 JSON 才能放在一起。

### 2、smoke 的中间处理过程在做什么

当 `smoke_splatplan.py` 接收到这些输入后，它先做的不是直接规划，而是构造上下文。第一步是根据 `--scene` 把预设字典里对应的机器人和体素信息取出来。第二步是通过 `GSplatLoader` 读取 `config.yml` 指向的 GSplat 模型，把场景变成后续规划可用的张量属性。第三步是根据 `--method` 决定要实例化 `SplatPlan` 还是 `SafeFlightCorridor`。第四步才是选取一组固定起终点，调用 `generate_path` 执行真正的规划。

这个顺序一定要理解。很多新人会把 `generate_path` 想成一条神秘黑箱命令，输入起点终点，输出轨迹。实际上，起点终点之前还有场景装载、机器人参数设定、体素边界建立和 planner 构建这些步骤。你越早理解这些“前置处理”，后面读 batch 和 overnight 脚本时就越不容易迷路。

### 3、smoke 的输出长什么样

一次规范的 smoke 运行，至少会产生两类输出。一类是结构化结果，也就是你通过 `--output` 指定写出的 JSON 文件。另一类是工程化证据，也就是 run 目录里的 `cmd.txt`、`stdout.log`、`env.txt`、`notes.md`。

先说 JSON。它通常会包含 `meta`、`device`、`plan_time_sec`、`start`、`goal` 和 `output` 这些字段。`meta` 里会记录场景名、方法名、加载时间、机器人参数、体素参数等；`device` 会告诉你这次是在 `cuda` 还是 `cpu`；`plan_time_sec` 记录的是整体规划耗时；`start` 和 `goal` 是这一次实际使用的起终点；而 `output` 里则是更贴近算法结果本身的字段，比如 `feasible`、`path`、`traj`、`num_polytopes` 和若干阶段耗时。

再说工程化证据。它们经常被新人低估，但其实非常重要。`cmd.txt` 说明这次到底跑了什么命令，`stdout.log` 说明运行过程中说了什么、报了什么，`env.txt` 说明当时的机器和环境上下文是什么，`notes.md` 则预留给人工补充结论、问题和后续动作。你以后做复盘、排错、周报和交接，很多价值不一定来自 JSON 本身，而是来自这些配套证据。

### 4、一次 smoke 运行最低怎样才算成功

这个问题非常关键。当前项目里，一次 smoke 不能因为“终端没报错”就直接算成功。最基本的成功标准至少有四条。第一，run 目录确实创建出来了，而且里面有 `cmd.txt`、`stdout.log` 和结果 JSON。第二，结果 JSON 结构完整，关键字段能读。第三，这次运行使用的场景、方法、配置路径和输出路径彼此一致，没有明显串场。第四，`output.feasible` 和耗时等字段至少在语义上能解释，不是空值、乱值或者明显异常。

需要特别提醒的是，`feasible = false` 并不总是等于“程序坏了”，但在入门阶段，如果你连这一点都解释不清楚，就还不能说自己真正理解了一次运行。真正成熟的说法应该是：程序链路跑通了，但在当前约束下这次规划不可行，或者程序链路没通，结果字段根本不完整。这两类情况是完全不同的。

## 三、从 batch 到 overnight，规模放大以后发生了什么

当单次运行变成成组实验，再变成长时段批跑，输入输出的意义都会升级。这一部分专门处理这种规模变化带来的理解变化。

### 1、batch 的输入比 smoke 多了什么

当你从 smoke 进入 batch，变化最大的不是“参数更多了”，而是实验对象从单次规划变成了成组样本。`scripts/run_official_style_batch.py` 在输入上仍然保留 `config`、`scene`、`methods`、`trials`、`seed`、`keep_traj_limit`、`output` 这些参数，但它内部会生成一整组起终点对，而不是只跑一次固定起终点。

这里的 `methods` 往往是一个列表，比如 `sfc-1,sfc-2,sfc-3,sfc-4,splatplan`。这意味着 batch 本身就是为横向比较而设计的。`trials` 决定每种方法要跑多少个样本，`seed` 决定样本顺序或随机过程的稳定性，`keep_traj_limit` 决定保留多少条详细轨迹记录，以避免 JSON 过于庞大。对新人来说，理解这些输入的重点不是参数名，而是它们分别在控制什么层次：方法集合、样本数量、随机性、结果保存粒度。

### 2、batch 的中间处理在做什么

batch 的核心流程可以理解成“在单次 smoke 的基础上，加上样本生成、方法循环和统计汇总”。它先根据场景预设生成一组围绕场景中心的起终点对，再按方法名构建 planner。随后，对每种方法，它会在多个 trial 上循环调用 `generate_path`，记录每次调用的可行性、耗时和部分轨迹结果，最后再把这些 trial 记录汇总成这一方法的整体统计。

这就是为什么 batch 输出里会有 `feasible_rate`、`avg_plan_time_sec`、`p95_plan_time_sec` 这些字段。它们不是某一条轨迹的属性，而是“一种方法在一批样本上的总体表现”。理解这一点后，你再看到图表和 CSV，就知道自己在看的是“总体行为”，不是单次偶然现象。

### 3、batch 的输出具体看什么

一次 batch 运行的主结构化输出通常是一个 `batch_results.json`。它里面至少会包含 `meta` 和 `results` 两层。`meta` 负责记录这次 batch 的整体背景，比如场景、方法列表、样本数量等；`results` 则通常是按方法组织的列表，每个方法条目里会有 `feasible_rate`、平均耗时、P95 耗时、保存轨迹数和若干 `trial_records`。

你第一次看这个 JSON 时，不要试图把所有 trial 细节全啃掉。最有效的方法，是先从每种方法的总体统计开始看。也就是说，先问：`splatplan` 的可行率多少，`sfc-1` 到 `sfc-4` 各是多少，平均耗时差多少。等这些总览数字有了感觉，再回头抽几条 `trial_records` 看具体轨迹细节。

如果可视化脚本也一起运行，那么你通常还会得到一组 PNG 图和一个简单的 Markdown 摘要。比如 `feasible_rate.png`、`plan_time_boxplot.png`、`traj_xy_overlay.png` 这些文件，就是为了把 batch 的主要统计用图形形式表达出来。它们不是替代 JSON，而是帮助你更快看懂 JSON。

### 4、overnight 比 batch 又多了什么

从 batch 到 overnight，真正新增的不是算法复杂度，而是“多轮任务管理”。`scripts/run_overnight_12h.sh` 会在指定总时长内反复创建 run 目录、调用 batch 脚本、保存结果并生成图表。也就是说，overnight 是“多轮 batch 的流水线”。

这件事对新人很重要，因为它提醒你：当实验从单轮走向长时段时，项目管理需求会迅速上升。你不仅要关心一轮跑得对不对，还要关心每轮的命名是否规范、日志是否完整、图是否生成、汇总是否顺利。这正是 wrapper 层存在的价值。

### 5、overnight 的输出应该如何阅读

一轮 overnight 跑完后，你往往会面对很多个 `formal_batch_<scene>_iterN` 目录。如果没有整理思路，很容易看花眼。更稳的阅读顺序是这样的。先看 post-report 阶段生成的总报告目录，通常里面会有 `overnight_summary.csv`、`overnight_summary.md` 和趋势图。因为这一层能先帮你回答“总体上哪种方法更好、哪几轮结果最值得回看”。

然后再回到具体某一轮的 run 目录，去看该轮的 `batch_results.json`、`figs/summary.md` 和各类 PNG。如果某一轮特别好或特别怪，再进一步打开它的 `stdout.log` 看中间过程。这个顺序非常重要。因为总报告帮你先筛重点，具体 run 目录再负责细看细节。

## 四、结果阅读、验收证据与假成功识别

很多人会跑，却不会验。这里集中讲结果该怎么看、证据该怎么留、假成功该怎么识别，以及 run 目录为什么要被当成档案袋。

### 1、跑完后优先打开哪些文件

这是当前项目里非常实用的一条经验。无论是 smoke、batch 还是 overnight，跑完以后都不要急着先看图，更不要急着凭终端最后一行文字下结论。最稳的顺序通常是：先看 `stdout.log` 末尾，确认任务到底是正常结束、异常退出，还是虽然结束但中途有关键警告；再看 `cmd.txt`，确认当前看的 run 与你记忆中的命令一致；然后看结果 JSON 的关键字段，确认 `scene`、`method`、`feasible`、耗时和输出结构合理；最后才去看图和 Markdown 摘要。

对 batch 和 overnight 来说，图很有用，但图是解释层，不是事实源头。真正的事实源头仍然是日志和结构化结果。如果这个阅读顺序建立起来了，你以后对结果的判断会稳很多。

### 2、`runs` 命名规范为什么重要

当前工作区统一采用 `runs/YYYY-MM-DD_HHMM_<topic>/` 的命名规则。表面看，这只是一个文件夹名字；但它其实承载了三层信息。第一，它告诉你任务发生在什么时候。第二，它告诉你这次任务是什么主题，比如 smoke、formal batch、overnight report。第三，它天然适合按时间排序，便于你后来回溯。

命名规范不是形式主义。实验一旦多起来，如果目录名里没有时间和主题，你会非常难找。更要命的是，未来做汇报时，你会拿不准自己说的是哪一轮结果。规范命名，本质上是在为未来的自己和未来的学弟减少混乱。

### 3、一次运行里“哪个脚本做了哪个事”

很多新人最想知道的其实就是这一点，所以这里直接说透。若是一次最小 smoke，通常是 `run_splatplan_smoke.sh` 负责创建 run 目录和准备环境，`smoke_splatplan.py` 负责真正读取模型、构建 planner 并执行单次规划。若是一次 batch，`run_official_style_batch.py` 是真正执行主循环和生成统计 JSON 的核心。若是 overnight，`run_overnight_12h.sh` 是大调度器，负责在时间窗口内多次调用 batch；`visualize_batch_results.py` 负责某一轮 batch 的图；`aggregate_batch_runs.py` 和 `post_overnight_report.sh` 负责事后汇总。若想让任务脱离当前终端长期运行，则 `run_in_tmux.sh` 负责把命令送进 tmux 并和 run 目录绑定。

你把这一层关系记住了，就不会再面对脚本列表时一脸茫然。你会知道：有些脚本是启动器，有些是主执行器，有些是汇总器，有些是看护器。

### 4、几种最常见的假成功场景

第一种假成功，是终端退出了，但 run 目录里只有日志，没有结构完整的 JSON 或图表。说明流程可能在中途就断了。第二种假成功，是 JSON 存在，但关键字段为空、缺失或语义明显异常。第三种假成功，是图已经生成，但图里的数字和 JSON 汇总对不上。第四种假成功，是 `feasible` 全是 `false`，但你却因为“程序没崩”就宣布方法跑通。第五种假成功，是看的 run 目录根本不是你刚才那轮命令对应的目录，自己把结果串场了。

学会识别假成功，是成长非常快的一步。因为它会逼着你从“看终端最后一行”升级到“核对日志、命令、JSON 和图之间的一致性”。

### 5、一次真正过关的运行，应该留下哪些证据

最小过关证据至少包括：一个命名规范的 run 目录；能说明运行背景的 `env.txt`；能复原操作的 `cmd.txt`；能追过程的 `stdout.log`；至少一个结构完整的结果 JSON；如果是 batch 或 overnight，最好再有图表和汇总 Markdown。再往上走一层，还应该有你自己在 `notes.md` 里留下的结论、问题和下一步。

证据这个词很重要。因为项目不是只做给当下这一分钟看的，而是要能交接、能复盘、能汇报。没有证据的“我昨天好像跑出来过”，在合作和科研里几乎没有价值。

### 6、读完这份文档后，你应该具备的能力

如果这一份文档起作用了，你现在应该已经能把一次运行拆成输入、处理和输出三段。你应该知道 `config.yml`、场景名、方法名、环境状态和命令行参数共同组成输入；知道 smoke、batch、overnight 只是同一主链路的不同规模；知道 run 目录、JSON、日志、图和汇总之间各自承担什么职责；也知道“没报错”不等于“真正成功”。

接下来最自然的下一步，就是进入 `04_顺序化快速上手_从第一天到批跑.md`。因为现在你已经知道一轮运行是什么样子了，下一步就该开始按阶段去做真正的动作了。

## 五、把“一次运行”真正讲明白

前面解决的是事实层，最后这部分解决的是解释层。目标是让你不仅知道一次运行发生了什么，还能把它复述出来、汇报出来、带着失败案例一起讲清楚。

### 1、如果把“一次运行”讲成人话，它其实更像一条流水线，而不是一条命令

很多新人最容易被一个错觉带偏，那就是以为“一次运行”就是自己在终端里敲下去的那条命令。这个理解不能说完全错，但确实太窄了。更贴近当前项目实际的说法是：一次运行是一条流水线。你在终端里敲的那条命令，只是把这条流水线启动起来；真正的运行，还包括它之前已经准备好的场景、模型、环境和路径边界，也包括它之后沉淀下来的日志、JSON、图表和汇总。只有把这些前后都看进去，你才算真的理解了“一次运行”。

我之所以反复强调这个角度，是因为它会直接改变你的学习方式。你如果把运行理解成一条命令，就会自然把注意力过度集中在“命令怎么写”；一旦命令敲完、终端滚了几行字，你就会误以为事情结束了。可如果你把它理解成一条流水线，你就会更自然地去问：这个命令前面准备了什么，这个命令中间调用了谁，这个命令后面留下了什么。问题一换，理解就会深很多。

对学弟来说，这个思路尤其重要。因为零基础同学最怕的并不是多看几页文档，而是明明跟着做了几个动作，却始终不知道这些动作属于哪一层。只要“一次运行是一条流水线”这个概念立住了，后面很多输入输出问题都会开始自己归位。

### 2、一次运行开始之前，你其实已经默认依赖了很多前置事实

有时候我们会说“我现在准备跑一轮 smoke”或者“我准备开一轮 batch”。这句话表面上像是在描述一个即将发生的动作，实际上它已经偷偷依赖了不少前提。比如说，这台机器现在是你自己的账户，不是你师兄的账户；你当前确实在 `/home/howard/Splat-Nav` 这个工作区，而不是某个同名但不是这个项目的目录；`splatnav` 这个 Conda 环境已经存在，里面的大部分关键依赖能 import；你手上的 `config.yml` 确实指向某个已经能读取的场景模型；你打算把输出写到的路径具备写权限；你现在看的脚本版本与当前工作区是一致的。

这些前提平时不会全都写在命令里，所以新人很容易忽略它们。可一旦哪一项不成立，问题就会出现，而且常常不是很显眼的那种。例如，你脚本命令看着全对，但 `config.yml` 背后的目标路径其实不存在，于是 loader 在很后面才炸；或者你当前 Python 没切到 `splatnav` 环境，前面甚至能跑几行，到了某个 import 才突然中断。你如果没有前置事实意识，就会很容易把这类错误误认成“算法问题”或者“代码问题”。

所以我希望学弟以后每次准备启动一轮运行时，脑子里先有一个更稳的自问：我这条命令不是从真空里长出来的，它依赖的前提今天都还成立吗？这个习惯看似慢一点，其实会极大降低后续返工的概率。

### 3、把 smoke 真正拆开来看：从你敲下命令那一刻，到 JSON 落盘，中间到底发生了什么

我们不妨把一次最典型的 smoke 运行完整讲一遍。因为只要这条最小链路你真的看顺了，后面的 batch、overnight 都会轻松很多。一次标准的 smoke，通常会从 `scripts/run_splatplan_smoke.sh` 这层 wrapper 开始，而不是直接从 Python 入口开始。这里有个非常重要的工程含义：项目没有要求你每次都手工创建结果目录、手工记录命令、手工保存日志，而是先由 shell 启动器帮你把“跑一次”该有的工程骨架搭出来。

这意味着，当你运行 `run_splatplan_smoke.sh` 时，脚本做的第一件事不是规划，而是先调用 `create_run_dir.sh` 去生成一个命名规范的 run 目录。这个目录里会先生成 `env.txt`、`notes.md`、`cmd.txt`、`stdout.log` 这些骨架文件。你可以把这一步理解成“先铺桌布，再上菜”。如果没有这一步，后面哪怕算法跑出来了，实验也还是零散的。

接下来，这个 shell 脚本会把你此次运行的命令写进 `cmd.txt`，然后激活 `splatnav` 环境，清掉运行时不希望强绑的 `LD_LIBRARY_PATH`，最后真正调用 `scripts/smoke_splatplan.py`。从这一刻开始，算法链才真正启动。也就是说，在 smoke 里，命令、环境、run 目录、日志挂接和算法入口并不是混成一团的，它们是分层完成的。学弟只要把这层顺序看清，就会很容易明白为什么当前工作区看起来文件很多，但其实是有分工的。

而到了 Python 入口 `smoke_splatplan.py` 内部，它首先不是直接算轨迹，而是先解析参数，再根据当前工作区的软链接/目录策略找到上游仓库根目录，然后把这个上游路径插入 `sys.path`。这一步解决的是“算法真实实现代码到底从哪里来”的问题。只有上游路径解析稳了，后面导入 `GSplatLoader`、`SplatPlan`、`SafeFlightCorridor` 这些核心类才有意义。

再往后，它会根据 `--scene` 去取对应场景的预设，包括机器人半径、加速度上限、速度上限、体素边界、分辨率以及和某些场景相关的均值配置。然后再通过 `GSplatLoader` 去读取 `config.yml` 背后的模型。这一步特别像“把场景请进来”。如果场景没有真正进来，后面的 planner 再聪明也无从谈起。也正因为如此，学弟以后碰到 smoke 出错时，不要只盯着 planner，往往 loader 这一层才是前几步最值得先查的地方。

最后，脚本才会根据 `--method` 决定实例化哪个 planner，并对一组固定的起终点调用 `generate_path`。这里为什么用固定起终点？就是为了降低第一次理解的难度。因为只要起终点也随机化，新手就又多了一层变量，很多比较就不稳定了。固定起终点的好处，是你第一次看 smoke 时，注意力可以集中在“链路有没有跑通、输出长什么样、可行性和耗时怎么解释”这些更基础的问题上。

### 4、如果你第一次 smoke 跑完了，最应该问自己的不是“成功了吗”，而是“我现在能把它复述出来吗”

项目学习里有一个非常关键但经常被忽略的节点，就是“能不能复述”。很多人会把“我亲手跑了一次”误以为“我已经理解了这次运行”。其实这两者差得很远。真正能说明你开始理解的，不是你终端里敲过那条命令，而是你能不能把这轮 smoke 的来龙去脉讲给别人听。

比如更成熟的复述应该大致像这样：这次我是通过 `run_splatplan_smoke.sh` 触发了一次最小规划测试；它先给我创建了一个 run 目录，把环境和命令挂进去；然后调用 `smoke_splatplan.py`；Python 脚本根据 `scene` 加载预设，根据 `config.yml` 用 `GSplatLoader` 读取场景，再按 `method` 构造 planner，最后对固定起终点执行规划并把结果写到 JSON。你看，这里面并没有高深的新概念，但它已经说明你不是只会敲命令了。

如果你现在还做不到这种复述，也完全没关系，但你要知道那意味着什么：说明你下一步最应该做的，不是再跑三次同样的命令，而是回头看一次刚才那轮 run 目录，结合脚本入口把流程顺一遍。很多时候，少跑一轮，多复述一遍，反而更能长理解力。

### 5、batch 为什么会让很多人第一次真正意识到“结果”这个词的分量

在 smoke 阶段，你面对的是一轮最小链路，它的价值是让你看见最基础的输入和输出。但一旦进入 batch，项目的味道会明显变掉。因为 batch 不再只要求“这条路径能不能出结果”，它开始要求“多个方法在一批样本上整体表现如何”。也就是说，结果不再是单个点，而开始变成一个统计意义上的面。

这一步对新人是很大的认知升级。因为在 batch 之前，你很容易把运行理解成“某个命令 + 某个输出 JSON”。而到了 batch，你会第一次被迫思考更像实验的问题：为什么要固定 seed，为什么要设 trials，为什么要把多种 method 放进同一次批跑，为什么要限制详细轨迹保存数量，为什么会有 feasible rate 和 p95 这种整体指标。这些问题一旦进脑子，你对项目的理解就已经从“脚本使用者”开始转向“实验参与者”了。

当前工作区里，`run_official_style_batch.py` 就承担了这个角色。它在工程上仍然是一个脚本，但在认知上它更像一张实验框架。学弟以后读它，不要只盯着循环里具体怎么写，而要先看到它的实验结构：先拿到场景和配置，再决定方法集合，再生成多组起终点样本，再对每种方法逐个 trial 跑，最后把 trial 结果压成统计摘要。这条结构感一旦建立起来，后面看 JSON、看图、看汇总都会顺很多。

### 6、batch_results.json 真正难的地方，不是字段多，而是你要知道每一层字段在回答什么问题

很多新人第一次打开 `batch_results.json`，会有一种“内容好多，但不知道从哪下嘴”的感觉。这个感觉很正常。因为 batch 输出的难点不在于 JSON 语法，而在于它把好几个层次的信息装在了一起。你如果没有先分层，就很容易把一条记录里不同层次的字段混着看，越看越乱。

一个比较稳的读法，是先把 batch 输出分成三层。第一层是“这一整轮 batch 的背景”，通常放在 `meta` 里，回答的是这轮实验在哪个场景、用了哪些方法、计划跑多少 trial、保存策略怎样。第二层是“每种方法的总体表现”，也就是 `results` 列表里每个方法条目顶部的 `feasible_rate`、平均时间、P95 时间这些字段，它们回答的是“这类方法总体上站得住吗”。第三层才是具体 `trial_records`，回答的是“某一次样本里到底发生了什么”。

你只要记住这三层，第一次看 batch JSON 就会轻松很多。正确顺序几乎总是：先看 `meta`，再看每个方法的总览统计，最后才抽几条 trial 细看。不要一上来就钻 trial 细节，那样非常容易在局部里打转，看半天却没抓到主结论。

### 7、图表不是用来替代 JSON 的，而是用来帮你更快发现应该回到 JSON 的哪一块

很多同学天然更喜欢图，因为图看起来直观。这个偏好没问题，但如果在学习阶段把图当成主要事实来源，会有两个风险。第一，图会帮你压缩信息，但也会顺便隐藏不少上下文；第二，你很容易先被某张“看起来不错”的图吸走注意力，却没意识到那张图到底是从什么数据压出来的。

当前工作区里的 `visualize_batch_results.py` 就是一个很典型的辅助层脚本。它做的事并不是替你判定方法好坏，而是把 `batch_results.json` 里最值得先看的几类统计压成图，比如 feasible rate 柱状图、plan time 分布图、轨迹投影图和一个 `summary.md`。它的正确用法不是“我只看图就够了”，而是“我先看图找到异常或重点，再回到 JSON 确认这个判断站不站得住”。

你以后越早建立这个顺序，结果判断就越稳。图是望远镜，JSON 是地面。只拿望远镜不落地，很容易飘；只盯 JSON 不抬头，也容易看不出整体形状。两者配合才是最舒服的状态。

### 8、overnight 的真正难点，不是“跑得久”，而是“多轮结果还能不能保持可读”

到了 overnight，很多新人会以为这是一个纯粹拼机器时间的阶段。其实机器时间当然重要，但更关键的挑战是：当 batch 变成多轮 batch 之后，结果还能不能保持可读、可归档、可比较。因为一旦 overnight 开始循环跑，事情就不再只是“某一轮跑得对不对”，而开始变成“第 17 轮和第 46 轮放在一起时，你还能不能一眼看出谁是谁、哪轮更值得关注、哪些图和哪些 JSON 是一一对应的”。

这正是为什么当前工作区用了 `run_overnight_12h.sh`、`aggregate_batch_runs.py`、`post_overnight_report.sh` 这套链。它们不是为了让命令显得高级，而是在解决一个很实际的问题：多轮实验如果没有统一归档和总报告层，第二天早上你面对的就不是成果，而是一地散文件。学弟越早理解这层价值，以后就越不会把工程化包装误认为“附加工作”。很多科研项目真正把人拖垮的，不是算法本身，而是结果一多就开始失去可读性。

### 9、run 目录为什么应该被当成“这一轮运行的档案袋”

如果一定要给 run 目录找一个很适合新人的比喻，我会愿意叫它“档案袋”。档案袋的价值不在于它看起来整齐，而在于与同一件事相关的证据都被放到了一个能回查、能搬运、能交接的地方。你以后只要看到某个 `runs/YYYY-MM-DD_HHMM_<topic>/`，脑子里最好立刻浮现的不是“一个输出目录”，而是“这是一轮运行的完整档案”。

这种理解会直接改变你看文件的方式。你不会再把 `env.txt` 视作无聊文本，因为它在记录这轮运行当时的机器和环境上下文；你不会再把 `cmd.txt` 当成重复内容，因为它在保存“我到底跑了什么”；你不会再把 `stdout.log` 看成杂乱输出，因为它其实是在保留过程证词；你也不会再把 `notes.md` 看成可有可无，因为那是人类判断、问题归纳和下一步动作最自然的落点。只要你把 run 目录当档案袋，对“证据”这件事的敏感度就会明显提高。

### 10、把 run 目录里的关键文件一个一个讲成人话

为了让这种档案袋意识更扎实，我们不妨把 run 目录里最常见的几个文件逐个讲成人话。`env.txt` 的作用，其实就是给未来的你和未来的别人留一句话：这轮运行当时站在什么环境上。它记录了时间、用户、主机、当前目录、GPU、Python 版本，有时还会附带上游仓库 commit。你可以把它看成“实验现场背景板”。

`cmd.txt` 更像操作记录单。很多同学刚开始会觉得，“我又不是不记得自己刚敲了什么，为什么还要写下来？”这个想法在命令很短、事情很少的时候似乎能成立，但实验一多、时间一长，人对自己做过什么的记忆会迅速模糊。`cmd.txt` 的价值，就在于把主观记忆换成客观记录。后面你如果需要复现、排错或汇报，它会非常值钱。

`stdout.log` 则更像过程录音。它不是只在出错时才有用。哪怕任务正常完成，日志也能帮你确认各阶段顺序、加载耗时、警告信息和结束位置。很多“好像成功了，但总感觉哪里不对”的情况，最后往往都是通过日志看出来的。

结果 JSON 则是算法与实验层的正式答卷。它不像日志那样是滚动文本，而是更结构化地保存了关键背景字段和结果字段。也正因为如此，它特别适合被后续脚本继续处理、画图、做汇总、拼成 Markdown。你以后只要理解了 JSON 是正式答卷，日志是过程录音，很多文件之间的关系就会自然得多。

最后是 `notes.md`。这个文件特别值得鼓励学弟去用。因为任何自动化脚本都擅长保存机器能自己知道的东西，但它保存不了人的判断。比如“这轮 smoke 其实链路通了，但场景配置我还没完全理解”“这轮 batch 看起来 sfc-3 比预期稳，需要回头对照论文解释”这种东西，只有你自己写下才会留下来。一个项目是不是越来越可交接，很多时候就差在这类人工摘要有没有被认真留下。

### 11、如果师兄问你“这轮运行输入了什么”，你最好不要只回答一个文件路径

这是一个很容易暴露理解层次的提问。很多新人被问“输入是什么”时，第一反应是回答 `config.yml` 路径，或者回答“我跑的是 old_union”。这些回答不算错，但都太单薄。更像样的回答，应该至少能同时覆盖几层：场景配置输入、方法选择输入、环境输入和命令级输入。

比如你完全可以这样回答：这轮运行用的是 `old_union` 场景，对应的模型入口是某个 `config.yml`；方法上我跑的是 `splatplan` 和几种 `sfc-*` baseline；运行环境是在 `splatnav` Conda 环境下，用当前工作区 wrapper 启动；命令层则是通过某个 shell 脚本或 Python 入口触发。你看，这样一说，别人立刻就能感觉到你不是只记了一个路径，而是知道输入是怎么分层的。

这类回答训练得越早，你后面做组会、做周报、写阶段汇报就越不会虚。因为复杂项目里，真正成熟的表达从来不只是“我输入了某个文件”，而是“我知道这轮运行站在怎样的一组前提与选择上”。

### 12、如果师兄问你“这轮运行输出了什么”，你最好也不要只回答“一张图”

和输入一样，输出也很容易被说窄。很多人第一次出图以后很兴奋，于是别人一问“输出是什么”，脑子里就只剩那张最显眼的图。可实际上，图只是输出的一种，而且往往不是最基础的那一种。对当前项目来说，输出至少要分成结构化结果输出、日志输出、归档输出和可视化输出。

更成熟的回答应该像这样：这轮运行留下了一个规范命名的 run 目录；里面有 `cmd.txt`、`env.txt`、`stdout.log` 这些工程化证据；有一个 smoke JSON 或 batch JSON 作为结构化结果；如果是 batch 以上规模，还会有图表和一个简单摘要。这种回答的好处是，它能一下子把“我知道什么叫真正的输出”表现出来。因为你已经不再把输出理解成一张图或一个终端文本，而是理解成一整套结果资产。

### 13、看起来最像“懂了”的时候，反而最容易忽略一致性检查

学习过程中有一个挺有意思的现象：最危险的时候，往往不是完全看不懂，而是已经看懂了一些，于是开始放松一致性检查。比如你一看到 JSON 里有 `feasible_rate`，就急着下结论；或者一看到某张图里蓝色柱子最高，就立刻说某方法最好；又或者一看到日志最后写着 completed，就默认这轮全对。这些都很像“已经开始会看结果”，但如果你不再核对命令、场景、方法、JSON、图和 run 目录之间是不是一致，就很容易掉进假成功。

所以我特别建议学弟在学习阶段，把“一致性”当成一个很值得练的词。一个结果值不值得信，很多时候不是看它长得漂不漂亮，而是看它上下文是不是闭合。命令和结果对得上吗，场景和图对得上吗，方法名和汇总项对得上吗，run 目录和你记忆中的那轮任务对得上吗。只要这层习惯开始长出来，项目判断力就会稳很多。

### 14、第一次自己解释一轮结果时，不妨按“背景、过程、结果、边界”这四句话来讲

很多新人面对结果时容易散，不是因为不知道点什么，而是因为没有表达骨架。我很推荐一个特别适合入门阶段的小骨架，就是四句话：背景、过程、结果、边界。第一句讲这轮运行是在什么场景、什么方法、什么规模下做的。第二句讲它通过哪条脚本链路跑起来。第三句讲它最后沉淀了哪些关键结果，比如可行率、耗时、图表或 JSON。第四句讲当前还不能过度解读什么，或者还有哪些地方需要继续核实。

这个骨架的好处，是它既不会把你逼成背稿机器，也不会让你讲着讲着失去主线。你以后无论是在师兄旁边口头说一下，还是在 `notes.md` 里留一句总结，甚至未来做 PPT，这四句话都很够用。对零基础学弟来说，先学会把结果讲成四句话，比一上来堆很多术语有用得多。

### 15、把“失败”也纳入输入输出视角，你对项目的掌控感会强很多

最后我特别想补一层：失败并不是输入输出视角里的例外，恰恰相反，它也是输入输出的一部分。也就是说，就算一轮运行没有得到你理想中的可行路径、没有生成完整图表、甚至在中途报错，它仍然留下了某些输入、某些过程痕迹和某些输出残片。你如果能用同样的分层方法去看失败，就会发现失败其实没那么可怕。

比如这轮任务报错了，那输入是不是还可以复原？可以，因为 `cmd.txt` 和 `env.txt` 还在。处理中断了，那能不能知道断在哪一步？可以，因为 `stdout.log` 还在。输出不完整，那能不能分辨是结构化结果没生成，还是图表环节没跑完？通常也可以。只要你开始这样看，失败就不再是“黑箱突然坏掉”，而会重新变成一条可以被拆解、被定位、被汇报的问题链。

这就是为什么我一直希望学弟早点建立输入、处理、输出这个三段式视角。因为它不只适用于“成功的一轮”，它同样适用于“没做成的一轮”。一旦这个视角稳了，项目就真的开始变成你能接得住的东西，而不再只是看上去会动、但自己心里发虚的一堆脚本。

### 16、读完这份 `03` 以后，最值得带走的不是更多字段名，而是一种“运行可解释”的底气

如果这份文档真正起作用了，那么你读到这里时，脑子里最该留下来的，不应该只是又多认了几个 JSON 字段或脚本名。更重要的，是你开始长出一种底气：哪怕面对一轮以前没见过的运行，你也知道该从哪里拆、从哪里看、从哪里讲。你知道输入不只是参数，输出也不只是一张图；你知道 run 目录不是垃圾桶，而是档案袋；你知道 smoke、batch、overnight 不是三套互不相关的东西，而是一条主线在不同规模下的展开。

这种底气对新人极其宝贵。因为复杂项目最磨人的，不是学习量本身，而是“我好像在做，但我解释不清”。一旦你开始能解释，项目对你的压迫感就会明显下降。它仍然复杂，但不再模糊。它仍然大，但不再一团黑。很多真正的入门，往往就发生在这一刻。

接下来最自然的动作，就是回到 `04_顺序化快速上手_从第一天到批跑.md`，把这里刚刚建立起来的输入输出意识，重新放回真正的动手路径里。因为理解到这一步以后，下一阶段就不该只是“知道”，而是要开始更稳地“做”。
